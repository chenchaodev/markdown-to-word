# 二期开发计划评审(@oracle ora-1 原文存档)

> 本文件为 @oracle(ora-1)评审结论原文存档,仅供开发者自查,不在 README 索引。
> 结论摘要已另落盘 docs/研究结论.md;按评审重排后的规划见 docs/路线图与迭代规划.md(提交 a3eae91)。

评审对象:二期开发计划(路线图 P0/P1/P2 清单)。已通读路线图、研究结论、ADR、状态速查,并抽查了 convert.ts / docx/render.ts / pdf/render.ts 关键实现。

---

## 总体评价

规划整体务实,P0 分组符合「投入小价值大」,但**有两处优先级倒挂**(页面设置被低估、PDF 书签被高估),且**目录 TOC 的页码难点被系统性低估**——P0 的「PDF 静态目录」和 P1 的「PDF 书签」其实是同一块硬骨头,拆在两级里会让批次边界失真。

## 逐项评审

### 1. 优先级合理性

**应升级:P1 页面设置面板(纸张/边距/方向)→ P0**
这是直接贩卖「中文排版可控」护城河的功能:中文正式文档对纸张/边距/方向是刚需,竞品(在线工具)多半有。成本很小:PDF 侧是 `@page` CSS + printToPDF 参数参数化(研究结论已铺路),docx 侧是 Section 标准属性(一小时内)。而且它和 P0 的分页控制共享同一「页面布局」上下文,拆开做必然返工。

**应降级**:
- **代码高亮主题切换(P0→P2 或砍)**:打印文档几乎没人换代码主题;PDF 模板现在硬编码 GitHub Light,换个主题只是换一组 CSS 变量,价值趋近于零。若做,给 2-3 个主题挂在设置里即可,不值得占 P0 位。
- **PDF 书签(P1→P2,且先 spike)**:见风险节,这是全清单最硬的一项,不该和「页面设置」同一优先级。

**应砍 / 无限期延后**:
- **Mermaid(P2 砍)**:成本最高(无 DOM 渲染环境,要 hidden BrowserWindow + 导出 PNG,运行时 +1MB),与护城河零相关,典型 YAGNI。
- **CLI 转正**:已有 `cli/index.ts` 调试通道,转正只是包装,价值低;右键菜单若做,价值高于 CLI 但也是通道类,统一延后。

**遗漏的高性价比项**:
- **标题 slug / id 生成**——TOC、书签、内部链接跳转三者的公共底座,现在 mdast 标题没有 id。应先做(一行代码的依赖,两个格式都吃),否则批次 2/3 都会卡。
- **拖放多文件 / 文件夹**——批量转换(P1)的输入前置,规划没写清输入形态;应随批量一起定义。
- **docx 导航窗格**——已半免费(见依赖节),只需在导出后行为/文档说明里提一句,零成本卖点。

### 2. 依赖顺序

- **设置持久化是明确的底座**:代码高亮主题、导出后行为、页面设置、记忆选项全部挂它,且 P1 页面设置也要记忆默认值。**第一批先做,但不单独发版**。手写 userData JSON 即可,不必引 electron-store(项目已是 ESM,少一个依赖少一份打包风险)。
- **分页控制 + 页面设置必须同批做**:两者共享渲染管线的页面上下文(纸张/边距/方向/分页符),拆两批 = 渲染管线改两遍。
- **PDF TOC 与 PDF 书签是同一技术难点,一次定型**:「标题→页码」映射问题无解则两者都只能做「无页码版」。方案分流见风险节——建议 P0 TOC 直接做「无页码 + 锚点链接」,书签单独立项先 spike。
- **docx TOC 与 PDF TOC 是两个独立实现,可并行**:docx 侧依赖的是真实 Heading 样式——**已确认满足**:`render.ts` 用 `HeadingLevel.HEADING_1..6`(Word 内置样式 + 大纲级别,导航窗格免费拿到),TOC 域 `\o "1-3"` 可收集。唯一未知是复杂域构造能力(见风险)。
- **外链图片下载零依赖,可任意批次插入**;注意 core 纯逻辑约束——下载放 main 进程,经现有 `imageResolver` / context 注入,架构上刚好有接口。
- **YAML 元数据先于封面页**:frontmatter 解析(建议 gray-matter,成本半小时)独立可用,title 还能喂给 TOC 页眉/文档标题;封面只是它的一种消费方式。与 TOC 是弱相关(封面排除出目录),先后无所谓。
- **批量转换与最近文件弱相关**:批量是输入形态(多选/文件夹)+ 队列 + 失败聚合,复用单文件 convert;「最近文件」是单转便利,可并行做。

### 3. 技术风险点

| 项 | 难度 | 结论 |
| --- | --- | --- |
| docx TOC Word 域 | 中,半天 spike | docx 9.x 有 `SimpleField`/`ComplexField` 类可拼 `TOC \o "1-3" \h \z \u` 复杂域(begin/separate/end 三段),可行性中高。**验收必须 Word + WPS 双实测 F9 更新**(WPS 对域的处理有差异)。失败红线:退化「静态标题列表 + 提示 F9 + 导航窗格(免费)」,不阻塞批次。值得现在投入——真 TOC 是「真 docx」心智的一部分。 |
| PDF 书签注入 | 高 | 写 PDF 不难(pdf-lib 可写大纲),**难在「标题→页码」映射**:printToPDF 产物无结构化信息,文本定位要 pdfjs-dist 逐页 `getTextContent` + 字符串匹配,而 Chromium 会把标题文本拆成多个 span(行内代码/加粗/跨页),匹配易碎。两条路:a) 无页码 TOC(零依赖,先做);b) 书签 = pdfjs 定位 + pdf-lib 注入,**先 spike 1-2 天**,失败红线:H1/H2 两级最小版或砍。结论:**现在不值得为 P1 投入,降 P2**。 |
| docx 分页符 | 低 | `pageBreakBefore`(段落属性)+ `PageBreak` run,半小时活。真正的决策点是**显式分页符语法**:`---` 已是 hr 语义不能占用;建议 `<!-- page-break -->` HTML 注释(remark 产 html 节点,现渲染跳过,识别成本低,兼容 Typora 生态)。 |
| 外链图片下载 | 中低,纯工程 | 超时(10s)/并发(3)/单图上限(可配)/同文档 URL 去重缓存/证书与防盗链。**失败策略建议:保留原 URL 引用 + 警告**(与现有缺失图片警告同构,保真优先);docx 侧失败 = 跳过 + 警告。值得现在投入:行业 #1 投诉的闭环。 |
| KaTeX vs OMML | 小-中 vs 高 | KaTeX:markdown-it 内联公式规则 + 渲染 + **字体要能加载**(临时 HTML 需 data URL 内嵌或拷字体,小坑),一周内可交付。OMML:`latex-to-omml` 类库质量需 spike,Pandoc 级别才可靠,保真差;放 P2 正确,且要预设「子集支持 + 降级纯文本/源码」兜底。**结论:PDF 侧现在值得投,docx 侧只承诺 spike 不承诺交付**。 |

### 4. YAGNI 审视

- **砍**:Mermaid(成本最高价值最低)、CLI 转正、代码高亮主题切换(降到 2-3 个主题挂在设置里是最小可接受形态,或直接砍)。
- **降级**:PDF 书签(P2 或两级最小版)、最近文件(P0 尾部,价值低但成本也低,可留)、封面页(除非目标用户是正式报告场景)。
- **保留但最小化**:PDF 预览(模板已铺路,成本小,顺手做)。

### 5. 与定位一致性

- **强化护城河**:外链图片下载(保真,#1 投诉闭环)、分页控制 + 页面设置(排版可控,核心)、TOC(正式文档心智)、封面 + YAML、脚注(正式性)、docx OMML(正式性,成本高)。
- **中性**:批量转换(真实需求,与护城河无关但呼声极高)、PDF 预览、raw HTML 白名单、多文件合并。
- **分散精力**:代码高亮主题切换、最近文件、Mermaid、CLI/右键菜单。

## 建议批次(每批独立交付验证)

**批次 1「排版控制 + 设置底座」**
设置持久化 + 记忆选项 · 导出后行为 · 分页控制(H1 分页 + 显式分页符)· 页面设置面板(自 P1 升入)· 标题 slug/id 生成
- 价值:护城河第一波(中文排版可控完整落地)+ 后续全部功能的设置底座
- 验收:设置重启后持久;docx/pdf 双格式下分页符、纸张、边距、方向实测正确(中文文档目测);显式分页符语法生效;打开所在文件夹/打开文件生效

**批次 2「保真 + 正式文档化」**
外链图片下载嵌入 · 目录 TOC(docx 域 spike 先行 / PDF 无页码锚点目录)· 封面页 + YAML 元数据 · PDF 预览(顺带)
- 价值:行业 #1 投诉闭环 + 正式文档标配(TOC/封面/标题),「真 docx」卖点坐实
- 验收:外链图断网可用 + 失败警告文案正确;docx TOC 在 Word 与 WPS 双实测 F9 更新;PDF 目录点击跳转(先实测 printToPDF 保留内部锚点链接);YAML 封面/标题生效;预览显示正确排版

**批次 3「批量 + 长文档」**
批量转换(多选/拖放文件夹 + 队列 + 失败汇总)· PDF 书签(先 spike)· 多文件合并(顺带,成本小)· 脚注(可延后)
- 价值:呼声最高的需求 + 长文档正式性
- 验收:10 文件批量转换 + 失败汇总报告逐条正确;书签在 Acrobat/浏览器跳转正确(spike 失败则按红线降级并记录到研究结论);合并文档标题层级正确

P2 剩余(raw HTML 白名单、OMML、Mermaid、CLI/右键)不排批:白名单随时可做(安全合规),OMML 只做 spike,后两项建议砍。

## 必须现在决定的技术取舍

1. **PDF 目录/书签的页码方案(最优先)**:建议「P0 目录 = 无页码 + 锚点链接」先行;书签单独立项,spike 失败红线 =「标题文本匹配不可靠 → 只做 H1/H2 或砍」。**同时先实测 printToPDF 是否保留页内锚点为 PDF 链接注释**——若不保留,P0 的 PDF 目录只剩纯文本列表,连 P0 内部也要降级。
2. **docx TOC 的复杂域能力**:开工即 spike(半天);失败退化为「静态列表 + F9 提示 + 免费导航窗格」,不阻塞批次 2。
3. **显式分页符语法**:批次 1 开工前定死,建议 `<!-- page-break -->`(不占用 `---` 的 hr 语义,与 Typora 生态兼容)。
4. **外链下载失败策略**:失败保留原 URL + 警告(保真优先),与现有缺失图片警告同构——这条定了之后,docx 与 pdf 两个渲染器都不用再纠结。

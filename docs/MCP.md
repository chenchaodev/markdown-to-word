# MCP 接入

本程序提供一个 [MCP](https://modelcontextprotocol.io) 服务端，让支持 MCP 的 AI 助手（如 Claude Code、Cursor、Cline 等）直接把 Markdown 转成 Word，而不必把文件内容粘贴进对话。

> **两种形态**：服务端既可从源码检出运行（需 Node.js >= 22.13 与已装齐的依赖，使用前先完成构建，见 [开发者手册](DEV-GUIDE.md) 的「命令」节），也可经安装版自带的转发器启动（无需 Node.js，见下方「安装版形态」）。两种形态暴露的工具、参数与返回值完全一致。

## 快速开始

源码检出形态在助手的 MCP 配置里加一段，然后重启助手：

```json
{
  "mcpServers": {
    "markdown-to-word": {
      "command": "node",
      "args": ["<项目路径>/dist/mcp/index.js"]
    }
  }
}
```

`<项目路径>` 填本程序在磁盘上的位置（含 `dist` 那一级的上一层）。配置完成后，助手的工具列表里会出现 `convert_markdown` 与 `readback_docx`。

启动后服务端会往标准错误写一行启动提示，这是正常的；协议本身走标准输入输出。

只装了安装包、不打算准备开发环境的，用下面的形态。

## 安装版形态

安装包自带一个命令行转发器 `m2w.cmd`，与程序可执行文件并列落在安装根目录。把 `M2W_ENTRY` 指向服务端入口，即可用它启动（不设该变量时转发器跑的是命令行入口）：

```bash
set M2W_ENTRY=dist\mcp\index.js
cmd.exe /d /s /c ""%LOCALAPPDATA%\Programs\MarkdownToWord\m2w.cmd""
```

这条命令行形态已实测跑通：标准输出上恰好两个 JSON 帧，一行一个。

**不能直接拉起 `.cmd`。** Windows 上用 `spawn` 直接启动会得到 `EINVAL`，必须经 `cmd.exe /d /s /c` 转发一道；而 `cmd /s /c` 会剥掉最外层一对引号，所以路径要写成上面的 `""…""`。这是调用方（脚本或客户端）要负责的事，不是转发器的缺陷。写法与理由见 [命令行用法 · 安装版形态](CLI.md#安装版形态)。

**不同客户端的配置写法不一样。** 各家助手的 `mcpServers` 段对「传环境变量」和「传命令数组」的处理各不相同：有的支持单独的 `env` 字段，有的只认 `command` + `args`，有的把整条命令交给 shell。上面给的是已验证可用的命令行形态；配置到某个客户端时，按那个客户端自己的 schema 写，把转发器的完整路径与 `M2W_ENTRY` 落进去即可，不要照抄别家的写法。

**安装版形态下的能力边界：**

- **标准输出上只有 JSON 帧。** 启动横幅与 crashpad 噪声都走标准错误。这是 stdio 传输能工作的前提：客户端按行从标准输出读 JSON，标准输出上多出一个字节协议就断。
- **不渲染 Mermaid 图表**，与源码检出形态一致，会在返回值的 `degraded` 字段里报出（见「降级：Mermaid 图表」）。
- **两种产物格式都提供**（`.docx` 与 `.pdf`）。PDF 经本程序自带的打印宿主子进程产出；宿主不可用时该次调用失败并给出可行动的说明（见「行为说明」）。

## 能力

服务端提供**两个**工具：

### `convert_markdown`

按 `format` 参数产出 `.docx` 或 `.pdf`，默认 `.docx`。

| 参数 | 必填 | 说明 |
|---|---|---|
| `input` | 是 | Markdown 文件的**绝对路径**，或包含 `.md` / `.markdown` 的目录绝对路径。目录会被递归收集 |
| `format` | 否 | `docx`（默认）或 `pdf`。取其它值即调用失败，并在失败说明里列出可用取值。省略则产出 Word，原有调用方式不受影响 |
| `outputPath` | 否 | 产物的完整绝对路径。只能配单个输入文件。路径已存在时本次调用失败，不会改名 |
| `template` | 否 | 内置排版预设 id，取值见 [命令行用法 · 内置排版预设](CLI.md#内置排版预设)。省略则使用默认排版 |

`outputPath` 的限制与命令行入口的 `-o` 相同，理由也一样：调用方点名要的就是这个路径，改名会让按固定名取产物的脚本取不到。

⚠ **`format: "pdf"` 的两条已知代价**，都源于 PDF 走打印宿主而非直接渲染：耗时以秒计（同一台机器上约为 Word 的三倍，见「行为说明」的超时取值），且 `degraded` 字段恒为空数组（见「降级：Mermaid 图表」）。

### `readback_docx`

方向与转换相反：把**本应用导出的** Word 文档回读成 Markdown。

| 参数 | 必填 | 说明 |
|---|---|---|
| `input` | 是 | 本应用导出的 `.docx` 文件的**绝对路径** |

产物落在源文件同目录 —— 同名 `.md` 与同名 `_media/` 图片目录；同名已被占用时自动递增，不覆盖既有文件。

返回值带各结构的条数（标题/段落/列表项/表格/图片/链接/公式/脚注/批注）与三类清单：`preserved`（完整还原了什么）、`dropped`（本次文档实际发生的丢失）、`notManaged`（本应用恒不还原的类别）。

⚠ **适用范围限本应用导出的 Word 文档**：标题层级、列表、表格、图片、链接与行内样式可完整还原；公式以纯文本保留（不是 LaTeX），批注正文、脚注正文与修订记录不还原，段落级排版（缩进/对齐/行距）与字符级外观（字号/字体/颜色）不进 Markdown。任意 Word 文档不保证。

## 返回值

每次调用返回一个结果对象：

```json
{
  "artifacts": [
    {
      "input": "/abs/path/笔记.md",
      "outputPath": "/abs/path/笔记.docx",
      "warnings": [],
      "degraded": ["mermaid"],
      "elapsedMs": 118
    }
  ],
  "degraded": ["mermaid"],
  "elapsedMs": 118
}
```

| 字段 | 说明 |
|---|---|
| `artifacts` | 每个产物的明细 |
| `artifacts[].input` | 输入文件的绝对路径 |
| `artifacts[].outputPath` | 产物的绝对路径 |
| `artifacts[].format` | 本项产物的实际格式（`docx` 或 `pdf`）。⚠ **这是返回结果里唯一的格式事实**：`outputPath` 可被 `outputPath` 参数钉到任意扩展名，从路径后缀反推格式会得出错误答案 |
| `artifacts[].warnings` | 警告标识列表 |
| `artifacts[].degraded` | 本项发生的降级，没有则为空数组 |
| `degraded` | 全部产物的降级并集，供助手一眼判断 |
| `elapsedMs` | 本次调用总耗时（毫秒） |

目录输入时，`artifacts` 每项对应一个产物文件。

## 降级：Mermaid 图表

**服务端没有图表渲染宿主，` ```mermaid ` 围栏会按等宽代码块写入 Word。** 这属于功能降级，因此会被**明确写在返回值里**——`degraded` 字段出现 `"mermaid"` 就表示这份产物里的 Mermaid 图是代码块而非图形，`artifacts[].degraded` 逐项标出，`degraded` 是全部产物的并集。

这样设计是刻意的：如果助手拿到一份「有图无图全看运气」的产物，同样的输入可能产出不同结果，助手就无法据此判断自己的回答是否可信。降级可见，助手才能决定是否提示需要人工补图，或改用图形界面转换。

不含 Mermaid 的文档不会出现在 `degraded` 里。

⚠ **`format: "pdf"` 下 `degraded` 恒为空数组**，即使文档里有 ` ```mermaid ` 围栏。PDF 路径不经 Markdown 解析，围栏会按等宽代码块原样写入 PDF，助手无法从返回值区分「这份 PDF 里的图是代码块」与「这份文档没有图」。

→ **选 PDF 时必须按「Mermaid 一律渲染为等宽代码块」自行处理**：需要图形图表时应改用 `format: "docx"`（可从 `degraded` 判断），或改用图形界面转换。

## 失败与重试

| 情况 | 助手看到什么 |
|---|---|
| 参数有问题（缺 `input`、路径不是绝对路径、路径不存在、目录里没有 Markdown、`template` 不存在、`format` 取值不合法） | 工具返回失败，附带可读的说明。`format` 的失败说明会列出可用取值 |
| 转换失败（源文件过大、渲染出错等） | 工具返回失败，附带错误原因 |
| `format: "pdf"` 但打印宿主不可用 | 工具返回失败，说明宿主未能启动，并区分「安装不完整」与「源码检出形态需先装依赖」两种情形 |
| `format: "pdf"` 且超过 PDF 路径的耗时上限 | 工具返回失败，说明已中止本次调用及上限取值 |
| `outputPath` 已被占用 | 工具返回失败，说明该路径已存在 |

**参数类错误都在返回值里，不中断会话。** 助手可以据此改参数重试，例如把相对路径换成绝对路径，或换一个产物路径。只有协议层面的问题（比如调用了不存在的工具）才会中断。

「未知预设」的报错会列出全部可用预设 id，助手据此即可自行纠正。

## 行为说明

**产物格式由 `format` 参数决定，两种都提供。** Word 直接渲染产出；PDF 经本程序自带的打印宿主子进程产出，机制与命令行入口同一份实现。宿主不可用时该次调用失败，并在失败说明里区分「安装不完整」与「源码检出形态需先装依赖」两种情形。

**不渲染 Mermaid 图表。** 见上一节。⚠ 两条路径的告知方式不同：Word 路径把降级写进 `degraded`，PDF 路径的 `degraded` 恒为空数组。

**单次调用的耗时上限按格式分档：Word 120 秒、PDF 360 秒。** 超时按取消处理并返回失败。PDF 取三倍不是拍的——同一台机器、同一份文档实测两条路径的耗时比稳定在 3 倍上下；沿用 120 秒会在某个篇幅上下造出一道「同一份输入，Word 过、PDF 挂」的格式相关悬崖（实测该文档的 PDF 侧被上限掐掉并返回失败，而助手无法从报错里区分「文档太大」与「转换卡死」）。取三倍让两条路径的可达篇幅对齐，即「换格式不该缩小能处理的文档」。

代价如实记下：一次 PDF 调用最长可阻塞服务端约 6 分钟。这仍是「有界的阻塞」而非「无界的挂死」——上限这道闸防的是后者。命令行入口不设这个上限（等多久由人决定），但 AI 助手不会主动中止一个卡住的调用，若不设上限，一次卡死会拖住后续所有调用。

**不读界面里的设置。** 助手调用的排版完全由本次参数决定，跨会话可复现。

**产物同名时自动改名。** 未指定 `outputPath` 时，若目标位置已有同名产物，会写成 `笔记 (2).docx` 或 `笔记 (2).pdf`，不覆盖既有文件——这与图形界面一致。

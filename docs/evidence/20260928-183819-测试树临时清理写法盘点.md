# 测试树临时目录/产物清理写法盘点

> 触发:2026-09-27 发版 3.14.1 后 `master` 的 CI 红两次,两次红**不同的段**,而代码相对上一次全绿的 run 零改动 → 判定为环境级不稳定,不是某一段的回归。用户裁决「先全树扫一遍统一到助手,登记,后续处理」。

## 结论先行

删除点分布:**走既有助手的只有 1 处生产用法**(`test/common/userdata.js`)+ 2 个助手自身测试;带退避重试参数的裸删 8 处;其余目录树删除基本是「裸删 + 无重试」,其中**高危 4 处**(裸删目录树 + 无重试 + 删不掉即抛 → 直接把段判红)。`test/main` 下 20 余处 `fs.rm(dir,{recursive,force}).catch(()=>undefined)` 属**吞错**:不判红但会静默残留,是环境噪音的次要来源。

## 两次 CI 红的根因不同(重要修正)

初判「两处红点同属临时目录清理」是**错的**,实测与代码核对后拆成两个独立问题:

| 红点 | 性质 | 根因 | 统一删除助手能否解决 |
|---|---|---|---|
| `test/segments/dist-manifest-gate.test.js:232` | **删除 API** | 裸 `mkdtempSync` + `finally` 内无重试 `rmSync`,runner 上撞 `ENOTEMPTY` | **能**,第一批改造直接命中 |
| `test/segments/install-smoke.test.js:762` | **进程树时序** | **不是删除点**。它等的是信标**文件消失**(等价于孙进程已被 `taskkill /T` 硬杀),失败说明硬杀耗时超过 8 秒预算 | **不能**,需另案改等待口径 |

`install-smoke` 的 `waitAbsent(beacon, 8000)` 干等 8 秒;同段 `:767` 的 `fs.rmSync(beacon)` 属非 win32 分支,与失败无关。

## 门禁防回退:可行,且与既有门禁不重复

`scripts/check-test-numbering.mjs` 是可抄的模板(纯文本扫描、显式扫描面清单、ALLOWLIST、exit 0/1、零新增依赖)。它按**文件文本**判定而非执行结果 —— 正是清理门禁要的口径(须在 tsc/测试之前跑)。

建议 `scripts/check-temp-cleanup.mjs`:扫描面复用 numbering 门禁同一份清单;规则 = 命中 `rmSync|rm|rmdirSync|unlinkSync` 且目标形如 `recursive: true`(或变量名含 dir/sandbox/tmp)而近邻无 `maxRetries` → 判红;ALLOWLIST 三类(助手自身 / 单文件删除 / 刻意验证删除失败)。与既有门禁判据互斥:numbering 管字面量内容、boundary 管 import 方向、本门禁管 fs 删除调用参数完备性。

**已知失效模式**:正则门禁易被「换写法绕过」。建议同时加一条**正向**要求(目录沙盒必须经助手创建),双判据才不易被改名规避。

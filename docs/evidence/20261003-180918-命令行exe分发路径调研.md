## 一、结论摘要

**最可行的一条**：复用已安装的 Electron 作Node 运行时（`ELECTRON_RUN_AS_NODE=1` + 本应用自己的 `electron.exe`）。理由是三条确证事实叠加 —— Electron 43 内置 Node 与 Node 24 LTS 同代（满足 `engines >= 22.13`）；`RunAsNode` fuse 默认开启且 electron-builder 未flip它（§五已在本仓真实产物上实测）；产物零额外体积。

**已死的两条**：`nexe` 无 ESM 支持且 README 自述只测过 Node 14/15（§三.4）；`bun build --compile` 把运行时换成 Bun，与「pdf 路线必须手上有 Electron `printToPDF`」正面冲突（§三.3）。

**卡住所有路径的那一条前置**（§四·D0，单列一节写透）：

> **`require("electron")` 在「已安装版」语境下必然失效 —— 它拿到的是开发机的 electron，不是用户装的那个。**
> 三条独立来源交叉确认：① `electron` 包的 `index.js` 全逻辑就是读同目录 `path.txt` 再拼 `dist/`；② 发布的包里**根本没有 `path.txt`**，它由 `install.js` 在开发机安装时生成；③ electron-builder 打包时剥离 `node_modules/electron`。
> ⇒ **不把 electron 定位逻辑从 `require("electron")` 改成「按 `dirname(process.execPath)` / 安装目录探测」，§三 里每一条路径都做不通。** 这一条与选哪条打包路径无关，是独立的前置改造。

**次要的两条前置**（同样与选路无关）：Node 24 LTS 的 SEA **只吃 CommonJS 入口**（§三.1），所以任何 SEA 路线都必须先把整个依赖图打成单个 CJS 文件；而 SEA 只吃**一个**入口文件 ⇒ **打包步骤在本项目形态下是强制的**。

**体量参考**：单文件 exe 路线下产物 ≈ `node.exe` **94 MB**（已确证）+ 依赖 blob，量级 100–130 MB（推论，依赖子图实际大小需实测）。

## 三、各路径的事实

### 3.1 Node 官方 SEA（single executable applications）

**成熟度[确证]**：文档顶部标注 **`Stability: 1.1 - Active development`**，引入版本 v19.7.0 / v18.16.0。来源：[nodejs/node main 的 SEA 文档](https://github.com/nodejs/node/blob/main/doc/api/single-executable-applications.md)

**未转正[确证]**：Node 22.x / 24.x 的官方生成流程仍是 `node --experimental-sea-config sea-config.json` + 外部注入工具 `postject`（Windows 上还需可选 `signtool remove`）。来源：[Node v24.21.0 SEA 文档](https://nodejs.org/docs/latest-v24.x/api/single-executable-applications.html)

- 25.5.0 起新增 **`node --build-sea sea-config.json`**，可直接产出可执行文件、不必手工 postject。来源：[v25.9.0 SEA 文档 History 表](https://nodejs.org/docs/latest-v25.x/api/single-executable-applications.html)、[v25.7.0 release notes](https://nodejs.org/en/blog/release/v25.7.0)
- `postject` 在 npm 上仍是 **1.0.0-alpha.6 / 2023-05-19**（长期 alpha，Node 官方文档直到 26.x 仍在用）。来源：[registry.npmmirror.com/postject/latest](https://registry.npmmirror.com/postject/latest)
- CI 只覆盖 Windows / macOS(arm64) / Linux（**不含 Alpine、不含 s390x**）。来源：v24 SEA 文档「Platform support」节

**对 ESM 的支持 —— 按版本严格分列[确证]**：

| Node 版本 | SEA 入口支持 | 原文依据 |
|---|---|---|
| **22.x / 24.x（含全部 LTS）** | **仅 CommonJS** | v24 文档：「The single executable application feature **currently only supports running a single embedded script using the CommonJS module system**.」 |
| **25.7.0 及以后的 25.x** | CommonJS **+ ESM** | v25 文档：「supports running a single embedded script using the **CommonJS or the ECMAScript Modules** module system」；release notes v25.7.0：「**SEA: Support an ESM entry point in Single Executable Applications** — #61813，SEMVER-MINOR」 |
| **26.x** | 同上，另新增 `"mainFormat": "commonjs" \| "module"`（默认 `commonjs`） | [v26.10.0 SEA 文档](https://nodejs.org/docs/latest-v26.x/api/single-executable-applications.html) |

对应 PR：`nodejs/node#61813`（ESM 入口）、`#62158`（ESM 入口的 code cache）。

**对本项目的含义[推论]**：

1. 钉 **Node 24 LTS**（与 Electron 43 内置同代）⇒ **必须先把整个依赖图打成单个 CJS 文件**再送进 SEA。硬前置，非可选。
2. 想用原生 ESM 入口 ⇒ 必须 **Node 25.7+ / 26.x**，即放弃 LTS；而 Node 25 已于 2026-03-31 EOL、26 是 Current。
3. **顶层 await**：CJS 入口本身不支持 TLA（语法错误）。Node 25.7+ 的 ESM 入口支持 TLA；在 24 上只能靠 bundler 把 TLA 包进 async IIFE（`@yao-pkg/pkg` ESM 模式即此做法，见 §三.2）。
4. **无论哪条 SEA 路线，SEA 只吃「一个入口文件」** ⇒ 打包步骤强制。

**与运行时动态 `require` 的相容性[确证]**（v24 SEA 文档「require(id) in the injected main script is not file based」一节）：

- 注入主脚本的 `require` **不是文件型 require**，除 `require.main` 外不具备普通 require 的任何性质；
- **只能加载内置模块**。原文：「Attempting to load a module that can only be found in the file system **will throw an error**.」
- 官方给的唯一补救：`const { createRequire } = require('node:module'); require = createRequire(__filename);`
- 同时：`__filename` 与 `module.filename` **等于 `process.execPath`**；`__dirname` **等于 `dirname(process.execPath)`**。
- 额外硬约束：**`useCodeCache: true` 时 `import()` 不工作**（v24/v25 文档均有此 Note）。

**⇒ 对本项目[推论]**：`createRequire(...)("electron")` 在 SEA 里**会失败**，除非先重建文件型 require；而重建后能否解析到 `electron`，取决于该包是否真在磁盘上 —— 由 §四·D0，答案是否定的。

**Windows 未签名 exe 的 SmartScreen / 杀软体验[确证]**（Microsoft 官方）：

- SmartScreen 的判定维度：**发布者声誉**（是否签名、证书是否可信）与**文件哈希声誉**（该文件是否被大量下载且无恶意报告）。
- **未签名 ⇒ 每个新版本都从零声誉重新积累。** 原文：「When a file is not signed, SmartScreen reputation must build for each new version of your files, starting from zero reputation.」「Unsigned files must build reputation anew with every update.」
- **无签名的表现 = 「Windows 保护了你的电脑」，用户必须点「仍要运行」；企业策略可直接阻断。** 自签证书与无签名同等对待。即使签名，新二进制在声誉积累前**仍可能**弹警告。
- SmartScreen 检查的是**下载来的文件**；原文称其「doesn't protect against malicious files on internal locations or network shares」，并提到「Enterprises may distribute files from Trusted Intranet locations not subject to SmartScreen review」。
- **另一套更严格的机制**：同页指出 Win11 的 Smart App Control 签名检查「apply to all executable files, **not just those downloaded from the Internet**」。本项目明确不签名（`docs/adr/adr-013`），这是已知取舍。
- 来源：[SmartScreen 概览](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/)、[SmartScreen AppRep](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)

**[推论][需实测]**：「安装目录里一个未签名 exe」与「官网下载的未签名单文件 exe」的差别**不在签名，在来源** —— 由安装器写入用户程序目录的文件通常不带 Mark-of-the-Web（Zone.Identifier 备用数据流），SmartScreen 一般不拦；官网直接下载的 exe 会被打上 MOTW 并触发警告。**两份 MS 文档均未提及 Mark of the Web**，此差异没有正面出处，须实测。

**ESM 支持[确证]**（[esm 指南](https://yao-pkg.github.io/pkg/guide/esm)）：**自 6.13.0 起支持 ESM。** `import`/`export` 自动转 `require`/`module.exports`；顶层 `await` 与顶层 `for await...of` **包进 async IIFE**；`import.meta.url` / `.dirname` / `.filename` 有 polyfill。

已知限制三条：① 同时用 `export` + 顶层 await 的模块**无法转译**，只以源码形式包含；② 自定义 `import.meta` 属性不生效；③ **动态 `import()` 可用但有限制**。

**两种打包模式[确证]**（[sea-vs-standard](https://yao-pkg.github.io/pkg/guide/sea-vs-standard)）：

- **Standard 模式** = 跑在 `pkg-fetch` 提供的**打过补丁的 Node 二进制**上（每版本约 600–850 行 patch 需 rebase）。优点：源码变V8 bytecode（IP 保护）。缺点：等 pkg-fetch 跟进、供应链上是自定义 fork。
- **Enhanced SEA 模式**（`--sea`）= 跑在**原版未打补丁的 Node** 上，用 `@roberts_lando/vfs` 做透明 `fs`/`require`/`import`。**ESM 入口 + 顶层 await 在所有 Node ≥ 22 目标上都可用**，经 `vm.Script` + `USE_MAIN_CONTEXT_DEFAULT_LOADER` 派发，**不做 ESM→CJS 转换**。代价：**不提供 bytecode 保护，产物是明文 JS**。另：`seaConfig.useSnapshot` 在该模式下不支持，须设 `false`。
- 官方文档结论：「**除非要源码保护，SEA 是新项目的推荐默认**」。

**自带 electron 补丁[确证]** —— 我直接读了产物文件`@yao-pkg/pkg@6.23.0/dictionary/electron.js`，内容为 `pkg.patches['index.js']` 把 electron 的路径解析从 `path.join(__dirname, fs` 改写为 `path.join(path.dirname(process.execPath), 'electron', fs`，并配 `deployFiles: [['dist','electron/dist','directory']]`。来源：[cdn.jsdelivr.net/npm/@yao-pkg/pkg@6.23.0/dictionary/electron.js](https://cdn.jsdelivr.net/npm/@yao-pkg/pkg@6.23.0/dictionary/electron.js)

⇒ 这是 §四·D0 那条死路的**现成解**，说明「打 exe + 运行时定位 electron 可执行文件」此事维护者已踩过并给了方案。**但[推论]** 它把 electron 整个 `dist` 塞进产物，与「单文件轻量 CLI」的初衷冲突（electron dist 体积在数百 MB 量级，需实测），该 patch 是否启用要单独评估。

**运行时路径语义[确证]**（[snapshot-fs](https://yao-pkg.github.io/pkg/guide/snapshot-fs)）：Standard 模式下包内文件带 `/snapshot/` 前缀（Windows `C:\snapshot\`），`__dirname` 被改写成 snapshot 路径；`process.cwd()` 是真实目录；**要访问真实文件系统必须用 `process.cwd()` 或 `dirname(process.execPath)`**。

## 四、对本项目的具体风险点

> 本节按被调研对象的形态分析，未读本仓代码；**若实际形态与描述不符须复核**。

### D0. `require("electron")` 在「已安装版」语境下必然失效 ★

**三条独立来源[确证]**：

1. `electron` 包 `index.js` 的全部逻辑就是读 `path.join(__dirname, 'path.txt')`，返回 `path.join(__dirname, 'dist', <path.txt 内容>)`。来源：[cdn.jsdelivr.net/npm/electron@43.7.7/index.js](https://cdn.jsdelivr.net/npm/electron@43.7.7/index.js)（全文读取）
2. **发布的 `electron` 包里没有 `path.txt`。** 包内顶层文件仅 `abi_version`、`checksums.json`、`cli.js`、`electron.d.ts`、`index.js`、`install.js`、`LICENSE`、`package.json`、`README.md`；`path.txt` 由 `install.js` 在**开发机安装时**生成。来源：[data.jsdelivr.com/v1/packages/npm/electron@43.7.7](https://data.jsdelivr.com/v1/packages/npm/electron@43.7.7)
3. electron-builder 打包应用时**剥离 `node_modules/electron`** —— 它是开发期依赖，应用运行时不存在该包。

**⇒ 结论[推论]**：当前 `require("electron")` 在开发机返回 `node_modules/electron/dist/electron.exe`；在用户安装后该模块不存在，或返回开发机路径。**它不能作为「找到用户那个 electron.exe」的手段。** REQ-166 那一行已独立记下同一事实（「CLI 的 pdf 经 `require("electron")`，而 electron 是开发期依赖 ⇒ 安装版 pdf 不可用」）。

**为什么这卡住所有路径[推论]**：每条候选路线产出的都是「一个自己带运行时 / 一个 VFS」的 exe，产物内**没有** `node_modules/electron`，也没有 `path.txt`；而 SEA 里注入主脚本的 `require` 更是**只能加载内置模块**（§三.1）。⇒ 「把 CLI 打成单文件 exe」的成败**不取决于选哪条打包路径**，而取决于是否先把 electron 定位逻辑从 `require("electron")` 改成「按 `dirname(process.execPath)` / 安装目录探测」。**这一条不改，§三 里每条路径都做不通。**

**现成解[确证]**：`@yao-pkg/pkg` 已把这条 patch 做进 dictionary（§三.2）；`ELECTRON_RUN_AS_NODE` 路线天然成立（CLI 与 `electron.exe` 同处一个安装目录，`dirname(process.execPath)` 直接就是它）。

### D1. 运行时按路径读取包内资源（字体 / 样式表 / `require.resolve` / 相对 `__dirname`）

| 路径 | 已知坑 | 来源 |
|---|---|---|
| **SEA（Node 24）** | 注入主脚本 `__filename === process.execPath`、`__dirname === dirname(process.execPath)`。**任何相对 `__dirname` 的读盘都会指向 exe 所在目录而不是包内。** 正确做法：资源进 `assets`，运行时用 `sea.getAsset(key,'utf8')` / `getRawAsset`。`getRawAsset` 返回的是**不可写** buffer（文档明确警告写了会崩） | v24 SEA 文档（§三.1） |
| **SEA + `useCodeCache`** | `import()` 失效 | 同上 |
| **`@yao-pkg/pkg`** | 包内文件在 `/snapshot/` 前缀下，`__dirname` 被改写成 snapshot 路径；读真实磁盘必须用 `process.cwd()` 或 `dirname(process.execPath)`。资源靠**构建期静态扫描**发现，`path.join(__dirname,'../assets/x.css')` 这种写法才会被收集 | [snapshot-fs](https://yao-pkg.github.io/pkg/guide/snapshot-fs) |
| **bun compile** | always bundles everything；worker 路径若非显式入口会去 `process.cwd()` 找 | [bun executables](https://bun.com/docs/bundler/executables) |
| **asar** | `fs.readFile` / `require` 被 patch 成虚拟目录，但 **asar 只读**；要拿真实文件须 `app.asar.unpacked` | [ASAR Archives](https://www.electronjs.org/docs/latest/tutorial/asar-archives) |

**[推论]** 本项目字体走 `src/core/docx/theme.ts` 集中配置（字体名，不读文件），但 PDF 路线的 CSS / HTML 模板、以及任何 katex 字体文件，几乎必然踩这条。**走 SEA 就必须把它们从「读盘」改成「从 assets 取 / 内联进 bundle」** —— 属行为改造，不只是打包配置。

### D2. 动态 `import()` / 动态 `require()` 解析出的模块名

| 风险点 | 事实 |
|---|---|
| SEA + `useCodeCache:true` | **`import()` 直接不工作**（官方 Note）[确证] |
| SEA 注入主脚本的 `require` | **只能加载内置模块**，解析文件型模块**抛错**；须先 `require = createRequire(__filename)`（官方给了这段代码）[确证] |
| pkg ESM→CJS 模式 | 官方 limitations 第 3 条：动态 `import()`「work but **may have limitations**」[确证] |
| pkg ESM→CJS 模式 | 官方 limitations 第 1 条：**同时含 `export` 与顶层 await 的模块不会被转译** —— 本项目若有这种模块须逐个排查[确证] |
| remark / markdown-it 系 | 均为 ESM-only 依赖。esbuild `--format=cjs` 可转，但依赖内部若用 `import.meta.url` 定位自身资源，转 CJS 后语义会变（esbuild 会给 CJS 输出注入 `import_meta` shim）**[需实测]** |
| **最致命** | `createRequire(...)("electron")` 这类「运行时按模块名解析」的调用，在 SEA 与 bun compile 下**都拿不到东西**（§四·D0）[推论] |

### D3. 子进程 spawn（pdf 路径要 spawn electron）

| 路径 | 可行性 |
|---|---|
| **SEA** | SEA 产物**只带 node 运行时，不带 electron**。CLI 必须**另外知道**用户 electron.exe 的绝对路径。**[推论]** 这是 SEA 路径最大的架构负担 |
| **`@yao-pkg/pkg`** | [确证] 有现成 patch（dictionary）。**[推论]** 但它把 electron 塞进产物内部，exe 体积暴涨，与「单文件轻量 CLI」初衷冲突 |

| **`ELECTRON_RUN_AS_NODE`** | **[推论]** 最自然：CLI 与 electron.exe 同处一个安装目录，`dirname(process.execPath)` 就是它 |
| **asar 通用坑** | **[确证] asar 内的二进制只能用 `execFile`，`exec` 与 `spawn` 不可用。** electron.exe 在 asar 之外（安装根目录），故 spawn 本身没问题；但**任何被打进 asar 的 helper 可执行文件都会踩这条**（[ASAR 文档「Executing Binaries Inside ASAR archive」](https://www.electronjs.org/docs/latest/tutorial/asar-archives)） |

## 五、`ELECTRON_RUN_AS_NODE` 与 fuse（事实）

### 5.1 官方表述与限制[确证]

来源：[Environment Variables（/docs/latest，抓取时为仓库 main）](https://www.electronjs.org/docs/latest/api/environment-variables)

- 「**Starts the process as a normal Node.js process.** In this mode, you will be able to pass cli options to Node.js as you would when running the normal Node.js executable」。
- **被禁用的 flag 只有五个**：`--openssl-config`、`--use-bundled-ca`、`--use-openssl-ca`、`--force-fips`、`--enable-fips`。原因原文：「Electron uses **BoringSSL** instead of OpenSSL when building Node.js' `crypto` module」。
- **唯一失效条件**：「If the `runAsNode` fuse is disabled, `ELECTRON_RUN_AS_NODE` will be ignored.」
- **无任何弃用/移除标注**，未发现弃用迹象。

`RunAsNode` fuse **默认为 Enabled**，只有显式 flip 才失效。来源：[Fuses 文档](https://www.electronjs.org/docs/latest/tutorial/fuses)

**[推论]** BoringSSL 这一处 `crypto` 差异对本项目风险低：`pdf-lib` / `jszip` / `iconv-lite` 均不依赖 OpenSSL 专有特性，且 `iconv-lite` 是纯 JS + 内置表，无原生绑定。

### 5.2 asar 与 `process.execPath`

**[确证]** asar 在 RUN_AS_NODE 模式下默认仍生效 —— 依据是 Electron 文档说 `ELECTRON_NO_ASAR`「is only supported in forked child processes and spawned child processes that set `ELECTRON_RUN_AS_NODE`」，言下之意 RUN_AS_NODE 进程本身带 asar 支持（`fs` / `require` 被 patch 成能把 asar 当虚拟目录）。来源：[Environment Variables](https://www.electronjs.org/docs/latest/api/environment-variables)、[ASAR Archives](https://www.electronjs.org/docs/latest/tutorial/asar-archives)

**[确证]** `process.execPath` 语义不变，仍是被执行的 `electron.exe` 路径。

**[推论]** 作为「跑一段 JS 脚本」的运行时可行（官方支持的既定用法，`child_process.fork` 本身就依赖它）；作为「用户 PATH 上的通用 node」有硬伤 —— exe 位置由安装器决定、用户不一定把它加进 PATH，且必须以**本应用自己的** exe 为准去定位。

### 5.3 产物路径解析（asar 内 vs 非 asar）

**[推证]** electron-builder 默认布局：`electron.exe`（或产品名 exe）在安装根目录，`app.asar` 与之同级 ⇒ **electron.exe 本身在 asar 之外**，可直接 `execFile`；`require('electron')` 在 asar 内不可解析（该包已被剥离）；asar 内的 `__dirname` 形如 `...\resources\app.asar\...`，要拿真实路径需 `app.asar` → `app.asar.unpacked` 映射，或用 `extraResources` 把东西放到 asar 外。

**[已实测推翻原推论]** 原推论是「CLI 产物应以**非 asar 的普通磁盘路径**存在（如 `resources\cli\` 或安装根）」。§六 的实测证明该结论**不成立**：asar 在 RUN_AS_NODE 下对 `fs` 完全透明，连 `dist/` 子树都能直接读到 ⇒ **代码不需要挪出 asar**，也就不需要 `asarUnpack`、不需要 `extraResources` 搬代码、不需要碰 `build.files`（那条本来会被 `check-ci-contract.mjs` 判红）或 asar 顶层清单（被 `check-asar-manifest.mjs` 写死）。真正必须在 asar 之外的只有**给用户敲的那一个入口**（`.cmd` 转发器 / 快捷方式）。定位 `electron.exe` 仍按 `process.execPath` 的 dirname，不靠 `require("electron")`。

## 六、实测补记（本仓真实构建产物）

> 本节的**样本**与 §二 的**当前版本坐标**不是同一版本，勿混为一栏：样本是较早的构建。

**[确证]** 主会话在仓库现有构建产物上实测：

```
ELECTRON_RUN_AS_NODE=1 ./release/win-unpacked/MarkdownToWord.exe -e "console.log(...)"
→ node=24.18.0 electron=43.2.0
```

两条结论：

1. **`RunAsNode` fuse 在 electron-builder 的真实产物里是开启的。** 这纠正了先前一个错误推断 ——「为了用它必须打开被 electron-builder 默认关闭的安全加固」—— **两次都不成立**：Electron 侧 fuse 默认 Enabled（§5.1），且 electron-builder 未 flip 它。
2. 该构建产物内含的 Node 是 **24.18.0**、Electron **43.2.0**；对照 §二，Electron 43 当前最新为 43.7.7、内置 Node 24.21.0。**样本 ≠ 当前坐标。**

**[确证]** 第二次实测：**asar 在 RUN_AS_NODE 模式下对 `fs` 完全透明**，`dist/` 子树可直接读到。

```
ELECTRON_RUN_AS_NODE=1 ./release/win-unpacked/MarkdownToWord.exe -e "<probe>"
  app.asar/package.json      → READ OK len=1297
  app.asar/dist/main/index.js → READ OK len=3736
  app.asar/dist/core/convert.js → READ OK len=7123
  app.asar/dist/cli/index.js → ERR ENOENT
  app.asar/dist/mcp/index.js → ERR ENOENT
  app.asar.unpacked/*        → ERR ENOENT
```

读法（两条都要说清，否则会误读）：

- `dist/cli` 与 `dist/mcp` 的 ENOENT **不是「asar 读不到 dist」**，而是**该构建早于 CLI/MCP 落地**（样本是 electron 43.2.0 的旧产物）。同期存在的 `dist/main` 与 `dist/core` 都读到了，即证明 `dist/` 子树本身可读。
- `app.asar.unpacked/*` 全 ENOENT 是**本就无 `asarUnpack` 配置**（`package.json` 未配该项），不是探测失败。

⇒ 直接后果：路线 B **不需要任何 asar 侧的打包改造**（不需 `asarUnpack`、不需 `extraResources` 搬代码、不碰被门禁写死的 `build.files` 与 asar 顶层清单）。需要在 asar 之外的只有给用户敲的入口本身。§5.3 与 §八 的对应推论已据此改写。

### 10.1 `.cmd` 形态下 MCP stdio 成立（规划担心的那个坑没出现）[确证]

落地前最大的未实测点是：`cmd.exe` 是否会破坏按行分隔的 JSON-RPC。**实测不成立。**

调用方侧有一条约束（**不是转发器缺陷**，但每个集成者都会撞上）：

| 现象 | 实测 | 归责 |
|---|---|---|
| Node 的 `spawn` 直接拉 `.cmd` | 得 `EINVAL` | 调用方 |
| 绕过办法 | 经 `cmd.exe /d /s /c` | — |
| `cmd /s /c` 会剥掉最外层一对引号 | 路径含空格须写 `""完整路径""` | 调用方 |

⇒ **各客户端按自己的 schema 配即可**，不必有统一写法；文档只给已验证的命令行形态，不编造任何客户端的 JSON 片段。

### 10.2 katex 资源定位：源码侧的推论在打包侧**是反的**[确证]

| 上下文 | 按模块自身位置上溯两级（现用） | `app.getAppPath()` 基准（另一条候选） |
|---|---|---|
| 源码检出 · 以脚本路径启动 | `<repo>/node_modules/katex/dist` ✓ | `<repo>/dist/main/node_modules/…` ✗ **分叉** |

## 十一、门禁覆盖缺口

已安装入口**零门禁覆盖**，而六份文档与官网都正在向用户承诺它。

**间接覆盖到一半**

| 门禁 | 实际覆盖 | 够不到的部分 |
|---|---|---|
| `check:dist-manifest` / `check:asar` | 两个入口**逐字节对 clean dist 清单** | 这是**漂移校验不是存在性钉** —— 必需条目清单不含它们；若不再被编译出来，gen 与 check 两边一起空，全链仍绿 |
| `check:unpacked-smoke` | 起真实 exe 跑 smoke | **不经转发器** |
| `check:install-smoke` | 真装 → 起 exe → 卸载，校验安装目录 / 卸载器 / 开始菜单 / 残留 | **不查 `m2w.cmd` 是否落位，也不跑它** |
| `check:pack-size` / `check:release` / `check:signature` | 存在性 / 指纹 / 签名状态 / 体积预算 | 与转发器无关 |

**完全无覆盖**

- `build.extraFiles` 是否真把转发器落到安装根（无任何门禁断言它在解包产物里存在，更无断言真安装后落位）
- 转发器的运行行为：`ELECTRON_RUN_AS_NODE` 转发、入口切换、stdout/stderr/退出码逐字节透传
- 全仓转发器文件名的字面量只出现在打包配置与源资产两处，门禁脚本与测试树里零引用

**后果**：`extraFiles` 被删或落点写错时**全链仍绿**，已装用户的入口静默消失。

**最低成本的一层**：让解包冒烟顺带断言转发器在解包产物里存在。台账那行见 [`docs/REQ.md`](../REQ.md)。

## 十二、安装后可发现性:能不能代做把安装目录加入 PATH

用户提出「安装时经同意后把安装目录放进 PATH」。**可行，但本仓无挂载点，且收益比直觉小。**

### 12.1 路子与现状

- `build.nsis` 当前只有 `oneClick: false` / `allowToChangeInstallationDirectory: true` / `license` / `artifactName` 四项，**没有 `nsis.include`**，也没有任何 PATH / 环境变量相关键 ⇒ 要做得新增一份 `.nsh` 挂进 `nsis.include`（纯增量，不碰现有四项；社区有成熟的 `AddToPath` 宏）。
- 写 `HKCU\Environment` **不需要管理员权限**，与现有 per-user 安装一致（卸载注册表本来就写在 HKCU）。

### 12.2 四件必须一起做的事

| # | 做什么 | 不做会怎样 |
|---|---|---|
| ① | 广播 `WM_SETTINGCHANGE` | explorer 与新进程才知道 PATH 变了；**已经开着的终端不会更新** —— 用户装完立刻敲命令找不到，会以为没装成功 |
| ② | 卸载时摘掉该条目 | `check-install-smoke` 按安装前后快照比对且**不硬编码键名**，多出来的那条 PATH 会被判成卸载残留 |
| ③ | 安装向导里说明 | 同 ①，用户没有预期 |
| ④ | 文档同步 | 文档正在承诺入口可用 |

⇒ 第 ② 条值得单独说：**门禁已经预装了这个判据**。也就是说实现时不必自己设计「卸载干净」的验证方式 —— 不摘就判红。

### 12.3 反直觉的代价:它会让另一条限制更隐蔽

`spawn` 不能直接拉 `.cmd` 这条限制（须经 `cmd.exe /d /s /c`、路径含空格要写 `""完整路径""`）**加 PATH 之后依然在**。

但用户的心理模型会从「这是个 `.cmd` 文件，我得用 `cmd.exe`」变成「这是全局命令，我直接 `spawn`」—— 而 Node 的 `spawn` 对 `.cmd` 仍给 `EINVAL`。

⇒ **PATH 把「找不到命令」变成了「命令找到了但 spawn 失败」**，净改善未必为正。

### 12.4 建议的顺序

**⚠️ 本节原写的建议已被实测推翻（2026-10-04），原文保留在下一段供追溯。**

原建议是「先做开始菜单快捷方式…用户可从快捷方式右键『固定到 PATH』自行走完这一步」。三条实测结论让它站不住：

1. **原生机制做不到**。electron-builder 26.15.3 的 `NsisOptions` 属性表里**没有 `shortcuts`**（`scheme.json` 的 `additionalProperties === false`，直接调 `validateConfiguration` 验证：`shortcuts` REJECTED、`include` ACCEPTED）；四个快捷方式相关的键都改不了指向，模板三处的目标参数硬编码为 `"$appExe"`。⇒ 只能引 `nsis.include` 挂自定义 `.nsh`。
2. **就算做出来也是个闪窗**。转发器无参运行走 `exitCodes.usage`（=1），把用法打到 stderr 后退出 ⇒ 双击是一个一闪即关的控制台窗口。它是需要参数的 CLI，不是可点击的应用。
3. **「固定到 PATH」这条退路本身不存在**。在 Win11 家庭版 10.0.26300 上，注册表六个 `shell` 键下均无 `AddToPath` / `PinToPath`，`HKCRlnkfileshell` 键本身不存在；遍历 `System32/zh-cn/` 全部 1219 个 `.dll.mui` 抽取含 `PATH` 的字符串，25 条全部无关（`MAX_PATH`、`SQLITE_*`、`PROFILEPATH` 等）。**该扫描带对照组校准**：同一方法在 `shell32.dll.mui` 成功命中「固定到任务栏」「全部解压缩」，故「没有」是事实而非扫描失败。

⇒ 原建议的立论「快捷方式零成本、且把 PATH 决定交回用户」两头都不成立：前者要引本仓当前没有的 `nsis.include` 挂载点且换来一个闪窗菜单项，后者依赖一个本机不存在的上下文菜单。**这不是渐进方案，是做完发现核心缺口原样存在。**

**另一条与本节原判断相反的实测**：卸载残留检查**只覆盖两条写死的路径**（应用自己的 `.lnk` 与其目录），一个名字不同的快捷方式对它**完全隐形** —— 脚本报「零残留」而用户看得见；且卸载器只删自己那一个快捷方式，不删自定义的。

**结论**：可发现性缺口的实质是「用户不知道完整路径」，而开始菜单快捷方式解决不了它。是否改为代做 PATH、或另选形态，属需要用户拍板的取舍，台账那一行记着。

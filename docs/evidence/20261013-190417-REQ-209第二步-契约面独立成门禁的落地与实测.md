## 一、为什么是「拆文件不拆进程」而不是「拆进程」

裁决依据见 `20261013-209第二步-裁生成链路的两条前提修正与路径裁决.md`。落地上它决定了三件事:

| 面 | 住在哪 | 为什么在那里 |
|---|---|---|
| 段 import + electron mock 注册 | `check-segment-contracts.mjs`(新门禁自己的 `collectSegmentContracts`) | 它是**契约与产物的共同前置**:产物面要读 `fixtures` 内容才能落盘。拆成两个进程等于重复付出 import 全部段的成本,而段 import 本身在真实仓上是秒级 ⇒ 代价真实,收益(进程隔离)本步不需要 |
| 契约判定的返回值 → 是否产出 | 同一处 | **前后置**关系:判红 ⇒ `continue` ⇒ 该段不产出任何产物。两处各判一次必然漂移,而漂移的后果是「契约判红却照样落了盘」——那种失败静默 |
| 产物文件名撞车 | 生成器 | 判的是「落盘会不会互相覆盖」,契约面不落盘,不判 |

⇒ 生成器 import 新模块拿「契约齐备的段」清单,自己只做:剔除 `fixtures === null` 的段 → `planFixtureOutputs` → `findOutputNameCollisions` → 排序 → 落盘 / `--check` 比对。

## 二、新门禁与另两道 fixtures 门禁的分工

三道门禁、同批都要过,各自可分别归因:

| 门禁 | 守什么 | 与生成器的关系 |
|---|---|---|
| `check-image-digests.mjs`(第一步) | 全部图片夹具的 sha256 基线;**并持有**「`fixtures = null` 是合法终态」的三档判定层 `classifyFixturesDeclaration` | 生成器 import 它跑字节审计(`--check` 里仍跑一遍);本步**不重造**那个判定函数,新门禁直接 import |
| `check-segment-contracts.mjs`(本步) | 段发现 + 逐段显式契约判定 + 豁免白名单自检 + 扫描面塌缩下限 | 生成器 import 它跑契约判定 |
| `gen-fixtures.mjs` | 产物面:命名 / 撞车 / README / 图片复制 / 落盘 / `--check` | 本体 |

⚠ `classifyFixturesDeclaration` 的单一来源仍在 `check-image-digests.mjs` —— 新门禁只是它的第二个消费方。这条「两份实现必然漂移、而漂移的后果是「哪些段合法」在两个文件里给出相反答案」的理由写在新门禁的 import 处注释里。

## 三、上链位次与理由

新步插在 `check:coverage-zero:selftest` 与 `check:fixtures` 之间(即链的**第 47/48 位**,链长 52 → 54)。

- **不学 `check:image-digests` 放第 24/25 位**:那道不 import 任何测试段,零段前置;本门禁必须 import 全部 146 段,而部分段 import `dist/**` 编译产物 ⇒ 放在 `build` 之前会在未构建的检出上判红(假红,且是「与本次改动无关」的那种最难归因的红)。
- **紧贴 `check:fixtures`**:两者前置相同(已 build + 纯 Node + electron mock),放在它**前面**是刻意的 —— 契约不齐时先看到契约问题,而不是先看到一长串产物漂移。
- 链长增量 2 步 = 新门禁 + 其 selftest,与 ADR-062 C7 改判后的判据一致(「链长的增量只应来自新门禁」)。

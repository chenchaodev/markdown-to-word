## 二、REQ-128「删除保护区锚点」—— 在 CI 上恒绿是结构决定的

### 2.1 根因:换了迭代方向,没换集合来源

锚点 `gates/repo/check-ci-contract.selftest.mjs:870-875`:

```js
[...real.buildOutputNames, ...real.packOutputNames].every(
  (name) => !real.cleanProtectedSegments.includes(name),
)
```

`cleanProtectedSegments` 由 `gates/repo/repo-manifest.mjs` 的 `scanTopLevel()` 派生,
而 `:536` 是 `readdirSync(root)` —— **迭代域是磁盘**。CI 上门禁排在 build 之前,
`dist` / `release` 不在盘 ⇒ 该集合里**不可能**有它们 ⇒ `.every()` **恒真**。

上一轮把断言改成从**声明侧**迭代(不再看 `cleanable` 的存在性),但**被检查的集合仍然
从磁盘来** ⇒ 空洞为真没消失,只换了张脸。该文件 `:866-868` 的注释**自己写着这件事**
(「它只在本地(dist 已 build)才真正被求值,而 CI 才是它唯一该有牙齿的地方」)。

### 2.2 判定路径与两道过滤

不成立需 `cleanProtectedSegments` 含该名字,须过两级(`repo-manifest.mjs:619-623`):

1. **类别过滤** —— `classifyProfile`(`:112-131`)判为 `artifact` / `other` 的永不进
   保护区;`isBuildOutput`(`:121`)/ `isPackOutput`(`:122`)/ gitignore / doc / 内容探针
   按序命中即定
2. **`!cleanable.has(name)`** —— `cleanable` = `buildOutputNames ∪ packOutputNames ∪
   build.files 正向首段`(`:610-618`),`:616` 另有 `isDirectory !== false` 过滤

### 2.3 实测的构造矩阵(探针跑在 `os.tmpdir()`,未动真实 dist/release)

| 构造 | 结果 | 机制 |
|---|---|---|
| A 基线 | 绿 | dist 靠 `cleanable` 双来源被剔 |
| B 干净检出(dist/release 不在盘) | 绿 | **集合由 `readdir` 派生 ⇒ 缺失即不可能入集 ⇒ 空洞为真** |
| C `build.files` 不提 dist | 绿 | dist 仍来自 `buildOutputNames` |
| D `.gitignore` 不含 dist/release | 绿 | 类别判定不看 gitignore(`:121` 先命中) |
| E `directories.output` → `out` | 绿 | `release` 类别仍是 artifact,被第 1 级挡掉 |
| F dist 内只有 exe 无代码 | 绿 | `isBuildOutput` 在 `:121` 先于内容探针 |
| **G `outDir:"dist.js"` 且顶层真有该文件** | **红** | `:616` 的 `isDirectory !== false` 剔出 `cleanable`,而类别是 `config` ⇒ 进保护区 |
| **K `outDir:"notes.md"`** | **红** | 同上,`doc` 类别;邻接 853/858/862 全绿 ⇒ **本锚点独家红** |
| **L `directories.output:"CHANGELOG.md"`** | **红** | 同上,走 `packOutputNames` 那半 |

⇒ **只有一类构造能让它红**:声明的产物名同时是一个**已存在的顶层非目录文件**。
任何目录形态的声明,无论怎么改 `build.files` / `.gitignore` / `directories.output`
/ dist 内容,都变不成红。

### 2.4 `release` 与 `dist` 两半的机制判定

**`release`:构造保证(代码级不可能),三重独立兜底**

1. `packOutputNames` 本身进 `cleanable`(`:611`),而它 = `declared(decl.packOutput)`
   (`:586`)—— **同一个来源**,自相矛盾不可能成立
2. 即便拿掉,`isPackOutput` 在 `classifyProfile` 里**先于** gitignore/doc/内容探针
   命中(`:122`),类别恒为 `artifact` ∈ `NON_PROTECTED`,第 1 级就挡掉
3. 就算去掉 `directories.output` 让它不再是 packOutput,`release/` 内无代码扩展名、
   无 Markdown 多数 → 落 `OTHER`(`:130`),同样 ∈ `NON_PROTECTED`

⇒ 不是「当前恰好如此」。改 `build.files` / asar 白名单 / `.gitignore` 都不会让它进保护区。

**`dist`:现状靠双来源冗余,不是构造保证,但极难单独击穿**

- 第一理由 `cleanable` 含 `buildOutputNames`(`:611`);第二理由 `cleanable` 还含
  `build.files` 正向首段(本仓 `package.json:98` 有 `dist/**`,实测 `heads=['dist','package.json']`)
- **`dist` 类别恒为 `build`(`:121`),完全靠 `cleanable` 剔除**,第一级过滤帮不上反向
- 要击穿须同时抽掉两个来源,而二者**同源于同一个 tsconfig `outDir` 的两处声明**

### 2.5 前两次反向验证失败的原因(方法论)

台账记的两次:①退回 `cleanable` 的存在性过滤 ②把 `buildOutputNames` 从 `cleanable`
来源整个删掉。**两次都只抽掉一个来源**,另一个还在 ⇒ 属性未变 ⇒ 必然绿。

> **反向验证必须打在「覆盖该属性的最小闭包」上,或一次抽掉全部来源。**

K/L 那种构造之所以有效,正因为它**绕开了 `cleanable` 的全体来源**(`:616` 的
`isDirectory` 过滤对非目录文件直接放行)。

反向验证另两条纪律:

- 必须在**断言真正被求值的形态**上做 —— 构造 B(产物不在盘)恒绿,只跑它会误判「无牙齿」;
  只跑 A(dist 在盘)则 CI 上恒绿
- 判红后**排除邻接锚点代打** —— K/L 实测 853/858/862 全绿,证明本锚点独家红;
  若邻接锚点先红,说明本锚点没被真正求值

### 2.6 修法方向(实施由 fix-8 承担,前置须端到端证实)

诊断方的探针是**复算交集**,**从未实际跑 selftest 确认 exit 1** ⇒ 实施前必须先端到端
证实。三条候选:

1. **声明侧不交无向**:断言 `[...buildOutputNames, ...packOutputNames]` 两两互不相交,
   且与 `packTopLevel.positive` 目录成员、锁文件、`artifactRootNames` 不相交 —— 全从
   声明枚举,不看磁盘
2. **纯合成树互斥锚点**(放已有 synthetic 树 `:814-821` 旁):造 dist/release 都不在盘
   的树,断言产物名**按声明仍被并入 `mirrorPaths`** 且**不出现在受保护候选计算里**
   —— 断言的是派生函数的纯函数输出
3. **非空洞断言**:`scanTopLevel` 是纯函数(root 入参),可在临时目录造「产物目录存在 +
   裸形态」的树,调它并断言 `cleanProtectedSegments` 不含它 —— 不依赖真实 dist 在盘

## 三、两处「门禁次序 vs 派生集合」的通用教训

`cleanProtectedSegments` 由 `readdir` 派生,而门禁排在 build 前 ⇒ **凡断言以该集合为
被检查对象的,都在 CI 上恒绿**。这不是这一条锚点的缺陷,是**门禁次序与派生来源的组合**
造成的。要根治得从次序或派生方式下手(例如让被检查集合从声明派生),不在单条锚点上打补丁。

⚠️ 本条**未立工作项** —— 目前只有这一条锚点被实测命中。若后续 `gates/repo/` 里再出现
同类「以 readdir 派生集合为断言对象」的锚点,应合并成一条。

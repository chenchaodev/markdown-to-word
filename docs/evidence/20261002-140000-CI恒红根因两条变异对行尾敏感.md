# CI 恒红根因：两条变异对行尾敏感（REQ-149 取证）

## 现象

GitHub Actions 的 `ci` job 连续两次推送红（`79e5983`、`fea1d24`），失败点：

```
[fail] release-notes-selftest:变异测试 2 项未达预期(静态面判据可能恒绿)
[fail] 变异未生效(字符串没匹配上):② 整块删掉「空 NOTES ⇒ exit 1」分支
[fail] 变异未生效(字符串没匹配上):④ 去掉对抽取模块的引用(退回内联自造)
```

而本地 `npm run verify:ci` 连续多轮全绿。

## 根因

`gates/repo/release-notes.mutation-test.mjs` 的 5 条变异里，**只有 ② 与 ④ 的匹配模式里含 `\n`**。逐字复制源正则实测：

| 变异 | LF | CRLF |
|---|---|---|
| ① 重新引入 `--generate-notes` | 匹配 | 匹配 |
| **② 整块删「空 NOTES ⇒ exit 1」分支** | 匹配 | **不匹配** |
| ③ 去掉 `pkg.version` 实参 | 匹配 | 匹配 |
| **④ 去掉对抽取模块的引用** | 匹配 | **不匹配** |
| ⑤ 去掉 `extractNotes` 调用 | 匹配 | 匹配 |

①③⑤ 靠的是纯字符串 `replace`，不含 `\n`，天然 EOL 无关。**恰好只有这两条挂**，与 CI 报错完全吻合 —— 吻合到这种程度，诊断不需要再猜。

链条完整：

1. `.gitattributes` 只有 `* text=auto` 加三条定点规则（`test/fixtures/**`、`docs/evidence/INDEX.md`），**没有钉 `.github/workflows/*.yml`**；该文件第 2-3 行自己的注释就写着「检出 EOL 交由各端 autocrlf/core.eol 决定」。
2. `ci` job 跑在 **Windows runner**（日志里 `D:\a\markdown-to-word\...`、`C:\Program Files\Git\bin\git.exe`），runner 的 `core.autocrlf=true`。
3. ⇒ workflow yml 检出为 CRLF ⇒ 那两条正则永不匹配 ⇒ 变异「未生效」⇒ selftest 判红。
4. 本机 `core.autocrlf` 同样是 `true`，但工作树里那份 `release.yml` 已是 LF（被工具写过，不是刚检出的），所以「本机绿、CI 红」。

## 一处值得单独记的：报错的其实是变异测试自己，而它的行为是对的

`runMutationTest()` 有一条值得保留的设计：**目标字符串没匹配上时报 fail，而不是当作「变异成功」**。也就是说，它在「无法完成验证」时拒绝 pass，而不是假装验证过 —— 这正是「构造 ⇒ 判红 ⇒ 撤回 ⇒ 复绿」要求的精神。

但它的文案把两种失败混在一行：`[fail] 变异未生效(字符串没匹配上)` 与 `[fail] 变异未被判红`。这次 CI 上那句「静态面判据可能恒绿」是**误导** —— 判据没恒绿，是测试自己的匹配器挑平台。这个文案缺陷已记录，未在本轮修（见末节）。

## 修法（两处都在本轮）

1. **两条正则的 `\n` 换成 `\r?\n`**。只加 `\r?`，**不改成 `\s*`** —— 后者会跨空行把不该删的块一起吞掉，变异就失去意义。已交叉验证：新模式在 LF 与 CRLF 下产出**逐字节相同**，删除行数与旧模式一致（② 删 4 行、④ 删 2 行，两种 EOL 下都一样），即没有扩大吞噬范围。
2. **`.gitattributes` 追加 `.github/workflows/*.yml text eol=lf`**。blob 本身已是 LF（`* text=auto` 保证入库归一），所以这条**不改变文件内容、只改变 Windows 上的检出行为**，不需要 `--renormalize`。

两处都做是刻意的：变异测试应当 EOL 无关（不靠 git 属性兜底），git 属性则消除整类问题。

## 验证

- LF 下 5 条变异全判红、恢复后复绿。
- **把工作树那份 `release.yml` 临时转成 CRLF（219 行全部 `\r\n`）后重跑，仍 5 条全过、退出码 0** —— 这是核心验收点。LF 下通过**不能**证明 CRLF 场景修好，因为 `.gitattributes` 只影响新鲜检出。
- 备份 sha256 与恢复后 sha256 逐字节相同，`git status` 对该文件无输出（工作树已复原）。
- 载体 `release-notes.selftest.mjs` 在 LF 与 CRLF 两种工作树状态下各跑一次，均 9 条断言 + 5 条变异全绿。

## 同类面排查结论

按文本读 workflow yml 的门禁共 5 个。除已知受害的那个外，其余四个**全部 EOL 无关**：

- `check-ci-contract.mjs` —— 整体读入 + 纯子串/捕获组正则，不按行 split；`stripYamlComments` 的 `m` 标志下 `.` 会吃掉 `\r`，不残留。
- `check-ci-contract.selftest.mjs` —— 只读自建夹具，夹具由 `writeFileSync` 落盘、JS 字符串 `\n` 原样写入，**恒为 LF**，与 runner 无关。
- `check-pinned-actions.mjs` —— `split(/\r?\n/)` 按行切，是本仓处理 CRLF 最正确的一处；另有「扫不到任何 `uses:` 即判红」兜底防空过。
- `registry.mjs` —— 整体读入 + 去注释 + `matchAll`，不按行 split。

**未发现任何「本该红却不红」的静默退化**（即无因 CRLF 退化为恒绿的判据）。给 workflow yml 钉 `eol=lf` 也不会让任何门禁变得不对 —— 钉 LF 后夹具形态与真实文件形态反而一致了。

## 相邻发现（均未修，留给裁决）

1. `runMutationTest()` 缺 `try/finally`（写坏 → 调判据 → 写回是裸三行）。若 `checkReleaseNotesContract()` 抛错，`release.yml` 会**永久留在被改坏的状态**，且污染是静默的 —— 下次 `git status` 看到它有 diff，容易被误当成有意改动提交进仓。修法约 2 行、零行为变化。
2. `gen-fixtures.mjs` 的图片复制比对是**裸 `Buffer.equals`**（同文件文本路径有 `normalizeEol`，图片这条没有），而 `.gitattributes` 只把 `*.png` 钉成 `binary`，但代码里的图片扩展名有 7 种。**当前仓库只有 48 个 md + 7 个 png，该形态不发作**；将来只要出现非 png 图片就可能误红，且无负向覆盖。
3. 「变异未生效」与「变异未被判红」应拆成两种文案或退出码 —— 否则下次同一现象仍要靠人工比对 `MUTATIONS` 表才能区分。

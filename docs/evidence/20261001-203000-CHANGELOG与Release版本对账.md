# CHANGELOG 与 GitHub Release 版本对账（2026-10-01）

> REQ-138 的前置实测。起因：改写 CHANGELOG 语体前要确认两侧版本一一对应，实测查出两处错位。

## 一、三方计数

| 侧 | 数量 | 取数命令 |
|---|---|---|
| CHANGELOG 版本条目 | **37** | `grep -cE "^## \[[0-9]+\.[0-9]+\.[0-9]+\]" docs/CHANGELOG.md` |
| `## [` 总行数（含待发版） | 38 | `grep -cE "^## \[" docs/CHANGELOG.md` |
| git tag | 50 | `git tag -l \| wc -l` |
| GitHub Release | **37** | `gh release list --limit 100 --json tagName \| jq length` |
| draft / prerelease | 0 / 0 | 同上命令加 `--json isDraft,isPrerelease` |

> **口径教训**：先前口头说的「38 个版本」是把 `## [待发版]` 也算进了版本条目。改写后的验收基线按 37 记，删掉整段 3.11.3 / 3.10.2 后为 **35**，补回 3.11.8 后为 **36**。

## 二、错位一：`## [3.11.4]` 有条目、无 Release

- CHANGELOG 有 `## [3.11.4] - 2026-08-31` 段（`git show v3.11.4:docs/CHANGELOG.md` 确认该 tag 上就有此段）。
- `gh release view v3.11.4` → `release not found`。tag 存在，Release 未生成。
- 影响：Lane 3（逐个 `gh release edit`）**没有 3.11.4 可改**。这是「Release 未生成」，不是「notes 要改写」，处置方向不同 —— 是否补建 Release 属发版动作，须用户裁决，本轮不动。

## 三、错位二：`v3.11.8` 有 Release、CHANGELOG 无该条目段

**根因**（`git show 0a740fe -- docs/CHANGELOG.md` 实测 diff）：

```
-## [3.11.8] - 2026-09-25
+## [3.12.0] - 2026-09-25
+
+### 改进
+- 关于页新增离线隐私说明:…
+- 用户手册新增「离线与隐私」常见问题,…

 ### 改进
 - 维护更新:功能与使用方式无变化,本版以内部工程与文档维护为主。
```

`0a740fe`（发 3.12.0）把 `## [3.11.8]` 这个标题**改名**成了 `## [3.12.0]`，而不是在其上方新增一节。结果：

1. **违反「版本条目只增不删」** —— v3.11.8 的正文没丢，但它的**标题**被顶掉了，于是 v3.11.8 在 CHANGELOG 里彻底不存在。
2. 3.12.0 底下留下**两个连续的 `### 改进` 节**，第二个（`维护更新:功能与使用方式无变化…`）就是 v3.11.8 的正文被遗弃在 3.12.0 标题底下。
3. GitHub 上 v3.11.8 的 Release 照常生成（`release.yml` 在 tag 推送时读当时的 CHANGELOG 顶部，那时 v3.11.8 还在），故两侧永久错位。

**为什么它一直在那儿没人发现**：第二、第三个 `### 改进` 节的位置合法（Markdown 不报错、指针门禁不判红），而 CHANGELOG 无任何门禁覆盖（`grep CHANGELOG gates/ test/ tools/` 零命中）。**这是「无门禁」的实证代价，不只是一个笔误。**

**修法**：在 `## [3.12.0]` 上方补回 `## [3.11.8] - 2026-09-25`（日期取 `git for-each-ref --format "%(creatordate:iso)" refs/tags/v3.11.8` = 2026-09-25），正文取那个遗弃的 `### 改进` 节原文。

**曾被误判的方向**：初判该节是「发版流程自述、应删除」。**错** —— 删掉它会让 v3.11.8 两侧都对不上，且那是版本历史不是内部信息。「维护更新:功能与使用方式无变化」这句确实是发版流程自述（按 `PUBLISH-GUIDE.md`「不写发版流程自述」应去掉前缀），但**该版本发生过这件事**这一事实必须留。

## 四、错位三：v0.21.0 ~ v3.11.4 共 13 个 tag 无 Release

`git tag -l` 有 50 个，GitHub 只有 37 个 Release。差额：`v0.21.0`–`v0.30.0`（12 个早期 tag）+ `v3.11.4`。

- v0.x 那 12 个是本项目改用 GitHub Release 之前的 tag，属正常历史，**无须处置**。
- `v3.11.4` 见第二节，与其余不同：它落在 GitHub Release 已启用的时期内，是**漏生成**而非「尚未启用」。

## 五、给 Lane 3 的输入（逐个 `gh release edit` 的前置）

备份已落 `C:/Users/chenc/AppData/Local/Temp/opencode/m2w-release-notes-backup/`：

```
index.json          37 条 tagName/publishedAt/isDraft
bodies/vX.Y.Z.json  37 份原始 notes（回滚依据；gh release edit 是覆盖式写，无 git 可回滚）
```

- **可改的只有 37 个**，CHANGELOG 侧 3.11.4 无对应 Release。
- 改写须按 tag 逐个取 CHANGELOG 同版本段，**不能按位置对齐** —— 两侧已有错位（3.11.8 / 3.11.4），按序号第 N 个对第 N 个必然错。
- `v3.13.2` 的 notes 仅一句「本次为内部维护版本,无用户可感知变化。」（`< 40` 字符），改写时保留该语义。
- `release.yml:180` 的抽取正则是 `/## \[[^\]]+\] - [^\n]+\n([\s\S]*?)(?=\n## \[|$)/` —— **取第一个匹配段**。若 `[待发版]` 段非空，抽中的是它。这是发版前置①拦的场景，本轮改写须保证 `[待发版]` 仍为空。

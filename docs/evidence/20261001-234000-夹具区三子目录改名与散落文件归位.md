# 夹具区三子目录改名与散落文件归位（REQ-143 方案原文）

## 起因

`test/fixtures/` 装的是**三种性质完全不同的东西**，而门禁与视觉工具都直接按硬编码路径读它。DEV-GUIDE 对该目录只有一句「静态样例入 `test/fixtures/`（acceptance/ 生成 + manual/ 手工）」——「生成」与「手工」是**来源**维度，不是**内容**维度，也没说清谁消费。

## 实测事实

### 一、三子目录各按不同命名轴

| 目录 | 命名轴 | 谁写 | 谁读 | git |
| --- | --- | --- | --- | --- |
| `acceptance/`（37 文件） | **生成器流程名**（验收阶段） | `gates/fixtures/gen-fixtures.mjs`（机器） | `gates/geometry/geometry/driver.mjs:87` · `dev/visual-check.mjs:118` · 人 | 跟踪（但机器生成，`check:fixtures` 逐字节守恒） |
| `manual/`（15 文件） | **使用方式**（人工目检） | 人 | 人（打开产出的 docx/pdf 看中文渲染） | md 与图跟踪；产出的 `.docx`/`.pdf` 被 `.gitignore:38-39` 排除 |
| `main/`（2 文件） | **消费者目录名**（`test/main/`） | 人 | `test/main/converter.test.js:47-48` · `test/common/dual-sandbox.js` | 跟踪 |

三套轴混用，读者必须逐个查源码才知道哪个是生成物。`converter.test.js:45` 的注释已自陈「静态文件直接放 `test/fixtures/main/`，不接 gen-fixtures」——即 `main/` 是**手工输入桩**，与 `acceptance/` 的机器产物是不同性质。

### 二、根目录散落两个 png

`test/fixtures/` 直接躺着 `g1-tiny.png`（70 B，1px 桩图）与 `img-800x400.png`（1886 B，尺寸边界图），而另外三个子目录都规整分了目录。

两者的消费面只有两处，且都不是「样例文档」：`test/common/dual-sandbox.js:158`（`path.join(B, "g1-tiny.png")`）与 `test/main/converter.test.js:226`（`path.join(FIXTURES_DIR, "img-800x400.png")`）。它们是**图像输入桩**，与 `main/converter-sample.md`（124 B 最小 md）同类。

### 三、`acceptance/` 是门禁的产物，寄放在测试树

它的完整链路：

```
gates/fixtures/gen-fixtures.mjs  扫描 test/ 三段目录 → 逐个动态 import 读 fixtures 契约
  → 落盘 test/fixtures/acceptance/<段基名>[-<场景>].md + README.md 索引
  → 复制 md 引用的本地图片（引用路径不改写，GUI 按 md 所在目录解析）
消费方：gates/geometry/geometry/driver.mjs:87、dev/visual-check.mjs:118（两份都按硬编码
        path.join(root,"test","fixtures","acceptance",n) 取样例文件名）
漂移守护：check:fixtures（gates/probe/gate-probes/gates/fixtures.mjs 探针覆盖）
```

即：**由门禁树生成、被门禁树与工具树共同消费、身份是「门禁产物」**，却住在测试树的夹具区里。它与 `src/main/smoke.ts` 的处境同构（实现必须在能产出它、且能随包分发的那一侧）——`smoke.ts` 因此住在 `src/`，`acceptance/` 却住在 `test/`，这是一个未消解的不一致。

### 四、`main/` 与 `test/main/` 撞名

`test/fixtures/main/` 与 `test/main/` 并列出现时，读起来像同一层的东西：一个是「输入桩数据」，一个是「主进程层的验收段目录」。若 REQ-142 落地（`test/segments/` → `test/core/` + `test/gates/`），`test/` 下将有 `main/` 与 `gates/` 两个段目录，`test/fixtures/main/` 的撞名会更刺眼。

## 方案

### 目标形态

```
test/fixtures/
├── docs/       ← 原 acceptance/，改名
├── input/      ← 原 main/ + 两个散落 png，改名并归位
└── manual/     ← 不变
```

三条改动的理由各不相同，逐条列：

**① `acceptance/` → `docs/`。** `acceptance` 是**流程词**（验收阶段），不是内容词。这批文件的内容是「一份渲染输入样例文档」——`docs/` 直说「给人读、给渲染器读的文档」，且与 `manual/` 归为同类（现在两者是同一类东西被拆成两个名字）。同时它消解了「生成物 vs 手工」被当成目录分类轴的误用：来源差异由 `gen-fixtures.mjs` 的 README 首行「勿手改」+ `check:fixtures` 漂移门禁表达，不需要目录名来表达。

**② 两个 png → `input/`。** 理由是它们与 `converter-sample.md` 同类（最小输入桩），与「样例文档」不同类。

**③ `main/` → `input/`。** 「main」不表达「是什么」，只表达「被谁读」，且与 `test/main/`（层）撞名。`input/` 是内容词。

### 步序（每步独立成提交）

1. **两个 png 归位**（最小、零语义风险，先做）。
   - `git mv test/fixtures/g1-tiny.png test/fixtures/main/`
   - `git mv test/fixtures/img-800x400.png test/fixtures/main/`
   - 连带改两处消费点：`test/common/dual-sandbox.js:158`、`test/main/converter.test.js:226`。
   - ⚠ `gates/fixtures/gen-fixtures.mjs` 的 `listImageFixtures()`（`:106-129`）从 `FIXTURES_DIR` 递归扫**全部**图片夹具并比对字节基线，只排除 `acceptance/`（`:115`）。移动会改 `rel` 路径 ⇒ `--print-image-baseline` 重新登记基线，否则 `check:fixtures` 判红。这是**预期行为**（判据答的是「磁盘派生」，移动就该重新登记），但必须走登记命令而不是手改 JSON。
2. **`main/` → `input/`**（含上面的两个 png）。
   - 连带：`shared/paths.js` 的 `FIXTURES_DIR` 常量**值不变**（仍指向 `test/fixtures`，只是子目录名变），故消费它的 6 个文件不需要改；改的是 `test/main/converter.test.js:45,47,48` 与 `test/common/dual-sandbox.js` 里拼 `main/` 子路径的地方。
   - `.gitignore` 无 `test/fixtures/main/` 条目，无需改。
3. **`acceptance/` → `docs/`。**
   - 连带（全部是硬编码路径，逐处核对）：`gates/fixtures/gen-fixtures.mjs:44`（`ACCEPTANCE_DIR`）、`gates/geometry/geometry/driver.mjs:87`、`dev/visual-check.mjs:118`、`test/segments/fixture-contract.test.js`（生成器契约的恒等断言）。
   - `gates/fixtures/gen-fixtures.mjs` 的落点文案（`:193`「勿手改」那行、`:591` 完成输出）同步改。
   - **`gates-stay-in-gates` 的 allow 面零改动**：ADR-038 那条规则允许的是字面前缀 `test/fixtures`（不是 `test/fixtures/acceptance`），改子目录名不动它。这也是本方案能保持边界规则不变的原因。

### 验证

- 开发回路：`M2W_ONLY='fixture-contract,converter,dual-pipeline-matrix,geometry-gate'` + `check:fixtures`（含 `--print-image-baseline` 重新登记后的复核）+ `typecheck` + `lint`。
- 提交前：`npm run test` 全量（动了 `shared/paths.js` 的消费面与门禁夹具路径，属「动了共享测试设施」）。
- 完成判据之一：**`check:fixtures` 绿**（它同时覆盖「生成产物与磁盘一致」与「全部图片夹具字节与基线一致」两条，是本改动的天然判据）。

### 不做的事

- **不把 `acceptance/` 提到顶层新目录**（如 `samples/`）。56 个文件不值得换一棵顶层树；留在 `test/fixtures/docs/` 时，`gates-stay-in-gates` 已允许 `test/fixtures`，零改动。
- **不把 `docs/` 改叫 `samples/` 或 `corpus/`**。`docs/` 与 `manual/` 同类（都是给人读/渲染器读的文档），命名轴是「内容是什么」；叫 `samples/` 会与 `manual/` 的「使用方式」轴继续混用。
- **不改 `.gitignore` 对 `manual/*.docx|*.pdf` 的排除**。那是「产物落源文件旁、自清理」的既有纪律，与本改动正交。
- **不迁 `manual/` 的产出物位置**。DEV-GUIDE 的输出隔离纪律（smoke 强制 `outputDir=""`、产物落源文件旁）已把它隔离开，动它属另一题。

## 与 REQ-142 的关系

两条**独立可执行**，但有一处耦合：

- 若 REQ-142 落地（`test/` 出现 `main/` 与 `gates/` 两个段目录），本条的第 2 步（`main/` → `input/`）的收益从「可选」升为「必要」——否则 `test/main/`（段目录）与 `test/fixtures/main/`（输入桩）并列，撞名更刺眼。
- 若只做本条而不做 REQ-142，`test/fixtures/main/` 的撞名问题依然存在但程度较轻，`input/` 仍是更准的名字。

建议执行顺序：REQ-142 → REQ-143（本条），使第 2 步的收益最大化。

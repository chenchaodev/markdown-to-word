## 四、Lane A 的两处发现（回退，但知识保留）

### 4.1 派单前提不成立：共享工程副本的 4 道门禁存在**读写**冲突

派单时我断言「共享沙盒那 4 道改动目标互不重叠，可并发」。**实测不成立** —— 冲突不在写面，在**读面**：

1. `gates/fixtures/gen-fixtures.mjs:433` 对 `SEGMENT_DIRS` 下**每个** `*.test.js` 逐个 `await import()`；而 dual-matrix 用非原子 `fs.writeFileSync` 改写 `test/segments/dual-pipeline-matrix.test.js`（`gates/dual-matrix.mjs:123`）。并发 ⇒ import 撞上截断窗口读到半截 ⇒ SyntaxError ⇒ fixtures 锚点假红。
2. smoke 用 `fs.appendFileSync` 往 `dist/core/convert.js` 追加必失败实现（`gates/app.mjs:155`）；dual-matrix 的锚点要跑 **26 行真实转换**，被测对象正是 `dist/`。并发 ⇒ dual-matrix 在 convert 被桩成必失败时变红，**红因不是矩阵判定 → 结论直接不可信**。
3. `gates/smoke/check-build-fresh.mjs:58-59` 比 `src/**` 与 `dist/**` 的最大 mtime；smoke 的追加会顶高 `dist/` 最大 mtime，build-fresh 的 `utimesSync` 又会改 `src/main/index.ts` 的 mtime。并发 ⇒ mtime 关系不确定。

真正可并发的只有三道：`coverage`（自带 `c8-` 沙盒 + `NODE_V8_COVERAGE` 隔离）、`dist-manifest`（自带 `manifest-` 沙盒）、`registry`（纯进程内合成对象）。**但这三道合计耗时本就短于含 5 次 Electron 启动的串行链，给再多槽也换不来时间。**

### 4.2 回退的决定性理由：`M2W_GATE_PROBES_CONCURRENCY=1` 静默丢门禁

Lane A 的实现把池槽位算成 `poolLimit = max(0, concurrency - 1)`（`report.mjs:250`）。设 `concurrency=1` 时池槽为 0 ⇒ **三道独立沙盒门禁整体从报告里消失**：`gates` 从 7 降到 4、`cases` 从 31 降到 10。

**且这一劣化不会被任何断言抓到** —— `test/segments/gate-probes.test.js:217` 只比对「落盘报告的门禁数 == 内存报告的门禁数」，两侧都是 4，恒等通过。`summary.gates` 计数只进 `[ok]` 日志文本（`:289`），无断言。

这正是 gate-probes 这套机制被建立起来要防的那一类**恒绿失效**（ADR-015 体系的核心动机）。默认值 2 下功能正常，但「设 1 关掉并发做逐条定位」是一个极自然的排障动作，落进静默丢门禁不可接受。

**故整条 Lane A 回退。** 4.1 的冲突结论是本次最有价值的产出，已记录于此；若将来重做，正确的前置是「给 smoke / dual-matrix 各建独立副本而非共用一份」，但那会改变 `gates/app.mjs:2-3` 明写的「两者 dist 形态一致」前提，属架构级决定。

## 七、S1（纯逻辑段迁纯 node 宿主）实测结论：**建议不做**

两个不确定源已收敛，结论是收益与成本不成比例。

### 7.1 可迁移段实测：107/125（此前粗筛的 ≈84 **低估了 23 段**）

逐段用 `electron-mock-loader` 在纯 node 下真跑 `run()`：125 段全部 import 成功（零超时、零 `dist/` 缺失），107 段 `run()` 抛错、18 段不抛错。

18 段不可迁移的根因里，**8 段确认不可救**：
- `printToPDF` 返回空 Buffer（6 段：`footnotes`/`merge-toc`/`merge`/`pdf-bookmarks`/`pdf-meta`/`toc-pagenum`）—— 要 mock 真渲染 PDF 等于在纯 node 里实现 Chromium
- `main/mermaid-service`（需真实渲染引擎出 PNG）
- `segments/pdf-postprocess` —— `src/core/cancel.ts:213` 把超时计时器 `unref`，纯 node 下事件循环直接空掉、进程以 exit 13 死（已独立验证：注入常驻句柄后同脚本退出 0）
- `segments/runner-report` —— 它测的正是 segment-host 本身

另 7 段（B/C/D/E 类：缺 `webContents.setWindowOpenHandler` / `win.isDestroyed` / `Menu.setApplicationMenu` / `screen.getAllDisplays` / `clipboard.readBuffer` / `session.fromPartition` 返 null）理论上可补 mock，但补完多落回上面那 8 段。**天花板就是 107。**

### 7.2 收益（本机口径，且比调研估计更低）

| 项 | 实测 |
|---|---|
| Electron 段宿主地板 | **598ms**（主会话实测，8 次中位） |
| 纯 node 段宿主地板 | **224ms**（主会话实测 201~290ms 中位；调研报 113ms，**乐观约 2 倍**） |
| 单段省 | ≈374ms |
| 107 段串行省 | ≈40s（调研估 51s） |
| ÷ 本机加速比 3.4 | **≈12s 墙钟**（调研估 15s） |

相对 CI `test:coverage` 136s 基线：**约 9%**（调研估 11%）。且这是**理论地板上限**，未扣「迁移本身要花的改动时间」，也未扣 7.2.3 的覆盖率风险。

**CI 侧不可预测**：CI 4 vCPU 上 Electron 地板未实测；REQ-055 的 2.7x 膨胀系数按其自身方法论约束不得作依据。若 CI 地板显著高于本机，收益同比例缩水。

另需打折：`gate-probes`(19.3s)/`install-smoke`(6.8s)/`clean-artifacts-gate`(5.8s) 三段在纯 node 下**能跑通但仍须独占**（gate-probes 的工作树指纹对 `output/` 敏感），迁它们不省时间。

### 7.3 三项成本

1. **`electron-mock-coverage.test.js` 是名字级守护，对方法级退化恒绿。** 它钉死的 `SRC_REQUIRED`/`TEST_REQUIRED` 是**具名导入的名字集合**（`electron-mock-coverage.test.js:26-43`），不校验方法齐全、不校验返回值语义。7.1 全部 B/C/D/E 类失败都是「导出具名、但缺方法或返回空对象」（`screen` 在清单里但无 `getAllDisplays`；`session` 在清单里但 `fromPartition` 返 null）。**新增的 mock 补丁若只加不改这条守护，同样是恒绿盲区** —— 须同步扩到方法级断言。
2. **覆盖率可能净损失。** 参数向量对 node 与 Electron 无差别（`--all` 分母来自 `--include` glob，ADR-016 已固化），但**分子会掉、分母不动** ⇒ 四项下降。基线余量：statements 93.06/90（3.06pp）、**branches 89.08/85（4.08pp，最薄）**、functions 93.59/90（3.59pp）、lines 93.06/90（3.06pp）。branches 恰是最易因控制流分叉而掉的指标。**掉哪几个文件、掉多少 pp 无实测**（未跑整轮采集）。
3. **语义漂移风险。** 至少一处已知反例：`pdf-postprocess` 注入常驻句柄即可跑通，但那改变了它所测的「超时降级」路径的运行环境 —— 属「跑得通但测的不是原来那件事」。「`run()` 不抛错」≠「测的东西与 Electron 下等价」，这是 107 这个数字的判定口径上限。

### 7.4 建议

**不做 S1。** 约 12s / 9% 的本机口径收益，换来「改 mock + 扩守护段到方法级 + 覆盖率四项可能跌破阈值 + 语义漂移逐段裁决 + 8 段确认不可救」。**S1 之后剩余空间进一步塌缩**：地板降到 224ms 后，`test:coverage` 的理论下界约在 90s 量级，而唯一还能拿大头的 S3（同进程批量）/ S4（复用宿主）/ S5（段合并）**全部正面推翻 ADR-015 或 REQ-027**（悬挂段杀不掉、段崩溃带走同批、失败 artifact 与超时前进度丢失）。

即：**不放松隔离纪律，就只剩约 12s 可拿；放松纪律换来的也只剩约 12~20s。** 这个交换在任何一档下都不划算，故建议 REQ-131 判作废、不做。若日后门禁形态大改（段数或 Electron 启动模型变化）再重看。

### 3.2 Lane B 回退：提速引入了新的失败模式

**收益是真的**（CI 段耗时 14209→8363ms，本机省 5.8s），但**在 run 36815393411 上判红**：

```

  实际 测试段子进程异常退出(3221225477 = 0xC0000005 STATUS_ACCESS_VIOLATION)
```

崩溃夹具本该以退出码 7 结束，被记成 Windows 访问冲突。而 `0xC0000005` 正是 `runner.js:394-400` 注释点名过的坑：**c8 的覆盖写手挂在被测进程的退出路径上，活着的 Electron 主进程硬退时回写覆盖会取代真实退出码。**

机理：预算从 8s 压到约 2s 后，崩溃夹具更早、更快走到硬退路径，撞上覆盖写手与硬退的竞争。本机 5 次全绿、CI 首轮全绿、次轮判红 ⇒ **时序竞争，非确定性失败**。

**教训（可复用）**：提速改动若落在「被测进程会被硬杀/硬退」的路径上，必须单独验证「改动是否改变了退出时机」——本轮只验证了「断言没被削弱」，漏了「有没有引入新的失败模式」，这是验证面的缺口。

Lane C 与覆盖写手无关（它只删了 12 次 `node --check`，不改任何退出路径），故单独保留。

## 八、lint 缓存坏种子（REQ-134，唯一一条经实测成立的提速）

### 8.1 结果

| 口径 | 修复前 | 修复后 |
|---|---|---|
| **lint 步** | 47.0s（六轮 37~47s，均值 41.7s） | **4.0s** |
| `verify:ci` 步 | 202~233s | **148s** |

### 8.2 机理：命中即不写 ⇒ 坏种子永不自愈

`actions/cache` 在 primary key **精确命中时不重新写入**。旧 key 当初写入的 11789 B 被后续每一轮原样 restore、自我复制。**「冻结」的真判据是三件事合看**，单看「体积恒定」不够：

1. `created_at` 停在 2026-09-30T11:04（REQ-031 建缓存那轮），此后未变
2. `last_accessed_at` 一直涨
3. post 日志 `Cache hit occurred on the primary key`

加 `-v2` 版本段 = 换新 key，强制重建为 17875 B（zip 压缩后，对应未压缩 ~178KB），缓存随即生效。

### 8.3 判读陷阱（我踩了，写下来防重复）

**换 key 后的第一轮必然是 `Cache not found`，那一轮 lint 43s 是冷启动的应有值，不能用来判成败。** 我拿第一轮读成「`-v2` 无收益」，把有效修复误判成无效；**第二轮命中（lint 4.0s）才是判据。**

> 一般化：**任何改变了持久化/缓存状态的改动，「生效」只能在第二次运行观察** —— 第一轮测的是过渡态。

### 8.4 一次失败的实验设计（也记下来）

为回答「缓存到底有没有用」做过一次两臂 A/B：缓存开 lint 43s、缓存关 lint 26s，看似省 17s。但**同轮里与缓存无关的 `test:coverage` 也快了 25s**（144→119s）⇒ 那一轮 runner 整体就快，**效应量与波动同阶，n=1 分不开**。

设计缺陷在提交前就该想到：跨轮比较 4 vCPU 共享 runner，而该 runner 的整体波动（~25s）大于预期效应（~17s）。要真分离需**同一次 job 内跑两次 lint 的配对设计**，不是跨轮对比。

所幸它不影响最终结论 —— 8.1 有干净的同状态前后对照（坏种子命中 47s → 真实缓存命中 4s），不依赖那次 A/B。

这是**本次唯一一个经 CI 实测成立的提速**，也是 `verify:ci` 里除测试外唯一的大项。相比之下第七节的 S1 经实测**无效**（CI 地板不降）。两者并列的事实说明：本仓测试耗时的大头（验收段地板、覆盖率）**目前没有已证的有效杠杆**，而门禁类开销（lint 缓存）反而藏着可回收的 43s。

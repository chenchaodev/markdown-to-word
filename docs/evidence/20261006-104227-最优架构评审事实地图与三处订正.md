# 最优架构评审：事实地图与三处订正（其中一处是订正评审自己）

> 本文件是一次全仓架构评审的**事实快照与踩坑记录**，只增不改。三条结论已升 `docs/adr/ADR-065`（renderer 功能层注入式重构）；其余各条的去向见文末「结论去向索引」。
>
> **本文件的作用不是描述现状，而是钉住「哪些数字被引用错过」** —— 评审过程中发现同一批事实被三份来源给出三个不同答案，而其中两个是错的。若不先把数字钉死，后续每一个引用它们的决策都会继承同一个错误。

## 摘要

评审覆盖 `src/`（168 文件 / 28.8k 行）、`test/`（143 段 / 51.6k 行）、`gates/`+`shared/`（约 38k 行）。结论是骨架正确、细节有糙，其中三处是结构缺口而非细节。

本轮最重要的产出不是结论本身，而是**订正过程暴露的一件事**：三份独立来源（两轮 explorer 事实地图 + 一轮 oracle 评审）对同一批实测数字给出了三个不同答案，其中两个是错的；而我自己用来裁决的第三个脚本，第一版和第二版也都是错的。**三次错误里有三次是同一个失效形态** —— 见 §三。

还有第二条 equally 重要：**动手订正之前必须先确认被订正的对象真的说错了**。§一.2 就是这样被拦下来的 —— 若照原计划执行，会把仓库一句正确的、带前置警告的历史陈述改成当前值。

## 一、三处订正（这三处是被引用错的数字）

### 1. 唯一文件级运行期环不在 `markdown ⇄ pipeline`，在 `core/i18n`（且仓库自己的 ADR 早就记了这件事）

**错误说法**：事实地图称「唯一的运行期环是 `core/markdown/ai-cleanup.ts` → `core/pipeline/*` 与反向的 `core/pipeline/{parse,precheck}.ts` → `core/markdown/*`」，并据此说 `core-markdown-no-pipeline` 那条 `pending` 规则对应一个文件级环。

**实测**：对 `src/` 全部可解析源文件跑 Tarjan SCC（脚本落点见 §四），**文件级 SCC 只有 1 个**：`core/i18n/{index,t,dom,warning}.ts` 四文件互连，全是值边。`markdown ⇄ pipeline` 是**目录级** 2 环 —— 具体成因是 `core/markdown/ai-cleanup.ts` 依赖 `core/pipeline/{frontmatter,parse}.js`，而 `core/pipeline/parse.ts` 依赖的 `core/markdown/{comment,slug,cross-ref,table-width}.ts` **都不依赖 `ai-cleanup`**。两侧引用的文件集不相交，所以文件粒度无环。

**旁证（这一条特别值得记）**：`docs/adr/ADR-064` 的「已知边界」节**早已明文记着这个 i18n 模块环**，还写清了成因、为何当前安全、以及不拆的理由（拆了反而多一个文件、且「键集唯一事实源」会散成两处）。也就是说：**仓库对这个环的认知是准确的，比门禁注释准确**；错的只是门禁注释那句「唯一的运行期环是 markdown ⇄ pipeline」。

**影响**：`core-markdown-no-pipeline` 这条判据的依据要改述 —— 它防的是「`ai-cleanup`（解析之后的变换）住在 `markdown/` 里」这一个**目录准入**问题，不是「打破一个文件级环」。原表述把它说成环，会让后来者以为存在一个需要拆开的循环依赖，实际只需要挪一个文件的归属。

### 2. 「6 条 `pending: true`」不是仓库的说法，是评审自己的说法 —— 这条是订正评审，不是订正仓库

**实测**：当前 `pending: true` 是 **5 条** —— `gates/repo/check-import-boundary.mjs` 的 4 条（`core-markdown-no-pipeline` / `core-pipeline-no-render` / `main-windows-no-up` / `core-no-duplicate-export`），加 `gates/repo/check-test-layout.mjs` 的 1 条（`test-top-dirs-exact`）。

**但仓库本来就没这么说过。** `check-import-boundary.mjs` 文件头写的是「T0 阶段新建的 6 条判据…**当初**一律带 `pending: true`」，紧接着一句「T2 每转正一条就摘掉一条标记，所以『还剩几条』是变的 —— **要数字去看规则表派生，别手数**」。

⇒ 那个「6」是**历史值**（T0 时刻的条数），而仓库不仅没说错，还预先写了「别手数」。评审把它当成「仓库声称当前有 6 条」并据此列为订正项，是**评审自己的过度声称**。

**判据**：这与 §一 的另两条性质不同 —— 那两条是仓库文本确实与实测冲突，这一条是**评审的转述与实测冲突**。若照原计划去「修」这条，会把一句正确的历史陈述改成当前值，而正确做法恰恰是仓库自己写的那句：**这个数字是派生的，不要写进文档**。故本条不动仓库任何文本；结论回到本节首句：当前值 5 条，要数字去看规则表派生。

### 3. renderer feature 目录间是 5 对双向，且门禁里那条普查命令本身有 bug

oracle 指出地图称 3 对、实为 5 对，并进一步指出**门禁注释里指定的官方口径命令自身算错**。已逐条核实：

- 门禁 `renderer-foundation-no-feature-dep` 规则上方注释里嵌的那条 `node -e` 普查命令，取 from 侧时用的是 `path.relative(R,x).split(sep).slice(0,-1).join('/')`（父目录链），于是 `convert/events/*.ts` 的 from 被算成 `convert/events` 而非 `convert` —— 漏记 `convert→settings` 与 `convert→wizard` 两条边，同时把 `convert→convert`、`settings→settings`、`ui→ui`、`wizard→wizard` 这类 feature 内部边误计为 feature 边。该命令输出 **13 条边 / 3 对双向**（其中 4 条是自环）。
- 按 feature **根目录**折叠后重算：**11 条边 / 5 对双向**，唯一单向的是 `wizard → settings`。

**这条的意义超出数字本身**：那是门禁注释里指定的「要重新取当前值就跑这条」的官方口径，它给出的数字是错的 ⇒ 任何按它对账的人都会继承这个错误。修它时连带要把注释里的 `13/3` 一起改掉，否则改完命令不改数字，下一个读者仍会读到旧值。

## 二、被证实为真、不必再查的部分

以下是评审中被多方独立指认且经核实的结论，后续工作可直接引用：

- **`src/core` 零 electron import**；`node:` 内建只出现在 5 个白名单文件，其中 3 个是纯字符串运算。
- **renderer → core 只有 4 个符号面**（i18n 桶 / settings-defaults / presets / error-message），其余 core import 全是 `import type`。
- **`src/convert` 是四交付面共用的 headless 装配层，宿主注入点恰好四个**（settings / printPdf / mermaidResolver / onAfterCommit）。
- **CLI 与 MCP 同层、零依赖**，但 MCP 只支持 docx（格式写死在函数体里）。
- **取消契约是全仓唯一跨层传播正确的错误身份**（`core/cancel.ts` 的错误码 + 装配层的取消错误继承 + 批量汇总按码判定）。
- **`atomic-json.ts` 是真正的耐久性工程**（文件 fsync + 父目录 fsync + 写队列串行 + EPERM 有界退避 + 失败不提交缓存），不是「加个 try/catch」。
- **门禁判定体协议**（IO 经上下文注入、判定体与 `main()` 分离）是 20 个 selftest 各自只写几百行的唯一原因 —— 这是本仓最值得保留的工程约定之一。
- **全仓零 `skip`/`only`/`todo`**（`skipped` 是被测业务字段，不是测试跳过）；所有 env 开关的理由都写在代码注释里。
- **测试 import 构建产物而非源码是对的选择**：必须跑要发布的那个产物，且沙箱 preload 的 CJS 形态与类型擦除只在产物上可测。缺 `.d.ts` 是缺口，该补缺口而不是换 import 目标（见 `ADR-069`）。
- **门禁代码量已大于产品代码**；测试树行数里约 37% 测的是门禁与测试框架自身。

## 三、最重要的教训：三次测量错误，同一个失效形态

这一节是本文件最该被继承的部分。

**我用来裁决三处订正的 SCC 脚本，前两版都是错的，而且两版都「自信地」输出了结论**：

| 版本 | 缺陷 | 它输出的结论 | 真值 |
|---|---|---|---|
| v1 | 文件清单只收 `.ts/.cts/.mts`（161→159 个），解析到 `.js` 的边被丢弃 | — | — |
| v2 | `resolveSpec` 返回绝对路径，而索引以相对路径为键 ⇒ **每条边都解析成 `null`，图是空的** | 「文件级 SCC 0 个、目录级双向边 0 条」 | 1 个文件级 SCC、28 条目录级双向边 |
| v3 | 加了两道自检后才可信 | 3 个文件级 SCC → 手工核对后确认 1 个真环 | 1 个 |

**v2 是最危险的一次**：Tarjan 在空图上必然报「0 个环」，而「0 个环」听起来像个干净的结论 —— 它会直接推翻两方都提到的 `core/i18n` 环。**如果当时没有手工抽查两条已知边（`i18n/index→t`、`i18n/t→index`），我就会把一个空洞结果当成事实写进评审结论。**

配套的第二个坑：SCC 报出 3 个文件级环，我差点直接采信。手工核对另外两个时发现 ——

- `preload.cts ↔ core/preload-api.ts`：**type-only** 边（`import type`），编译期擦除，不是运行期环；
- `settings-panel ↔ settings-save`：**根本不是环** —— 反向的 3 处命中全部落在文档注释里，其中一处就是注释中引用的那段 `import` 示例文本。正向是 `settings-panel.ts:40` 的真值 import，反向无真 import。

⇒ **图里有环 ≠ 有运行期环。** 任何以正则扫 import 建立的依赖图，都必须区分值边与类型边，否则会把擦除掉的边算成结构性缺陷。

**归纳成三条可复用的判据**：

1. **测量脚本必须自检已知答案**。断言「图非空」不够 —— v2 的图大小断言是我第三版才加的，而真正有效的是**逐条断言若干条已知边存在**（`i18n/index→t`、`i18n/t→index`、`markdown→pipeline`、`pipeline→markdown`）。自检要在**输出结论之前**跑，且要挑那些「若脚本坏了就一定会缺」的边。
2. **工具给出的聚合数字要与手工小样本对账**。本案例里 5 对 vs 3 对的差别，正是拿门禁自己指定的那条命令跑一遍、再按另一种口径手算一遍才发现的。**当同一个数字有两个来源时，两个来源之一错的概率远高于「都错且错得一样」。**
3. **注释里的数字与它指向的命令必须一起改**。门禁注释里那条普查命令是「官方口径」，它的数字被下一个读者当事实引用；只修命令不改数字，等于没修。

## 四、可复算的脚本落点

本轮的三个测量脚本（Tarjan SCC、renderer feature 边普查、门禁注释里那条命令的修正版）都是一次性的，**刻意没有落进仓库** —— 它们是这份快照的取证工具，不是长期资产。若日后要复算，从本节描述重建即可，重建时**务必带上 §三 的自检断言**。

复核命令入口（不复制脚本，只指出各判据的权威出处）：

- 文件级环 / 目录级双向边：对 `src/` 全量源文件跑 Tarjan，并断言 `core/i18n` 四文件在同一个 SCC 内。
- `pending: true` 计数：门禁文件头已内嵌该 grep 命令（`check-import-boundary.mjs` 第 51 行附近），以它为准，不在注释里复述数字。
- renderer feature 边：判据本体是 `renderer-foundation-no-feature-dep` 那条规则，跑 `npm run check:boundary` 即得。
- `check:src-layout` 判红项：以 `--enforce` 跑一次为准。ADR-064 第 15 条记的「3 个首行不是注释」已过期，实测 6 个（新增 `core/text/mdast-utils.ts`、`renderer/about-preload.cjs`、`renderer/lang-bootstrap.js`）—— **引用那条 ADR 时须带实测**。

## 一、外部事实（可复核）

### 1. docx 侧的中西文间距：默认就是开的，**不需要写任何代码**

来源：Microsoft Learn《AutoSpaceDE Class》（引 ISO/IEC 29500-1 第 1 版原文），`https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.autospacede`

> **autoSpaceDE (Automatically Adjust Spacing of Latin and East Asian Text)** — This element specifies whether inter-character spacing shall automatically be adjusted between regions of Latin text and regions of East Asian text in the current paragraph.
>
> If this element is omitted on a given paragraph, its value is determined by the setting previously set at any level of the style hierarchy… **If this setting is never specified in the style hierarchy, its value is assumed to be *true*.**

同族 `w:autoSpaceDN`（中文与数字）同规则。关断形态是 `<w:autoSpaceDE w:val="false"/>`。

**推论与实测**：`docx@9.7.1` 不提供这两个元素的 API（`node_modules/docx` 全树零命中 `autoSpace`），本仓也不写它们 ⇒ Word 侧**本就开启**。故本工作项 **docx 侧零改动**；「加一个能关掉的开关并在 docx 侧生效」需要解包 `styles.xml` 注入 `docDefaults` 再重打包（jszip 已是依赖），代价与收益不成比例，已否决。

### 2. PDF 侧的中西文间距：`text-autospace: normal` 是正解

来源：W3C i18n《Managing inline spaces in Chinese & Japanese》`https://www.w3.org/International/articles/styling/inline-space`

> The CSS specification expects that, with no styling, the browser should automatically insert a gap between runs of ideographs or kana characters and runs of alphanumeric text… **the best you can probably do is: `text-autospace: normal;`**
>
> **None of the three major browser engines currently support the use of `replace`.** In fact, it's worse. If you add the `replace` keyword, Gecko and WebKit browsers will no longer apply the gaps they would produce without it.

该文亦记：clreq 建议中西文间距**至多 ¼ em**，CSS 规范建议约 1/8 em，**宽度由浏览器决定，CSS 不可调**。本仓取浏览器默认值。

支持情况：MDN《text-autospace》列 `normal` = `ideograph-alpha` + `ideograph-numeric`（中西文之间、中数字之间各加间距），是继承属性；Blink 已实现并进入 Baseline（2025-11），本仓 Electron 43 的 Chromium 远高于该版本。`text-spacing-trim: trim-start` 同族：收掉段首/换行到行首的开引号多占的半个字宽（W3C 该文场景 3 正是「2em 缩进 + 两端对齐 + 行首「」」）。

## 二、三项裁决（用户 2026-10-21 当场拍板）

| 裁决 | 取法 | 否决的选项与代价 |
|---|---|---|
| 字号制形态 | **下拉 + 保留 pt stepper** | ① Word 风格单一下拉替换 stepper：视觉更像 Word，但要移除 ± 按钮、改 IA 文档与冒烟断言，改动面更大。② 扩范围到 5–42pt 支持全字号表：会允许 42pt 正文这类不合理文档，且要动范围校验与相关测试。 |
| 混排间距是否做成可关的开关 | **常开、不新增设置** | ① 新增开关但仅 PDF 生效：关断时两格式观感不一致。② 新增开关且 docx 也真关断：需解包 `styles.xml` 注入关断形态再重打包（见 §一.1），成本最高。 |
| 是否顺带做行首标点缩排 | **本次一并纳入** | 不纳入的代价：中文排版包缺一环，且 W3C 场景 3 正是本仓「2em 缩进 + 两端对齐」的默认组合。 |

## 三、交付物与落点

- **core**：`src/core/settings/typography.ts` 新增 `CJK_FONT_SIZES`（9 档，按 pt 升序）、`cjkFontSizeOfPt`、`cjkFontSizePtOfId`。**只收正文字号域（8–24pt）内的档** —— 号数制全表的 24pt 以上（初号/小初/一号）与 8pt 以下（六号及更小）落在域外，越界档不选。反解按 0.5 网格**精确匹配**：离网格（如 9.2pt）或不在表内（如 11pt）一律 `null`，静默吸附会把两值不同的档误标。
- **PDF**：`src/core/pdf/template-css.ts` 的 `body` 规则内加 `text-autospace: normal` 与 `text-spacing-trim: trim-start`（不另起规则块）。
- **UI**：设置抽屉 `#cjkFontSize` 与向导 `#wiz-cjkFontSize` 两个下拉，**派生控件**（真值仍是 `typography.bodySizePt`，不新增持久化键 ⇒ schema / 预设 / 校验域 / 号段一律不动）。抽屉侧按派生键登记（先例 `templatePreset`），几何清单同步登记；档位文案经三语字典。
- **测试**：新增段 `test/core/cjk-font-sizes.test.js`（字号表形状 + 双向反解 + 三语文案齐备）；`test/core/typography.test.js` 与双管线矩阵 `body-typography` 行补 PDF 侧断言与 docx 侧「不得出现 autoSpace 关断形态」负向断言。

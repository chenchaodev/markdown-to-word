# WriteHooksOf 按组窄化失效：一处类型宣称与实况不符

> 结论去向：未升 ｜ 本条是**发现**而非**决定**，三个修的方向一个都没裁决（第六节明列未选），按本仓纪律「未升格」；交付记录落在 `docs/REQ.md` REQ-244（待拍板），将来若裁决路线再升 `docs/adr/ADR-0NN-*.md`。

> 2026-10-14。由 REQ-243 收尾时泳道附带发现，主会话以**纯读 + 类型推导**核实（全程未改任何代码、未跑探针）。结论：`src/renderer/settings/settings-controls-table.ts:577` 的宣称对四处按组声明**不成立**，但 `WriteHookRegistry` 那一侧**仍有效**，故非全面失效。

## 一、被判定的那个宣称

`src/renderer/settings/settings-controls-table.ts:577`：

```
/** 某组自己的那几条写侧钩子(多写/漏写都在 tsc 期报错)。 */
export type WriteHooksOf<G extends ControlGroup> = {
  readonly [K in HookedWriteKey as GroupOf<K> extends G ? K : never]: WriteHook;
};
```

同源宣称第二处，`src/renderer/settings/settings-bindings-app.ts:75`：

```
 * 键集仍由 `WriteHooksOf<"app">` 反推校验,多写/漏写照样 tsc 报错。
```

## 二、失实效应的推导（关键三步，全部可从源码读出）

**第一步：`ControlGroup` 是一个联合，共 7 值**（`:29-36`）：

```ts
export type ControlGroup =
  | "preset"
  | "typography"
  | "headerwatermark"
  | "numbering"
  | "convert"
  | "app"
  | "mirror";
```

（以下称这七个字面量的并集为 `U`。四处按组声明用到的 `"convert"` / `"typography"` / `"headerwatermark"` / `"app"` **都是合法取值**，不存在形参约束违反。）

**第二步：所有条目工厂的 `spec.group` 都声明成完整联合 `U`，没有一处按具体组收窄。**

三个工厂的签名里 `group` 字段全是 `readonly group: ControlGroup`：

| 位置 | 工厂 | group 的声明 |
|---|---|---|
| `:111` | `ValueEntry` 接口 | `readonly group: ControlGroup` |
| `:136` | `ChipEntry` 接口 | `readonly group: ControlGroup` |
| `:155` | `DerivedEntry` 接口 | `readonly group: ControlGroup` |
| `:168` / `:186` | `valueEntry` spec / `chipEntry` spec | `readonly group: ControlGroup` |
| `:212` | `derivedEntry` spec | `readonly group: ControlGroup` |

⇒ `CONTROL_ENTRIES[K]["group"]` 对**每一个** K 都求值为同一个类型 `U`，而不是该条目自己的那个字面量组名。

**第三步：于是 `as GroupOf<K> extends G ? K : never` 与 K 无关。**

把第二步代进去，映射类型的 `as` 子句对每个键算出的都是**同一个**谓词：

- 若 `G` = `U`（完整联合）⇒ `U extends U` 为真 ⇒ **所有** `HookedWriteKey` 都保留。
- 若 `G` 是 `U` 的任一真子集（如 `"app"`。注：`"app"` **不在** `U` 五个值里，见下）⇒ `U extends G` 为假 ⇒ **一个键都不保留**，得到 `{}`。

也就是说这个条件**只会整体成立或整体落空**，不可能按组细分——而设计意图恰恰是「按组细分」。

## 三、失效面与仍有效的面

**失效面：四处按组声明拿到的实为 `{}`。**

| 位置 | 声明 |
|---|---|
| `settings-bindings-convert.ts:60,65` | `WriteHooksOf<"convert">` |
| `settings-bindings-typography.ts:91,103` | `WriteHooksOf<"typography">` |
| `settings-bindings-headerwatermark.ts:46` | `WriteHooksOf<"headerwatermark">` |
| `settings-bindings-app.ts:77,85` | `WriteHooksOf<"app">` |

把对象字面量赋给 `{}` 类型永远成功（`{}` 接受任何对象，且空目标不触发多余属性检查）⇒ **这四处的键集完全没有 tsc 保护**，`:577` 与 `:75` 的宣称是假的。

⚠ **一处读错，留档免得后人重犯**：核实过程中曾以为 `"app"` 不在 `ControlGroup` 取值域内、并据此写下「形参约束违反」的推断。**那是错的** —— `"app"` 与 `"mirror"` 都在域内（`:35`/`:36`）。错误来源是第一次读类型联合时 `sed` 范围取窄（29,34），把联合的末两个值截掉了。⇒ **读联合类型不能只截一段**；本例中核心推导（`GroupOf<K>` 对每个 K 都是同一联合）与这个读错无关，但任何依赖「域内有哪些值」的结论都会被它带偏。

**仍有效面：登记册那一侧是真的。**

`settings-controls-table.ts:583`：

```ts
export type WriteHookRegistry = WriteHooksOf<ControlGroup>;
```

`G` 用的是完整联合 ⇒ 所有 `HookedWriteKey` 保留 ⇒ `WriteHookRegistry` 是**真正的全键表**。「全登记册意义上多写/漏写报错」仍然成立。⇒ **本条不是全面失效，是「按组」这一层整个失效。**

## 四、为什么这值得单独记一条

它不是「某处类型写得不够好」，而是**一处被写进注释的保证失效了**。`settings-bindings-*.ts` 四处按组表的键集防多写/漏写，靠的就是 tsc；现在这道防线静默消失，而**没有任何机器看守会发现**（它不产生诊断、不报错，只是不再拦）。同类形态本仓已有命名：`ADR-062` 判 L11 的 basename 口径为假绿时用的判据是「那是**假绿**」—— 这里正是「防线恒绿」。

## 五、核实方法（为何不写探针）

最初想写一个 `probe.ts` 用 `@ts-expect-error` 实测。**放弃**，两个原因：

1. 当时全链 `verify:ci` 正在后台跑，链上就有 `typecheck`。往仓根 `cp` 一个 `.ts` 文件会在链的读窗口内造成**真阳性**（并发写导致读取那刻文件不自洽）。主会话已因此承认为疏忽。
2. 推导本身已完备且**每一步都能从现有源码读出**（第二张表的五个 `group:` 声明行号是硬证据），不需要运行期证据。若将来要立项修，那时再补探针不迟。

## 六、修的方向（**未裁决**，此处只列不选）

1. **让工厂保住字面量组名**：三个工厂的 `spec.group` 从 `ControlGroup` 改为泛形参 `G extends ControlGroup`，`group: G`。这保住 `GroupOf<K>` 的按组收窄，代价是 `CONTROL_ENTRIES` 的类型显著复杂化，且 `satisfies` 注解处要重新收拢。
2. **改为显式两张表**：钩子键的组归属不用「从 `CONTROL_ENTRIES` 反推」，直接单独声明 `HOOK_GROUPS: Record<ControlGroup, readonly HookedWriteKey[]>`，再由此派生 `WriteHooksOf`。反向保证仍在，且不再依赖间接推导。
3. **只改注释**：若判断「按组键集保护不值得那个复杂度」，就把 `:577` 与 `:75` 的宣称改成实话（写明只有登记册侧有保护）。**最低成本，但把问题留在原处。**

⚠ 无论选哪条，**第一步都该先实测确认失效面**：写一个 `probe.ts` 故意把某组钩子表漏一个键/多一个键，看 tsc 是否真的不报错。本节的推导已完备（第二节三步全部可从源码读出），但那推导**只证明「键集为空 ⇒ 无检查」这一条逻辑**，没有在真实 tsc 上跑过；且当时全链在跑、往仓里 cp `.ts` 会造成真阳性，故当时刻意没做。

# 转换结果到剪贴板 · 调研与设计依据(issue #1 诉求 2)

> 来源:GitHub issue [#1 便携版及转换markdown代码为word内容到剪贴板需求](https://github.com/chenchaodev/markdown-to-word/issues/1),2026-10-16 提出。
> 取证方式:`explorer` 一条(管线侧)+ `librarian` 一条(格式裁决)+ `oracle` 一条(交付面设计裁决,只读);**承重结论由主会话在本地复核**(`package.json` 版本 · `node_modules/electron/electron.d.ts` · `src/core/pdf/template.ts` · `src/renderer/convert/file-list.ts`)。**未跑任何门禁链与构建**。

## 一、方向区分(最容易被标题误导的一点)

3.10.1 已交付的「剪贴板直转」是 **剪贴板文本 → 转换**(输入侧,`src/main/ipc/register.ts:519` 的 `clipboard:read`;CHANGELOG.md:293)。issue 诉求是 **转换结果 → 剪贴板**(输出侧)。
⇒ `src/main/ipc/channels.ts:13` 的通道全表**无 `clipboard:write`**;renderer 现有两个「复制」按钮只复制**文件路径**(`src/renderer/convert/events/dialogs-events.ts:160`、`:206`)。**输出侧零实现**,不是「已有功能的延伸」。

## 二、管线就绪点(改动不渗进 core)

- core 头注明写「无 IO、无 Electron」(`src/core/convert.ts:1-17`),外部能力全经 `ConvertContext` 注入(`:98-161`)。
- 入口 `convert(md: PreprocessedMarkdown, format, context)`(`:238`);**入参不是裸字符串**(frontmatter 已由 `src/convert/preprocess.ts` 的 `prepareMarkdown` 剥离)。
- 产物:docx 分支 = `Buffer`(`:185`,产出 `:335-359`);pdf 分支 = **完整 HTML 字符串** + 页眉页脚模板(`:216`)。
- **落盘在 core 之外**:`src/convert/run.ts:138 emitConvertedArtifact` → `:221 persistArtifact` → docx `:248 commitArtifact` / pdf `:256 printPdf`;`printToPDF` 在主进程(`src/main/converter/electron-side.ts:53`)。⇒ 新增「不落盘」通道 = **编排层加一个分支**,不动 core。

## 三、格式裁决(`librarian` 查实)

- Word/WPS 认的富文本只有 **CF_HTML**(剪贴板注册名字面量是 `HTML Format`,**不是** `CF_HTML`)与 **RTF**。
- **Word 自有格式此路不可用**:`WordprocessingML` / `Flat OPC` / OLE「Word Document」**无第三方可写的公开剪贴板格式**(`WdPasteDataType` 取值域里没有它们)⇒ 「要 docx 那样全保真」只能走 COM 在光标处插入,不是剪贴板格式能达成的。
- CF_HTML 规范要点(MS Learn「HTML Clipboard Format」,一手):UTF-8(Windows 文本通用的 UTF-16 的例外)· 头含 `Version` / `StartHTML` / `EndHTML` / `StartFragment` / `EndFragment` · **偏移按字节计** · fragment 须由 `<!--StartFragment-->` / `<!--EndFragment-->` 逐字包裹。**偏移「字节 vs 字符」在微软自家博客与规范原文之间措辞冲突,以规范为准。**
- **本仓不需自己拼头**:Chromium 在 Windows 上把 `clipboard.write({ html })` 走 `HtmlToCFHtml` 自动补头 ⇒ 传 HTML 片段即可。**强推断**(依据 Electron `electron_api_clipboard.cc` 委托 Chromium `ScopedClipboardWriter` + 四份 Chromium 派生实现,官方源在本沙箱不可达),**上线前须实测一次**。
- **Electron 版本面(本地实读)**:`package.json:179` = `electron ^43.2.0`,实装 `node_modules/electron/package.json` = `43.2.0`;`electron.d.ts:6978` `write(data, type?)` 对象形 · `:6994` `writeBuffer` · `:7007` `writeHTML` · `:7015` `writeRTF` **均在**(旧 API)。**44 起全部重构为 `ClipboardItem` 且渲染进程彻底不可用** ⇒ 写入点应封成**主进程单点**,便于日后迁移。

## 四、两个缺口(已定对策)

1. **CSS** —— pdf 侧全在 `<style>` 块里(`src/core/pdf/template.ts:163`),而 Word 粘贴走 MSHTML、**基本丢 `<style>` 与 class**。
   **对策:渲染期直接产出行内 `style="…"`,不引任何 CSS 内联依赖。** 因为走的是独立渲染路径(见 §七),没有样式表就无所谓内联;`juice` 被否(它内联的是**选择器声明**,且不解析 `::before { content: counter() }`,对本项目反而是负收益)。⇒ **本步不新增依赖**。
2. **图片** —— 正文图是 `file://`(`template.ts:100-102` 注释原话;`src/core/pdf/rules/image.ts:51-55` 只改写本地图为 file://),而 **`file://` 跨应用粘贴不保**;logo 已是 base64(`:74`)。
   **对策:base64 内嵌 + 复用既有字节预算**(`src/core/resource-limits.ts` 的 `ImageBudgetLedger` / `maxImageBytes` / `maxDocumentBytes`,pdf 外链内嵌已在用);**超限必须给 warning**,不能靠 Chromium 剪贴板静默失败(上限约 256 MiB,`clipboard_win.cc` 的 `kMaxClipboardSize`,**超限静默失败**)。**用户 2026-10-18 拍板取此对策。**

## 五、本仓独有的资产:OMML(决定后置)

`src/core/docx/handlers/math.ts:10` 序列化 **`<m:oMath>`** ⇒ 本仓**已有 LaTeX → OMML 能力**,而 Word 的 HTML 导入器**恰好认 OMML**;pdf 侧则走 KaTeX HTML(`src/core/pdf/render.ts:26`)。用户场景是「DeepSeek 的回答」——**公式是常见成分**,直接照搬 pdf 模板会让**公式粘进 Word 退化成图片或纯文本**。
**决定:本步不注入 OMML**(MVP 按 KaTeX HTML 产出并在降级清单登记,兜底退回等宽 TeX)。理由:本仓 OMML 是 `docx` 库**组件**(`MathComponent[]`,非裸 XML 字符串),且「Word/WPS 是否认 HTML 剪贴板里的 `<m:oMath>`」**零实测依据** ⇒ 验证成本高、结果不确定。**用户 2026-10-18 拍板后置**,并设了一道人工实测闸门(Word 365 / WPS 各一次)作为是否重启该选项的条件。

## 六、边界清单(HTML 剪贴板能丢什么)

**一定丢**:页眉 · 页脚 · 页码 · 目录域(活 TOC 字段)· 分节与页面设置 · Word 命名样式定义 · 脚注/尾注 · 批注/修订/交叉引用字段。
**可保**:字符格式(粗斜下划线删除线 · 字体含东亚字体 · 字号颜色高亮 · 上下标)· 段落格式(对齐缩进行距段间距)· 表格 · 列表 · 代码块 · 超链接 · base64 内嵌图片。
**待实测**:分页符(`page-break-before/after:always`)是否被粘贴采纳。
**关键判断**:用户描述的「临时粘一段答案进 Word」场景,**「一定丢」的项一个都不需要** —— 这是取 A 档、不上 COM 的根本理由。

## 七、交付面设计裁决(`oracle`,2026-10-18)

**1. 新建独立渲染路径,禁复用 `PdfArtifact.html`** —— 在 core 侧新建 `src/core/clipboard/render.ts`,产出可直接粘贴的内联 style 片段。复用 pdf 产物有三处硬伤(逐条落到机制):
   - **编号会静默消失**:pdf 的标题/题注编号是 `h1::before { content: counter(h1c) }`(`src/core/pdf/template-css.ts:175-212`),**不进文本节点**,任何内联方案都无法物化。**这一条单独就足以否决复用。**
   - 整篇 pdf HTML 是打印文档(`@page` / 分页 / 封面 / 页眉页脚两遍法),剥离它等于对成品 HTML 做正则手术 —— 正是本仓已弃用的反模式(`convert.ts:228-229`、`postprocess.ts:33-35`)。
   - `file://` 图片跨应用不保。
   ⇒ 代价是存在「同解析器(markdown-it)下的两种序列化」,需在 `convert.ts` 头注追加一行有意差异说明。**不新增 `ConvertFormat` 取值**(见 §九)。

**2. 写入点与 IPC 形状** —— 通道 `clipboard:write`(与既有 `clipboard:read` 成对,遵循 `域:动作`)。载荷传「源路径 + markdown + 选项」**由主进程渲染**(渲染所需能力只在主进程可注入;renderer 是 sandbox)。**写入点收在 `src/main/services/clipboard-write.ts` 单文件** —— 它是 Electron 44 `ClipboardItem` 迁移的唯一触点。装配层新建 `src/convert/clipboard.ts`(零 electron,注入 `ClipboardWriter` 能力,缺省即报错不降级,与 pdf 的 `printPdf` 同口径)。**不复用** `temp-html.ts`(它管临时文件,剪贴板不需要任何文件)。返回载荷单源放 `src/core/ipc-contract.ts`。

**3. UI 入口 —— 行级按钮(用户 2026-10-18 定)**
   落点有现成结构:`src/renderer/convert/file-list.ts:77-120` 的 `renderQueue()` 对 **n≥1** 都渲染 `li.multi-item`(n=1 只是少了拖拽手柄与序号),且**每行已有 `.multi-actions` 动作区**(`:110-114`,目前只有移除按钮)⇒ **原地扩展,不是新开槽位**。
   **范围:每行都有(n≥2 即批量逐项)** —— 用户 2026-10-18 拍板,放弃了「本步只做单文件」。
   ⚠ **必须守住**:标签与既有「复制路径」按钮(`dialogs-events.ts:160/206`)在**词义层**分开 —— 复制的是**内容**不是路径,不得只写「复制」。视觉与措辞归 `@designer`。
   **技术后果**:行上还没有产物 ⇒ 点击时必须**现渲染**,因此它仍是一次转换调用,只是输出到剪贴板而非文件,**且不写进 `format` 设置**。

## 八、三档选型与拍板

| 档 | 手段 | 保真 | 成本 | 结论 |
|---|---|---|---|---|
| **A** | CF_HTML | 丢全部页面级结构,正文格式可保 | 中 | **用户 2026-10-18 拍板取此档** |
| B | RTF | 对 Word 略高于 HTML | 本仓**零生成器**,表格与 CJK 需手写(同行 Delphi `CnMarkDown.pas` 自称不支持表格) | 未取 |
| C | DOCX + COM 光标插入(同行 PasteMD 选型) | 全保真 | 高:引入 Word/WPS COM 自动化,且要求目标应用在跑 | 未取,与本仓「离线转换器」定位冲突 |

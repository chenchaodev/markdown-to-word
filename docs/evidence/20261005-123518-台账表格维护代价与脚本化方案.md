# 台账与计划表的维护代价：三种处置的实测与选定方案

> 结论去向：落 REQ.md 行 ｜ 对应台账行 REQ-194（号以 `docs/REQ.md` 号段为准）
>
> 原文写作时间：2026-10-05。调研方式：只读代码普查（耦合面定位）+ 实测文档行。

## 一、问题陈述

`docs/REQ.md`（188 行台账，4 节 × 6 列）与 `docs/PLAN.md`（321 行，15 张表）大量依赖 Markdown 表格。表格的维护代价高于散文，且已实际产生失准 —— 本轮不是预防性担忧，是**已发生事实的盘点**。

## 二、已实测的三类失准

### 2.1 列数错位，门禁只出声不判红

⚠️ **本节已被 REQ-193 抢先，且根因比本文原先写的更细 —— 以 REQ-193 为准。** REQ-193 实测 5 处破损（已修 1，剩 `:126` / `:127` / `:174` / `:315`），其结论是：**根因不是裸换行，是单元格里的竖线分隔符 —— 即使包在反引号里也会被 markdown 切开**。本文初稿把它写成「未转义竖线」，那个表述会把人导向「加转义就够」的错误修法；真正的修法是**不让人手写表格格**（见 §五 Phase 1）。

判据侧的机制仍然成立：`gates/repo/check-pointers.mjs:1281-1287` 与 `:1599` 的列数守卫在 `row.cells.length !== row.headerCount` 时**整行退出全部判定，且只出声不判红**，靠 `:2133-2141` 推进结论行 `gaps` 才可见。`gates/repo/check-docs.selftest.mjs:628` 就有「故意写未转义 `|`」的用例，说明这条路径是被知道的。

⚠️ **另一处覆盖关系**：`checkTableShape()`（C7）**只作用于台账** —— `check-pointers.mjs:1918` 的调用点传的是 `PROJECT_PROBE` ⇒ **PLAN.md 的表格形态根本无人看守**，`check:docs` 全绿也发现不了（REQ-193 同日实测）。本文 §五 Phase 2 因此**不是新提案，是 REQ-193 的一半**，已改为交叉引用。

### 2.2 同一个上限有两套字面，且其中一套无人守

- `docs/REQ.md:59` 与表头 `:61` 写 **≤100 字**，门禁常量 `WHY_LIMIT_DONE = 150`（`check-pointers.mjs:1479`）。
- `docs/REQ.md:210`（已作废节表头）写 **≤200 字**，该节不在 `section.includes('已完成')` 分支内（`:1613`），实际走 `WHY_LIMIT = 250`。

判定本体只读常量、不读表头文字 ⇒ 那两处字面**没有任何判据会响**。

### 2.3 列按名取 ⇒ 改形状会静默退化而非判红

`locateRegistry:1146-1147` 按「含『号』/ 含『状态』」定位列，`ledgerTextCols:1531-1532` 按「含『标题』/ 含『为什么停在这』」定位。列名一改，判定不是变红，而是**匹配不到任何列 ⇒ 零覆盖全绿**。这比「表格难维护」更坏：门禁从守门人变成装饰。

## 三、耦合面实测（换形状的代价）

耦合高度集中在两个文件，各自还有一份**独立实现**的切格函数：

- `gates/repo/check-pointers.mjs`（2206 行）—— 台账判定的**全部**落点。关键位置：`:918-923` `SECTION_STATUS` 节名相容表 · `:974` `normalizeHeaderCell` · `:1030-1071` `checkTableShape`（C7 结构判据）· `:982-1003` `splitTableRow` · `:1163-1183` 号段表定位 · `:1476-1480` 三个上限常量 · `:1579-1621` `checkLedgerShape`（C1/C2）。
- `gates/repo/check-plan-in-progress.mjs` —— PLAN.md 判据本体。`:78` `STATUS_MARKERS` · `:84` `MIN_STEP_ROWS = 3` · `:180-201` **另一份** `splitTableRow` · `:227-260` `parsePlanSteps`（靠「首格剥得出 `T\d+` id」识别子步行）。

配套夹具（改形状必须同批改，否则假红）：`test/gates/check-pointers-ledger.test.js:81-83` · `test/gates/check-pointers-e2e.test.js:60-61`（列名与本仓实际不同，正证「按名取」）· `gates/repo/check-docs.selftest.mjs:60-100` · `gates/repo/check-plan-in-progress.selftest.mjs:80-160`。

跨仓面：形状的单一事实源是全局配置目录 `templates/docs-init/REQ.md:22-42` 与 `templates/docs-init/PLAN.md:46-52`；`DOC-SYSTEM.md:10` 把「同一行」写成形状约束，与全局 `AGENTS.md` 六第 2 条「『有哪些事』与『为什么停在这』必须同刻被同一人读到」同源。**竖列化直接推翻该约束** ⇒ 需改配置仓规则 + 下游模板，且属「改变原规则要求的动作」，按全局 `AGENTS.md` 一只能加严不能放宽，须经用户确认。

## 四、三条路的裁决

| 方案 | 裁决 | 理由 |
|---|---|---|
| ① 每行换特殊分隔符（竖列化） | **不做** | 耦合面在两个判定本体的 ~15 处落点 + 4 份夹具 + 配置仓模板与规则；且列按名取使改形状的后果是**静默零覆盖**而非判红；并推翻「同一行同刻可读」这条被明文写下的约束 |
| ② 脚本统一维护 | **采纳**，且是 ① 的正确替代 | 现状 15 张表全靠人手 `edit`，没有任何写入口。脚本提供受约束的写入口，顺带获得校验能力 ⇒ **不必改形状即可消掉 §2 的三类失准** |
| ③ 数据外置为 JSON、md 变生成物 | **不做** | 会把「事实与理由同处一行」拆成「数据在一处、渲染在另一处」，正是全局 `AGENTS.md` 六判为必然漂移的形态 |

**② 的关键设计约束**：脚本读写**现有 md 表格**，md 仍是唯一事实源，只新增写入口。若反过来把 JSON 变事实源，收益（机器可读）与代价（唯一事实源被搬到人不去读的地方）不成比例。

## 五、选定方案：三个阶段

### Phase 0 ｜ 把静默失效变成判红

不动表格形状，只改判定本体：

1. 列数守卫由「出声」升为进 `gaps` 判红（`check-pointers.mjs:1281`、`:1599`，出口在 `:2133-2141`）。
2. 四节表头一致性纳入检查 —— 顺带治 §2.2 的两处字面漂移：删掉 REQ.md 表头的括注数字（`:61`、`:210`），改由门禁常量单点持有、人读侧指向它。

**预期**：立刻抓出 §2.1 的三处既有错位（须先手工修掉，否则新判据上线即红 —— 顺序：先修数据，再上判据）。

### Phase 1 ｜ 台账维护工具（**两段式：先项目跑通，再进模板**；落位见 §7.0）

**次序是用户 2026-10-05 裁决**，不是实现细节 —— 它决定了两件事的归属：漂移风险何时产生、模板拷贝清单何时改。

**段一 · 在本项目实现并跑通**

1. 抽 `shared/markdown-table.mjs`（纯解析，两份现存实现取并集），`check-pointers.mjs` 与 `check-plan-in-progress.mjs` 改 import；**判定体一行不动**（净减行数 ≈ 0，这是预期结果 —— 抽的是解析不是判据）。
2. 写 `tools/req-edit.mjs`：先只读三命令（`next` / `show` / `pool`，可独立验证、零风险），再写侧三命令（`add` 自动取号＋同步号段两格 · `set` 多列、自动转义竖线、校验列宽 · `move` 搬行＋按目标状态重选字数档）。`check` 归门禁，**不重写 R1–R8 / C1 / C2**。
3. ✅ **已核销（2026-10-05，用户裁决：保留 grep、只修理由）** —— 原步骤要求「把 `docs/REQ.md:22` 那条 grep 示例改为指向 `pool`」，**按字面不可实施**，其顾虑的前提也不成立：
   - **`pool` 给不出「本节行数」**：实测它输出的是**跨「待拍板」＋「在办」两节的扁平行列表**（`- REQ-001 [待拍板] …`）、**不计数**；而该注记说的是「**本节**行数」，且按 `REQ-RULES.md` 本节同时含「待拍板」与「未开工」两种状态。三者对不上。
   - **「grep 逐字依赖形态 ⇒ 脆弱」这个前提不成立**：那个「行首 `| REQ-`」形态是**门禁强制**的（R3 号形态 ＋ C7 表形状），不是书写约定 ⇒ 形态若变，**门禁先判红**，不存在「grep 悄悄返回 0」这个失效形态。
   - **实际改动**：`docs/REQ.md` 两处小节注记（待拍板节与已完成节，**同一语义曾写两遍且措辞不同**）由「本节行数」改为「本节**数据行**数」＋「**按节筛**」，并各加一句防呆「**别改成指向 `pool`**」及其理由（不可行的原因）—— 否则下一个人会「顺手」把它指向一个给不出该数字的东西。
4. 「改状态是一次会制造违规的操作」（REQ.md 头部自述，因上限按状态分档）这个坑由 `move`/`set` 自动处理，不靠人记。

**段一验收（不过不进段二）**：`pool`/`show` 对现有台账零改动通过（幂等）· 三种人为变异（超列宽 / 竖线 / 号段不同步）判红 · 构造一行 5 格（表头 6 列）时 `show` **必须报错退出**（返回「字段 3 = …」即为错，§7.3）· `check:docs` 与 `check:boundary` 绿。

**实现期三处主动偏离（已裁决接受）**：

1. **`set` 的列名加了一张别名表**（原样精确匹配优先，匹配不到再走别名）。**理由成立**：台账真实表头在同一列上有多种写法（`为什么停在这`/`为什么停在哪` ＋ 已完成/已作废两节的括注差异），纯精确匹配会让那两节**静默不可写** —— 静默不可写正是本方案要消灭的那类失败形态。门禁侧 `ledgerTextCols` 同样用 `includes()` 双写法，两处口径一致。

3. **搬空源节时的补空行做成条件补**（下方已是空行就不补），否则会在合规台账上多插一个空行。

**一处规则既有缺口（工具只是撞上它，没有引入它）**：**「已作废」节没有分档**。台账该节表头写 `≤200 字`，而门禁 C2 只量 `section.includes('已完成')` ⇒ 实走 `WHY_LIMIT`(250)。工具按「非已完成 ⇒ 250」实现，与门禁一致。⚠️ 这是 §2.2「同一上限两套字面」的第三个实例，段二收口时要一并处理。

### 7.1 `shared/markdown-table.mjs` 的 API 与「取并集」硬要求

```js
export function splitTableRow(line)      // 收整行，自己 trim
export function isSeparatorRow(cells)    // 剥 ` * 后测 /^:?-+:?$/
export function tableBlocks(lines)       // 连续 | 行成块；块内允许空行与 <!-- -->
export function normalizeHeaderCell(cell)// 去空白 * ` ：
export function normalizeLedgerCell(cell)// 去 ` 与 ~~
export function locateRegistry(text)    // 表头含号+状态 → 行集（跨节合并、列映射逐块挂）
export function ledgerTextCols(header)   // 按「标题」/「为什么停在这」定位，不按下标
export function rangeTable(text)        // 号段表：首格 项、次格 值
```

⚠️ **必须取两份现存实现的【并集】，不是挑一份删一份** —— 实测两份**并不相同**：

| | `check-pointers.mjs:982` | `check-plan-in-progress.mjs:180` |
|---|---|---|
| 入参 | 整行，自己 trim | 已 trim，无条件剥首竖线 |
| 尾竖线 | `!t.endsWith('\\|')` —— 末尾转义竖线不被吃掉 | 无此判据 |
| 分隔行 | 只 trim | 先剥 `` ` `` `*`（容忍 `` `--- `` 那种写法） |
| 导出 | 私有（`:982`） | 已 export（`:180`） |

各自多出的判据**都在补自己的真实坑**（尾转义竖线、带装饰的分隔行）⇒ 丢任何一条都是回归。这就是「三处 `splitTableRow` 里最该合并的那次」。

### 7.2 命令与内建不变量

| 命令 | 行为 | 内建不变量 |
|---|---|---|
| `next` | 只打印下一个可用号，不写 | 取号**只从号段格读**，不数数据行、不从 git 历史推导 |
| `add` | 追加一行到「待拍板」节末 ＋ 同步号段两格 | 状态初值 `待拍板`；三位零填充；**号永不复用**；下一个号将超三位 ⇒ 停下报错，不自行扩位 |
| `set <号> <键>=<值>…` | 改一至多列（键值对形式，**不做位置参数** —— 列名是中文且将来可能增列，位置参数必然歧义） | 列名精确匹配；超该列上限 ⇒ **拒绝并指路 evidence/adr，不截断**；状态变更触发自动搬行（见 7.4） |

### 7.3 查询命令：只为「读出来的形态可信」，不为「方便读」

**不构成理由的那一条**：访问性不缺 —— 现在直接 `read` 文件就能读到任何一行。加查询命令的理由若是「方便」，那 `grep` 已经够了。

**真理由**：§2.1 与 REQ-193 的实测根因是「单元格里的竖线即使包在反引号里也会被 markdown 切开」。后果是**原始那一行看起来是 6 格，markdown 渲染出来只有 4 格** —— 人和 agent 读**原始行**都会读错字段，**且读错时没有任何信号**。这正是 §2.2 的两处上限能长期错着、列错位能长期存活的原因。

`check` 答「这份台账形状对不对」（**判决**），`show` 答「第 X 行说了什么」（**数据**）。**判决绿不等于数据读得对** —— 两者不是同一件事，不能互相顶替。

**`show` 是 `pool` 的特例**（`show REQ-194`），不重复实现。

**刻意不加的三类**：

| 想加的 | 不加的理由 |
|---|---|
| `find <子串>` / 筛选 / 排序 | `grep` 已能找号，找到后 `show` 就能读对。**再加一层筛选就是造第二套查询语言**，而 grep 的匹配能力不会比它差 |
| `stats`（分节计数） | `docs/REQ.md:22` 那条 grep 已够用；且行数按全局 `AGENTS.md` 三第 4 条本就不该进文档 |
| `render`（重排全表） | 会重写与本次无关的行，风险收益比不划算 |

**⚠️ 一条比命令清单本身更重要的架构要求**：**查询命令与写命令必须共用同一个解析函数，且该函数在「格数 ≠ 表头列数」时必须显式报「这行解析不可信」，而不是照样吐出一个看似完整的字段集。**

理由：门禁侧现有**两份独立实现**的 `splitTableRow`（`gates/repo/check-pointers.mjs:982` 与 `gates/repo/check-plan-in-progress.mjs:180`，两份并不相同 —— 见 §7.1 的并集要求）。脚本若再写第三份，同一个坑就是第三次。⇒ **两份现存实现与脚本解析器共用同一个 `shared/markdown-table.mjs`**（§7.0），**要么至少把「格数不符」这个信号透出来，而不是自己吞掉**。

**验收判据（可构造）**：造一行 5 格（表头 6 列）⇒ `show` **必须报错退出**；若它返回「字段 3 = …」就是错的 —— 那是「静默返回看似完整的数据」，是本方案要消灭的那类失败形态，不是它的实现。

### 7.4 `set 状态` 自动搬行；`move` 不接受状态参数

- **多列更新不是可选功能**：判断依据列上限**按状态分档**（在办 250 → 已完成 150），改状态那一刻这段文字必然要重写。只支持单列的接口会逼人分两次写，**中间态就是违规态**。
- **`set 状态=X` 与 `move` 是同一个操作**，不该是两条独立路径 —— 否则两个入口做同一件事，迟早有一个漏掉连带动作。实现上：`set` 遇跨节状态变更自动委派 `move`。
- **例外**：`待拍板 ⇄ 未开工` 是**同节内换**（R8 相容表里「待拍板」节同时容纳这两个状态），**不移动行**。其余四种跨节（未开工→在办→已完成/已作废）都自动搬。
- **`move` 不接受 `--状态`**：状态由目标节**唯一推导**。允许两个参数就制造了矛盾而脚本只能挑一个 —— 这类矛盾应在接口层就不存在。

⚠️ **归一不是等价替换：`isSeparatorRow` 的口径反转过一次（2026-10-05，用户裁决）**。过程与教训比结论本身更值得记：

- **归一时的判断（错的）**：直接采用 `shared/` 那份（先剥 `` ` `` 与 `*` 再测，即 §7.1「取并集」的方向），理由是「本仓 197 份 md 跑出 0 差异」。**那份语料 100% 是正例、一条带装饰的伪分隔行都没有** ⇒ 0 差异只证明「本仓现有文件判定不变」，对**负空间零证明力**。「我这份语料里没有反例」对「判据对反例是否正确」什么也没说。
- **实测反例（假绿）**：`` | `---` | `---` | … | `` 紧跟表头时，GFM **不认**它是 delimiter row ⇒ 整块渲染成普通段落、根本不是表格 ⇒ 表形状已破坏。宽口径下 `checkTableShape` **findings=0（绿）**。更隐蔽的一处：伪分隔行落在**表块中段**时，`locateRegistry` 把它当分隔行跳过 ⇒ **不进数据行集** ⇒ R 族「号形态错」对它**零判且零出声**（用 HEAD 版门禁对照：改动前 errors=1、改动后 errors=0）。
- **裁决与修法**：**收窄 `shared/` 那一层**（只 `trim()`，不剥装饰），门禁 4 处消费点直接用它。**不**在门禁侧加包装层 —— 收窄位置选错会漏掉 `locateRegistry` 内部那处（第一版就是这么漏的，`locateRegistry` 在 `shared/` 里，门禁的包装管不到它）。
- **为什么反转不算推翻 §7.1 裁决**：那条裁决给的理由是「漏判真分隔行的后果是把它当数据行读进去」，描述的是**变宽松**的坏处；而门禁侧改宽的坏处是**变宽松导致漏判形状**，方向相反。且该理由的原始受害者（PLAN 子步门禁）已于 2026-10-05 随载体退役 ⇒ **前提已消解**。
- **对写侧工具无代价**：实测 `tools/req-edit.mjs` 对真实台账 `docs/REQ.md` 的 4 个登记表块**零影响**（分隔行号与数据行集合逐字相同）；畸形输入下方向也安全 —— 伪分隔行被当**数据行**，走 `assertRowShape` 与列宽校验（响亮失败）而非静默跳过。
- **负向性质由夹具钉住**：`test/gates/check-pointers-ledger.test.js` 的「伪分隔行」3 条 case。实测改回宽口径**恰好 3 条转红**、窄口径 41 条全绿 ⇒ 钉子是真的钉住了。

⚠️ **两处形状转换不是逐字搬运，改回旧数会静默漏判**：`tableBlocks` 旧形状的 `rows` **含表头**、新形状不含，故 `checkTableShape` 的门槛从 `rows.length < 2` 改写为 `< 1`（「块内至少表头+分隔行」的等价表达）。照旧形状把 `< 1` 改回 `< 2`，会漏判「只有表头+分隔行」的**空节** —— 而空节是合法态，判 0 错，故那个错**不产生任何红灯**。已验证：空节判绿、非登记表零覆盖。

⚠️ **原第 1 条「三份漂移 A/B/C」已作废** —— 它是「解析层放哪」的子问题，而落位已定（§7.0：解析层进 `shared/`，是`gates` 与 `tools` 唯一共同的合法依赖）。且**两段式次序把漂移问题延后了**：段一期间本仓只有 `shared/` 一份解析，「三份」根本不存在。真正的漂移是段二之后的「模板副本 vs 各项目副本」，由待裁决 2 的版本锚点治理。

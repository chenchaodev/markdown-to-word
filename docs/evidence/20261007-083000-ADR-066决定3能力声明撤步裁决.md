# 2026-10-07 ADR-066 决定 3 能力声明撤步裁决

## 一、目标与结论

`ADR-066` 的**决定 3** 写的是：「每个交付面**声明**自己的能力集，『支持哪些格式』由声明派生，不再各写一份硬编码分支」（该 ADR 决定节第 3 条）。本次是它落地前的只读评审，结论是 **撤步，不做**：不引入交付面能力对象，不引入格式查表派生，也不新增守「声明 vs 分支」的门禁。

撤步的不是目标，是**形态**：ADR-066 背景四指出的缺口（能力差异靠函数体字面量）在今天**已经有了一份处置**，就是 `src/core/convert.ts:3-13` 那条手工维护的清单；而决定 3 设想的收益判据（「声明 vs 分支」可机械比对）经实测**不可达**。二者合起来 ⇒ 结构化声明在本仓拿不到它唯一值钱的那个属性。

## 二、三条理由

### 理由一：那份清单里的分支，3 处零或负收益

逐处性质判定见 §三。一句话：**5 处里只有 `src/cli/index.ts` 那处的差异真是「能力差异」，而它最不该套能力表**（理由二）。

### 理由二：真正符合能力差异的 2 处，套对象字面量是净负收益

- **`src/cli/index.ts:224`** —— `if (format === "pdf")` 两侧分别是 `convertPdfViaHost(job)`（走子进程重入 Electron）与本进程转换。**两侧的差别是「进程形态」，不是「支持哪些格式」**：pdf 面在这里之所以不同，是因为它必须离开当前进程去拿 `printToPDF` 宿主能力（`src/main/cli-pdf-host.ts:45,103` 复用 `src/main/converter/electron-side.ts:53` 的 `renderPdf`）。套一个 `cli.formats` 对象字面量，等于给一个**二元 `if`** 加一跳查表 —— 判据没变强，可读性变差。
- **`src/mcp/tools.ts:196`** —— `format: "docx"` 是**字面量参数，不是分支**。要让「支持哪些格式由声明派生」，就得写成 `cli.formats[0]`；而 `tsconfig.json:11` 的 `noUncheckedIndexedAccess` 之下，索引取值未必被推成 `"docx"`，为省一个字面量要多付一次窄化。**MCP 不支持 pdf 是产品决策**（台账「MCP 是否支持 pdf」那一行仍在待拍板），把一个待定布尔值提前固化成类型，反而把「日后支持了」变成一次改类型。

⇒ **能力差异是真的，但差异的轴不是「支持哪些格式」**。真正的轴在 §六。

### 理由三：「声明 vs 分支」不可机械比对

- 声明侧说的是**「支持哪些格式」**（一个格式名的集合）。
- 分支侧实际判的是**「哪些条件走 pdf 路」**（控制流归属：输入参数值、进程形态、扩展名映射、阶段粒度）。
- 两边**没有共同的可枚举词表**。分支归属是控制流属性，不是可提取的记号 —— 想把它抽成记号，先得把它改写成记号，那就是这次要做的事本身。**判据与被判定对象互相定义 ⇒ 恒真或恒红，没有第三态。**

## 三、5 处分支的逐处性质判定

清单来自 `src/core/convert.ts:3-13`（该注释自陈是**手工维护的索引**，并说明刻意不写可自动复算的 grep 指针）。

| 位置 | 判的是什么 | 换查表的收益 |
|---|---|---|
| `src/core/convert.ts:244` | 双管线分派：docx 走 remark → docx，pdf 走 markdown-it → HTML | 负。两套**不相交的渲染器**（`ADR-014` 定的方向），查表反而要求两侧签名同构 |
| `src/convert/run.ts:143` | 进度粒度差异：docx 只发 `render` | 负。`ADR-066` 的「不做的事」一节**自己写了**「本条不统一 docx 与 pdf 的阶段数量」，把它变成查表是把明写的取舍藏进数据结构 |
| `src/convert/run.ts:167` | 只有 pdf 侧才注入细粒度 `onStage` 回调 | 负。同样是阶段粒度，且它的正确形态由决定 1 的阶段联合一并解决 |
| `src/convert/paths.ts:82` | 扩展名映射：`docx` → `.docx`，其余 `.pdf` | 零收益。是映射不是能力判定，判据形态（文件存在 + 行号在范围内）不因换表而变强 |
| `src/cli/index.ts:224` | 进程形态：pdf 子进程重入 / docx 本进程 | 唯一真差异，但它是**二元 `if`**，套表是净负收益（见理由二） |

`src/mcp/tools.ts:196` 不在这份清单里 —— 它不是分支（理由二）。

## 四、对照基线：`src/core/convert.ts:3-13` 已有的那份清单

这次要落成的东西与它**是同一诉求的两种形态**，而 06c-2（`docs/PLAN.md` 的 #06 步）**并未承诺更强的判据**。它已经做到的事：

- 逐处列出 5 个点位并**给出排除理由**：`src/convert/run.ts:238` 判的是 `artifact.kind`（产物判别）不是 `format`，不是同一族判定（该注释 `:7-8` 记的就是这次踩过的坑：曾写「共 6 处」而括号内只列 5 项）。
- 把另外两类不算入的点也写明了（`cli/options.ts` 与 `renderer/wizard/book-wizard.ts` 的 `"both"` 属 `CliFormat` 映射）。
- **自陈「刻意不写可自动复算的 grep 指针」**（`:11-13`）并给出理由：唯一能稳定匹配这 5 处的模式也会命中注释自己那行散文，滤注释就得叠第二道正则，而叠错的代价是「指针算出来的数」本身不可信。

**该形态在本仓的唯一已知成本数据点**（`:7-8` 记录的「共 6 处」与实际 5 项之差）**很小，且不产生静默错误** —— 表现是括号内少列一项，人扫得出来。对照判据两种失效形态里更坏的那个（「静默绿」），它站得住。

## 五、唯一真收益点及其归因纠正

`src/renderer/convert/events/convert-actions.ts:74` 的 `if (info.stage === "print") cancelBtn.disabled = true;` 是本次唯一实打实的收益点（pdf 特有知识泄漏到 UI 层）。但：

- **它不属于决定 3**。动机归 `ADR-066` **背景二**（pdf 特有知识以 stage 字面量特判形式出现在转换事件层）＋ **后果节第 ① 条**（决定 1 的连带项漏了一张表）。决定 3 讲的是「交付面声明能力集」，与此无关。
- **正确形态是阶段属性表，不是交付面能力表**。理由是可中断性随**阶段**变、不随**交付面**变：`src/main/cli-pdf-host.ts:45,103` 复用 GUI 侧的 `renderPdf`，所以 **CLI 的 pdf 转换同样会发 `print` 阶段**；只是 CLI 没有取消按钮。⇒ 若按决定 3 的形态声明 `CLI.interruptible: false`，它描述的是一个**不存在的消费点** —— 这条声明既不为真，也不能被任何判据核对。

## 六、两份同类门禁为什么不构成同构先例

| 门禁 | 它比对的两侧 | 为何不构成先例 |
|---|---|---|
| `gates/repo/check-transform-dispatch.mjs:12-14,26-30` | 枚举点**文件集合**与扫描面；它的声明面（键名字典 `aiCleanup` / `obsidian`）是**有限词表** | 比的是文件集合、词表有限。格式判定**没有有限词表** —— 「哪些条件走 pdf 路」不是可枚举的键名 |
| `gates/repo/check-copy-sites.mjs:23-27` | 复制点白名单与实参里的仓库相对路径字面量，**双向逐一相等** | 成立是因为声明与被声明**在同一份代码里可双向枚举**。格式声明若放成能力对象，也只能单向枚举（声明里有的格式未必有分支） |

⇒ 两份门禁的共同前提是「两侧同源可枚举」。交付面能力声明与格式分支**不满足**这个前提。

## 七、对撤步有利的既成事实

`docs/PLAN.md` #06 步的退出条件一列写的是「阶段为穷尽判别联合，漏一个 kind 编译红；降级由 core 登记、交付面透传；两处 `ConvertContext` 改名完成」—— **该列不含能力声明**，撤步不动它一个字即成立。也就是说 #06 步的验收口径本来就与决定 3 无关，撤步不需要重写退出条件。

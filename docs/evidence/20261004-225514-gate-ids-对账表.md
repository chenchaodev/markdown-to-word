## `successorState` 是**能力承接度**，不是「文件在不在」

- `exists` —— 完全承接:该文件覆盖探针的全部能力
- `partial` —— 部分承接:该文件只覆盖一部分能力,缺口在 lost 字段里逐条写明
- `to-create` —— 无承接:P6 后该能力无人接手,successor 指向 S1 要新建的文件

⚠️ successorState 是**能力承接度**,不是「文件在不在」—— 把 partial 标成 exists 会把缺口藏起来(主会话第一版就犯了这个错,把 smoke 的机制缺口标成了 exists)。

## 起草过程中被实测推翻的三处（留档，防后人重犯）

1. **「build-fresh 的诊断含具体文件名」—— 假的。** 该门禁诊断**恒为**「构建产物过期(存在晚于 dist 的 src 改动),请先运行 npm run build」，不含文件名。这条是我**转述方案评审的未核实断言**，S1a 执行时实测发现。要真补需改 `evaluateFreshness` 返回具体路径（＝改 `shaped` 契约 ＋ `protocol.mjs` 归一），属接口变更，待裁决。
2. **「`registry.mjs` 只许改 `PROBE_CARRIER_SCRIPTS`」—— 这条约束站不住。** R3 的反向检查要求每个 carrier **必须被某道门禁的 `probes[]` 认领**，否则判 `probe-carrier-orphan`；只登记 carrier 实测得 2 条 orphan。S1a 因此在 `GATE_REGISTRY.fixtures` 与 `GATE_REGISTRY["build-fresh"]` 的 `probes[]` 各加一条认领项（各 5 行，附理由）。
3. **`blocksP6` 与 `successorState` 可以自相矛盾。** S1a 执行方翻了 `successorState`（`to-create`→`exists`）却没清 `blocksP6` ⇒ 「完全承接」与「阻塞删除」并存。已加自检：`*successorState==="exists" && blocksP6===true*` 判红。

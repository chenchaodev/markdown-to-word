## 二、诊断

> **这个项目已经完成"工程自洽"、尚未开始"市场验证"：它把全部不确定性都内部化成了 86 份 ADR + 142 份证据 + 58 步门禁，而对外的信号通道只有一条（GitHub Releases + 未签名安装包），这条通道 2.5 个月只产生约 30 次下载、1 star、0 issue —— 于是每一条"已完成"都在陈述作者自己的满意，而不是一个用户的满意。**

失衡在三处，不是"做得不够多"，而是**投入方向与瓶颈错位**：

1. **验证投在了产物上，没投在需求上** —— 58 步门禁、覆盖率阈值、167 个测试段验证的是"这个 docx 生成器是否正确"。而仓里**早有一份被写好、从未执行**的需求侧验证规程（`20260808-103100-易用性调研.md` 第 84-93 行）：全仓检索无任何执行记录。**外部验证通道不存在**，不是弱，是零。
2. **加法与减法同时在扩张** —— 10 月 src 只占 11.9% 改动行，同期用户可见面在**增**（4.0→4.9 共 56 条 CHANGELOG 条目）；界面面同时在**增**（42 个抽屉控件、6 组、七步向导、5 预设），**没有一处做过"砍掉什么"的决策**。
3. **需求侧的"待办"是决策债务，不是需求信号** —— 待拍板中 5 行是作者 2026-08 自己否决、2026-09-29 又恢复的；唯一基于真实需求缺口的 REQ-005，取证结论是"有需求出处，但无用户呼声…当前无任何用户侧记录"。

补足一句：**过去 2.5 个月的实际产出曲线是"发版曲线"（约 60 个 release，其中三版明写"无用户可感知变化"），不是"使用曲线"。**

## 三、五条互斥路径

### A · 分发与信任优先（把唯一存在的东西变得"敢装、找得到"）
- **解决的假设**：产物已够格，瓶颈是安装摩擦（SmartScreen「未知发布者」；杀软误报）与零可发现性。
- **付出**：winget / scoop manifest（需稳定 release 通道）；落地页 + 真实演示视频；**代码签名是持续付费且需续期**，且要推翻已终审的 REQ-050（`docs/REQ.md`「代码签名」行：2026-09-29 用户裁决转为永久不做）——这是花钱买，不是修缺陷。
- **失败模式**：安装摩擦不是约束。下载涨了、star/issue 仍为 0——因为**没有拉力**，装完不回来。
- **放弃判据**：winget + scoop + 落地页上线后 30 天，README 下载徽章累计 **< 50**（即新增 < 20 次）→ 立即放弃。**除非已有企业/内部分发渠道强制要求签名，否则不买证书。**
- → 台账 **REQ-272**（重看条件：REQ-265 跑出信号后；或 30 天内外部安装 ≥50 则提前）

### B · 执行仓内已写好的真人可用性验证（+ 需求侧探针）
- **解决的假设**：产品可能"作者能用、别人不能用"；且作者**无法自己看见**一个非作者能否在无协助下完成"把这份 md 变成能发给别人的 Word"。
- **付出**：5 位用户 × 3 任务（SUS + 任务完成率 + 点击数），中文 Markdown / 排版社区招募，约 1 周作者时间 + 极小激励。**成本最低、置信度最高。**
- **失败模式**：被试全是技术型自选样本；产品在他们手里全过，但目标人群（非开发者学生 / 办公）在别处失败——验证了错误的人群。
- **放弃判据**：若 **≥3/5 用户**完不成规范任务、或**说不出它比 Pandoc / Typora 好在哪**（一句话说不出来）⇒ 这是**产品表达 / 默认流失败**，不是功能不足 ⇒ 禁止加功能，转 C / D。若 5 人全过且 ≥3 人提到同一件事 ⇒ **那件事成为未来 90 天唯一的路线图条目**。
- → 台账 **REQ-265**（需求获取与可用性实测）· **REQ-266**（真实需求下的优先级取舍）

### C · 把 MCP / CLI 当成产品本体（不再以"桌面应用"为形态）
- **解决的假设**：2026 年"Markdown → 真 Word + 中文排版可控"的**增量需求由 AI 对话流产生**（产品自己已隐含此假设：剪贴板直转、MCP 服务端）。MCP 生态自带发现机制，绕开 SmartScreen。
- **付出**：现在只有"源码检出 `node dist/mcp/index.js`"与"装了应用 + `M2W_ENTRY`"两种形态，文档自陈"不同客户端的配置写法都不一样…没有统一写法" ⇒ 需一条命令的安装形态（指向 REQ-163 库模式，但当前打包面为零）；需一段"agent → md → docx → 回读"的真实演示（readback 已具备）。
- **失败模式**：MCP 消费方是技术人群，而技术人群已有 pandoc / docx.js 等成熟方案；**文档排版类工具在 agent 工具位里是很窄的品类**。另外 npm 发布还牵扯 GPL-3.0 下的包身份与命名占用。
- **放弃判据**：登记到 ≥2 个 MCP 发现渠道后 30 天，**跨 ≥5 个不同安装点的外部调用 < 30 次** ⇒ 判定"AI 是渠道"假设不成立，停掉 npm 包装投入。
- → 台账 **REQ-273**（MCP 通道拉一把）· 库模式本体见 **REQ-163**

### D · 收窄成一个滩头（明确做减法）
- **解决的假设**：面太宽（42 控件 + 6 组 + 七步向导 + 5 预设 + 双管线 + 批量 / 合并 / 剪贴板 / CLI / MCP / 回读）导致 30 秒内无法被理解；README 186 行、官网是一张功能清单，没人能说出它是干什么的。
- **付出**：删掉数月工作成果（单人维护者内部摩擦最大）；需重写 README / 官网 / 向导。
- **失败模式**：**在没有用户数据之前收窄 = 猜**。砍掉的可能正是让第 0 位用户愿意试的那部分；且减法不创造需求。
- **放弃判据**：收窄版落地 30 天后，下载 / star / issue 三者**均无变化** ⇒ 宽度假设错误 → 回滚（代码保留，只改叙述与默认预设）。
- → 台账 **REQ-274**（收窄默认流与首屏叙述，**只改叙述与默认预设、不删功能**）

### E · 维持现状（继续加功能 / 保持发版节奏）—— **反面选项**
- **反面理由**：这是仓内流程已经在走的默认路径，不需要任何新决策，因而**最容易被默认选中**；但它自己的领先指标是平的：约 60 个 release、约 30 次总下载、1 star、0 issue、0 topics。它是在选一个**指示器已经显示为负的策略**。而且它每次都在放大 42 控件这个采纳障碍，同时**不产生任何一个新数据点**。待拍板"恢复自己旧否决"的模式就是这条路径的典型产物：**决策债务增长，需求信号为零**。

## 四、排序与理由

按"单位投入的用户价值 × 可达性 × 判断把握"：

| 序 | 路径 | 理由 |
|---|---|---|
| **1** | **B · 真人验证 + 需求探针** | 唯一能产出**新数据类型**的动作（作者之外的用户行为），成本最低（规程已在仓内写好），可达性高。**它是 C / D / A 的前置**：没有它，其余三条都在猜。 |
| **2** | **C · MCP / CLI 本体化** | 上行最不对称（发现机制自带、绕过 SmartScreen、交付面今天就在仓内），且是唯一一条不与"桌面应用"定位冲突的增长路径。置信度中等（AI 是否是本工具的渠道＝假设）。 |
| **3** | **D · 收窄滩头** | 价值中等偏上（"讲不清是干什么的"是真实缺陷，且零成本），但**必须在 B 之后**——否则是猜；且减法对单人维护者的心理成本最高。 |
| **4** | **A · 分发与信任** | 摩擦确实存在，但被 30 次下载 / 60 个 release 的量级强烈提示：**约束在需求侧不在安装侧**。且"签名"部分是负 ROI（ADR-013 自己论证过）。应在 B / C 出信号后再启。 |

**默认不该选的是 E。** 判别式很简单：E 是唯一一个**不需要任何新决策**的选项，因此在单人项目里它有最大的默认引力；而它同时是唯一一个**已被自身领先指标证伪**的选项。

## 六、反证与推翻信号

**已验证事实 vs 推测的分界**：第一节的实测值、以及外部竞品数字均为实测；"品类需求弱""AI 是渠道"为**假设，未经一手用户验证**。

**可能错在哪**

1. **"没人用"可能是计量问题** —— 下载徽章按 release 资产计数，用户可能把 portable zip 转发出去。若真实使用量是徽章的 5–10 倍，诊断从"无 traction"变成"**无反馈回路**"——而这会让 B 更紧急，**推荐结论不变**。
2. **"面太宽伤害采纳"本身来自作者 2026-08 的调研，而那份同样没被真人验证过** —— 同一个闭环里的结论，故 B1 里专门安排了"5 人里几人说不清差异化"这个直接问题；若 5 个人都能一句话说清，宽度就不是瓶颈，D 应降级。
3. **可能高估 MCP / CLI 的上行** —— 文档排版类工具在 agent 工具位里是窄品类，agent 很可能直接调 pandoc 或 docx.js。**但 B3 成本极低（登记 + 录屏），所以它作为探针而非赌注**。
4. **最大的反证可能不是策略层，而是目标层** —— 作者也许要的是工程密度极高的作品集 / agent 驱动开发的实验场。86 份 ADR + 0 用户侧投入，与"有意的工程展览"同样自洽。若目标确为作品集，则全部增长选项皆错，正确解是 C2（打磨 + 发布 + 如实讲清）。
5. **签名按"不买"给建议，但存在反向理由** —— 若有企业 / 内网 / 受管终端的强制签名要求，签名是准入条件而非增长手段，此时应把 A 提到第 2 位。这属作者身份信息，不在本次评审的判断范围内。

**应推翻上述全部结论的可观察信号（出现即推翻，不再微调）**

- 30 天内**外部安装 ≥ 50**（明显偏离当前约 0.5 次/release 的基线）→ 需求存在，之前只是没被看见 → 直接转 A 并认真考虑签名。
- 出现**任一来自外部用户的、内容具体且反复出现的 issue** → 需求侧信号成立 → 立刻把功能工作对准该 issue，探针降级为常规运营。
- B1 中 **≥4/5 用户能一句话说清差异化且都完成规范任务** → "面太宽 / 表达不清"假设被证伪 → **D 出局**，回到"按需求加功能"，B2 升级为主线。
- MCP 在 30 天内 **≥20 个不同安装点** → "AI 是渠道"假设成立 → C 升为第一路径，库模式与 CLI 包装立刻开工。
- 连续 90 天周表显示下载 / star / issue **全部零增长且外部调用零** → 诚实结论是"该品类当前无需求"，停止一切增长投入，定位永久改为个人工具 + 作品集，并**如实对外说明**。

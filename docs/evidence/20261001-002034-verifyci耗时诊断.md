### 订正:15.4s ≈ `maxWaitMs` 上限,即「每场景都不收敛」(2026-10-01 补)

独立评审时发现一个本文件漏看的算术关系,复核后成立:

- 每场景恰好 1 次 `measureStable`(`scripts/geometry/worker.mjs:175-180`),其超时上限 `maxWaitMs` 默认 **15000ms**(`driver.mjs:80`)。
- 验算:21 × 15.0s = **315.0s**,加每场景 `settleMs` 0.25s × 21 = 5.2s,合计 **320.2s**,与实测场景跨度 307.2s 差 4%。
- 即 **15.4s/场景 ≈ 15.0s 超时上限 + 0.4s 其余**。反向可推:跑满 15s 需约 100 轮 150ms 轮询。

**因此本节开头「sleep 地板只有 20s、调 sleep 这条路不存在」这句结论方向对、但归因错** —— 不是「工作量一致所以均匀」,而是**每个场景都把收敛等待跑到了上限**。零抖动来自超时上限,不是工作量。

`measureStable`(`driver.mjs:186-201`)的收敛判据是 `JSON.stringify(cur) === JSON.stringify(prev)` 且稳定窗满足;超时则返回最后一次采样。头注明写「残留不稳定会由判定层的恒定/越界断言暴露」(`driver.mjs:184`)——**即超时是设计上允许的路径,但设计意图是「偶发超时」,不是「21 次全部超时」**。

两种机制对应完全不同的修法,且**当前无法区分**:

| 机制 | 判据特征 | 修法 | 可能收益 | 覆盖损失 |
|---|---|---|---|---|
| (a) 收敛条件永不满足(某字段在相邻 poll 间抖动,如分数像素下摆动) | 跑满上限,采样仍在变 | 修判据或容差 | 可能省 250s+ | 零 |
| (b) 单次 `executeJavaScript` 本身很贵(40 抽屉控件 + 全部节点) | 也跑满上限但采样其实已稳 | 按场景裁剪度量脚本 / 截图 env 开关 | 未知 | 零 |

区分 (a)/(b) 只能靠打点 —— 这正是 REQ-112 的内容。**在此之前,「优化 geometry」的任何提案都无法验证收益。**

**一条方法论约束**:打点数据必须来自 CI,不能用本机跑分代替。REQ-055 已实测本机 16 核与 CI 4 vCPU 的耗时不可比(膨胀机制是 Electron 进程启停争抢,与核数无关)。

**执行形态**:每档 1 个 Electron 进程 + 1 个隐藏窗口跑完 21 场景(`scripts/geometry/worker.mjs:88-101`);档位默认仅 `native` 单档,编排层逐档串行(`scripts/geometry/orchestrator.mjs:189-218`)。故 323.5s 全在单进程单窗口的 21 场景循环内,不含多档叠加。

**判据性质**:全链**无像素比对**,判据是结构不变式(视口容纳/溢出/恒定组/控件存在·组归属·组序·裁切)+ CSS 令牌计算色恒等(`scripts/check-geometry.mjs:5-31`)。跨 DPI 的 rect diff 只在**同一次运行内**各档互比,基线只在内存,头注明写「不落任何跨运行基线文件」(`check-geometry.mjs:62-69`)。**17 张截图只写盘供人看,不参与判定。**

## 十一、打点实测结果(REQ-112,2026-10-01 补;本节为后续追加,上文不改)

上面第二节的推断**已由实测取代**,此处记最终结论。

### 落地的改动

- `scripts/geometry/driver.mjs`:`measureStable` 返回值由裸采样改为 `{ value, timing }`,`timing` 含 `polls` / `elapsedMs` / `converged` / `minStableMs` / `maxWaitMs`。把「是否收敛」显式带出,是因为原先只能靠「elapsed ≈ maxWaitMs」反推。
- `scripts/geometry/worker.mjs`:逐场景累计 `timing`(视口 / 驱动 / 落定 / 截图 / 合计)挂进 `sample.timing`,经编排层自动进 `report.json`;运行时输出每场景一行 + 循环后一行汇总。
- 该函数全仓仅一个调用点(`worker.mjs`),`test/` 零命中,无测试依赖其返回契约;`report.json` 键集合无断言 ⇒ **0 行门禁因加字段判红**。

### 实测(本机 native 档,dpr=2,21 场景)

```
[geo:timing] 21 场景合计 325030ms —— 落定 316682ms(21/21 场景跑满 15000ms 上限)
              / 视口 101ms / 驱动 155ms / 截图 2726ms
```

| 项 | 数值 |
|---|---|
| 场景合计 | 325030ms |
| **落定(`measureStable`)** | **316682ms = 97.4%** |
| 视口落定 | 101ms |
| 交互驱动 | 155ms |
| 截图(17 次 `capturePage` + 写盘) | 2726ms |
| **收敛场景数** | **0 / 21** |
| 每场景轮次 | 96–97 轮 |
| 单轮均耗 | 156.0ms(= `wait(150)` 轮询步长 + 约 6ms 实际 `executeJavaScript`) |

### 结论(取代上文第二节的归因)

1. **323.5s 的成因是轮询等待,不是采样成本。** 落定一项占 97.4%;每场景 96 次 `wait(150)` = 14.4s,而真正的 `executeJavaScript` + 解析每轮仅约 6ms。**上文第二节「余下 300s 落在真实采样成本」已被实测否定**,该处是残差归因。
2. **「收敛条件永不满足」确证,机制 (a) 成立、机制 (b) 排除。** 21/21 场景 `converged: false`,全部跑满 `maxWaitMs`。若采样本身收敛,`minStableMs` 为 250ms / 1500ms,2–10 轮内即应返回;跑满 96+ 轮只可能是相邻两轮采样逐字节不等。
3. **本机与 CI 的差异只有一个且不影响该结论**:本机 dpr=2、CI dpr=1,但**两侧都跑满 15000ms 上限**,故振荡与缩放档位无关。
4. **杠杆量级因此改变**:若收敛问题修好,该门禁有望从 323.5s 降到数十秒量级 —— **远大于「挪独立 job」的净收益 215s**,且不动门禁链、不动 ADR、不动 required checks。这是「先打点再决定」这条排序的直接回报。
5. **本机数不可当 CI 耗时预测**:本机 16 核 vs runner 4 vCPU 不可比(REQ-055)。但「是否收敛」是机制属性、跨环境一致,故机制结论可直接采信,耗时量级不可。

### 仍未定位的一点

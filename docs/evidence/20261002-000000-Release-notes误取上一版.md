# Release notes 抽取误取上一版（REQ-145 取证）

## 现象

`v3.16.2` 发布后，GitHub Release 页面的 notes 显示：

```
### 修复

- 修复了一些问题。
```

这是 **`v3.16.1` 的条目**。3.16.2 没有任何修复 —— 那 11 个提交全是目录重组、门禁细节、覆盖率产物落点（见 `docs/evidence/20260930-204956-仓库自描述与三层划分.md` 同批的 ADR-049~052）。页面上的这句话是关于本版的**错误陈述**，比不写更糟：读者会以为这一版修了东西。

## 根因

`.github/workflows/release.yml:180`（修改前）：

```js
const m = md.match(/## \[[^\]]+\] - [^\n]+\n([\s\S]*?)(?=\n## \[|$)/);
```

判据是「取**第一个**带日期的版本头」。而 `## [待发版]` 后面**没有 ` - 日期`**，整行匹配不上 ⇒ 正则落到下一个 `## [x.y.z] - 日期`，也就是**上一版**。

原注释承诺的兜底（第 169 行）：

> 提取为空(未写 CHANGELOG)时回退 --generate-notes(commit 列表)

在有过上一版之后**永不触发** —— 抽取结果永远非空，只是取错了节。

## 为什么这次踩到

「本次发布无用户可感知变化 → `[待发版]` 留空」是 CHANGELOG 逃生阀明确允许的用法（`PUBLISH-GUIDE.md` 发布前检查 ① 的「逃生阀」条：*不要为了发版硬凑一条*）。也就是说**每一次走逃生阀的发版都会命中这个缺陷**，而逃生阀的使用频率不低（内部重构类版本天然如此）。

本次的具体成因是顺序：tag 先推、`[3.16.2]` 条目后补。tag 触发 workflow，checkout 的是 tag 指向的 commit，那个 commit 上 `[待发版]` 是空的。但**顺序只是这次的条件，缺陷本身与顺序无关** —— 只要本次版本的条目不在 tag 的树里，就会取到上一版。

## 修法

判据从「第一个版本节」改为「**按 `package.json` 版本号定位**」。于是「notes 与本次发布的版本对应」成为结构保证，不再依赖「第一个版本头恰好是本次」这种巧合。

三层落地：

| 层 | 载体 | 答的问题 |
| --- | --- | --- |
| 实现 | `gates/repo/release-notes.mjs` 的 `extractNotes(md, version)` | 抽得对不对 |
| 行为 | `gates/repo/release-notes.selftest.mjs`（9 条断言，含 4 条负向） | 那个实现在各种输入下会不会取错 |
| 静态面 | `gates/repo/check-release-notes.mjs` + `release-notes.mutation-test.mjs` | 发布时会不会用错实现 / 那两条判据会不会自己恒绿 |

`workflow` 侧同步改两处：抽取改调模块并传 `pkg.version`；空 notes 从「静默回退 `--generate-notes`」改为 **`exit 1` 响亮失败** —— 抽不到条目是发版流程漏步，不是「本次无变更」（后者仍应写一行说明，否则 Release 页面是空的）。

## 实施中撞到的两个判据缺陷（都已修，记在此以免复发）

**其一：`problems` 写成模块级数组。** `checkReleaseNotesContract()` 每次调用都往同一个数组 push、从不重置 ⇒ 第二次调用返回上次的诊断一并（**诊断累积**）。链内被调两次就假红。变异脚本第一次跑就撞出这个形态。已改为函数内局部数组，并在注释里写明原因。

**其二：判据②写成两个独立 `if` 导致整块删除时双双失效。** 原写法一个 `if` 查 guard 存在、另一个查 `exit 1` 出现过；当整个 `if [ -z "$NOTES" ] … fi` 块被删掉时，两个 `if` 都落空，判据**报绿** —— 即「守卫没了反而绿」。已改为单一事实：判红条件与 `exit` 必须落在同一个 `if` 块内（正则 `if [ -z "$NOTES" ] … exit 1 … fi`）。

两条都属于「判据本身可能恒绿」这一类，而它们只有在**变异测试**（逐条改坏被守护对象、证明判据真会红）下才暴露 —— 正向跑一次绿什么也证明不了。

## 一个通用教训（已并入 LESSONS.md）

写「静态面判据」时，**每个判据都要有对应的变异**（改坏被守护对象 → 证明这条判据会红）。只跑正向的话，一个「在目标被整块删除时失效」的判据会一直绿着 —— 这与 `LESSONS.md` 里「断言恒真常源于夹具初值自带期望态；须补一条反向断言才真能红」同型，只是这次的载体是 workflow 文本而不是夹具。

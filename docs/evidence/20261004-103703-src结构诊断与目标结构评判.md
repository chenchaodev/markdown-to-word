## 2. `core` 内部零约束 = 「没人管」还是「管不了」？

### 裁决：是「没人管」，不是「管不了」。** 而且不需要给 `core` 加 9 条层向规则 —— 只需要 2 条。

### 依据

我实测了 `core/` 9 个子目录的**运行期**目录级依赖图（剥注释、剔除 type-only import、Tarjan 求 SCC）：

```
唯一 SCC>1:  core/markdown ⇄ core/pipeline          ← 2 条反向边
其余全部无环：
  core/cancel.ts → resource-limits.ts
  core/convert.ts → cancel, docx, pdf, pipeline, settings
  core/docx       → cancel, i18n.ts, image, markdown, resource-limits, settings, style, util
  core/i18n.ts    → i18n/(字典)
  core/pdf        → cancel, i18n.ts, image, markdown, resource-limits, settings, style, util
  core/pipeline   → i18n.ts, image, markdown, util
  core/image, core/util, core/style, core/settings : 叶子（零出边）
```

**这是关键证据：`core/` 内部的依赖图几乎是一片 DAG。**「管不了」的前提是像 `renderer/` 那样实测出 5 对双向 —— `core/` 没有。`docx` 与 `pdf` 之间只有1 条边且是 type-only（`pdf/template.ts` → `docx/chrome.js` 的 `HeaderLogoData`）。

唯一的环是 `markdown ⇄ pipeline`，且它的成因是**一个文件放错了目录**，不是架构性的纠缠。`markdown/ai-cleanup.ts` 需要 `parseMarkdown` —— 这说明它属于「解析之后的变换」，而 `parse.ts` 属于「解析」。两者在概念上是不同阶段，但被放进了两个互为上下游的目录，且这个上下游是**反的**（变换依赖解析器，解析器不依赖变换）。

### 该不该加判据：加，但只加 2 条，且都指向同一个动作

| 规则 id | scope | forbid | 判红条件 | 现状 |
|---|---|---|---|---|
| **`core-markdown-no-pipeline`** | `core-markdown` | `layer:../pipeline/`（相对说明符前缀） | `core/markdown/**` 出现 `../pipeline/` 说明符 | **当前即红**（`ai-cleanup.ts` 2 处）→ 这就是它的价值：它把「ai-cleanup 放错了」变成机械可判的事实，而不是靠人推理 |
| **`core-image-no-markdown`** | `core-image` | `layer:../markdown/` | `core/image/**` 出现 `../markdown/` 说明符 | 当前绿。守的是「图片不是一个 markdown 特性」这条已经成立的不变量 |

**只加这两条的理由**：它们不是「分层」，是**两条边界的存在性判定**。给 `core/` 加「docx 不得依赖 markdown」这类方向规则会立刻误报（`docx → markdown` 有 22 条运行期边，且这是设计意图：docx handler 消费 markdown 原语）。给 `core/` 加 9 条方向规则就是把 `renderer/` 的错误答案套到 `core/` 上。

**「不要给 core 加层向规则」的理由（这是我要明说的判断）**：`core/` 的真实结构不是9 个平层，而是 **2 个汇聚点（`docx` / `pdf`）指向 7 个被复用原语的叶子目录**。原语之间的依赖（`markdown` ↔ `pipeline`）是**实现细节**，不是架构决策。为它写方向规则等于把实现细节升格成架构。

## 5. AI 落笔判据

### `src/` 不需要 1:1 映射，但需要「一职责一文件 +名字即职责」

`test/` 能用 1:1 是因为「一个被测主体 ↔ 一个段文件」是天然对应。`src/` 没有这种天然对应（一个文件常被 43 个文件 import），所以判据形态不同：**目录给类别，文件名给主体，且同名只允许一份。**

**agent 接到「给 X 加功能 / 改 Y」时的定位程序（不读文档）**

```
1. X属于哪一层？ 按「改的是什么」判，不按「文件在哪」判：
    纯转换逻辑 → core/ 装配与 IO → convert/
     Electron 宿主 → main/  浏览器界面 → renderer/
     进程外交付面 → cli/ 或 mcp/
   这 6 条与 SRC_TOP_LAYERS 逐字对应，且 SRC_TOP_LAYERS 是 allow-list（新建顶层默认非法）

2. core/ 内部按「改的是什么」二选一（这是唯一需要判断的地方，判据是 3 个问句）：
     改「markdown 语法原语」        → core/markdown/     （slug/cross-ref/comment/html-whitelist/table-width/obsidian/...）
     改「解析与编排」                → core/pipeline/     （parse/frontmatter/precheck/merge/ai-cleanup）
     改「图片」                      → core/image/        （resolver/sniff/size/path-policy/request-guard/index）
     改「设置」                      → core/settings/     （defaults/schema/typography/presets/render-options）
     改「渲染 docx / pdf」           → core/docx/ 或 core/pdf/
     改「文案」                      → core/i18n/         （字典在 zh/en/ja，警告构造器在 warning.ts，DOM 在 dom.ts）
   判据可机器验：core-markdown-no-pipeline / core-image-no-markdown / core-pipeline-no-render 三条
   规则把这三个问句的答案边界钉死 —— 「我该放 markdown 还是 pipeline」不再是判断题，
   因为 markdown → pipeline 被判红，pipeline → docx/pdf 也被判红。

3. 文件名 =主体名。同名只允许一份（src-no-duplicate-basename），
   所以「有没有一个已经叫 X 的文件」是可 grep 的确定事实，不是回忆。

4. 需要新建符号时：先 grep 同名 basename（9 组现存重名里5 组是有意的对位实现，
   4 组是历史撞名 —— src-no-duplicate-basename 的白名单逐条列出后者）。
```

**关键设计取舍：不给 `src/` 建「模块 → 文件」映射表。** 理由是 `core/convert.ts` 有 43 个消费文件、`core/i18n.ts` 有 60 个 —— 一个真正的枢纽，任何以它为键的映射都会退化成「枢纽的清单」，而枢纽不该有清单。`src/` 侧的对应工具应该是**反向索引**：`npm run owners -- <模块路径>` 打印「谁 import 了它 + 它属于哪棵树 + 它的镜像测试段路径（ADR-062 的 L1 派生）」。约 40 行，与 ADR-062 的 `npm run where -- <模块>` 共用同一个 import 图扫描器。

**让「追加进已有文件」阻力最小**：这在 `src/` 侧的形态与 `test/` 不同 —— 一个 agent改 `core/pdf/rules/image.ts` 时，应该**追加 case 到该文件**，而不是新建 `image-foo.ts`。机制不是门禁（无法机器判「这个 case 该放哪」），而是**目录准入判据的排他性**：`core/pdf/rules/` 只收 markdown-it 规则，一个新文件若不是规则，`core-pipeline-no-render` 之外没有规则会拦它 —— 所以要给 `core/pdf/rules/` 一条 `pdf-rules-are-rules` 判据：**该目录内每个文件必须被 `pdf/render.ts` 或 `pdf/template.ts` 的某个 visitor 表登记**（从磁盘派生 visitor名单，未被登记的文件即孤儿 →判红）。这条判据同时挡掉「新建一个没人调用的新文件」。

| 规则 | 从 | 到 | 理由 |
|---|---|---|---|
| `faces-no-outside-src` | `prefix:../../` | **`layer:..`** | 我实测了 `resolveLayer` 的行为（`path.posix.join` + `split('/')[0]`）：`cli/sub/a.ts` import `../../core/x.js` → join 得 `core/x.js` → 首段 `core` → **不报**（正确，这是合法边）；`cli/sub/a.ts` import `../../../test/x.js` → `../test/x.js` → 首段 `..` → **报**（正确）。即 `layer:..` 与深度无关，`prefix:../../` 会在 `cli/` 长出子目录后把合法的 `../../core/x.js` 误报 |

## 7. 与 ADR-062 的耦合 —— **这是本次最关键的一项**

### 会不会推翻那套镜像？**不会，但会改它的派生输入。**

ADR-062 的不变式是 `test/<R>/<rest>.test.js ⟺ <R>/<rest>.<ext>`，其中 `R` = **磁盘派生的镜像源集合**。§3 的改动全部发生在 `src/` 的**内部路径**上（`core/markdown/ai-cleanup.ts` → `core/pipeline/ai-cleanup.ts` 等），**`src/` 的六个顶层子目录一个都不增不减**。

所以：
- **L1/L4/L7/L9（镜像完整性、位置正确、顶层集合、下限）不受影响** —— 派生源集合不变
- **受影响的只有一件事**：某个 src 模块搬家后，它的镜像段路径跟着变。例：`core/markdown/image-size.ts` → `core/image/size.ts`，则镜像段从 `test/core/markdown/image-size.test.js` 变成 `test/core/image/size.test.js`。**这不是「推翻镜像」，是镜像按定义该有的行为** —— 位置即身份，源文件换位置，身份跟着换
- **L1 豁免表（81 项基线）要按新路径重建**：`--write-baseline` 跑一次。豁免表以模块路径为键，路径变了键就变

### 顺序：**src先行，ADR-062 后跟，且 src必须在 ADR-062 的 P1 之前完成**

明确答案：

```
① 本方案（src 结构）           ← 先做完，含它自己的门禁
② ADR-062 P1（check-test-layout 只报告模式）  ← 派生 src 的最终形状
③ ADR-062 P2–P5（搬文件 + 豁免表 ratchet）
④ ADR-062 P6（门禁元框架退役）
```

**为什么是这个顺序（这是我要论证的关键点）**

ADR-062 的 L1 是**ratchet**（豁免表「只许减不许增」），L3 是「豁免的模块已有测试文件 → 判红」。ratchet 的正确用法是：**先让 src稳定，再一次性生成基线，之后只许减**。

如果反序（先做 ADR-062 的基线，再改 src）：
- 81 项豁免表的键是**当前**的 src 路径。src 一搬，L3 判「豁免的模块已不存在」—— 但 L3 现在的措辞是「已有测试文件 → 判红」，「模块已不存在」这一形态未被覆盖，会产生一类**语义模糊的红**（是删豁免？还是路径变了？）
- 每次 src 搬文件都要手改豁免表，而豁免表改动会出现在 diff 里被review —— **在一个仍在结构性变动的时期，这制造了大量无信息量的 diff**

正序的代价是：ADR-062 的 P1 拿到的 src 已经是终态，基线一次生成即准确。

**唯一的反向依赖需要点出**：`src-file-header`、`src-no-duplicate-basename` 这两条新门禁**必须在 src 搬文件之前就位**（先判红 → 再改 → 转绿）。这与 ADR-062 自己的「先建判据不搬文件」是同一个模式，且 ADR-062 已把它写成 P1。**所以本方案自带同构的两阶段：P0 建判据（只报告）→ P1 搬文件（转判红）**，与 ADR-062 完全对齐。

## 9. 风险与代价

### 会失去什么

| 失去 | 严重度 | 补偿 |
|---|---|---|
| **`core-markdown-no-pipeline` 转绿前的判红期**（即「ai-cleanup 在 markdown 里」这个状态被门禁持续报红） | 中 | 这是**故意的**：先判红 → 搬文件 → 转绿。若要避免中间态红，可先搬文件再上判据，但那样就失去了「判据先立」的纪律。**推荐承受这个中间态**，它的 diff 就是搬文件的理由 |
| **`core/util/` 这个名字**（约 40 处 import 路径引用） | 低 | 改名是机械的。且新名字让准入判据可写 |
| **`core/style/colors.ts` 作为「双管线共享色」这个显式声明** | 低 | 并入 `theme.ts` 后，「双管线共享什么色」不再由目录名表达，而是由 `WATERMARK_*` 这两个常量的消费点（`docx/chrome` + `pdf/template`，实测各 1 处）表达。**可 grep，可验证** |
| **9 组重名 basename 中的 5 组有意对位**（`render`·`mermaid`·`table`·`index`·`about`） | 无 | 进 `src-no-duplicate-basename` 白名单，逐条写明为什么 |

### 最容易静默出错的三处

1. **🔴 `i18n` 拆分（201 → 4 文件，60 个消费方）**
失效形态：`t()` 的**回退链语义**在拆分中被改坏。实测回退链是「当前语言 → en → key」，`current` 是 `core/i18n.ts:146` 的模块级 `let`。若 `current` 落到 `dom.ts` 里，`setLanguage` 与 `applyStaticTexts` 会读不同的状态 —— **且测试全绿**（`test/core/i18n-registry.test.js` 测的是注册表形状，不是跨模块的状态一致性）。
   **对策**：① `current` 必须留在 `t.ts`，`dom.ts` **只 import 不导出**它；② 搬完后立刻跑 `test/renderer/i18n.test.js` + `test/core/i18n-registry.test.js` + `test/renderer/settings-bindings-app` 相关段；③ 加一条门禁：`core/i18n/dom.ts` 不得 `export` 任何 `let`/可变绑定（文本判据，`export let` 即红）

2. **🔴 `main/ipc/types.ts` 删除 + `renderer/state/state.ts` 缩（两个 type re-export 的删除）**
   失效形态：type-only import 在**编译期**才有意义。漏改一处 import 路径 ⇒ tsc 立即红（这是**安全的**）。但更隐蔽的是：若有人把某条 `import type` 改成值 import（例如为了拿 `t()` 而 import整个 i18n 模块），就会把 43 个消费方的依赖面静默扩大。**不会红**，因为方向合法。
   **对策**：`core-no-duplicate-export` —— `core/ipc-contract.ts` 声明的每个 type 不得在 `src/` 内被第二个文件 `export type` 转出（白名单：`main/ipc/types.ts` 待删后为空）。这是 ADR-062 的 `test/gates/contract-single-source.test.js:184` 已经有一份清单的形态，把它升格为 `src/` 侧的门禁

3. **🟠 `main/converter/index.ts` 删 7 个跨层转出（6 个消费文件）**
   失效形态：**漏改一个消费方 ⇒ 段崩**。但更糟的是反向 —— 若某个消费方为了「少改一处」而改成从 `../converter/index.js` 取装配层符号，桶又长回来，且没人发现。头注已经自述过这个诱惑（「桶出口不再转手，消费方直连 core，避免双入口」）。
   **对策**：`main-ipc-no-assembly` 判红的是「`main/ipc/**` 引用 `../../convert/`」。但它覆盖不到 `main/windows/preview.ts`（它 import `../converter/index.js` 而非 `../../convert/`）。**需要一条更宽的规则**：`main/**` 不得经 `main/converter/index.js` 取 `src/convert/` 的符号 —— 这需要静态分析转出来源，当前门禁架构做不到。**保守做法**：桶瘦身后，在 `main/converter/index.ts` 的头注写明「本桶只转出本目录 5 个实现」，并把「桶里出现 `../../convert/` 字面量」作为 `main-ipc-no-assembly` 的判红条件扩展到 `main/**` 全部文件（判据：`main/**` 出现 `converter/index.js` 的**同时**出现 `../../convert/` 说明是转出而非直连 —— 过度简化）。**最终裁决：接受这个缺口，在 ADR 里显式登记为已知边界**，因为正确的判据（跨文件符号来源追踪）超出本仓门禁架构的能力，而为它建机制不值得### 一句话总结

`src/` 的**顶层分层是本仓最成功的治理**，一个字都不该动。真正的自伤集中在**四个文件承担了多份职责且名字只说了其中一份**（`i18n.ts` · `cancel.ts` · `ConvertContext`×2 · `settings-*.ts`），以及**一条已存在2 年的运行期依赖环**（`markdown ⇄ pipeline`）。全部19 条里，**7 条要动、6 条部分动、6 条不动或提法有误**。而 `core/` 的内部零约束**不是管不了，是没人管** —— 加 2 条边界的存在性判定就够，加方向规则会把 `renderer/` 的错误答案套上来。

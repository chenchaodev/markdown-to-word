# REQ-218 #10 阶段③ · 跨 feature 边拆边工作单

## 一、这份是什么

`gates/repo/check-import-boundary.mjs` 的 `LAYER_RULES` 新挂一条 `renderer-features-no-cross-import`（`scope: 'renderer-features'` · `forbid: peer:${RENDERER_PEER_ROOTS.join(',')}` · **`pending: true`**）。pending 期间它的命中归 `info` 通道、**不进 `problems`、不影响退出码** —— 故 `check:boundary` 与 `check:boundary:dist` 双侧仍 **exit 0**。

**info 通道逐处打印的那些命中，就是阶段④ 要拆的边。** 这是 ADR-075 §三「③ 新 peer 规则挂 `pending: true`（info 通道列出的现存边清单**就是拆边工作单**）」那句话的兑现。

**取数命令（口径可复跑）**：

```bash
npm run check:boundary      # src 侧（.ts 源）
npm run check:boundary:dist # dist 侧（tsc 产物）
# 逐条抓取（每行一条边）:
npm run check:boundary 2>&1 | grep '^\[info\] boundary:\[pending\].*renderer-features-no-cross-import'
```

## 二、两处口径的实测数字（**必须两处都报，不能只报一个**）

| 口径 | 命令 | 命中数 | 退出码 |
|---|---|---|---|
| src（`.ts` 源） | `npm run check:boundary` | **44** | 0 |
| dist（tsc 产物） | `npm run check:boundary:dist` | **44** | 0 |

**逐条对拍结果：两侧 44 条边一对一完全相同** —— 无「src 有 dist 无」、也无「dist 有 src 无」的条目（逐条按 `源文件(去扩展名) | 目标 feature` 建键比对，30 个键值两侧逐一对上，差额 0）。

**为什么两侧条数相同（与直觉相反，须写明而非含糊带过）**：任务书预判「产物里目录结构相同但文件名不同，条数可能不同」，实测**不同点不在文件名而在边本身**：

1. 本规则用的是 `peer:` 形态，判定走 `resolveOwner` —— 它把相对说明符**归一化后取前两段**（`renderer/convert/events/drop.ts` + `../../wizard/book-wizard.js` ⇒ `renderer/wizard`）。**文件名不参与判定**，只决定「从侧文件」；两侧同一份源码编译出的产物目录结构与文件名逐一对应，故边集必然相同。
2. **无 type-only 边**（实测 src 侧带 `type-only` 字样的命中 **0** 条）—— 这才是两侧本该分叉的那个口子：`type-only` 在产物侧被编译期整体擦除，一旦有跨 feature 的 type-only import，src 侧会多出一条而 dist 侧报不出。本批 44 条全是**值 import**，故两侧齐平。**阶段④ 拆边时若引入了 `import type` 形式的跨 feature 边，两侧就会分叉**，届时工作单要按两处分别记，不能只抄一个数。

## 五、阶段④ 要注意的形态（拆边时的机械事实）

1. **`renderer/ui/` 是最热的入边汇点**：21 条跨 feature 边指向它（settings 10 · convert 8 · wizard 3），而它的出边只有 6 条。⇒ 它极可能成为「大家都要的那一个」而被留在原地共享 —— 那样只是把边从 21 条换成 21 条经组合根注入的形参，**边数不降**，阶段⑥ 转正时门禁才会红。ADR-075 禁令 3「不得用白名单压绿现存跨 feature 边」正是为这一形态准备的。**具体热点是 `renderer/ui/dom-ops.ts`**（单文件被 **15** 条边指向：settings 7 · convert 6 · wizard 2 —— 逐条核自 §三 三张 ui 目标表；ui 另 6 条指向 `dialogs` 4 / `toast` 2）。
2. **`renderer/wizard/wizard-steps.ts`（4 条出边，全指向 settings）与 `wizard-steps-delivery.ts`（3 条，指向 settings ×2 + convert ×1）出边高度同构** —— 都指向 `settings/{settings-save,settings-logic}`。这两个文件像是一对被复制出来的，拆边时应**一并**处理，否则会出现「一个拆了另一个没拆」的半状态。
3. **`renderer/settings/settings-bindings-*.ts` 共 5 个文件**：4 个各有 1 条 `→ ui/dom-ops` 出边（`-convert` / `-headerwatermark` / `-preset` / `-typography`），第 5 个 `settings-bindings-app.ts` 有 3 条（ui ×2 + convert ×1）。逐文件拆 = 5 份改动；宜在同一个提交内一并接完（提交单元仍按 ADR-075 §三 的「机制/整步」划，不按 feature 划）。
4. **`renderer/convert/events/dialogs-events.ts` 单文件持有 6 条出边**（settings 3 · ui 2 · wizard 1），是 convert 侧唯一的出边集中点；`renderer/convert/events/` **整个子目录**合计 10 条出边（占 convert 全部 13 条里的 10 条），其余 3 条分散在 `convert-flow.ts`(2) 与 `file-list.ts`(1)。⚠ 旧 `prefix:` 形态对这个子目录的边是**真漏判**的（`../../ui/` 不以 `../ui/` 开头）—— 阶段② 换成 `peer:` 后按解析结果判，本工作单里这 10 条全部是真判出来的，不是普查脚本按目录折叠出来的。
5. **`renderer/ui/recent-files.ts` 是 ui 侧的唯一出边集中点**（4 条：convert ×2 + settings ×2，占 ui 全部 6 条里的 4 条）；`ui/dialogs.ts`(1) 与 `ui/first-run-guide.ts`(1) 各 1 条。
6. **组合根 `renderer/renderer.ts` 不在本工作单里**，且**它现在不在这一档 scope 的命中面内**（实测：带 / 不带 `RENDERER_FEATURE_SCOPE_EXCEPT_FILES` 的登记，`renderer-features-no-cross-import` 双侧命中数一字不变，组合根那 8 条 import 两侧都不报）。⇒ 阶段④ 往组合根加接线**不会**增加本清单的条数；但若阶段④ 顺手把 scope 命中面从「`renderer/<功能根>/` 前缀」改成「renderer 下排除基础层/样式层的全部文件」，组合根就会立刻进命中面 —— 那时那条排除面登记（`renderer/renderer.ts`）是它继续合法的唯一依据。
7. **动态 `import()` 与拼接 specifier 不在本判据覆盖内**（`collectImports` 只抽静态 `import`/`export from` 与 CJS `require`）。⇒ 工作单是**下界**，不是全集；「44 条拆完即 exit 0 转正」这句话的前提是**期间没有人写下动态形式**。ADR-065 §后果已点名此边界。

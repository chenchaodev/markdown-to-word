# 2026-10-07 REQ-219 宿主分档撤步裁决

## 一、目标与结论

`ADR-067` 决定「段契约一个字不改，只把宿主分成纯 node 与 Electron 两档，并加一条门禁守住分档不腐烂」，计划表上对应 #07 步。本次是它开工前的只读评审，结论是**撤步，不做**：不实现第二档宿主、不加那道分档门禁。

**撤步理由不是「实测过无效」**（措辞上不能留这个歧义，见 §六），而是三条各自独立成立的事实：**退出条件量错了收益** · **计划要求的那道门禁在本仓判据不可达** · **唯一那条非时间收益已被别的路径兑现**。

## 二、理由一：退出条件量的是三样成本里最小的那一样

`ADR-067` 背景二点名的三样成本是 **Electron 启动 · userData 重定向 · 超时预算**，而计划表 #07 的退出条件只写「纯 node 档段不需要 userData 重定向」—— **另两样（都是主项）一条都没进**。

**userData 重定向这一项的实测体量**：三步同步 fs 操作（`mkdtempSync` 造目录 · 写结果文件 · `rmSync` 删目录，`test/harness/runner.js:541` / `:469` / `:633`）。逐项计时：

```
node -e "const fs=require('fs'),os=require('os'),path=require('path');const N=100;function t(f){const s=process.hrtime.bigint();f();return Number(process.hrtime.bigint()-s)/1e6;}let mk=0,wr=0,rm=0;for(let i=0;i<N;i++){let d;mk+=t(()=>{d=fs.mkdtempSync(path.join(os.tmpdir(),'m2w-probe-'))});wr+=t(()=>{fs.writeFileSync(path.join(d,'result.json'),'{}','utf8')});rm+=t(()=>{fs.rmSync(d,{recursive:true,force:true,maxRetries:3,retryDelay:50}));}console.log((mk/N).toFixed(3),(wr/N).toFixed(3),(rm/N).toFixed(3),((mk+wr+rm)/N).toFixed(3))"
```

输出三列依次是三项的毫秒均值（`mkdtempSync` · 写结果文件 · `rmSync`），第四列是三项之和。**本机一次实测在 1ms/段 量级**（三列都在零点几毫秒区间）。

⚠ **具体数值与机器、盘、Defender 状态绑定，本文件不复述它** —— 论证依赖的是**量级差**（亚毫秒级 fs 操作 × 段数，仍然只是百毫秒量级）对上 **Electron 启动的秒量级地板**，而后者已有实测记录在案（见 §六引的那份 CI 实测快照），不在本文重测。**门禁阈值与本版本发布事实之外的可运行数字只写指针**，上列命令即是重取它的那一条。

## 三、理由二：计划要求的那道门禁在本仓判据不可达

`ADR-067` 的分档判据是「段的传递依赖闭包是否触及 electron」，其背景四与后果节都写「**可由现有 import 图扫描器算出**」。**实测：那不是事实。**

### 2.1 本仓没有闭包解析器

`gates/repo/check-import-boundary.mjs` 有可复用的单文件抽取 `collectImports()`（`:1194`），但它的两个编排入口 **`analyze()`（`:1347`）与 `analyzeTreeBoundaries()`（`:1793`）都是逐文件跑规则** —— 全仓没有任何一处做传递闭包。唯一带「闭包」字样的实现 `shared/copy-closure.js` 提供的是**词法层**两个函数（`lexSource` / `skipQuoted`，`:51` / `:112`），它自己的文件头（`:9-10`）写明整套闭包判定**已随「沙盒副本闭包」机制整删**，只退役消费方、留下这份词法事实。⇒ **「现有扫描器能算闭包」是背景四的一处事实错误**，须订正。

### 2.2 更硬的阻塞：反向锚点在正当段上必然假红

后果节「门禁要双向有牙」要求反向锚点是「Electron 档闭包内**确实**出现 electron」。而 `test/harness/runner-report.test.js` 是**正当的 Electron 档段**（它按段首注释第 1 条自测逐段子进程隔离模型），它的**静态 import 只有五样**：`node:fs` / `node:path` / harness 下的 `paths.js` / `temp-resource.js` / `runner.js`（`:46-50`），**零 electron**。

它的 electron 依赖是**运行期制造**的：把含 `import { app } from "electron"` 的段源码**写到磁盘沙盒**（`:329-332`、`:348-351`），再经嵌套编排 `spawn` 执行。**任何静态 import 图都看不见这一步** ⇒ 正向判据在它身上恒绿（可以标 node 档），反向锚点在它身上恒红（闭包里没有 electron 却要求有）。⇒ **在这一段上「档位」是「子进程之宿主的属性」，不是「段自身 import 的属性」—— 判据的主体选错了。** 同一形态在 harness 侧还有两处同源：`test/harness/pdf-utils.js:8` 与 `test/harness/settings.js:9` 是静态引 electron 的真 Electron 档共享件，而 `test/harness/segment-host.mjs:25` 正是 ADR-067「实施时的连带项」里要新写的那个 node 档入口 —— 三者说明「宿主属性」与「段 import 属性」是两个量。

## 四、理由三：唯一那条非时间收益，已由别的路径兑现

ADR-067 自己写「**最大的收益**」是：让「`core`/`convert`/`cli`/`mcp` 零 electron」从**门禁描述的目标**变成**测试系统的实测属性**。**该目标今天已经成立，且不靠 #07** —— 三条互相独立的机制各占一角：

- **源码面**：层向规则表里 `bare:electron` 对 **core**（`gates/repo/check-import-boundary.mjs:137`，`core-no-host`）· **convert**（`:151`，`convert-no-host`）· **cli/mcp 共用的交付面**（`:221`，`faces-no-host`）三层各有一条硬禁；`faces-no-host` 的 `reason` 里明写「生产安装根本没有 electron，需要宿主能力时由该面用子进程重入」，与 `src/main/cli-pdf-host.ts` 的做法同名同机制。
- **mock 完整性面**：`test/behavior/electron-mock-coverage.test.js` 把「mock ⊇ src 用到的全部 electron 具名导入」做成静态断言，其第 4 条（段首注释 `:16`、断言处 `:224`）就是「core 侧零 electron import —— 层向 core-no-host 的旁证」。
- **运行期面**：`gates/fixtures/gen-fixtures.mjs` 的段级 import 豁免白名单 `SEGMENT_EXEMPTIONS`（`:63`）**当前为空**，文件头 `:57` 写明这个「空」意为「全部段在纯 Node + electron-mock 下均可 import」；`check:fixtures` 在 `verify:ci` 链内每轮逐段 `await import()`（`:466`），任一段的导入依赖真的触及 electron 就会当场红。

⇒ #07 要新增的那条收益，今天已由**三条各自 fail-closed 的机制**兑现；它新增的是第四份同类覆盖，收益是零。

## 五、对撤步有利的既成事实（一条也别动）

- **隔离模型原封不动**。ADR-067 明写段契约一个字不改、ADR-015 立的那五项（每段独立进程 · 独立 userData · 硬超时杀进程树 · 退出码判读 · 0 段判红）一项都不动。撤步撤的是「谁来当子进程可执行文件」这层，**不是那五项** —— 本次撤步不会让任何现有的失败归因能力退化。
- **`resolveNode()` 已在，且已被多段复用**（`test/harness/node-exec.js:45`）。将来若真要做分档，落点已经存在，不需要重新发明。
- **计划表 #07 的写域与 #08 的写域不重叠**（#07 是 runner/segment-host 与共享面，#08 是 assert/case 与各段），撤步不制造任何写冲突。

## 六、一条必须写清的边界：REQ-133 的失败**不能**平移过来

本仓做过同方向的事，且被否决过 —— `cb3eb9c`（宿主默认改纯 node）随后 `c74a39a` revert，台账 REQ-133 已作废，其记录是「**CI 实测地板不降反升**」「否决理由是『方向无效』非『收益不够大』」。**只看这一条会得出「所以 ADR-067 也别做」的结论，那是错的。**

**那次的形态与 ADR-067 不是同一件事**：那次用 `spawn(process.execPath, …)` 并只设 `ELECTRON_RUN_AS_NODE=1` —— **那仍然是 `electron.exe`**。而 `test/harness/node-exec.js:40-41` 明文写着「**刻意不接受 electron.exe —— 用它就必须设 `ELECTRON_RUN_AS_NODE`，那就不是纯 node 了**（段要断言的『不经 electron』这条语义会静默失真）」。⇒ **REQ-133 试的是「换个运行模式」，ADR-067 要的是「换可执行文件」**；前者被否决的原因（创建 `electron.exe` 这个进程的成本压不掉，`ELECTRON_RUN_AS_NODE` 只改进程内模式）**在 ADR-067 的形态下不适用**。

⚠ 反过来也要防一句：**本次撤步不能被读成「实测过这条路无效」**。本次没有做这个实测，撤步的三条理由是 §二 §三 §四，与 REQ-133 的实测结论**无因果关系**。写 ADR 状态注、台账行或任何转述时都不许合并这两件事。

## 七、与 ADR-066 决定 3 撤步的同病关系（可引用，但要说明是同病不是同一件事）

两次撤步是**同一个病的两个实例**：ADR 的背景/后果段引用了一个**本仓并不存在的现成能力** —— ADR-066 假设「声明 vs 分支」可机械比对（实测两侧无共同可枚举词表），ADR-067 假设「现有 import 图扫描器」能算传递闭包（实测本仓无闭包解析器）。

**但两件事的处置不同，不要互相套用**：ADR-066 撤步后仍有 `src/core/convert.ts` 头注那份清单兜底；**ADR-067 撤步后没有任何东西兜底**，因为它本来就不产出「声明」，只产出一道门禁。⇒ **本次撤步的连带面比 ADR-066 大**：它要求同步订正计划表的完成标准（其中「node 档闭包无 electron」撤步后永远不成立）、相划分与依赖关系，详见 §八。

## 九、关于 #08 那条依赖的判断

计划表 #08 行原写「必须在 #07 之后（共用 harness）」。**该依赖对 #08 的实质不成立**，判据三条：

3. **次序约束的真实来源在 #09**：#09 的「必须在 #08 之后」写明理由是「表格化要用统一断言库」—— 那条**成立且必须保留**。#08↔#09 是真依赖，#07↔#08 不是。

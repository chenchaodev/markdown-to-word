## 一、为什么 pdf 能挂在「纯 node 的 MCP」上

当初 ADR-060 否决「MCP 暴露 pdf」的理由是「pdf 需要 Electron 宿主,而 MCP 跑纯 node」。**该理由把 pdf 当成了进程形态**;实际上:

- 装配层要的只是注入进来的 `printPdf`(ADR-060「注入点恰好四个」那一条),**装配层本身零 electron**(门禁 `convert-no-host`)。
- 拿到那个能力的手段在 CLI 上早已建成:纯 node 侧**写任务文件 → spawn `dist/main/cli-pdf-host.js` → 读结果文件**。
- 于是「MCP 也要 pdf」= MCP 复用同一套 spawn 机制,**协议通道(仍是纯 node 的 stdio)不必碰 Electron**。

机制原先住在 `src/cli/host-launch.ts`。搬进 `src/convert/pdf-host-launch.ts` 的理由有两条,都与「MCP 也要用」直接相关:

1. **ADR-060 定了 `cli` 与 `mcp` 是同层的两个 adapter、二者零依赖**(原文见 ADR-060 分层段),故两面共用的机制只能落在两层之下 —— 与 `src/convert/delivery-settings.ts` 的处置同一形状(那份文件头就写着这条理由)。
2. 该模块**本来就** `import { PDF_HOST_FLAG } from "../convert/cli-pdf-job.js"`,是半个装配层模块落在交付面下 —— 只有 CLI 用 pdf 时代的就近放置。

**依赖方向实测**:搬动后 `src/mcp/tools.ts` 与 `src/cli/index.ts` 互不 import,都只向下引 `src/convert/`(门禁 `check:boundary` 实测通过,结论行含「cli/mcp 两个进程外交付面(同层 adapter)不引用 renderer、不 import electron、不逃出 src/」)。

搬动顺带暴露的**深度假设未变**:`pdfHostEntry()` 拼的是 `<root>/dist/<层>/..` → `dist/main/cli-pdf-host.js`,`cli` 与 `convert` 两层深度相同,故编译产物深度假设在搬层后仍然成立(`test/convert/pdf-host-launch.test.js` 的第五条断言即这条假设的护栏)。

## 二、两条路径的耗时实测(deadline 裁决的依据)

口径:本机 Windows,合成文档(每节 = 一个 `##` 标题 + 一段含公式 `$x^2+y^2=z^2$` 的正文 + 一个三列表),经**真实 MCP 客户端形态**跑 —— 派生纯 `node dist/mcp/index.js`,stdin 送 `initialize` + `tools/call` 两帧,读 stdout 的 `structuredContent.elapsedMs` 与进程 wall 时长。

| 源文件 | 节数 | docx | pdf | pdf/docx |
|---|---|---|---|---|
| 89 KB | 600 | — | 7.4s | — |
| 179 KB | 1200 | 6.3s | 19.3s | **3.1×** |
| 363 KB | 2400 | 28.4s | 82.9s | **2.9×** |
| 546 KB | 3600 | ~67s(外推) | **>120s(实测被 deadline 掐掉)** | — |

小文档(12 行、含公式)对照:docx 90ms,pdf 1.65s。⇒ pdf 的固定开销是一次 Electron 冷启动 + `printToPDF`,量级 ~1.5s;随篇幅增长的部分 pdf 约为 docx 的 3 倍(Chromium 布局与逐页绘制 vs 文档树构建)。

**两条路径的耗时都随篇幅超线性增长**(docx:179 KB→6.3s、363 KB→28.4s,翻倍即 ~4.5 倍)。上表是**本机当前文档形状的一次实测,不是性能指标**。

### 裁决

`CONVERT_DEADLINE_MS`(docx)= **120s 不变**;新增 `PDF_DEADLINE_MS` = **3 × 120s = 360s**,3 是上表的实测比值不是拍的。

- **沿用 120s 会造出一道格式相关悬崖**:546 KB 上下,docx 过、pdf 被 deadline 掐掉,而 agent 从 `isError` 文案里**分不出「文档太大」与「转换卡死」** —— 两者的下一步动作完全不同(拆小输入 vs 查环境)。
- **3 倍让两条路径的可达篇幅对齐**(都落在 ~730 KB 上下),对应口径是「换格式不该缩小能处理的文档」。
- **代价如实记下**:一次 pdf 调用最长阻塞 server 约 6 分钟。这仍是**有界阻塞**而非无界挂死 —— deadline 这条闸防的是后者。判红实测:超时那次返回 `isError` + 文案「pdf 宿主超时未完成(上限 360000ms),已中止本次调用」,且**产物未落盘**(无半成品),同一 server 进程后续仍能继续服务下一次 `tools/call`。

## 三、`degraded` 在 pdf 路径上的形态(为什么恒为空)

| 格式 | mermaid 围栏实际渲染成 | `degraded` 字段 |
|---|---|---|
| docx | 等宽代码块 | `["mermaid"]`(core 在转换时判定、随产物带出,装配层原样透传) |
| pdf | 等宽代码块 | **恒为空** |

**不是同源**:core 的 pdf 分支不做 remark 解析(传原文给 markdown-it),也就不产 `mermaidDegraded` —— `src/core/convert.ts` 的 `DocxArtifact.mermaidDegraded` JSDoc 第 ② 条明写「将来若 pdf 面也需要此事实,该字段的语义要重新裁决,**不要顺手扩到 pdf 分支**」。

故本次**没有**在 MCP 侧自行解析补上:那正是 docx 路径上刻意消掉的第二次解析(`src/mcp/tools.ts` 文件头契约 2),且 core 的 JSDoc 把这件事标成结构裁决。处置改为**对 agent 据实声明**:工具描述里写明「pdf 产物的 `degraded` 恒为空」,且 `renderSummary` 对含 pdf 的一次 call **无条件**加一行提示(而不是只在 `degraded` 非空时加)—— 否则「degraded 为空」会被读成「这份文档没有 mermaid」。

实测佐证:同一份含 ```mermaid 围栏的文档,docx 返回 `degraded: ["mermaid"]`、pdf 返回 `degraded: []` 且人读文案点名了这件事。

**这是能力矩阵上的一处真缺口**(ADR-060 表下方已按该表的「空缺处即当前真缺口」口径记明),补齐需在 core 的 pdf 分支新增一次 AST 构建 —— 结构裁决,不在本工作项内。

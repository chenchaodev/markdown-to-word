# 目录结构评审（重组后复核）

> 探查时间：2026-08-24 02:26:55
> 性质：只读评审，未做任何代码改动。
> 来源：@oracle ora-1（全量结构 + 约 20 个关键文件头部/import 核实）+ 主会话汇总。
> 背景：20260823-230554-目录结构优化方案.md 的五批次重组已实施完毕，本评审为实施后的独立复核。

## 一、总体结论

整体结构健康：core（纯逻辑、无 Electron）/ main（进程编排 + IO + Electron）/ renderer（DOM/UI）三层分离执行得很一致，core 内部按「输出格式域（docx/pdf）+ 共享语法域（markdown/image/pipeline）+ 横切契约（settings/i18n/util）」分域清晰，两条管线的子目录粒度对称（handlers ↔ rules）。

真正的结构性问题只有两个：**跨进程契约类型寄居在 main 层造成 renderer→main 反向依赖**，以及 **test/ 的 segments/main 边界与项目自己声明的口径不符**。其余均为小瑕疵或仅需注意的点。

## 二、建议移动清单

### P1 — 跨进程契约类型归位 core（依赖方向破口，收益最大）

| # | 对象 | 建议 | 理由 |
|---|---|---|---|
| 1 | `src/main/ipc/channels.ts` 中 `ConvertProgressPayload`/`ConvertMode` 类型 | 类型迁至 core（如 `core/ipc-contract.ts` 或并入 settings-defaults 同级契约文件） | renderer/state/state.ts type-only import 它，构成 renderer→main 反向依赖；与 `core/settings/settings-defaults.ts`「跨层契约收敛于 core」先例对齐。channel 名常量和 handle/register 实现留 main 不动 |
| 2 | `src/main/persist/ui-state.ts` 中 `UiState`/`RecentFile` 类型 | 同上迁 core | 被 renderer/renderer.ts、renderer/state/state.ts、renderer/ui/recent-files.ts 三处 type-only import；持久化 load/save 实现留 main/persist/ |

注：与 20260823 方案「明确不做清单」中的 BatchResult/BatchItem 契约收敛同性质——契约收敛到 core 属行为面变更，当时裁定另开迭代；本两项可与之合并为同一「契约归位」迭代。

### P2 — test/ 目录与自述口径对齐（机械整理，低风险）

acceptance.mjs 头注释自述「segments/=core 渲染、main/=主进程层」，项目 AGENTS.md 亦声明 test 含 segments/+main/ 两层：

| # | 对象 | 建议 |
|---|---|---|
| 3 | `test/segments/ipc-channels.test.js` | → `test/main/`（直测 dist/main/ipc/channels.js） |
| 4 | `test/segments/ipc-logic.test.js`、`image-downloader.test.js`、`presets-import.test.js` | → `test/main/`（分别直测 main/ipc/logic.js、main/services/image-downloader.js、main/persist/settings.js） |
| 5 | `test/segments/settings-logic.test.js`、`renderer-pure.test.js` | → 新建 `test/renderer/`（直测 dist/renderer/...；归位后 test 树与 src 三层一一对应，需同步扩展 acceptance.mjs 自动发现根，一处改动） |
| 6 | `test/fixtures/pdf-css-sample.css` | → `test/fixtures/manual/`（全仓零代码引用，仅 CHANGELOG 提及，唯一用途是 GUI 手动导入 CSS） |

⚠️ 口径冲突提示：20260823 方案曾裁定「test/ 维持 segments/ 主题式命名，不镜像 src」。本评审建议实质是部分镜像 src 分层（segments 只留 core 渲染段）。两者取其一需用户裁定；若采纳本评审，应同步更新 acceptance.mjs 头注释与 AGENTS.md 测试体系描述。

## 三、无需移动、仅注意的点

- **mermaid 三同名各归其位但易误读**：`core/markdown/mermaid.ts`（25 行纯契约）/ `core/pdf/mermaid.ts`（pdf 占位替换逻辑）/ `main/services/mermaid-service.ts`（Electron 隐藏窗口渲染服务）。职责核实无误、各归其位；建议改名澄清（如 `core/pdf/mermaid-placeholder.ts`），不必移动。
- **resolver 契约的家不一致**：`ImageResolver` 契约在 `core/image/`（按资源域），`MermaidResolver` 契约在 `core/markdown/`（按语法域）。同为「main 实现、core 注入」模式，口径不同但都讲得通，低优先级。
- **`core/pipeline/merge.ts` vs `main/converter/merge.ts` 同名不是归属错误**：前者纯函数无 IO（文件头自证「可单测」），后者 fs 读文件 + 服务编排，分层正确。同名只是噪音。
- **i18n 放 core 根正确**：虽然 applyStaticTexts 触 DOM（仅 renderer 调用），但模块加载零副作用，且 core 的 keyed warning 契约和 main/renderer 双侧消费决定它必须住共享层；i18n-dict.ts 配对同处合理。
- **settings 三处目录不是平行重复**：`core/settings/`（契约+默认值单源）、`main/persist/settings.ts`（持久化 IO）、`renderer/settings/`（面板 UI）各司其职，正是分层该有的样子。
- **`main/services/image-downloader.ts` 留 main 正确**：无 Electron 依赖、理论可下沉 core，但做真实网络/fs IO，与 core「纯逻辑无 IO」定位冲突——IO 实现住 main 是对的边界。
- **`renderer/lang-bootstrap.js`（纯 JS）位置正确**：CSP `script-src 'self'` 拦内联脚本，必须独立文件在 `<head>` 同步执行，紧邻 index.html 合理。
- **`main/preload.cts` 独立于 ipc/ 目录**：沙箱 preload 无法 import 项目 ESM（channels.ts 头注释已记录，靠 ipc-channels.test.js 恒等断言兜底漂移），位置受技术约束，合理。
- **`renderer/dom/` 仅 refs.ts 一个文件**：粒度略碎但无害，不值得单独动。
- **fixtures 根部 `g1-tiny.png`/`img-800x400.png` 与 `acceptance/` 下同名文件是刻意双份**：前者供 segments 测试经 FIXTURES_DIR 引用，后者由 gen-fixtures 生成的自包含验收样例，不算冗余错误。

## 四、优先级

1. 问题 1–2（契约类型归位）：收益最大，修复依赖方向原则的实际破口；可与 BatchResult/BatchItem 收敛合并为一个迭代。
2. 问题 3–5（test 归位）：一致性整理，机械低风险；实施前先裁定与 20260823「test 不镜像 src」裁定的取舍。
3. 问题 6 及改名类澄清项：顺手即可。

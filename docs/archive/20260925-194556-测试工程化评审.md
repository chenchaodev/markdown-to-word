## 总结

当前测试体系已经具备较强的核心链路覆盖：大量段采用真实 `dist` 转换、docx XML 回读、PDF `pdf-lib` 回读和 Electron smoke；CI 已包含 coverage、fixture 漂移、smoke；版本与 lockfile 当前一致。早期归档报告中“fixture 未进 CI”“CI 无 coverage/smoke”“npm start 无新鲜度守卫”“Node floor 未验证”等结论已过时，不应直接复用。

## 一、已证实的缺口

### 1. 高：Release 门禁与 CI 门禁不一致

**证据**

- CI 执行：
  - `npm run build && npm run typecheck && npm run lint`：`.github/workflows/ci.yml:35-37`
  - `npm run test:coverage`：`.github/workflows/ci.yml:39-42`
  - `npm run check:fixtures`：`.github/workflows/ci.yml:44-47`
  - `npm run test:smoke`：`.github/workflows/ci.yml:49-51`
- Release 只执行：
  - build/typecheck/lint：`.github/workflows/release.yml:53-55`
  - `npm run test`：`.github/workflows/release.yml:57-58`
  - 打包：`.github/workflows/release.yml:60-64`
- Release 没有 smoke、coverage、fixture drift、视觉门禁。

**影响**

tag 可以绕过 CI 主门禁，直接进入发布构建。若 tag 对应提交未经过 smoke/coverage/fixture 校验，发布资产可能仍能产出。

**优化方向**

- 将 release 复用同一个完整验证脚本，而不是复制部分命令。
- 建议单一入口 `verify:release` 至少串联：
  `build → typecheck → lint → test:coverage → check:fixtures → test:smoke → dist`。
- 如果 `dist` 必须在验证之后执行，应在脚本和 workflow 中保持同一顺序。
- 将 release 与 CI 的 Node 版本、依赖安装源、门禁命令抽取为统一配置或复用 workflow。

**验证方式**

- 在临时分支制造一个“`check:fixtures` 失败但 acceptance 通过”的提交，确认 release job 也会失败。
- 对 tag `v*` 触发完整流程，确认每个门禁均有独立 job/step 记录。
- 对比 CI 与 release 实际执行命令清单。

### 2. 高：视觉检查不在任何 CI/release 门禁内

**证据**

- `test/tools/visual-check.mjs:1-8` 明确写明“供人工/代理目检布局一致性（不参与 CI 门禁）”。
- `package.json:44` 仅有手动 `ui:shots`。
- CI/release workflow 未调用 `ui:shots`。

**影响**

- 布局换行、舞台高度、640/880 窗口尺寸、转换中跳动等 renderer 回归可能只能依赖人工目检。
- 当前 `ui:shots` 不是“视觉 gate”，只是截图生成器；输出 `output/artifacts/ui-v4/` 被 `.gitignore:7-8` 排除，也没有基线 diff 或像素/几何失败条件。

**优化方向**

分成两层：

1. **可自动化几何 gate**
   - 复用现有 `visual-check.mjs` 中的 `getBoundingClientRect`、scrollHeight/clientHeight 探针。
   - 对关键布局输出 JSON 快照。
   - 在 CI 中断言关键几何值、溢出、舞台高度稳定性。
2. **截图基线 gate**
   - 保存经确认的基线 PNG。
   - 使用固定 Electron/Chromium、窗口尺寸、DPI、字体环境和固定 fixture。
   - 采用明确容差的像素 diff，而不是仅输出截图。
3. 人工视觉审查仍可保留，但人工审查不应是唯一的布局防线。

**验证方式**

- 修改 `.stage`、`.actionbar` 或参数条布局，确认几何 gate 失败。
- 在不同 Windows DPI/字体环境下重复运行，评估基线稳定性。
- 验证截图工具失败、截图空白、窗口未 ready 时均能返回非零退出码。

### 5. 中：覆盖率仅统计 `dist/**`，存在“覆盖测试运行产物但未覆盖源文件/未执行路径”的盲区

**证据**

- `package.json:46`：
  `c8 --reporter=text --include="dist/**" ... electron test/acceptance.mjs`
- `tsconfig.json:17` 开启 `sourceMap`，理论上可映射回 TS，但 c8 的 include 目标仍是 dist。
- 覆盖率阈值为 statements 90、branches 85、functions 90、lines 90：`.github/workflows/ci.yml:39-42` 与 `package.json:46` 同步。
- `docs/BACKLOG.md:50` 记录当前基线为 93.92/88.84/93.15/93.92。

**影响**

- `dist` 中未执行/未加载的模块可能不进入统计。
- c8 的全局阈值无法识别某些文件完全未加载，尤其 GUI 编排、窗口、菜单、IPC 注册等仅在特定路径执行的模块。
- 源文件与编译产物的映射若发生变化，可能导致报告口径漂移。

**优化方向**

- 增加按文件/目录的最低覆盖门槛，重点关注：
  - `src/main/windows/**`
  - `src/main/ipc/**`
  - `src/main/services/**`
  - renderer 入口及 GUI 编排
- 保留总覆盖率门禁，同时增加关键目录/关键文件覆盖门禁。
- 对未加载文件使用 `--all` 或生成零覆盖清单，避免“未执行即不在报告”。
- 将 baseline 记录、阈值调整和放宽理由纳入 CI/文档。

**验证方式**

- 新增一个故意不执行的源文件，确认当前报告是否出现。
- 将一个关键文件覆盖率降到 0，确认全局 90% 可能仍通过。
- 对 `dist` 与 `src` source map 做映射一致性检查。
- 比较修改前后报告中的文件集合和未覆盖文件集合。

### 6. 中：runner 是段级串行框架，失败定位粒度粗，超时后仍可能有后台副作用

**证据**

- `test/common/runner.js:36-43` 只要求每段导出 `run()`，错误以异常汇总。
- `test/common/runner.js:78-111` 所有段串行执行。
- `test/common/runner.js:46-53` 明确承认超时无法安全终止悬挂 promise。
- `test/common/runner.js:65-74` 超时后继续放行后续段，并为迟到 rejection 挂空 catch。
- `test/acceptance.mjs:73-90` 超时或失败后最终硬退出。

**影响**

- 一个悬挂段可能在后续段运行期间继续写文件、占用 BrowserWindow 或修改模块缓存。
- 失败结果只有段级，不能直接知道是哪一个断言/场景失败。
- 失败测试的清理可能不执行，导致下一次运行受残留状态影响。

**优化方向**

- 段内采用结构化测试用例和统一 assertion helper，至少输出：
  - suite/test case 名；
  - 期望值；
  - 实际值；
  - 差异摘要。
- 为每段提供 `setup/afterEach/finally` 生命周期。
- 对需要真实 Electron 的段增加段级资源清理注册。
- 对超时段增加“超时后资源状态”诊断。
- 若未来改为子进程隔离，应为每段定义超时、退出码和产物传递契约；当前项目已将该项列为“不做”，可作为已知限制持续监控。

**验证方式**

- 制造一个段超时且持有 BrowserWindow/文件句柄的探针。
- 观察后续段是否受到污染、是否产生未处理 rejection 或 EBUSY。
- 制造一个段内多个断言依次失败的样例，检查报告是否能定位到具体 case。
- 检查 `finally` 是否覆盖每个测试段的失败路径。

### 7. 中：fixture 生成器存在“部分跳过”和正则驱动的静默漏检风险

**证据**

- `test/tools/gen-fixtures.mjs:36-44` 只扫描 `test/segments` 和 `test/main`。
- `test/tools/gen-fixtures.mjs:123-129` 通过源码正则寻找 `export const fixtures`，无法识别其他导出形式。
- `test/tools/gen-fixtures.mjs:61-86` 对无 fixtures 的测试段 import 失败仅 `console.warn` 后跳过。
- `test/tools/gen-fixtures.mjs:89-99` 通过 Markdown 图片正则提取本地图片。
- 当前 CI 已将 `npm run check:fixtures` 接入：`.github/workflows/ci.yml:44-47`，因此旧报告“未接 CI”已不成立。

**影响**

- 新测试段使用不同 fixture 导出形式时，生成器可能不生成样例，但验收测试仍通过。
- 测试段 import 失败可能被当作可跳过，导致 fixture 集合不完整而 CI 未必将其识别为错误。
- Markdown 图片语法变化、HTML 属性顺序或嵌套语法可能造成图片未复制。

**优化方向**

- 将“声明式 fixture”改为显式注册或统一导出 API，避免正则探测。
- 对测试段中疑似包含 fixture 关键字但未成功导出的情况失败，而不是跳过。
- 对图片引用解析增加 fixture 解析测试，覆盖转义、空格、尖括号、HTML 单引号、嵌套括号。
- 校验 `README.md` 索引、源测试段、生成文件三者集合严格一致。
- 将“fixture 数量/文件名/图片引用完整性”作为显式检查，而不是只做文本内容 diff。

**验证方式**

- 新增一个使用非正则形式的 fixture 段，确认当前生成器行为。
- 删除或重命名一个 fixture 段，确认 `--check` 能发现 README/文件漂移。
- 构造包含复杂 Markdown 图片路径的 fixture，确认复制完整。
- 对无 fixtures 段故意制造 import 错误，观察是否错误地继续成功。

### 8. 中：Electron mock 只服务 fixture 生成，mock 与真实 Electron 链路存在天然偏差

**证据**

- `test/tools/electron-mock.mjs:3-6` 明确是“最小 mock”，只供 `gen-fixtures` 纯 Node 环境。
- `test/tools/electron-mock.mjs:8-17` 的 `app.getPath()` 返回空字符串，事件和生命周期均为空实现。
- `test/tools/electron-mock.mjs:19-44` 的 `BrowserWindow` 不具备真实窗口行为，webContents 方法为空实现。
- `test/tools/electron-mock.mjs:46-70` 多个 Electron API 为空壳。
- `test/tools/gen-fixtures.mjs:19-27` 通过 loader 将 `electron` 短路到 mock。

**影响**

fixture 生成成功不代表段模块能在真实 Electron 中正常 import/运行；mock 覆盖面不足时可能只在生成阶段失败，或反过来漏掉真实 API 约束。

**优化方向**

- 将 mock 的用途和禁止用途写入测试工具契约，并增加 mock API parity 探测。
- 对 fixture 生成只验证“可导入 + fixture 数据”，不要将其视为段运行验证。
- 对新增 Electron import 建立显式 mock 导出完整性测试。
- 保持真实 Electron 验证集中在 acceptance/smoke，避免在 mock 上增加业务行为模拟。

**验证方式**

- 枚举测试段中所有 `electron` 命名导入，与 mock 导出集合比对。
- 对每个 mock API 运行最小调用探针，检查返回值/方法存在性。
- 在真实 Electron acceptance 中运行同一 import 链。
- 故意删除一个 mock 导出，确认 fixture 工具能给出明确失败。

### 9. 中：构建新鲜度守卫是 mtime 启发式，不能保证 dist 完整性

**证据**

- `scripts/check-build-fresh.mjs:15-42` 只计算目录内最大 mtime。
- `scripts/check-build-fresh.mjs:48-58` 只判断 dist 是否为空以及 src 最大 mtime 是否更新。
- `scripts/check-build-fresh.mjs:20-31` 对目录不存在/stat 失败静默忽略。
- `package.json:39,43` 中 `start`、`test:smoke` 使用该守卫。
- `package.json:40` 的 `test` 直接重新 build，因此 acceptance 主链有新鲜度保证。

**影响**

以下情况可能被错误判定为“新鲜”：

- 删除 src 文件但 dist 残留旧文件；
- dist 只生成了部分文件；
- 编译中途失败但已有旧 dist；
- mtime 被恢复、复制或版本控制操作改变；
- 静态资源复制遗漏而 TS 文件时间未变化。

**优化方向**

- 使用构建 manifest/hash，而不是单纯最大 mtime。
- 至少校验关键 dist 文件集合：入口、renderer 静态文件、preload、smoke 所需服务。
- build 成功时写 manifest；`start/test:smoke` 校验 manifest 与当前源文件集合/哈希一致。
- 失败时不静默跳过 stat；对关键目录缺失直接失败。

**验证方式**

- 删除一个 src 文件但不 build，验证守卫失败。
- 删除一个 dist 关键文件，验证守卫失败。
- 修改 renderer 静态资源但不重新 build，验证失败。
- 模拟 `statSync` 抛错，验证错误不会被静默吞掉。
- 校验 `npm test` 与 `npm start` 的新鲜度语义是否一致。

### 10. 中：Node 20 “floor”实际不是 `engines` 声明的 20.19

**证据**

### 11. 中低：依赖锁定策略不统一，存在可重复性与发布漂移风险

**验证方式**

- 模拟镜像 tarball 不可用时，确认错误信息与重试策略。

## 二、建议增强（不是已证实缺陷）

### A. 统一断言框架和结构化测试报告

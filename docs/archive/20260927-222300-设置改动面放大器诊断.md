# 设置改动面放大器诊断（第一、二轮全文）

> 用户原始困惑：加一个「AI 生成内容清理」这类输出内容级能力时，**改动面非常大、动静很大**，怀疑是抽象没做好、代码结构有问题。
>
> 用户的四块划分：① 界面逻辑 ② 转换的各种配置及实现 ③ pdf/docx × 批量/单个/合并 = 6 种转换模式 ④ 其它（自认可能漏了）。

---

## 结论摘要

**「6 个转换模式」不是 6 套实现，而是 2 套。** 批量只是 `single.ts:73 convertImpl` 的并发池（`batch.ts:91` 逐文件调它）；合并是 `mergeConvertImpl`；两者在 `convert()` 调用点结构同构。真正的格式分叉全库**只有一处** —— `core/convert.ts:192` 的 `if (format === "pdf")`，文件头注释自陈「当前实现是二分分支，不是格式注册表」。

**所以「大动静」的来源不是模式多，是「一个选项要穿透多少层手工样板」。** 同样一个内容级能力，插在哪一层决定工作量差 2 倍：

| 插在哪 | 实现次数 | 需改 src 文件 | 需改 test 文件 | 参照 |
|---|---|---|---|---|
| main 层字符串预处理（格式分叉**之前**） | 1 次，双格式自动生效 | **12** | 4 | `aiCleanup` 三个开关 |
| core 渲染层（格式分叉**之后**） | 2 次，docx/pdf 各一 | **22** | 7 | `equationNumbering` |

**AI 清理之所以便宜，恰恰是因为它选在了分叉点之前做纯字符串处理。** 一旦要影响排版语义（编号、水印、目录）就得进 `ConvertContext` → `buildConvertContext`（18 字段手写映射表，`context.ts:186-212`）→ 双侧 `RenderOptions` 各声明一遍。

**真正的债集中在「设置已加载」这条链的上下游；渲染之后的一切都收敛得很好。**

## 第二部分：架构判定

### 1. 痛点不在渲染层

docx/pdf 渲染层的抽象是全仓做得最好的部分：共享语义层（`cross-ref.ts` / `slug.ts` / `html-whitelist.ts` / `image-path-policy.ts`）是真抽象，`ADR-014` 明确接受了双管线双实现的代价。**不要动那里。**

真正的债是：`AppSettings` 是一个平铺的袋子（21 键，只有 4 个是分组对象），而**每一层都各自手写枚举它的字段**。持久化枚举 4 遍、renderer 枚举 10 遍、i18n 枚举 3 遍、运行时映射分散在两个互不相干的函数里。**AI 清理是第一个落在「渲染前变换」这个新类别上的能力 —— 这个类别在当前架构里没有家**，所以它只能自己发明一条映射（`preprocess.ts:90-101`），于是全链路被穿透。

实测代价（commit `09dd7b9`，3 个 boolean）：**13 个代码文件 + 8 个文档文件**。

### 2. 成因排序

**① 配置的表达形式问题 —— 主因。** `AppSettings`（`settings-defaults.ts:181-230`）是平铺的。`aiCleanup` / `aiCleanupTidy` / `aiCleanupRewrite` 是**三个平级顶层 boolean**（`:213/:219/:225`），而 `headerFooter`（`:89-100`）和 `watermark`（`:121-130`）**已经是分组对象** —— 项目知道正确形状，只是没在这里用。

一个键组的固定落点共 **15 个站点**（完整清单见本文第一部分第 3 节与第二部分第 3 节）。最贵的四处（`persist/settings.ts` 的 4 处）每一处都要独立回答「旧 settings.json 缺这个键怎么办」—— `:181` 注释写着「新增开关为可选字段(旧 settings.json 缺省视为合法)」。**这不是重复代码，是每个新键都要重新做一次向后兼容决策。**

**运行时映射的分裂（第二重代价，最易被忽略）：** `buildConvertContext`（`context.ts:186-212`）手写枚举 9 个渲染相关字段；AI 清理不在其中 —— 它走了另一条路 `aiCleanupOptions`（`preprocess.ts:90-101`）。**实测 `core/convert.ts` 对 `aiCleanup`/`obsidian`/`AppSettings` 的引用数为 0** —— core 的转换入口根本不知道这两个设置存在。**所以「加一个新类别的设置」= 发明一个新 mapper，而不是加一行。**

**② 抽象方向错：层按「进程」切，不按「变化原因」切。** 内容语义在 `core/markdown/ai-cleanup.ts`，选项组装在 `main/converter/preprocess.ts:90-101`，产品契约 `AiCleanupOptions`（`ai-cleanup.ts:18-31`）与 `AppSettings` **零结构对应**。一个 core 能力，其配置装配住在 main。

同源症状：renderer 的预检链。`convert-flow.ts:123-194` 有 `withPrecheck` + `runPrecheckChain` + `precheckedCommand` + 一个模块级 `chainCovered` Set，原因写在 `:171-175`：成书向导一条命令里连转 docx+pdf 两次（`book-wizard.ts:211` 的 `withPrecheck([], …)`），预检锁被外层链占着，内层不能起新链。**这 70 行锁缝合机制存在的原因，是 single/batch/merge 之上没有「一次转换请求」这个概念。**

**③ 缺抽象 —— 真实，但范围比用户想的小。** 两处真重复，恰好都在 AI 内容区：

- **`SourceRange` 定义了两次**：`ai-cleanup.ts:33-36` 与 `precheck.ts:255`

**`afterConvert` 段在批量路径是第三份实现**：`batch.ts:121-124` 独立写了 `if (firstOk?.outputPath) { await runAfterConvert(…) }` —— 逻辑与 single/merge 的 `if (!ctx.skipAfterConvert)` **不同构**（批量不判 `skipAfterConvert`，改为「取第一个成功项」），但调用的 `runAfterConvert` 是同一函数。

### 逐条裁决：该统一 vs 不该统一

| 项 | 判定 | 理由 |
|---|---|---|
| `persistArtifact(...)` 调用 | 该统一 | 签名与参数集一致；`baseName` 是可选第 7 参 |
| `throwIfCanceled` `:126`/`:183` | 该统一 | 逐行同位 |
| `throwIfCanceled` `:143`/`:199` | 该统一 | 两侧注释都刻意论证了这个位置（「勿只依赖落盘前的检查点」）—— **这个刻意性要保留进共享骨架的注释** |
| `onProgress?.("read")` / `("render")` / `onStage` 透传 | 该统一 | 条件与展开式相同 |
| `warnings.push(...outWarnings)` | 该统一 | 逐行同位 |
| **`throwIfCanceled` `merge.ts:147`** | **不该统一** | merge 独有：N 文件有界并发读取（`MERGE_READ_CONCURRENCY=4`）期间的取消窗口。**合并它 = 要么删掉真实防护，要么在 single 造假闸门** |
| **`skipAfterConvert`** | **不该统一，且现状是错的** | `single.ts:138` 有真实写入者（`batch.ts:57` 置 `true` → `batch.ts:95` 传给 `convertImpl`）。`merge.ts:198` 的 `if (!ctx.skipAfterConvert)` **恒真** —— 全仓唯一 writer 是 `batch.ts:57`，而 batch 只调 `convertImpl`；`mergeConvertImpl` 唯一调用点 `register.ts:488` 的 ctx 来自 `createConvertContext`（无参）→ 该字段 `undefined`。**`merge.ts:100` 的注释「批量调用方经 skipAfterConvert 让位」对 merge 是错的 —— batch 从不调 merge** |
| **`runAfterConvert` 归属** | 不该统一 | single/merge 各传 `settings.afterConvert`；`batch.ts:123` 传快照且作用于**第一个成功项**。三处语义不同 |
| `baseName` 缺省 | 该统一为参数，但要小心 | single 传 `undefined` 让 `resolveOutputPath` 内部从 `sourcePath` 推；统一时不能让 merge 的显式值被 single 的缺省逻辑覆盖 |

### 抽象边界判定

**能共用，但边界必须画在「markdown 已就绪」之后。抽函数 > 抽对象 >> 抽主管线。**

- **抽函数（推荐）**：1 个新模块 + 2 个消费点。batch 零改动，preview 零改动
- **抽「转换请求」对象（不划算）**：收益是让 renderer 3 个 `runXxx` 与 main 2 个 handler 共用形状，但**它们在不同进程** —— 跨进程复用要过 `ipc-contract.ts`(186 行) + `preload-api.ts`(102 行) + `ipc/types.ts` + `channels.ts` 四个契约文件，换一层 JS 参数封装
- **抽主管线（不做）**：会扭曲进度粒度与 skipAfterConvert 语义

**「会不会把 N 文件→1 产物压扁成 1 进 1 出」：不会。** N→1 的塌缩已经在骨架上游完成 —— `mergeMarkdowns`(`merge.ts:154`) 把 N 个文件压成一段 markdown，发生在 `persistArtifact` 之前。**共享骨架的入参是「一段 markdown」，骨架内部根本看不到「几个文件进来」。**

**真正的压扁风险在别处：** `skipAfterConvert`（若主管线把「拥有者判定」收进自己，会把不对称变成隐式规则）· 进度粒度（`batch.ts:88-89` 在 `convertImpl` **外面**把「每文件一次 stage」包成批次进度；抽得太高才会被迫把 `index`/`total` 塞进回调签名，**那才是真正的压扁**）。

### 行为等价性与测试护栏

**等价性机械可证**（逐行同构 + 7 处参数差异），不是「重构后靠测试证明」。但现有测试**有一个洞**：

**`merge.ts:147` 没有专属测试。** `merge-cancel.test.js` 的三个场景是「预取消」「`setTimeout(0)` 途中取消」「deadline 过期」—— **没有一个把取消精确卡在「并发读取完成之后、`mergeMarkdowns` 之前」**。**抽取时误删或误移这道闸门，现有测试不会红。**

**第二个洞：`merge.ts:198` 是恒真死分支**，现有测试不可能覆盖（永远走 true 分支）。抽完后建议**删掉**并在 ADR 写明「该分支恒真，删除不改变任何行为」，同时纠正 `merge.ts:100` 的错误注释。

可直接当等价性证据的测试：`test/main/converter.test.js`（645 行，产物级断言）· `test/main/convert-cancel.test.js` · `test/main/converter-after-convert.test.js` · `test/main/artifact-commit.test.js` · `test/main/paths.test.js` · `test/main/preview.test.js` · `test/main/window-close-abort.test.js`。

### 不要动清单（相似但刻意）

1. `merge.ts:147` 的第 4 道取消闸门
2. `batch.ts:88-89` 的进度包装（在 `convertImpl` 外面）
3. `batch.ts:49-58` 的 `batchCtx` 让位构造（`skipAfterConvert: true` + signal/deadline 透传）—— 共享骨架必须**读** `ctx.skipAfterConvert`，不得自己判断拥有者
4. `renderPdf` 内部的双闸门（`printToPDF` 不可中断的补偿机制，merge 复用已自动继承）
5. 参数/预算校验段（`single.ts:81-85` 查扩展名 vs `merge.ts:114-128` 查空数组/上限 —— **判据完全不同，合并会造出语义模糊的校验器**）
6. merge 专属的 `metadata` 形参（`merge.ts:112`，single 无此形参）
7. `buildConvertContext` 三调用点的差异（preview 传 `renderMermaid` 降级、不共享 `imageResolver` 缓存、不传 `convert` —— 都是有意的）

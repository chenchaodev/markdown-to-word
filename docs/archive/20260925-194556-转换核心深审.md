## 1. [高] PDF 外链图片下载缺少超时、大小上限和取消能力

**证据**

- `src/core/pdf/postprocess.ts:135-157`
  - 收集所有外链图片 URL；
  - `worker()` 对每个 URL 直接 `await resolver(url)`；
  - 仅通过 `EXTERNAL_IMAGE_CONCURRENCY = 3` 限制并发；
  - 没有任何超时、AbortSignal、响应体大小上限或取消检查。
- `src/core/image/image-resolver.ts:7-12`
  - `ImageResolver` 契约只有 `Promise<Buffer | null>` 和可选 `exists`，没有超时、取消、输入长度或输出大小约束。
- `src/core/convert.ts:114-185`
  - `convert()` 没有取消参数，也没有渲染预算。

**触发条件**

Markdown 中包含大量外链图片，或单张 URL 指向长期不响应的服务器。Electron 主进程中的 resolver 若采用网络请求，单个请求即可让整个 `renderPdfHtml()` 长时间不返回；取消操作也只能在外层放弃等待，不能停止底层下载。

恶意输入还可以用大量不同 URL 造成 resolver 长时间占用；即使最终 base64 成功，内存峰值也可能远大于 Markdown 源文件。

**影响**

- GUI 转换无法及时响应关闭/取消。
- 网络资源、内存和事件循环被恶意或异常文档长期占用。
- 失败后仍可能继续处理后续 Mermaid/KaTeX/模板阶段。

**优化方向**

将 resolver 契约扩展为显式预算：

- `AbortSignal`；
- 单 URL 超时；
- 单图片最大字节数；
- 文档总图片数/总字节数预算；
- 超时和超限区分错误码并进入 warning；
- 在每个异步边界和 worker 循环中检查取消。

**建议验证**

1. 注入永不 resolve 的 resolver，验证取消能在规定时间内结束。
2. resolver 返回超大 Buffer，验证在超过上限时中止且不进入 base64。
3. 生成数千个不同外链 URL，验证并发数、总量和内存均有上限。
4. 验证部分图片超时后其余图片仍按既定降级策略完成。

**置信度：高。**

## 2. [中高] 本地图片检查无并发上限，和外链图片的“并发 3”策略不一致

**证据**

- `src/core/pdf/postprocess.ts:89-110`
  - `await Promise.all([...new Set(srcs)].map(async src => ...))`
  - 每一项直接调用 `resolver.exists(src)` 或 `resolver(src)`，没有 worker 池或并发上限。
- 对比 `src/core/pdf/postprocess.ts:70-71, 157`
  - 外链图片明确限制为 `EXTERNAL_IMAGE_CONCURRENCY = 3`。

**触发条件**

文档包含大量不同的本地图片路径，例如几千张图片或大量不存在的路径。只要 resolver 触达文件系统、杀毒软件、挂载目录或其他阻塞 IO，就可能同时创建大量 Promise/系统调用。

**影响**

- 大量并发文件访问可能导致事件循环、IO 队列和 Windows 文件系统压力显著上升。
- 失败 warning 的追加顺序不稳定，测试若依赖顺序会出现 flaky。
- 与外链图片的已知资源边界不一致，难以形成统一的可测试契约。

**优化方向**

将本地检查改为与外链图片相同的 worker 池，或抽取统一的有界并发执行器；同时明确：

- 去重后的图片数量上限；
- warning 顺序是否保证按源码顺序；
- `exists` 失败是否立即中止还是逐项降级。

**建议验证**

- 注入 1000 个 resolver，实时记录最大并发数。
- 让 resolver 按不同延迟返回，确认 warning 顺序契约。
- 覆盖 resolver 不提供 `exists` 时的回退路径。
- 在 Windows 下挂载高延迟目录进行 smoke 测试。

**置信度：高。**

## 3. [中高] 核心渲染没有取消/超时边界，取消语义只存在于 main 外层

**证据**

- `src/core/convert.ts:114-118` 的 `convert()` 只接收 `md`、格式和 context，没有 `signal`/deadline。
- `src/core/docx/render.ts:186-189` 逐块 `await renderBlock(...)`，没有取消检查。
- `src/core/pdf/render.ts:222-250` 依次执行 parse、图片检查、Mermaid、外部图片、KaTeX 阶段，没有取消检查。
- `src/core/convert.ts:84-89` 虽有 `onStage` 进度回调，但该回调仅用于上报，不承担取消。

**触发条件**

- 极大 AST/Markdown；
- Mermaid 渲染阻塞；
- 图片 resolver 阻塞；
- KaTeX 资源处理或模板构建耗时；
- 用户在 main 层请求取消，但底层 Promise 尚未结束。

**影响**

即使 UI 显示“正在取消”，核心渲染仍继续占用 CPU、内存和外部资源。取消不是资源级取消，只是调用方不再等待或部分状态被丢弃。

**优化方向**

- 在 `ConvertContext` 增加 `signal?: AbortSignal`。
- 在 `renderPdfHtml`、`renderDocx` 的块级循环、异步 resolver 调用之间检查。
- 将 signal 传入图片 resolver、Mermaid resolver、KaTeX 加载。
- 取消错误使用独立错误类型，避免被当作普通转换失败。
- 对同步的 remark/markdown-it 解析也考虑 worker/分片或至少在解析前后检查取消。

**建议验证**

- 在每个阶段注入延迟 resolver/Mermaid resolver，验证取消后不再进入后续阶段。
- 取消发生在 docx 第 N 个 block 时，验证后续 block 不再构造。
- 验证取消不会写入半成品文件。
- 验证取消和普通 resolver 异常的错误码、文案、warning 不混淆。

**置信度：高。**

## 4. [中] frontmatter 对单独 `\r` 的支持与正文解析不一致，可能导致元数据边界错位

**证据**

- `src/core/pipeline/frontmatter.ts:24`
  - frontmatter 结束匹配使用 `/\r?\n---[ \t]*(?:\r?\n|$)/`。
  - 开始和结束分隔行都要求 LF 或 CRLF。
- `src/core/pipeline/parse.ts:44`
  - docx 的行切分支持 `/\r\n|\n|\r/`。
- `src/core/pdf/render.ts:215`
  - PDF 表格宽度行切分同样支持单独 `\r`。
- `src/core/convert.ts:123-126`
  - frontmatter 解析结果决定 `body`，因此会影响两条管线。

**触发条件**

输入为经典 Mac/某些工具生成的单独 `\r` 换行：

```text
---
title: 文档
---

# 标题
```

**预期与实际**

- `parseFrontmatter()` 很可能无法识别 frontmatter；
- metadata 为空；
- `body` 保留原始 frontmatter；
- 标题可能被正文渲染，且封面/标题元数据与 docx/PDF 均受到影响。

**影响**

同一输入在支持 CR 的下游行解析器中看似“能处理换行”，但前置 frontmatter 已经丢失语义，造成跨模块不一致。

**优化方向**

统一换行规范：

- 在入口先规范化 `\r\n`/`\r` 为 `\n`，或让 frontmatter 正则显式支持 `\r`；
- 明确是否保留原始换行（如果后续需要源码位置/表格列宽，建议统一后保留映射）。

**建议验证**

增加 UTF-8、UTF-16、GBK 文本的三种换行组合 fixture：LF、CRLF、CR；分别断言：

- metadata 是否正确提取；
- body 是否不含 frontmatter；
- docx/PDF 标题数量、目录、表格列宽是否一致。

**置信度：高。**

## 5. [中] DOCX/PDF 选项映射不对称，存在未来行为漂移风险

**证据**

- `src/core/convert.ts:146-149`
  - PDF 传递 `pageSetup`、`typography`、`breakBeforeH1`、`toc`、`equationNumbering`，但没有显式传递 `headingNumbering` 或 `captionNumbering`。
- `src/core/convert.ts:173-176`
  - docx 同样没有传 `headingNumbering`/`captionNumbering`，但其 `RenderOptions` 在 `src/core/docx/render.ts:87-96` 明确定义了这两个选项。
- `src/core/pdf/render.ts:79-83` 同样定义了这两个选项，并在 `:189-190` 从 `typography` 取默认值。
- `src/core/convert.ts:6-18` 与 `src/core/docx/render.ts:6-18` 都声明两套选项语义需人工同步。

**当前行为判断**

当前两条路径都可能依赖 `typography` 默认值，因此未必立即产生用户可见错误；但 `convert()` 没有将显式 context 值转发给任一管线，调用方即使按 `ConvertContext`/渲染选项理解传入显式编号开关，也不会被核心入口使用。

**触发条件**

调用方未来增加：

```ts
convert(md, "pdf", {
  typography,
  headingNumbering: false,
  captionNumbering: false,
  ...
})
```

期望显式选项覆盖 typography，但 PDF 仍按 `typography` 计算；docx 也可能同样忽略显式值。

**影响**

- 核心公开入口的真实契约不清晰。
- GUI/CLI/测试若绕过 renderer 传显式选项，可能得到与 docx/PDF renderer 直接调用不同的结果。
- 后续新增编号相关选项时容易继续漏传。

**优化方向**

二选一：

1. 明确 `ConvertContext` 不支持 heading/caption 显式覆盖，只接受 typography；
2. 更推荐补齐 `ConvertContext` 字段并在 PDF/docx 两条映射中显式转发。

同时添加 contract test，断言同名选项在 `convert()` 入口的优先级一致。

**建议验证**

- 直接调用 `renderPdfHtml` 与 `renderDocx`；
- 通过 `convert()` 调用；
- 显式传 false、typography 为 true；
- 断言标题/题注编号结果完全一致。

**置信度：高（当前默认路径）；中高（显式 API 影响取决于当前调用方是否需要这些字段）。**

## 6. [中] PDF HTML 后处理依赖正则，标题/目录结构可被内容构造干扰

**证据**

- `src/core/pdf/postprocess.ts:24`
  - `extractHeadings()` 用正则匹配：
    `/<h([1-3])[^>]*id="([^"]+)"[^>]*>(.*?)<\/h\1>/g`
- `src/core/pdf/postprocess.ts:40`
  - 目录文本虽经 `escapeHtml(text)`，但 id 直接插入 `href="#${id}"`。
- `src/core/pdf/postprocess.ts:59-67`
  - 页码注入依赖固定 `<li class="toc-lN"><a href="#id">...</a></li>` 结构。
- `src/core/pdf/rules/html.ts:73-77`
  - 非白名单 HTML 会被转义，但白名单允许文本和 `span` 等标签。

**触发条件**

标题包含引号、HTML 实体、特殊字符，或渲染规则产生复杂嵌套结构；标题 id 来自 slug，slug 规则若允许特殊字符/编码差异，目录链接和页码注入可能出现不匹配。

**影响**

- 目录文本与正文标题可能不一致。
- 页码无法注入或被错误注入。
- 目录/书签的 HTML 结构依赖字符串格式，后续模板或规则变更容易破坏。
- 极端输入可能造成 O(n) 级别重复扫描和大字符串拼接。

这不是已确认的 XSS：`buildTocHtml` 对文本做了 escape，且 HTML 白名单不允许属性；但“结构正确性”仍依赖脆弱正则。

**优化方向**

- 让 heading-id 规则在渲染时直接记录结构化标题，而不是渲染后从 HTML 反向解析；
- 或使用受限 HTML parser/token 数据构建目录；
- 目录项通过统一 DTO 生成，避免重复拼接；
- 对 id 做严格 slug 字符集约束并在生成链接时统一编码。

**建议验证**

- 标题含 `<`, `>`, `&`, `"`、emoji、重复标题和超长文本；
- 标题 id 发生重复；
- 标题含嵌套 `span/code/strong`；
- 两遍 PDF 渲染注入页码，断言所有 h1-h3 目录项均有正确页码。

**置信度：中高。**

## 8. [中] 编码回退策略会把任意非法 UTF-8 二进制输入当作 GB18030 文本

**触发条件**

- 随机二进制文件；

**优化方向**

- 编码检测增加置信度/合法性检查；
- 对控制字符比例、NUL 字节、替换字符比例设阈值；
- 区分“疑似 GBK”与“二进制/未知编码”；
- 最好由调用方先限制输入类型和大小，并对损坏输入返回明确错误。

**建议验证**

- 随机字节、NUL 字节、UTF-16 无 BOM、Shift-JIS、截断 GBK；
- 断言损坏二进制不会被当作普通 Markdown 继续完整渲染；
- 断言未知编码的 warning/错误码可区分。

**置信度：中高。**

新增/修改以下边界之一：

- `<br>` 与 `<br/>`；
- 大小写标签；
- 标签间空白；
- 文本中的 `<`；
- 嵌套白名单标签；
- 注释和分页符。

**影响**

PDF 与 DOCX 可能出现同一输入一边渲染、一边转义/跳过。现有测试能覆盖常规情况，但对扫描器差异组合的覆盖有限。

**优化方向**

将表达式扫描抽成共享 tokenizer/parser，PDF 和 DOCX 只负责从不同输入形态调用；或者至少用同一组 fixture 对两侧进行 property/differential testing。

**建议验证**

- 同一 HTML 字符串分别走 `convert(..., "docx")` 和 `convert(..., "pdf")`；
- 对标签大小写、空白、自闭合、嵌套、文本 `<`、未闭合、属性、注释生成组合；
- 断言 HTML 是否被渲染/转义/跳过两侧一致。

**置信度：中高。**

## 10. [低中] PDF 与 DOCX 对页码、目录和分页的行为不是同一语义

**证据**

- `src/core/convert.ts:6-18` 明确承认两条管线有多个有意差异：
  - docx 静态目录/Word 域目录；
  - PDF 目录通过 HTML 锚点；
  - 公式、脚注、Mermaid 表现不同。
- `src/core/pdf/render.ts:230-235`
  - PDF 先拼封面、目录、正文，再做外部图片处理。
- `src/core/docx/render.ts:174-185`
  - DOCX 先预扫再生成封面/目录。
- `src/core/pdf/postprocess.ts:53-67`
  - PDF 页码需要主进程两遍打印后从 PDF 目标解析并回填。
- `src/core/docx/render.ts:89-92`
  - DOCX 的目录模式由 `tocMode` 区分 static/field。

**触发条件**

开启 PDF 两遍页码模式、封面/目录同时开启、标题跨页、目录本身有分页、正文包含连续显式分页符。

**影响**

同一 Markdown 的两种输出可能在：

- 目录页是否占页；
- 目录项是否带页码；
- 目录项顺序；
- 分页符造成的空白页；
- 标题页眉/封面行为

上出现差异。部分差异可能是产品有意设计，但目前主要由注释和测试隐式维护。

**优化方向**

建立跨格式“语义差异矩阵”：

- 明确哪些是格式必需差异；
- 哪些是产品要求一致；
- 将共同行为抽成纯函数/契约测试；
- 对连续分页、封面+目录、标题跨页建立双格式 smoke fixture。

**建议验证**

- 同一 fixture 分别输出 docx/pdf；
- 对页数、目录条目、标题编号、题注编号、公式编号、脚注、显式分页符做对照；
- 将“允许差异”显式写入断言，而不是依赖人工观察。

**置信度：高（存在差异已由代码注释确认；具体产品影响需主会话结合验收定义确认）。**

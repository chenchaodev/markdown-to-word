### ② `contentWidthPx` 推导 —— 真实的、未被记录的数值漂移

- docx `render.ts:141` + `:156`：`twipsToPx(mmToTwips(geometry.contentWidthMm))` = `round(mm × 56.6929) / 15`
- pdf `render.ts:322`：`mmToPx(pageGeometry.contentWidthMm)` = `mm / 25.4 × 96`

实测：

| 版心 mm | docx | pdf | 差 |
|---|---|---|---|
| 96.00 (A4纵向) | 362.866667 | 362.834646 | **3.20e-2 px** |
| 183.00 (A3) | 691.666667 | 691.653543 | 1.31e-2 px |
| 34.00 (A5) | 128.533333 | 128.503937 | 2.94e-2 px |
| 101.90 (Letter) | 385.133333 | 385.133858 | -5.25e-4 px |

根因：`56.6929 / 15 = 3.7795266666…` vs `96 / 25.4 = 3.7795275590…`。硬编码的 `56.6929`（`settings-defaults.ts:161`）是 `1440/25.4 = 56.692913…` 的截断，docx 因此吃了两次精度损失（常数截断 + `Math.round`）。

**而两处注释都宣称「同口径」：** `docx/render.ts:140`「复用核心 validator 的视觉方向结果」、`pdf/render.ts:320-321`「landscape 视觉宽度为纸高，**与 docx 侧 textWidthTwips 同口径**」。**宣称与代码不符，且从未有人发现** —— 差值在 0.03px 量级，肉眼和断言都看不出来。

### ③ 题注章节号门控 —— 真实漂移，代码自认但归因错误

- docx `captions.ts:96`：`chapter: ctx.config.headingNumbering && chapter > 0 ? chapter : null` —— **位置性**（到此处为止数过几个 h1）
- pdf `xref.ts:149`：`opts.headingNumbering && hasH1` —— **存在性**（`hasH1` = 全文任意位置有 h1，`xref.ts:75`）

边界文档（图/表题注出现在首个 h1 **之前**，而全文后面还有 h1）：docx 出「图 N」，pdf 出「图 0.N」。

`pdf/rules/caption.ts:17-19` 原文归因为「文档开头（首 h1 之前）的图题注在无 h1 文档中按纯序数渲染，有 h1 文档中渲染为「图 0.N」（**与 docx 侧「图 N」的差异为 CSS counter 无法条件输出的罕见边界，验收清单已标注**）」。

**但这个归因是错的。** `xref.ts:148-151` 的静态编号文本是 **JS**，`headingCounters.h1` 在手边，完全可以条件输出。它没有条件输出，是因为它照抄了 CSS 分支的 `hasH1` 口径。**根因是决策重复，不是平台限制。**

### ④ 公式编号算法 —— 两侧各写一遍，已漂移过两次（均已修复）

- docx：`handlers/equations.ts:57` `buildEquationContext`（AST 预扫 → `indexByNode`/`labelIndex`/`skipSet`）
- pdf：`rules/equation.ts:25` `overrideEquationRule`（token 流扫描 → `eqIndex`/`data-eq-index`/`data-eq-label`）

**两个独立算法，不是共享函数** —— 与 `heading-numbering.ts` 的处理方式相反（那里抽了共享）。

已漂移两次并修复：
- `equation.ts:50-52`：「口径对齐 docx：整段『纯文本串接』恰为 `{#eq:label}` 即命中 —— **此前要求唯一 text child，粗斜体包裹的 label（如 `**{#eq:a}**`）双格式登记结果不同**」
- `template-css.ts:190-191`：「遗留修复：此前缺 `counter-increment`，序数恒为 0，所有题注显示『图 N.0』」

### ⑤（附带）pdf 内部自漂移 —— 真平台限制

`template-css.ts:177-179`：「已知罕见边界：无 h1 且首个标题前无 h2 的 h3，**CSS 显示「0.1」而引用文本为「1」**」。pdf 的 CSS 显示层与 pdf 自己的 JS 引用文本不一致。`heading-numbering.ts:8-9` 自述「pdf 显示层（CSS counter）无法复用 JS 函数（平台限制）」—— **不是设计债。**

### tsc 为什么兜不住

| 接口 | 位置 | 字段数 | **required** |
|---|---|---|---|
| `RenderOptions`（docx） | `core/docx/render.ts:79-117` | 19 | **0 个，全部为 `?`** |
| `RenderPdfHtmlOptions`（pdf） | `core/pdf/render.ts:87-148` | 20 | **2 个**（`baseDir:87`、`fs:134`） |

- 两个接口**都不 `extends` 任何共享基类型**，无 `Required<>` / `Pick<>` / `satisfies` 约束，**字段交集没有任何类型级表达**
- 实际生效的检查只有两条：多余属性检查（删了一侧字段却忘删字面量会报错）+ 类型匹配
- **捕获不到**：在 `RenderOptions` 新增字段而**忘记加进** `convert.ts:250-270` 字面量 → **不报错**，该选项静默为 `undefined` 走 render 内默认；两侧新增不同名字表达同一语义 → 不报错；两侧默认值字面量不同 → 不报错

### 正确收敛形态（不强迫 docx 实现 pdf-only 字段）

**不能做「两侧共用一个 options 接口」** —— 那会让 docx 被迫声明 `katexDir`/`pdfCss`/`onStage`/`fs`。

**正确形态：只把共有子集抽成基类型，两侧 options 交叉继承。**

- 共有 15 字段进共享基类型：`imageResolver` / `guard` / `imageBudget` / `metadata` / `title` / `warnings` / `pageSetup` / `typography` / `breakBeforeH1` / `toc` / `headingNumbering` / `captionNumbering` / `equationNumbering` / `mermaidResolver` / `watermark`
- pdf 侧继承 + 加 `baseDir`（必填）/ `fs`（必填）/ `katexDir?` / `pdfCss?` / `onStage?`
- docx 侧继承 + 加 `tocMode?` / `headerFooter?` / `headerLogo?`

**收益**：15 个共有字段的类型与 JSDoc 只写一遍；新加一个 C 类键少改 1 处类型。**它不解决漏传** —— TS 对可选字段没有默认值检查，**要解决漏传必须配「默认解析收进共享函数」**。

## 第八部分：两路分析结论的冲突与裁决

**冲突：** 一路判「实现侧基本不需要收敛，剩下 4~5 处小而尖的重复」；另一路系统枚举 45 项，得 **14 共用 / 31 分叉**，并确认 2 处设置项静默失效。

**裁决：两个都对，差在方法与分类口径。**

- 前者是**抽样**（4~5 个点），后者是**全量枚举**。
- 后者的 31 是个**上界** —— 里面混了大量**载体所迫**的 fork（例：「行内公式顶层判定」docx 走 AST 遍历、pdf 走 token 深度追踪 —— 同一规则、两种数据结构，不是重复决策）。前者恰好做了这个区分。
- **真实标尺只有一条：同一输入 → 不同输出。** 后者自己标出了该子集（7b 的 #6 #7 #9 #10 #11 #15 #16），前者的 4~5 也在这个量级附近。**结论不变，但「3 处已修且被锁住」的说法漏报了未修的那几条。**

**代价的真实形态不是代码冗余，是设置项静默失效** —— 而 2 个失效缺陷**恰好落在矩阵零覆盖的 4 个键上**（`typography` / `breakBeforeH1` / `headerFooter` / `watermark`），再加「矩阵不是门禁」+「anchors 已 25.8% 指向空行/注释、1 条越界」三条机制叠加。

**⇒ 真正缺的既不是重构也不是抽象，是一张「双管线决策项台账」+ 一个保证新 C 类键会进表的机制。**

## 第九部分：裁决

### 9.1 不引入「能力」抽象（与 `ADR-014` 冲突，不是补充）

四条理由：

1. **能力层已经存在，只是不叫这个名字。** `core/markdown/*` 的共享模块就是能力层 —— cross-ref 有 12 个消费方。再加一层 interface 只是给已有结构补个名字。
2. **YAGNI：8 个能力撑不起一层抽象。** 一层抽象的维护成本正比于「每加一个能力要改几处抽象层」。载体专属抽象已经有了两套（`CtxConfig` 全必填 vs `RenderPdfHtmlOptions` 几乎全可选），再加一层总层数 3，净收益只是「少写一遍 JSDoc」。
3. **与 `ADR-014` 的关系是「冲突」。** ADR-014 规定的手段是**函数级共享**（`heading-numbering.ts` 抽 3 个纯函数）；能力抽象要求**声明级共享**，而**载体恰恰是 ADR-014 明说「差异是设计意图」的那一部分**。把「差异是设计意图」的东西抽象成统一接口，是在撤销 ADR-014 的核心判断。
4. **会诱发具体过度抽象。** 若统一声明「输入 + 期望输出」，`PdfArtifact`（html + 2 模板串 + tocMode + headings + metadata）与 `DocxArtifact`（buffer）就必须统一形状 —— **而这两个形状的差异由载体决定，不可消除**。

**反证：`fs: PdfFsCapabilities`（`pdf/render.ts:78-84`）刻意只声明两个函数**，头注写着「能力面收窄到本渲染路径确实需要的两次读，新增用途必须显式改这个接口，而不是顺手拿到整个 fs」。**这是反能力声明的刻意设计** —— 用「能力接口」的名义去统一它恰好会破坏它。

**最小替代形态（若坚持留名）：** 不加 interface，零代码改动 —— 在 `core/markdown/` 目录头注里写明「本目录是**决策层**；其下 `docx/` `pdf/` 是**载体层**」，并把共享模块标为「决策层单源」。

### 9.2 该收敛什么

| # | 内容 | 形状 | 行为等价 | 性质 |
|---|---|---|---|---|
| ① | **默认解析收进共享函数**（12 个字面量 → 1 个来源；把 docx 已有的 `ctx.config` 全必填形态推广到 pdf） | 1 个新纯函数 + 2 消费点各改 3~5 行 | 可做到是（需逐键断言） | **唯一能治「漏传静默降级」** |
| ② | `SharedRenderOptions` 交叉继承（15 共有字段） | 2 文件纯类型，运行时零影响 | **严格是** | JSDoc 单源；**单独做无效，必须配 ①** |
| ③ | `contentWidthPx` 推导单源化 | 1 处 | **否 —— 会改产物（0.03px）** | 最低优先级，可选；ADR 须写明「两处『同口径』注释此前与代码不符」 |
| ④ | 决策项台账（45 项逐条分类：载体所迫 / 实质漂移 / 设置项失效 / 已被矩阵锁住）+ 矩阵门禁探针 + 补 4 行覆盖 | 1 份台账 + 1 探针 + 4 行（约 120 行） | 探针与测试行不改产物 | **防复发机制** |
| ⑤ | `watermark.angle` 符号单源化 | 1 常量 + 2 消费点 | **可能改产物** | **先人工确认是否真反转** |
| ⑥ | `watermark.opacity` 在 docx 侧的处理决策 | 1~2 文件 | 取决于决策 | **确认的失效，取向需产品裁决** |
| ⑦ | `headerFooter.headerMode:"default"` 统一或登记为 allowedDiff | 裁决后定 | 取决于决策 | **需要产品裁决** |

**①②③ 是纯收益；④ 是机制补缺；⑤⑥⑦ 是缺陷，其中 ⑤ 可能比 ②③ 重要一个数量级（用户可见的方向反转 vs 0.03px）。**

### 9.3 明确不要动

1. `core/markdown/*` 的共享模块 —— 决策层已建好，12 条 `mustMatch` 在锁，**全仓最值得保留的设计**
2. 载体分层（`docx/handlers/*` vs `pdf/rules/*`）—— ADR-014 明确接受，`pdfCss` 就是载体差异换来的产品能力
3. `headerFooter` 在 pdf 侧被烘焙成两个模板串（`convert.ts:238-239`）vs docx 拿原对象（`:267`）—— **刻意**。统一会强迫 pdf 侧理解 `headerLayout: center/leftRight`，而 pdf 根本不需要这个区分
4. `fs: PdfFsCapabilities` 收窄到两个函数 —— **反过度抽象的刻意设计**
5. **公式编号的两套算法**（`equations.ts:57` / `equation.ts:25`）—— docx 走 AST 预扫（能提前算 `skipSet`），pdf 走 token 流（只能渲染期边走边记），**两者可用的输入信息不同，强行共享要引入一个中间表示 = 净增复杂度**。已发生的两次漂移都被矩阵锁住，这是「决策重复被测试契约覆盖」的正确形态
6. CSS counter 与 JS 引用文本的不一致（`template-css.ts:177-179`）—— **真平台限制**
7. 能力（capability）抽象层 —— 见 9.1

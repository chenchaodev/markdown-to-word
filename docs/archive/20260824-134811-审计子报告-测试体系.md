## 维度 1：测试框架与 runner —— 自研零注册机制

**实现**（runner.js 共 91 行）：
- 零注册发现：discoverSegments() 按目录顺序 readdir + 文件名排序，段文件只需导出 async function run()。新增测试 = 新建文件，确实零注册。
- 执行模型：**纯顺序**，无并行；失败以段为粒度 try/catch 汇总，报告就是完整 error.stack。
- 看门狗：单段超时用 Promise.race 竞速，注释坦承「只把超时段标记为失败以放行下一段，不终止悬挂段」——悬挂段的 promise 继续在后台跑，迟到 rejection 靠空 catch 吸收。超时后该段可能仍在写产物/持有 BrowserWindow。
- 断言能力：**为零**。没有 assert 库、没有 diff 增强（ROADMAP.md:86 明确记录「diff 增强未做」），每个测试段各自内联 assert/assertEq 或裸 throw。

**发现的缺陷**：
1. **死配置旋钮**：runner.js:71-73 支持 M2W_SEGMENT_TIMEOUT_MS 回退，但 acceptance.mjs:50-52 恒传入 Number(M2W_ACCEPTANCE_SEGMENT_TIMEOUT_MS ?? 180000)（永不为 undefined），所以 M2W_SEGMENT_TIMEOUT_MS 是**死代码**。同一功能两个环境变量名，ROADMAP.md:86 的记载也混用了两个名字。
2. 无单段筛选能力：改一个 handler 只能全量重跑 45 段（约数分钟），没有 --only/name filter。
3. 无并行、无重试、无逐断言定位（失败只到段级堆栈）。

**node:test 成本收益对比**：
- 收益侧：Electron 43 内置 Node 20+，node:test 可用；白得 describe/it 分组、--test-name-pattern 单段筛选、spec/tap reporter、并发控制。
- 成本侧：现有 runner 已稳定服役，迁移要动入口和 CI 命令，风险低但非零。
- **结论**：runner 本身维护成本极低（91 行），「是否值得自研」不是主要问题；真正的欠账是**没有单段筛选和死旋钮**这两点。折中方案是不换框架，给 discoverSegments 加一个环境变量过滤参数即可覆盖 80% 痛点。

## 维度 6：electron-mock.mjs 的 mock 策略

策略：gen-fixtures 在纯 Node 下通过 module.register() 挂 resolve 拦截 loader 把 electron specifier 短路到 mock。mock 本体是空实现集合。

质量评价：
- **聪明之处**：抓住「段模块顶层只 import 声明、方法在 run() 内才调用」的特征，空实现即可让动态 import 通过；mock 只服务 fixture 生成不参与真实验收，避免 mock 漂移污染断言。
- **脆弱点**：① mock 面是手工清单——新增 electron 命名导出时会抛 SyntaxError 且错误信息不指出「缺哪个导出」，排障要猜；② BrowserWindow 构造器里 webContents 是每次新建的孤立对象；③ app.getPath 返回空串。总体定位克制、文档清楚、脆弱性可控；建议仅在 mock 缺导出时报错信息里列出 specifier 即可大幅降低维护成本。

## 维度 8：gen-fixtures 生成与 --check 的实际使用情况

机制：扫描段文件中 export const fixtures 正则探测，import 段模块取字符串落盘，顺带复制图片、生成 README 索引；--check 内存重生成逐字比对。

**两个硬发现**：
1. **没有任何自动化流程调用它**。package.json 定义了 script，但 ci.yml 全文只有 checkout/setup-node/npm ci/typecheck+lint/npm run test 四步；release.yml 同样。git 历史上 gen-fixtures.mjs 仅 1 个 commit = 纯手动工具，fixtures 是否陈旧完全靠自觉。
2. **--check 当前在本机必然失败，且是系统性失败**。实测 exit 1，全部 25 个 md + README.md 都报「首处差异第 1 行」，差异行内容肉眼完全相同。根因实证：磁盘 fixture 含 CRLF；本机 core.autocrlf=true；仓库**没有 .gitattributes**。生成器写出 LF，git checkout 规范化成 CRLF，readFileSync 读回的字节串与内存 LF 串永不相等。**校验机制在任何 Windows 默认配置的克隆上都是坏的**——又因为 CI 不跑它，坏了两版都没人发现。

修复建议：加 .gitattributes（*.md text eol=lf 或至少 fixtures -text）并把 check:fixtures 挂进 CI 一行；或 --check 比较前做 EOL 归一。

## 维度 10：测试运行性能

**关键事实：不存在「每个 test.js 独立起 Electron」的问题。**
- npm run test = **1 个 Electron 进程**，45 段同一进程内顺序动态 import；userData 在 whenReady 前重定向到一次性临时目录。test:all 共 2 次启动。
- 进程内真实开销单元是 htmlToPdf：每次新建隐藏 BrowserWindow → printToPDF → destroy，全量一轮约 13 次，printToPDF 是单段耗时主导项。
- 观测设施已有（总耗时 + 最慢 5 段排行），CI 注释给出全流水线 10-15 分钟基线；段默认看门狗 180s。
- 进一步提速空间不在多进程而在段内并行化 printToPDF 或引入筛选能力。

## 维度 11：命名与组织一致性

- **两层标准并存但边界有渗漏**：segments 名义按内容主题、main 按层，但实际有 5 个「层归属不属于 core」的段住在 segments/（ipc-channels、ipc-logic、presets-import、renderer-pure、settings-logic）——它们按的是第三条隐含标准「零 Electron API 纯逻辑 → segments,需要 Electron 环境 → main」。三种标准叠加，新人推断「新测试放哪」需要读目录注释。main 内部也有例外：gbk-encoding.test.js 是 main 层唯一的主题式名字。
- **describe/it 全仓为零**，统一扁平 export async function run() + [ok] 进度标记 + 中文断言消息。风格高度一致，但缺少结构化分组意味着失败粒度永远是「段」。
- fixtures 命名小混淆：g4-smoke.png 名字带 smoke 却与 smoke.mjs 无关，g4/smoke 字样是历史批次编号残留。

## 维度 12：其他发现

1. **测试对象是 dist 不是 src**：npm run test 链式 build 保证新鲜闭环成立；但绕过 npm 直接 electron test/acceptance.mjs 会静默测旧产物无提示。值得在 README 层面显式警示。
2. **CRLF 地雷不止影响 check:fixtures**：任何未来对 fixture 内容逐字节比对的测试都会踩同一坑；无 .gitattributes 是根因。
3. **死代码清单**：png-utils.js 全文件；M2W_SEGMENT_TIMEOUT_MS 回退分支；pdf-css-sample.css 孤儿 fixture。
4. **文档数字漂移**：ci.yml 与 STATUS.md 的「40 段」vs 实际 45 段。
5. **watchdog 语义缺陷已自知未解决**：超时段无法取消，迟到 rejection 静默吞掉。
6. **正面亮点**：断言文化极强（负向断言、回归锚注释、实现事实带源码行号）；ESM 单例状态用 query-string 动态 import 取全新实例是干净手法；smoke 双重隔离与恢复纪律在同规模项目里少见。
7. **测试段自描述质量参差的小信号**：gen-fixtures 生成的 README 索引直接搬 JSDoc 首行，导致 3 个场景共用一段截断描述且以冒号结尾，人工实测者难以区分场景差异。

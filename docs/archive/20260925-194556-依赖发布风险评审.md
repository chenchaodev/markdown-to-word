## 只读风险评审结论

评审范围：`package.json`、`package-lock.json`、TypeScript/构建配置、Electron Builder 配置、CI/Release 工作流，以及 Electron/docx/markdown-it/remark/KaTeX/Mermaid 的实际引用。未修改任何文件。

验证日期：2026-09-25。  
依赖现状来自项目 `.npmrc` 指定的国内镜像 `https://registry.npmmirror.com`。

---

### 总体判断

- **未发现立即阻断发布的已知高危代码执行漏洞**；Electron 窗口普遍启用了 `sandbox`、`contextIsolation`、关闭 `nodeIntegration`，PDF HTML 有 CSP 和 HTML 白名单，Mermaid 使用 `securityLevel: "strict"`。
- **主要高风险集中在构建环境契约和发布供应链**：
  1. 项目声明 Node `>=20.19`，但 Electron 43.2.0 和三个 `@mdit/plugin-*` 明确要求 Node 22+；CI 与发版却运行 Node 20。
  2. Release 未配置 Windows 代码签名，且未要求签名成功。
  3. 构建未清理 `dist`，删除/重命名 TS 源文件后可能把陈旧 JS 打入安装包。
  4. CI/Release 使用浮动的 runner、Node 大版本和可变 Action tag，不能严格复现历史构建。
  5. 国内镜像不实现 npm audit API，当前 CI 也没有其他漏洞扫描门禁，安全状态不可见。

# 高严重性

## 1. Node 支持边界自相矛盾，发布流水线实际运行在依赖不支持的 Node 20

### 仓库证据

- 项目声明 Node `>=20.19`：  
  `package.json:31-33`
- Release 使用 `node-version: 20`：  
  `.github/workflows/release.yml:44-47`
- Node 20 地板门禁也使用 `node-version: 20`：  
  `.github/workflows/ci.yml:53-71`
- Electron 43.2.0 明确要求 Node `>=22.12.0`：  
  `package-lock.json:4314-4331`
- Electron 间接依赖 `@electron/get@5.1.0` 同样要求 Node `>=22.12.0`：  
  `package-lock.json:170-188`
- 三个 `@mdit/plugin` 都明确要求 Node `>=22`：
  - `package-lock.json:1286-1299`
  - `package-lock.json:1301-1317`
  - `package-lock.json:1324-1337`

### 已验证影响

这不是“应用运行时 Node 版本”问题：Electron 主进程使用的是 Electron 内置 Node，开发依赖和打包工具使用的是宿主 Node。Electron 官方明确区分宿主 Node 与 Electron 内置 Node：

- 官方前置条件文档：  
  https://www.electronjs.org/docs/latest/tutorial/tutorial-1-prerequisites
- 官方版本与 Node 支持策略：  
  https://www.electronjs.org/docs/latest/tutorial/electron-timelines

当前可能出现：

- `npm ci` 在 Node 20 下产生 `EBADENGINE` 警告；
- 安装脚本、Electron 下载器或未来 npm 严格 engine 行为变化后，发版直接失败；
- 本地“支持 Node 20.19”的声明没有依赖层依据；
- CI 所谓的“地板验证”验证的是**未经上游声明支持的组合**。

### 优化方向

这需要主会话先处理项目契约冲突，不能静默选择：

1. **保持当前 Electron 43 和当前 `@mdit/plugin-*` 不回退**，将开发/构建 Node 下限统一提升到上游共同要求的 `>=22.12.0`；这会修改项目当前“Node >=20.19，勿回退”的硬约束表述，需负责人明确批准。
2. CI、Release、本地文档统一使用同一个明确 Node 版本。
3. 不建议通过回退 Electron 或 `@mdit/plugin-*` 解决，因为这会违反项目既定技术路线；也不建议建议 markdown-it 15 回退/升级。

### 验证方式

- 在 Node 22.12.0 和当前声明地板 Node 20.19 分别执行 `npm ci`，保存完整 `EBADENGINE` 输出。
- `node -p "require('./node_modules/electron/package.json').engines.node"`
- 对三个 `@mdit/plugin-*` 执行同类 engine 检查。
- CI 增加显式 `node --version && npm --version && npm config get engine-strict`。
- Electron 启动后记录 `process.versions.electron/node/chrome`，避免和宿主 Node 混淆。

## 2. Windows 安装包未配置代码签名，发布可能静默产出未签名程序

### 仓库证据

- Builder 只配置 NSIS、x64、语言及安装目录，没有证书、`sign` 或 `forceCodeSigning`：  
  `package.json:61-79`
- Release 直接执行 `npm run dist` 并上传 EXE：  
  `.github/workflows/release.yml:60-64`、`.github/workflows/release.yml:89-96`
- 脚本没有签名后的验签步骤：  
  `package.json:48`

### 官方依据

electron-builder 官方 Windows 签名文档说明，配置签名方法或凭证后，builder 会签名可执行文件和安装程序，以便 SmartScreen 和自动更新验证发布者及文件完整性：

https://www.electron.build/code-signing-win

官方源码同时表明：

- 未设置 `forceCodeSigning` 时默认是 `false`；
- 没有签名且未强制签名时，构建可以成功完成。

因此当前配置存在“发版成功，但产物未签名”的可能。

### 影响

- Windows SmartScreen 警告概率增大；
- 用户难以验证发布者及下载后文件是否被篡改；
- 企业环境可能直接阻止安装；
- 后续若引入自动更新，更新链路也依赖发布者身份和包完整性。

### 优化方向

- 配置受控的 Windows 代码签名证书，并通过 CI secret/受限环境变量传入。
- 设置 `forceCodeSigning: true`，确保无证书时发版失败，而不是产出未签名包。
- 打包后执行 `Get-AuthenticodeSignature`，确认 `Status` 为 `Valid`、签名者符合预期。
- latest.yml/安装包上传前保存 SHA-256。

### 验证方式

```powershell
Get-AuthenticodeSignature .\release\MarkdownToWord-Setup-3.12.0.exe |
  Format-List Status,StatusMessage,SignerCertificate
```

同时在无证书的测试 job 中确认 builder 会 fail closed。

## 3. 构建未清理 `dist`，删除/重命名 TS 源文件可能把陈旧产物打入安装包

### 仓库证据

- `build` 仅为 `tsc && node scripts/copy-renderer.mjs`：  
  `package.json:35-39`
- TypeScript 输出到共享 `dist` 目录并开启增量：  
  `tsconfig.json:15-19`
- 拷贝脚本只清理 `dist` 中的 HTML/CSS 和两个显式脚本，不清理陈旧 `.js/.js.map`：  
  `scripts/copy-renderer.mjs:27-39`、`scripts/copy-renderer.mjs:42-63`
- Builder 打包整个 `dist/**`：  
  `package.json:56-60`

### 影响

若某个 `.ts` 文件被删除或重命名，`tsc` 通常不会自动删除其旧 `.js/.js.map`。旧 JS 会继续留在 `dist`，并可能：

- 被 `dist/main/index.js` 的残留导入链加载；
- 被 Builder 无意收入 ASAR；
- 掩盖模块删除、入口迁移或重构错误；
- 导致本地、CI 和干净工作区构建结果不同。

这是实际可重复性风险，不只是理论上的体积问题。

### 优化方向

- 每次正式 build 从空 `dist` 开始；
- 增量 `.tsbuildinfo` 也应与干净构建基线隔离，或在删除源文件时确保不会掩盖陈旧输出；
- 增加“干净工作区构建”和“脏工作区构建”的产物文件清单对比；
- 打包前对 ASAR 内容建立 manifest，禁止出现无对应源入口的陈旧模块。

### 验证方式

由主会话在临时副本中：

1. 构建一次；
2. 删除或重命名一个不再被引用的 TS 文件；
3. 不清理 `dist` 再构建；
4. 比较两次 ASAR 文件清单和主入口可达模块；
5. 验证干净构建与增量构建的 manifest 是否一致。

# 中严重性

## 4. Release/CI 构建输入高度浮动，无法严格复现历史发布

### 仓库证据

- 使用浮动的 `windows-latest`：  
  `.github/workflows/ci.yml:17-21`、`.github/workflows/release.yml:18-22`
- Node 只固定到 `22` 或 `20` 大版本，没有固定 patch：  
  `.github/workflows/ci.yml:25-29,62-65`、`.github/workflows/release.yml:44-47`
- Action 使用可移动 tag，而非不可变 commit SHA：  
  `.github/workflows/ci.yml:23,26,60,62`、`.github/workflows/release.yml:24,44,69`
- `npm ci` 保证 npm 依赖按 lock 安装，这是已有的良好基础：  
  `.github/workflows/ci.yml:31-33`、`.github/workflows/release.yml:49-51`

### 影响

同一个 tag 后续重建时，runner 镜像、Node patch、npm、Action 实现和部分构建工具环境均可能变化。lockfile 只能固定 npm 图，不能固定整个构建环境。

### 优化方向

- 固定 Node patch，例如明确的 `22.x.y`；Node 边界统一后，CI 与 Release 使用同一版本。
- 对发布关键 Action 固定到完整 commit SHA，并保留版本注释。
- 记录并随 Release artifact 保存：
  - Node/npm 版本；
  - Electron/Chromium/内置 Node 版本；
  - `npm ci` 后的生产依赖树；
  - Builder 配置和 ASAR manifest；
  - 安装包 SHA-256。
- 若业务不要求字节级可复现，至少做到“依赖与工具链可追溯”。

### 验证方式

在两个不同时间/不同 runner 上构建相同 commit，比较：

- 安装包 SHA-256；
- ASAR 内文件列表；
- 每个文件 hash；
- 若要求字节级一致，再比较 PE 时间戳、NSIS 元数据和 ZIP/ASAR 顺序。

## 7. KaTeX 对不可信/超大 TeX 未设置资源上限

### 仓库证据

DOCX 路线调用：

```ts
katex.renderToString(tex, {
  output: "mathml",
  throwOnError: false,
});
```

位置：`src/core/docx/handlers/math.ts:63-66`。

PDF 路线注册 `@mdit/plugin-katex` 时未传安全/资源选项：

`src/core/pdf/render.ts:163-168`。

### 官方依据

KaTeX 官方安全文档说明：

- `maxSize`：限制用户指定尺寸，防视觉布局攻击；
- `maxExpand`：限制宏展开，防无限循环；
- `trust`：控制可加载外部资源或修改 HTML 属性的命令；
- `maxSize` 默认是 `Infinity`。

官方资料：

- https://katex.org/docs/options.html
- https://katex.org/docs/security.html

`trust` 相关 HTML 命令默认是关闭的，因此当前没有证据表明存在默认 `\href`/`\includegraphics` 放行问题；主要缺口是 `maxSize`、`maxExpand` 未设边界。

### 影响

若用户打开他人提供或自动生成的恶意 Markdown，宏深度/尺寸攻击可能造成：

- 主进程长时间占用 CPU；
- 转换 IPC 卡住；
- 超大 MathML/HTML 输出；
- 内存压力或界面无响应。

当前 KaTeX 0.18.1 的 HTML 命令默认安全策略降低了 XSS 风险，但资源消耗边界仍不足。

### 优化方向

- 在两条公式路径统一传递有限制的 KaTeX options：
  - 明确 `trust: false` 或严格回调；
  - 设置合理 `maxExpand`；
  - 设置合理 `maxSize`；
  - 保持现有 `throwOnError:false` 降级语义。
- 转换入口另外限制 Markdown 文件大小和公式节点长度。
- 避免只依赖 15 秒 Mermaid timeout；KaTeX 是同步在主进程执行，超时包装无法中断已卡住的同步计算。

### 验证方式

加入恶意/压力 fixture：

- 深度宏递归；
- 极大尺寸/空间；
- 大量公式；
- `\href`、`\includegraphics`、`\htmlClass`；
- 未闭合命令。

记录转换耗时、峰值内存及是否始终返回可解释降级结果。

## 11. 新鲜度守卫基于全目录最大 mtime，不能证明逐文件对应

### 仓库证据

- 守卫只比较 `src/**` 与 `dist/**` 全部文件的最大 mtime：  
  `scripts/check-build-fresh.mjs:15-46`
- 仅在 `srcMaxMtime > distMaxMtime` 时判过期：  
  `scripts/check-build-fresh.mjs:48-57`

### 影响

如果某个源文件被修改，但其 mtime 早于 dist 中另一个无关文件的最大 mtime，守卫可能放行陈旧对应产物。该守卫只能作为辅助，不能替代干净构建和内容级验证。

### 优化方向

- 正式测试/发布始终 build；
- 以输入文件 hash、构建 manifest 或 CI clean checkout 为准；
- 若保留守卫，明确它是弱防护，不承担正确性证明。

### 验证方式

人工把某个旧源文件 mtime 调早后执行 smoke，确认该弱守卫可能放行；再验证内容 hash/manifest 方案能拦截。

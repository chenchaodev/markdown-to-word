## 维度 1：总体架构

**入口编排（convert.ts，138 行）——清晰，但有一处真实浪费**

`convert()` 是干净的格式注册表模式：frontmatter 剥离 → 分发到 docx/pdf 渲染器 → 返回判别联合 `ConvertArtifact`。头部注释（convert.ts:6-19）用一张「双管线差异表」声明两路线差异是有意的并逐项挂测试段指针，这是很好的架构自我说明。

**发现一个实质问题：pdf 路线重复解析。** convert.ts:98 `const ast = parseMarkdown(body)` 无条件执行，但 pdf 分支（convert.ts:100-122）只用 `body` 字符串，`ast` 完全未消费——remark 解析 + 全标题 slug 遍历在每次 PDF 转换时白做一遍（renderPdfHtml 内部由 markdown-it 另行解析）。`ast` 应移入 docx 分支惰性构造。

**深层不对称**：docx 路线的解析责任在 convert 层（传入 AST），pdf 路线的解析责任在 pdf/render 层（传入原文）。这直接导致了上述浪费；也使两条路线的「解析产物契约」无法共享（mdast vs token 流）。

**docx 路线内部结构——质量高**。分层：parse.ts（解析 + slug 底座）→ prescan.ts（五轮预扫）→ render.ts（编排 + Document 组装）→ handlers/*（11 个按内容主题拆分）。依赖方向单向且有明确的解环工程记录：ctx.ts:3-4「子模块 → ctx，不反向」、render.ts:47-48「settings-defaults 单源解 convert⇄render 环（B7）」、bookmark.ts:5-7 独立成模块避免 captions→render 运行时环。递归簇的共置理由写得很清楚（content.ts:1-6：五函数相互递归必须同模块）。

**pdf 路线内部结构——同样清晰**。markdown-it 实例组装（buildMarkdownIt）→ core 规则族（caption_recognize/eq_numbering/xref_recognize/html_whitelist）→ renderer 包装（heading-id/xref anchor/math_block/image）→ 后处理链（checkLocalImages → replaceMermaidPlaceholders → buildTocHtml → embedExternalImages）→ 模板装配。B8 拆分后 rules/ 按类别分文件、shared.ts 收敛三处同构深度跟踪（shared.ts:9-16 注释明确记录收敛史）。onStage 四阶段上报（render.ts:189-203）与 main 侧 printToPDF 衔接顺畅。

## 维度 3：双管线重复（重点）

### 3.0 slug.ts 与 pdf/rules/heading-id.ts —— 不重复，单源成立
heading-id.ts:7 直接 `import { uniqueSlug } from "../../markdown/slug.js"`；docx 侧 parse.ts:6 同样导入。两侧共用同一 slugify/uniqueSlug 实现，「seen」Map 各自在各自管线闭包内维护（parse.ts:34 / render.ts:184），算法同源、生命周期各自隔离，无漂移风险。此项设计合格。

### 3.1 标题章节编号 —— 三份平行实现，最大漂移面
同一「h1 增 → 下级清零」计数逻辑存在三处：
- docx 预扫：prescan.ts:49-68（headingCounters）+ chapterNumberFromCounters（prescan.ts:101-114）；
- pdf 计数扫描：xref.ts:80-124（scanXrefDefinitions 内 counters）；
- pdf 显示层：template.ts:159-167（CSS counter 规则）与 template.ts:177-184（题注分支）。

且存在**已知的行为分歧**：docx 跳过前导零级（无 h1 时 h2 引用显示「1」，prescan.ts:97-98 started 标志），pdf 刻意保留（「0.1」，xref.ts:116-118 注释「差异在报告注明」）。即同一篇无 h1 文档的 `[章节](#sec:x)` 引用在 Word 里显示「1」、PDF 里显示「0.1」。注释虽声明有意，但三份实现靠人肉镜像（prescan.ts:99 自认「仅镜像……会漂移(免更新路线已声明)」）。**值得提取**：一个纯函数 `computeHeadingNumbers(headings[]) => Map<node,label>` 供 docx 预扫与 pdf 扫描共用（CSS counter 无法复用属平台限制，但两份 JS 计数可以合一）。

### 3.2 公式编号 —— 语义等价的两份实现
docx equations.ts:34-69 与 pdf equation.ts:25-99：全文连续编号、后随 `{#eq:label}` 段登记并跳过、orphan 处理、numbering=false 时 label 段仍隐藏但不登记——六条语义逐条对应，分别实现在 mdast 节点模型和 token 流模型上。合并成本高（数据模型不同），现状可接受；但正则 `/^\{#eq:([\w-]+)\}$/` 两处硬编码（equations.ts:48 / equation.ts:57），应进 cross-ref.ts 与 kindLabelRegex 并列。

### 3.3 交叉引用 label —— 常量已单源，正则族未收尽
CROSS_REF_KINDS 已单源（cross-ref.ts:15-19）并有恒等断言守护（contract-single-source.test.js:20-25）✓。但引用 href 正则仍双份硬编码：`/^#(fig|tab|sec):([\w-]+)$/` 于 link-xref.ts:63 与 xref.ts:174；`/^#eq:([\w-]+)$/` 于 link-xref.ts:28 与 equation.ts:78。另外 docx captions.ts:84 的 `/\s*\{#(fig|tab):([\w-]+)\}$/` 本可用现成的 kindLabelRegex(kind)（cross-ref.ts:30-32，pdf 侧已在用）却手写了合并版——单源化的半成品。**低垂果实**：把这三条正则并入 cross-ref.ts。

### 3.4 图片尺寸计算 —— 不算重复，机制本就不同
docx 走像素上限 scaleToFit（image-run.ts:20-26，max-width 400px 不放大），pdf 走 CSS `img { max-width: 100% }`（template.ts:116）。一个是绝对像素嵌入、一个是版心相对宽度，属平台语义差异而非逻辑复制。无需提取。

### 3.5 Mermaid 处理 —— 降级骨架重复 + 警告对象字面重复
两侧流程对称：docx code-block.ts:19-40（resolver try/catch → PNG → 失败降级代码块）；pdf render.ts:119-127 占位 + mermaid.ts:17-59 替换。其中**警告对象完全逐字重复两份**：
- `warn.mermaidEmpty`：「Mermaid 渲染失败： 渲染服务返回空结果…」code-block.ts:28-31 ≡ mermaid.ts:41-44；
- `warn.mermaidFailed`：模板串一致 code-block.ts:34-38 ≡ mermaid.ts:49-53。

对比之下 image 族有 image-warning.ts 单源、crossRefNotFound/highlightFallback 有 i18n.ts 工厂（i18n.ts:46-64）——mermaid 是警告通道里唯二没有工厂函数的 key。**值得提取**两个构造函数。

### 3.6 行内 HTML 白名单 —— 判定已单源，表达式扫描仍双份
判定函数 isAllowedInlineHtml 单源 ✓（html-whitelist.ts，头注释明说原为逐字副本）。但「如何从输入流中组合出白名单表达式」仍是两份近似算法：docx normalizeInlineHtml（inline-html.ts:130-175，节点流合并）vs pdf matchAllowedHtmlExpression（html.ts:15-49，源码栈扫描）——两者对 br/自闭合/嵌套的处理规则逐条对齐，靠注释互指同步（inline-html.ts:4-6，目前单向）。运行期守卫 assertInlineTagStylesMatchWhitelist 只护住标签集表格，不护这两份扫描逻辑。合并难度大（输入模型不同），至少应在两处头注释互加「修改须同步」的双向指针。

### 3.7 字体约束核查
AGENTS.md 要求 docx 字体走 theme.ts 集中配置。实测合规：正文字体唯一来源是 typography 设置经 renderDocx styles.default 注入（render.ts:226-234），theme.ts 只收固定样式常量且头注释明说删除了原兜底角色（theme.ts:4-6）；全 core 无散落 fontAscii/fontEastAsia 硬编码；pdf 侧字体来自同一 TypographySettings（template.ts:51）。等宽字体 CODE_FONT（theme.ts:10）在 docx 侧全部取用，pdf 侧 Consolas 写在 CSS 中（template.ts:86）属另一技术栈，可接受。

## 维度 5：prescan.ts

**做什么**：正文渲染前的五轮全文扫描（prescan.ts:26-35 头注释与实现一一对应）：① 脚注定义索引；② 题注上下文；③ 章节 label；④ 公式编号上下文；⑤ 目录条目。返回 `{ tocEntries, captions, equations }` 结构化结果，就地写入 ctx 三张表。

**一致性风险评估——总体安全，三点注意**：
1. **节点身份键安全**：captions/equations 以 mdast 节点对象本身作 Map 键，预扫与渲染遍历同一棵 AST 对象，无重标识碰撞风险 ✓
2. **镜像漂移已声明**：chapterNumberFromCounters 是 docx numbering 模板（render.ts:135-151）的手工镜像，prescan.ts:99 明确承认「模板变更会漂移」。加上 pdf 侧第三份镜像，这是全库最脆的一致性点。
3. **一处过期注释造成误读**：render.ts:300-301 称公式无编号信息时「理论不可达」——实际当 `equationNumbering=false` 时 buildEquationContext 不登记任何节点（equations.ts:42），每个 display 公式都走这条「理论不可达」路径。行为正确（居中不编号），注释错误。

另注：预扫门控 `ctx.headingNumbering !== true`（prescan.ts:51）与渲染门控 `=== true`（render.ts:400）语义一致，但依赖可选字段的双重否定表达，易在改动时引入偏差。

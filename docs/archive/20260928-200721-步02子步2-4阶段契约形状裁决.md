# 步 02 · 子步 2-4「阶段契约最薄版」的形状裁决

> 2026-09-28 · 只读评审，未改任何代码。评审对象是规格里唯一设计未被钉死的子步，落点是最核心的 `core/convert.ts`，故先评审再实现。

## 二、五个候选形状的逐项裁决

| 形状 | 裁决 | 决定性理由 |
|---|---|---|
| 1 最薄字段（`ConvertContext` 加一个可选的变换设置字段） | **否决** | ① 它断言「这批设置影响渲染」—— 假（`convert()` 收到的是变换后正文，F2）；直接撞 `CODE-GUIDE.md` 「不造类型谎言」。② 它**自己就是第三个 mapper**：F4 两种措辞下 2-2 已占一个枚举点，再加这个字段就凑成三处，与本步退出条件自相矛盾。③ 步 04 的「按类别批量映射」会顺手把它接上，届时一个静默无效的字段变成事实上的假开关 |
| 2 反向契约（`convert()` 返回「变换已由谁完成」的标记） | **否决** | 返回标记的消费者数为 0（产物只被 main 落盘与测试断言），无人读 = 另一种类型谎言；且要动 `ConvertArtifact` 判别式联合，破坏面超出「1~2 文件」 |
| 3 阶段类型分离（渲染那份由变换那份类型派生） | **否决** | 「渲染那份由变换那份派生」在无消费方时是纯类型体操；且 `ConvertContext` 已有 30+ 字段，再拆一层派生类型要同步 3 处构造器（`context.ts`、`merge.ts`、测试 helper），与「最薄版」冲突 |
| 4 只加声明（core 导出 `export type PreprocessedMarkdown = string` 给形参加别名 + JSDoc 记阶段顺序） | **部分采纳** | 唯一不撒谎的形状：JSDoc 记阶段顺序是合法的「契约记录」。弱点是**注释不进任何工具面**，重命名/漂移无人拦。补法：给形参一个 core 导出的类型别名 —— 它**被签名使用**不是死声明，且因是 `string` 的别名而不断言任何强制力；日后要变品牌化，改声明点即可，调用点意图不变 |
| 5 让阶段成为 core 里的真模块 | **采纳** | 把「渲染前变换阶段」变成 core 里的真模块：新增 `core/markdown/preprocess-body.ts`，导出窄契约类型（`{ obsidian: ObsidianSettings; aiCleanup: Pick<AiCleanupSettings,"tidy"\|"rewrite"> }`，沿用 F5 的「总开关不进 core」惯例）+ 纯分派函数；`main/converter/preprocess.ts` 退化为 IO/frontmatter 薄壳。此时 `core/convert.ts` 的别名指向的是**真实存在的上游阶段**，JSDoc 里的名字有处可指 |

## 三、净收益对比

**降档为 JSDoc + 别名**
- 收益：阶段顺序在 `core/convert.ts` 有可 grep 的锚点；成本约 10 行；无行为变化。
- 代价：诊断里「加一个输出内容级能力要改 12~22 个源文件」那个数字**一点不会动** —— 那个收益其实已由 2-1（分组）+ 2-2（映射下沉）交付完毕，2-4 从来不在成本曲线上。

**做形状 5**
- 收益：① 「新增一个渲染前变换类设置」的枚举点**落在 core**，main 侧改动恒为 0，这才让 adr-024 后果行「持久化侧只改 `AppSettings` + 迁移 + core 的阶段契约」名副其实；② 退出条件「只被枚举 2 处」在**实质**上成立（分派 1 处 + 档位映射 1 处，`buildConvertContext` 仍不映射）。
- 代价：2 个文件；**与 adr-024 备选方案第 3 条冲突** —— 该条否决「把 `preprocessBody` 整体下沉 core」，理由写的是「要读文件、解码、收集 warning，依赖宿主能力」。**该理由描述的是 `prepareMarkdown`，不是 `preprocessBody`**（后者是纯函数、零 IO）。所以这是当初否决过宽，需按「推翻既有 ADR」流程出新文件或标注取代关系，不能默默做。

**做完之后下一个会踩的坑**（按可能性排序）
1. **同名双源**：core 有了 `preprocessBody` 之后，main 的旧同名函数若没删干净，两个 dispatcher 并存 → 总开关门控出现第二个实现点，直接破 adr-024 要点二。判据：删完后 `rg -n "preprocessBody" src/` 应只在 core 与一处薄调用点命中。
2. **门控被绕过**：未来若出现第二个调用方直接调 `cleanupMarkdown`（测试已经这么干：`preprocess.test.js`），就丢掉总开关。防线是入参类型不含 `enabled`（F5 惯例），并在 core 侧注释写明「本函数不含总开关判定」。
3. **枚举点悄悄变三处**：步 04 的批量映射时把变换类键组顺手接进 core context。防线是门禁而不是类型。

## 四、三个待答问题

**Q1：2-4 与 2-2 的顺序？**
**2-2 必须先做，且顺序有决定性。**
- 走形状 5：硬依赖。2-2 未落地时，core 的 dispatcher 要么 import main 的映射函数（反向依赖，违反单向），要么把映射表复制进 core（当场造出第三处枚举）。
- 走形状 1：**2-2 一落地就应否决形状 1**（枚举点从 2 变 3）；反过来若 2-4 先做，会做出一个随后必须删的字段。
- 一句话：**2-2 先做会自然淘汰形状 1；2-4 先做会制造返工。**

**Q2：值不值得做？**
按原样**不值得，建议降档**。判据（三条同时满足才做）：
1. **是否存在消费方？** 没有消费方的字段 = 类型谎言，直接否。
2. **它是否改变任何人下次改代码的动作？** 形状 1/2/3 的答案是「不改变」。形状 5 的答案是「改变」（新增枚举点在 core）。
3. **它是否可被工具强制？** 注释与别名不被任何门禁覆盖；能写成 `scripts/check-*.mjs` 断言的，才算真契约。

据此：**形状 1/2/3 否决；形状 5 做（先解 ADR 冲突）；若 ADR 冲突短期解不了，则只做形状 4 的最薄版并把退出条件改写成门禁。**

顺带修正一处前提：2-4 无论选哪个形状都碰不到步 03 的收益面（步 03 全在 `src/renderer/` + `settings-logic.ts`，依赖的是 `AppSettings` ↔ 控件声明的派生关系），所以「不能牺牲步 03」这条约束对本决策**不绑定**，不必为它让步。

**Q3：验收判据（可跑、可自检）**
1. `npm run typecheck` 与 `npm run lint` 通过，且新增告警数为 0。
2. `npm run test` 通过，**且 `test/` 下零文件改动**（`git status --porcelain -- test/` 输出为空）—— 这条比「行为等价」可自检：任何需要改测试来迁就的改动，都说明它不是行为等价。
3. `node scripts/check-import-boundary.mjs` 通过，且新文件**不在** `CORE_NODE_BUILTIN_FILES` 名单内（逐文件白名单语义）。
4. **把退出条件写成门禁并自证会红**。建议的门禁语义是**取反后的不变量**（比原条件更值钱）：
   - 渲染层（`src/core/convert.ts` + `src/core/docx/**` + `src/core/pdf/**`）出现 `aiCleanup` / `obsidian` 标识符 → 退出码非 0；
   - 变换类设置的枚举点恰好 2 处且都在 `src/core/markdown/**` → 计数漂移即红。
   写门禁时先注入一次故障演示它会红，再提交 —— 沿用步 01 的 1-1「护栏必须自证有效」。

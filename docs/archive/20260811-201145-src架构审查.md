## 总体评价

**架构骨架是健康的,问题集中在「契约重复」与「单体文件」两类。**

- **分层正确**:core/(纯逻辑、无 IO/Electron)→ main/(编排 + Electron)→ renderer/(UI),依赖方向单向,core/ 可独立测试与 CLI 复用,与项目 AGENTS.md 架构方向一致。
- **好的设计**:取消机制状态参数化(ConvertContext 随调用携带,根治 fd40480/f809c57 全局状态残留);convert.ts 格式注册表 + context 注入图片/警告,保持 core 纯净;settings.ts 手写校验 + 原子写,零依赖且防御充分。
- **刻意代价**:docx(remark→mdast→docx 库)与 pdf(markdown-it→HTML→printToPDF)双管线是 ROADMAP 定稿选型,代价是同一业务语义两套平行实现(题注识别、公式编号、交叉引用、HTML 白名单),目前靠注释互指 + 测试锁定一致性——这是最大的结构性风险源。
- **注释质量高**:踩坑实证(如 docx 书签 id 冲突、landscape 尺寸勿交换、KaTeX 字体等待)记录详尽,「勿回退」标注清晰。

## 高优先级

### H1. 内联 HTML 白名单逻辑逐字复制两份,双格式契约靠人工同步
- **文件**:src/core/docx/render.ts L1100-1136(ALLOWED_INLINE_TAGS + isAllowedInlineHtml)与 src/core/pdf/render.ts L270-306 逐字重复;另有 normalizeInlineHtml(docx L1219)与 matchAllowedHtmlExpression(pdf L314)是同一语义的第二套实现。注释自认「与 PDF 侧逐字一致,双格式契约,须同步修改」。
- **问题**:任何白名单变更(加标签/改校验)漏改一处即双格式行为漂移,且无编译期/测试期强制。
- **建议重构**:抽 src/core/html-whitelist.ts 单一实现(纯字符串逻辑,零依赖),docx/pdf 各自 import;normalizeInlineHtml 与 matchAllowedHtmlExpression 的差异(节点流合并 vs 源码扫描)保留在各自侧,但共享标签集与校验核心。
- **风险**:低——纯函数抽取,双格式测试已锁定行为。**收益**:消除漂移根因,后续加标签只改一处。

### H2. 契约类型与默认值三处重复(renderer / main / core)
- **文件**:TypographySettings/PageSetup 定义于 core/typography.ts、core/convert.ts,main 侧 settings.ts 引用 core,但 renderer.ts L74-116 又内联复制了一份,且 DEFAULT_SETTINGS(renderer L146 vs main L32)、校验范围常量(MARGIN_MIN/MAX、BODY_SIZE_MIN/MAX renderer L264-271 vs settings.ts L49-50)全部重复。注释要求「任一侧改动必须同步另一侧」。
- **问题**:这是可零成本消除的重复——TS import type 编译期擦除,renderer 直接 import type { TypographySettings } from "../core/typography.js" 完全不违反 contextIsolation;DEFAULT_SETTINGS 是纯数据,可下沉 core 共享。
- **建议重构**:renderer 类型全部改从 core import type;DEFAULT_SETTINGS 移到 core(如 core/settings-defaults.ts),main/renderer 共用。
- **风险**:低——纯类型与常量迁移,行为不变。**收益**:消除三处漂移,改字段不再需要三处同步。

### H3. docx 图片固定 400×300 渲染,非 4:3 图片被拉伸变形
- **文件**:src/core/docx/render.ts L1073-1077,imageToDocx 硬编码 transformation: { width: 400, height: 300 }。
- **问题**:所有图片(无论原始宽高比)都被强制 400×300,竖图/横图/方形图全部变形;且 sniffImageType 对 webp 等未知类型回退 "png"(pdf 侧 mimeFromBuffer 支持 webp,docx 侧不支持,双格式不一致)。
- **建议重构**:从 Buffer 解析 PNG/JPEG 尺寸(魔数后读 IHDR/SOF 字段,零依赖几十行),按原始宽高比缩放至最大宽度(如 400px 宽,高度按比例);webp 至少降级为占位文本 + 警告而非静默当 png 写入(Word 打开会破图)。
- **风险**:中——涉及产物视觉变化,需更新 docx 渲染测试断言。**收益**:修复真实可见的产物缺陷。

## 中优先级

### M1. merge.ts 图片绝对化正则无法处理含括号的 URL
- **文件**:src/core/merge.ts L24 IMAGE_RE = /!\[([^\]]*)\]\(([^)\s]+)(\s+["'][^"']*["'])?\)/g。
- **问题**:[^)\s]+ 遇 https://en.wikipedia.org/wiki/Foo_(bar).png 这类含 ) 的 src 会截断;引用式图片 ![alt][ref] 与 <img> 语法完全不处理(合并后相对路径失效)。合并模式是文本层正则替换,这是其固有脆弱点。
- **建议**:至少把 src 匹配改为支持括号配对的扫描(或先经 remark 解析再按 AST 重写,但改动大);引用式图片可记录为已知限制。
- **风险**:中(正则改动需回归 merge 测试)。**收益**:修复合并模式的真实边界 bug。

### M2. renderPdf 临时 HTML 文件名无随机后缀
- **文件**:src/main/converter.ts L224 m2w-${process.pid}-${Date.now()}.html;同文件 index.ts L78 的预览窗口已用随机后缀。
- **问题**:批量并发 2 时理论上有同毫秒竞争(写同一文件互相覆盖);且 renderPdf 的 finally 删除与预览的 closed 删除语义不一致。
- **建议**:与 preview 一致加 Math.random().toString(36).slice(2, 8)。一行修复。

### M3. currentCtx 全局变量:多窗口场景取消会串台
- **文件**:src/main/index.ts L36、L133、L147。
- **问题**:单窗口 OK,但未来多主窗口(或预览窗口触发转换)时,后启动的转换覆盖 currentCtx,先启动的转换取消按钮会取消错对象。
- **建议**:按 event.sender.id(webContents)建 Map 存 context,convert:cancel 按来源窗口取;或至少记录为已知限制。

### M4. settings:set 并发写存在丢更新竞态
- **文件**:src/main/settings.ts L134-140(saveSettings 在 await writeFile/rename 之后才更新 settingsCache)。
- **问题**:用户快速连续改两个设置项时,两个 IPC handler 并发:后启动的 handler 读到旧 cache,先完成的写回覆盖后完成的 cache 与文件 → 前一个改动丢失。窗口极小但真实存在。
- **建议**:写队列串行化(模块级 promise 链),或写前同步更新 cache(写盘失败再回滚)。

### M5. pushRuns 与 pushRunsSync 约 100 行重复
- **文件**:src/core/docx/render.ts L821-1022。
- **问题**:async 版(图片/脚注)与同步版(标题用,图片降级占位)是同一 switch 的复制,公式交叉引用逻辑双份维护。
- **建议**:统一为单一 async 版本(标题渲染也 await,标题内图片仍按现有降级语义处理),消除重复。行为不变,测试可锁定。

### M6. 三处图片警告收集职责重叠
- **文件**:core/convert.ts L63-89(collectMissingImageWarnings stat 预扫)、core/docx/render.ts L1053-1058、core/pdf/render.ts L698-734。
- **问题**:docx 链路对本地图片先 stat 再 readFile 两次 IO;警告文案三处不统一(「缺少图片文件」vs「外链图片下载失败」)。
- **建议**:把缺失检查并入 imageResolver 失败路径(单次 IO),文案统一;当前行为已被测试锁定,改动需同步测试。

### M7. extractHeadings 正则解析渲染后 HTML
- **文件**:src/core/pdf/render.ts L660-668。
- **问题**:/<h([1-3])[^>]*id="([^"]+)"[^>]*>(.*?)<\/h\1>/g 依赖渲染细节(属性顺序、无嵌套同标签),标题渲染规则变化时需同步;与 docx 侧 collectPlainText 语义(实体解码 vs 原文)不完全一致。
- **建议**:可接受(实测覆盖),但记录为技术债;若未来标题加 class/嵌套结构,优先改为在 markdown-it 渲染期收集(如 env 通道)而非事后正则。

### M8. resolverCache 与 HTTP 下载缓存无上限
- **文件**:src/main/converter.ts L60、src/main/image-downloader.ts L19-31。
- **问题**:按 baseDir 缓存 resolver,resolver 内 HTTP 图片缓存无大小上限;长期使用(大量不同目录 + 远程图片文档)内存累积。
- **建议**:当前可接受(键为路径),记录即可;若未来支持大量远程图,加 LRU。

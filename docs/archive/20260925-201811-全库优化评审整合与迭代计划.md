## 1. 执行摘要

### 1.1 总体判断

- 六份报告共约 **126 个原始编号条目**（含问题、建议、低优先项和观察），规范化后约 **90 个主题**，其中约 55–60 个可进入候选问题池；不能把 126 直接当成 126 个独立缺陷。
- 当前没有已证实的 Critical 级任意代码执行或稳定大规模数据破坏问题。窗口隔离、CSP、HTML 白名单、Mermaid strict、临时 HTML 独占创建、SSRF 基础防护、70 段测试、smoke、coverage 等基线总体可靠。
- 最需要优先建立的不是新功能，而是四个不变量：
  1. **同一时间同一 renderer 只有一个用户操作**；
  2. **可选预处理不能静默改写用户内容**；
  3. **持久化与最终产物不能因竞态丢失、覆盖或留下半成品**；
  4. **取消、资源预算、失败和降级必须有明确且可测试的语义**。
- docx/pdf 双管线保持独立；应统一输入准备、设置、预算、错误和共同语义测试，不合并 remark 与 markdown-it。
- 任何 Node floor、预设作用域、本地图片信任边界、代码签名和视觉基线都不能由评审代理自行拍板，必须进入决策记录并取得用户确认。

### 1.2 整合后的优先级定义

| 优先级 | 含义 | 处理原则 |
|---|---|---|
| P0 | 可能破坏数据/安全/发布契约，或高概率造成用户操作错误 | 先建立不变量、测试安全网和发布门禁，再做结构优化 |
| P1 | 已证实的功能回归、生命周期竞态、可访问性或持续性架构问题 | P0 契约稳定后分批处理 |
| P2 | 可维护性、测试工程、性能、可选体验和工程化增强 | 不扩大高成本自动化面，按价值进入 backlog |
| P3 | 低风险、局部、条件性或可选提升 | 有明确价值时再做 |
| N | 推测、待实测、已登记限制或明确不做 | 保留事实，不直接创建实现任务 |
| F | 已验证的良好基线 | 作为回归守护，禁止整改误伤 |

## 2. 证据、冲突与状态规则

### 2.1 证据等级

1. **已证实**：当前源代码控制流、已有测试或可重复只读探针直接支持。
2. **条件性**：需要特定输入、时序、平台或产品配置。
3. **推测**：尚未实测，不能写成已确认漏洞。
4. **建议增强**：不是当前行为缺陷。
5. **正向事实**：已经做对、必须保留的行为。
6. **已登记限制/明确不做**：引用 `BACKLOG.md`，不重复包装成新需求。

### 2.2 冲突裁决顺序

1. 当前源代码和可重复运行结果；
2. 项目 `AGENTS.md` 硬约束；
3. 当前 `ADR.md`；
4. 当前 `STATUS.md`、`ROADMAP.md`、`BACKLOG.md`；
5. 本轮六份原始评审；
6. 更早的 archive 快照。

旧报告已修正的结论不得重新升级。例如 fixture drift 已经进入 CI、acceptance 已隔离 userData、测试 JS 已纳入 ESLint、`start`/`smoke` 已有 freshness 守卫。

## 6. 分阶段代码优化迭代计划

> 每个阶段拆为独立可回退提交；代码、测试、必要配置和文档同批。实施前读取 `CODE-GUIDE.md`；命令/文件占用/构建异常时读取 `WINDOWS-GUIDE.md`。不使用 `reset --hard` 或改写历史。

### 阶段 0：整合登记、决策冻结与最小发布护栏（P0）

**目标**：建立 issue register、决策记录、测试矩阵和 CI/Release 共用入口，不先改核心行为。

## 一、已证实的缺口

### 1. 高：Release 门禁与 CI 门禁不一致

**证据**

- CI 执行：
  - `npm run build && npm run typecheck && npm run lint`：`.github/workflows/ci.yml:35-37`
  - `npm run test:coverage`：`.github/workflows/ci.yml:39-42`
  - `npm run check:fixtures`：`.github/workflows/ci.yml:44-47`
  - `npm run test:smoke`：`.github/workflows/ci.yml:49-51`
- Release 只执行：
  - build/typecheck/lint：`.github/workflows/release.yml:53-55`
  - `npm run test`：`.github/workflows/release.yml:57-58`
  - 打包：`.github/workflows/release.yml:60-64`
- Release 没有 smoke、coverage、fixture drift、视觉门禁。

**影响**

tag 可以绕过 CI 主门禁，直接进入发布构建。若 tag 对应提交未经过 smoke/coverage/fixture 校验，发布资产可能仍能产出。

**优化方向**

- 将 release 复用同一个完整验证脚本，而不是复制部分命令。
- 建议单一入口 `verify:release` 至少串联：
  `build → typecheck → lint → test:coverage → check:fixtures → test:smoke → dist`。
- 如果 `dist` 必须在验证之后执行，应在脚本和 workflow 中保持同一顺序。
- 将 release 与 CI 的 Node 版本、依赖安装源、门禁命令抽取为统一配置或复用 workflow。

**验证方式**

- 在临时分支制造一个“`check:fixtures` 失败但 acceptance 通过”的提交，确认 release job 也会失败。
- 对 tag `v*` 触发完整流程，确认每个门禁均有独立 job/step 记录。
- 对比 CI 与 release 实际执行命令清单。

**验证方式**

- 在未标注测试中故意引入类型错误，确认当前门禁行为。
- 临时加入一个错误 `run` 导出或错误 dist import，验证 typecheck 能捕获。
- 对所有测试运行 `tsc -p tsconfig.test.json --checkJs` 对比渐进门禁。

### 6. 中：runner 是段级串行框架，失败定位粒度粗，超时后仍可能有后台副作用

**证据**

- `test/common/runner.js:36-43` 只要求每段导出 `run()`，错误以异常汇总。
- `test/common/runner.js:78-111` 所有段串行执行。

- `test/acceptance.mjs:73-90` 超时或失败后最终硬退出。

**影响**

- 一个悬挂段可能在后续段运行期间继续写文件、占用 BrowserWindow 或修改模块缓存。

**优化方向**

- 段内采用结构化测试用例和统一 assertion helper，至少输出：
  - suite/test case 名；
  - 期望值；
  - 实际值；
  - 差异摘要。
- 为每段提供 `setup/afterEach/finally` 生命周期。
- 对需要真实 Electron 的段增加段级资源清理注册。
- 对超时段增加“超时后资源状态”诊断。
- 若未来改为子进程隔离，应为每段定义超时、退出码和产物传递契约；当前项目已将该项列为“不做”，可作为已知限制持续监控。

**验证方式**

- 制造一个段超时且持有 BrowserWindow/文件句柄的探针。
- 观察后续段是否受到污染、是否产生未处理 rejection 或 EBUSY。
- 制造一个段内多个断言依次失败的样例，检查报告是否能定位到具体 case。
- 检查 `finally` 是否覆盖每个测试段的失败路径。

### 9. 中：构建新鲜度守卫是 mtime 启发式，不能保证 dist 完整性

**证据**

- `scripts/check-build-fresh.mjs:15-42` 只计算目录内最大 mtime。
- `scripts/check-build-fresh.mjs:48-58` 只判断 dist 是否为空以及 src 最大 mtime 是否更新。
- `scripts/check-build-fresh.mjs:20-31` 对目录不存在/stat 失败静默忽略。
- `package.json:39,43` 中 `start`、`test:smoke` 使用该守卫。
- `package.json:40` 的 `test` 直接重新 build，因此 acceptance 主链有新鲜度保证。

**影响**

以下情况可能被错误判定为“新鲜”：

- 删除 src 文件但 dist 残留旧文件；
- dist 只生成了部分文件；
- 编译中途失败但已有旧 dist；
- mtime 被恢复、复制或版本控制操作改变；
- 静态资源复制遗漏而 TS 文件时间未变化。

**优化方向**

- 使用构建 manifest/hash，而不是单纯最大 mtime。
- 至少校验关键 dist 文件集合：入口、renderer 静态文件、preload、smoke 所需服务。
- build 成功时写 manifest；`start/test:smoke` 校验 manifest 与当前源文件集合/哈希一致。
- 失败时不静默跳过 stat；对关键目录缺失直接失败。

**验证方式**

- 删除一个 src 文件但不 build，验证守卫失败。
- 删除一个 dist 关键文件，验证守卫失败。
- 修改 renderer 静态资源但不重新 build，验证失败。
- 模拟 `statSync` 抛错，验证错误不会被静默吞掉。
- 校验 `npm test` 与 `npm start` 的新鲜度语义是否一致。

## 二、建议增强（不是已证实缺陷）

### A. 统一断言框架和结构化测试报告

当前测试大量使用本地 `assert`、`throw new Error`，例如：

- `test/renderer/settings-logic.test.js:47-48`
- `test/main/converter.test.js:39-40`
- `test/segments/` 多个段均采用手写异常。

优点是依赖少、错误信息直接；缺点是没有统一 diff、断言计数、case 级报告和标准生命周期。可考虑：

- 保持现有零注册 runner；
- 引入轻量 assertion helper，不强制迁移全部测试；
- 支持 `assert.equal/deepEqual/match/rejects/throws`；
- 每个场景输出 case 名和期望/实际值；
- 最后输出断言数、失败数、跳过数。

不建议仅为迁移框架而破坏现有 Electron 运行模型。

### B. 将 smoke 从“诊断设施”提升为稳定发布契约

`test/tools/smoke/smoke.mjs:87-120` 具备真实链路，但文件注释定位为“开发诊断设施”，且部分设置写入依赖保存/恢复。

建议增加：

- smoke 启动前后的用户数据目录快照；
- 所有设置/UI 状态变更均使用统一 `try/finally`；
- 产物清单和 magic number、页数、书签结构均固定输出；
- 将 smoke 结果写入机器可读 JSON，供 CI artifact 上传。

### C. 对失败路径和资源清理建立统一审计

目前部分测试通过手工 `backupSettings`/恢复：

- `test/common/settings.js`
- `test/main/converter.test.js`
- `test/main/settings.test.js`
- `test/main/i18n.test.js`

建议统一：

- `withTemporarySettings`
- `withTemporaryUiState`
- `withTemporaryOutputDir`
- `withElectronWindow`

所有临时资源均登记并在 `finally` 清理。验证应覆盖：

- 断言失败；
- 转换抛错；
- PDF 生成失败；
- 用户取消；
- 进程异常退出前可清理的文件。

### D. 为 CI 增加可重复性和环境指纹

当前 CI 只显示 Windows runner + Node 版本，未形成完整环境指纹。建议记录：

- OS build；
- Electron/Chromium 版本；
- Node 版本；
- npm 版本；
- 字体列表/默认字体；
- DPI/缩放；
- Git SHA；
- 依赖 lockfile hash。

这些信息对 Electron、PDF、Mermaid、截图和中文字体测试的复现尤其重要。

### E. 为 package scripts 增加静态契约测试

建议自动检查：

- `package.json` 中每个脚本引用的文件存在；
- CI workflow 调用的 npm scripts 均存在；
- README/DEV-GUIDE 中记录的命令仍存在；
- `test:all`、`verify:ci`、`verify:release` 的包含关系符合文档；
- 关键依赖确实被 runtime/build/test 代码引用。

### F. 增加发布产物的可安装/可启动验证

`package.json:48` 的 `dist` 只负责构建 NSIS。建议发布门禁增加：

- `--dir` unpacked 构建；
- 检查 asar 内文件清单；
- 启动 unpacked 应用并确认主窗口存活；
- 在隔离环境执行安装、启动、卸载；
- 校验版本、latest.yml、安装包文件名和 package.json 一致。

这属于发布工程增强，当前 release workflow 尚未覆盖。

### G. 增加依赖与安全门禁

## 1. Node 支持边界自相矛盾，发布流水线实际运行在依赖不支持的 Node 20

### 仓库证据

- 项目声明 Node `>=20.19`：  
  `package.json:31-33`
- Release 使用 `node-version: 20`：  
  `.github/workflows/release.yml:44-47`

- Electron 43.2.0 明确要求 Node `>=22.12.0`：  
  `package-lock.json:4314-4331`
- Electron 间接依赖 `@electron/get@5.1.0` 同样要求 Node `>=22.12.0`：  
  `package-lock.json:170-188`
- 三个 `@mdit/plugin` 都明确要求 Node `>=22`：
  - `package-lock.json:1286-1299`
  - `package-lock.json:1301-1317`
  - `package-lock.json:1324-1337`

### 已验证影响

这不是“应用运行时 Node 版本”问题：Electron 主进程使用的是 Electron 内置 Node，开发依赖和打包工具使用的是宿主 Node。Electron 官方明确区分宿主 Node 与 Electron 内置 Node：

- 官方前置条件文档：  
  https://www.electronjs.org/docs/latest/tutorial/tutorial-1-prerequisites
- 官方版本与 Node 支持策略：  
  https://www.electronjs.org/docs/latest/tutorial/electron-timelines

当前可能出现：

- `npm ci` 在 Node 20 下产生 `EBADENGINE` 警告；
- 安装脚本、Electron 下载器或未来 npm 严格 engine 行为变化后，发版直接失败；
- 本地“支持 Node 20.19”的声明没有依赖层依据；
- CI 所谓的“地板验证”验证的是**未经上游声明支持的组合**。

### 优化方向

这需要主会话先处理项目契约冲突，不能静默选择：

1. **保持当前 Electron 43 和当前 `@mdit/plugin-*` 不回退**，将开发/构建 Node 下限统一提升到上游共同要求的 `>=22.12.0`；这会修改项目当前“Node >=20.19，勿回退”的硬约束表述，需负责人明确批准。
2. CI、Release、本地文档统一使用同一个明确 Node 版本。
3. 不建议通过回退 Electron 或 `@mdit/plugin-*` 解决，因为这会违反项目既定技术路线；也不建议建议 markdown-it 15 回退/升级。

### 验证方式

- 在 Node 22.12.0 和当前声明地板 Node 20.19 分别执行 `npm ci`，保存完整 `EBADENGINE` 输出。
- `node -p "require('./node_modules/electron/package.json').engines.node"`
- 对三个 `@mdit/plugin-*` 执行同类 engine 检查。
- CI 增加显式 `node --version && npm --version && npm config get engine-strict`。
- Electron 启动后记录 `process.versions.electron/node/chrome`，避免和宿主 Node 混淆。

## 2. Windows 安装包未配置代码签名，发布可能静默产出未签名程序

### 仓库证据

- Builder 只配置 NSIS、x64、语言及安装目录，没有证书、`sign` 或 `forceCodeSigning`：  
  `package.json:61-79`
- Release 直接执行 `npm run dist` 并上传 EXE：  
  `.github/workflows/release.yml:60-64`、`.github/workflows/release.yml:89-96`
- 脚本没有签名后的验签步骤：  
  `package.json:48`

### 官方依据

electron-builder 官方 Windows 签名文档说明，配置签名方法或凭证后，builder 会签名可执行文件和安装程序，以便 SmartScreen 和自动更新验证发布者及文件完整性：

https://www.electron.build/code-signing-win

官方源码同时表明：

- 未设置 `forceCodeSigning` 时默认是 `false`；
- 没有签名且未强制签名时，构建可以成功完成。

因此当前配置存在“发版成功，但产物未签名”的可能。

### 影响

- Windows SmartScreen 警告概率增大；
- 用户难以验证发布者及下载后文件是否被篡改；
- 企业环境可能直接阻止安装；
- 后续若引入自动更新，更新链路也依赖发布者身份和包完整性。

### 优化方向

- 配置受控的 Windows 代码签名证书，并通过 CI secret/受限环境变量传入。
- 设置 `forceCodeSigning: true`，确保无证书时发版失败，而不是产出未签名包。
- 打包后执行 `Get-AuthenticodeSignature`，确认 `Status` 为 `Valid`、签名者符合预期。
- latest.yml/安装包上传前保存 SHA-256。

### 验证方式

```powershell
Get-AuthenticodeSignature .\release\MarkdownToWord-Setup-3.12.0.exe |
  Format-List Status,StatusMessage,SignerCertificate
```

同时在无证书的测试 job 中确认 builder 会 fail closed。

## 3. 构建未清理 `dist`，删除/重命名 TS 源文件可能把陈旧产物打入安装包

### 仓库证据

- `build` 仅为 `tsc && node scripts/copy-renderer.mjs`：  
  `package.json:35-39`
- TypeScript 输出到共享 `dist` 目录并开启增量：  
  `tsconfig.json:15-19`
- 拷贝脚本只清理 `dist` 中的 HTML/CSS 和两个显式脚本，不清理陈旧 `.js/.js.map`：  
  `scripts/copy-renderer.mjs:27-39`、`scripts/copy-renderer.mjs:42-63`
- Builder 打包整个 `dist/**`：  
  `package.json:56-60`

### 影响

若某个 `.ts` 文件被删除或重命名，`tsc` 通常不会自动删除其旧 `.js/.js.map`。旧 JS 会继续留在 `dist`，并可能：

- 被 `dist/main/index.js` 的残留导入链加载；
- 被 Builder 无意收入 ASAR；
- 掩盖模块删除、入口迁移或重构错误；
- 导致本地、CI 和干净工作区构建结果不同。

这是实际可重复性风险，不只是理论上的体积问题。

### 优化方向

- 每次正式 build 从空 `dist` 开始；
- 增量 `.tsbuildinfo` 也应与干净构建基线隔离，或在删除源文件时确保不会掩盖陈旧输出；
- 增加“干净工作区构建”和“脏工作区构建”的产物文件清单对比；
- 打包前对 ASAR 内容建立 manifest，禁止出现无对应源入口的陈旧模块。

### 验证方式

由主会话在临时副本中：

1. 构建一次；
2. 删除或重命名一个不再被引用的 TS 文件；
3. 不清理 `dist` 再构建；
4. 比较两次 ASAR 文件清单和主入口可达模块；
5. 验证干净构建与增量构建的 manifest 是否一致。

### 官方依据

KaTeX 官方安全文档说明：

- `maxSize`：限制用户指定尺寸，防视觉布局攻击；
- `maxExpand`：限制宏展开，防无限循环；

- https://katex.org/docs/options.html

### 影响

- 主进程长时间占用 CPU；
- 转换 IPC 卡住；
- 超大 MathML/HTML 输出；
- 内存压力或界面无响应。

### 优化方向

- 在两条公式路径统一传递有限制的 KaTeX options：
  - 明确 `trust: false` 或严格回调；
  - 设置合理 `maxExpand`；
  - 设置合理 `maxSize`；
  - 保持现有 `throwOnError:false` 降级语义。
- 转换入口另外限制 Markdown 文件大小和公式节点长度。
- 避免只依赖 15 秒 Mermaid timeout；KaTeX 是同步在主进程执行，超时包装无法中断已卡住的同步计算。

### 验证方式

加入恶意/压力 fixture：

- 深度宏递归；
- 极大尺寸/空间；
- 大量公式；
- `\href`、`\includegraphics`、`\htmlClass`；
- 未闭合命令。

**类别**：[功能缺陷] [硬性规范]

**现状 / 影响**

`#dropZone` 同时是 `role="button"`、`tabindex="0"`，并在祖先上监听 Enter/Space；内部又包含选择、粘贴、向导、预览、追加、清空、引导按钮和大量表单控件。处理函数没有判断事件目标是否来自当前元素，也没有统一阻止内部按钮的 `keydown` 冒泡，只有部分入口停止 `click`。

具体影响：

- 在“粘贴转换”“成书向导”“预览”“清空”等内部按钮上按 Enter/Space，事件会先被祖先识别为“打开拖放区”，并 `preventDefault()`，导致原按钮动作被取消或走错动作。
- 首启引导按钮只处理自身 `click`，没有阻止冒泡：

  - 点击“知道了”会关闭引导，又打开文件选择框。
- `role="button"` 内嵌 radio、select、button，对屏幕阅读器形成非法或高度误导的交互树。

这不是单一无障碍瑕疵，而是核心空态操作和首启路径的鼠标、键盘双重故障。

**优化方向**

优先取消整个舞台的按钮角色，把舞台改为 `role="region"` 或普通容器：

- 文件选择通过明确的“选择文件”按钮完成；
- 舞台空白区域如仍需点击打开选择器，使用不包裹交互控件的独立背景层；
- 至少应让祖先 `keydown` 只在 `event.target === dropZone` 时响应；
- 所有内部交互控件统一阻止会触发祖先语义的 Enter/Space/click 冒泡。

**验证方式**

- 在 640×560 与常规窗口逐个用鼠标、Enter、Space 操作：选择、粘贴、向导、首启三步、预览、追加、清空。
- 检查任一内部控件操作时只发生一个动作、一个系统对话框。
- 用 Accessibility Tree 确认舞台不再显示为包含交互后代的单一 Button。

# High

## H1. 同一 renderer 可并发发起转换，context 注册会互相覆盖

**状态：已证实**

### 证据

- `src/renderer/convert/convert-flow.ts:34-53` 的 `withPrecheck()` 没有 `prechecking` 或 in-flight 锁。
- `src/renderer/convert/events/convert-actions.ts:23-41` 可从按钮重复触发。
- `src/main/ipc/register.ts:68-84` 以 `senderId` 为唯一键执行：
  - `ctxByWebContents.set(senderId, ctx)`
  - finally 中无条件 `delete(senderId)`
- `src/main/ipc/logic.ts:52-66` 的 `runConvertTask()` 无条件注销 context。
- `src/main/windows/web-contents-registry.ts:12-16` 是单值 `Map<number, ConvertContext>`，不是操作集合。

### 影响

并发转换时可能出现：

1. 第二次 context 覆盖第一次；
2. 第一次 finally 把第二次 context 删除；
3. `convert:cancel` 找不到真正运行中的 context；
4. 主窗口关闭确认误判，可能直接销毁正在写的窗口；
5. 两个 renderer 流程同时修改同一个 `state.mode`；
6. 预检弹窗的单一 `precheckResolve` 被第二次调用覆盖，第一次 Promise 永远不结束。

### 优化方向

在 **main 进程建立权威 single-flight 约束**，不要只依赖 renderer 按钮禁用：

- 每个 `webContents.id` 只允许一个活动操作；
- 第二次请求明确返回 busy，或进入受控队列；
- context 注销使用 compare-and-delete：只有当前注册的 context 才能删除；
- renderer 增加 `prechecking` 状态，预检期间禁止新的转换命令；
- 预检弹窗使用单实例 Promise 管理。

### 验证

- 在 DevTools 中不等待第一次 `window.api.convert()`，立即发起第二次；
- 快速双击转换按钮、连续按 `Ctrl+Enter`；
- 预检弹窗打开时再次触发转换；
- 观察：
  - 最大活动转换数是否为 1；
  - cancel 是否只取消当前操作；
  - 关闭主窗口是否始终正确弹确认；
  - 第一个预检 Promise 是否必然结算。

## H6. 路径递归和批量输入没有可靠资源上限

**状态：已证实的结构性风险；具体 DoS 影响需构造输入**

### 证据

- `src/main/converter/paths.ts:80-114` 使用 `path.resolve()` 作为 `seen` key；
- `fs.stat()` 会跟随 symlink/junction；
- 因此 lexical path 去重不能阻止指向祖先目录的循环；
- 没有深度、条目数或总字节数上限。
- `src/main/converter/merge.ts:62-67` 对所有输入文件 `Promise.all()`，一次性读入内存。
- `src/main/ipc/register.ts:226-237,271-301` 只校验数组元素类型，不校验文件数量和大小。
- `src/core/pdf/postprocess.ts:83-110` 的本地图片检查也是无界 `Promise.all()`。

### 影响

- junction/symlink 目录可导致无限递归；
- 选择大目录可能长时间占用主进程；
- 恶意或误选的大批量文件可能导致内存暴涨；
- 大量本地图片可产生大量并发 IO；
- 合并转换没有总资源预算。

### 优化方向

- 明确 symlink 策略：
  - 默认跳过 symlink/junction；或
  - `realpath` 后做 visited，并加深度/条目上限；
- handler 层限制文件数量；
- 转换前限制单文件字节数；
- 合并采用有界 worker；
- 图片检查使用有界并发；
- 对整份文档增加总图片数/总字节预算。

### 验证

- 创建指向祖先目录的 junction；
- 选择包含大量文件的目录；
- 传入数千路径；
- 使用超大 Markdown；
- 观察 CPU、内存、IO 和 UI 是否仍可响应。

**验证：**

**影响**

## 1. [高] PDF 外链图片下载缺少超时、大小上限和取消能力

**证据**

- `src/core/pdf/postprocess.ts:135-157`
  - 收集所有外链图片 URL；
  - `worker()` 对每个 URL 直接 `await resolver(url)`；
  - 仅通过 `EXTERNAL_IMAGE_CONCURRENCY = 3` 限制并发；
  - 没有任何超时、AbortSignal、响应体大小上限或取消检查。
- `src/core/image/image-resolver.ts:7-12`
  - `ImageResolver` 契约只有 `Promise<Buffer | null>` 和可选 `exists`，没有超时、取消、输入长度或输出大小约束。
- `src/core/convert.ts:114-185`
  - `convert()` 没有取消参数，也没有渲染预算。

**触发条件**

Markdown 中包含大量外链图片，或单张 URL 指向长期不响应的服务器。Electron 主进程中的 resolver 若采用网络请求，单个请求即可让整个 `renderPdfHtml()` 长时间不返回；取消操作也只能在外层放弃等待，不能停止底层下载。

恶意输入还可以用大量不同 URL 造成 resolver 长时间占用；即使最终 base64 成功，内存峰值也可能远大于 Markdown 源文件。

**影响**

- GUI 转换无法及时响应关闭/取消。
- 网络资源、内存和事件循环被恶意或异常文档长期占用。
- 失败后仍可能继续处理后续 Mermaid/KaTeX/模板阶段。

**优化方向**

将 resolver 契约扩展为显式预算：

- `AbortSignal`；
- 单 URL 超时；
- 单图片最大字节数；
- 文档总图片数/总字节数预算；
- 超时和超限区分错误码并进入 warning；
- 在每个异步边界和 worker 循环中检查取消。

**建议验证**

1. 注入永不 resolve 的 resolver，验证取消能在规定时间内结束。
2. resolver 返回超大 Buffer，验证在超过上限时中止且不进入 base64。
3. 生成数千个不同外链 URL，验证并发数、总量和内存均有上限。
4. 验证部分图片超时后其余图片仍按既定降级策略完成。

**置信度：高。**

## 9. [低中] 共享 HTML 白名单仍保留两套扫描实现，存在边界漂移风险

**证据**

- `src/core/markdown/html-whitelist.ts:1-8` 明确声明 PDF 与 DOCX 各自维护扫描器，修改需人工同步。
- PDF 扫描器：`src/core/pdf/rules/html.ts:18-51`。
- 共享判定器：`src/core/markdown/html-whitelist.ts:24-55`。

**触发条件**

新增/修改以下边界之一：

- `<br>` 与 `<br/>`；
- 大小写标签；
- 标签间空白；
- 文本中的 `<`；
- 嵌套白名单标签；
- 注释和分页符。

**影响**

**优化方向**

将表达式扫描抽成共享 tokenizer/parser，PDF 和 DOCX 只负责从不同输入形态调用；或者至少用同一组 fixture 对两侧进行 property/differential testing。

**建议验证**

- 同一 HTML 字符串分别走 `convert(..., "docx")` 和 `convert(..., "pdf")`；
- 对标签大小写、空白、自闭合、嵌套、文本 `<`、未闭合、属性、注释生成组合；
- 断言 HTML 是否被渲染/转义/跳过两侧一致。

**置信度：中高。**

## 10. [低中] PDF 与 DOCX 对页码、目录和分页的行为不是同一语义

**证据**

- `src/core/convert.ts:6-18` 明确承认两条管线有多个有意差异：
  - docx 静态目录/Word 域目录；
  - PDF 目录通过 HTML 锚点；
  - 公式、脚注、Mermaid 表现不同。
- `src/core/pdf/render.ts:230-235`
  - PDF 先拼封面、目录、正文，再做外部图片处理。
- `src/core/docx/render.ts:174-185`
  - DOCX 先预扫再生成封面/目录。
- `src/core/pdf/postprocess.ts:53-67`
  - PDF 页码需要主进程两遍打印后从 PDF 目标解析并回填。
- `src/core/docx/render.ts:89-92`
  - DOCX 的目录模式由 `tocMode` 区分 static/field。

**触发条件**

开启 PDF 两遍页码模式、封面/目录同时开启、标题跨页、目录本身有分页、正文包含连续显式分页符。

**影响**

同一 Markdown 的两种输出可能在：

- 目录页是否占页；
- 目录项是否带页码；
- 目录项顺序；
- 分页符造成的空白页；
- 标题页眉/封面行为

上出现差异。部分差异可能是产品有意设计，但目前主要由注释和测试隐式维护。

**优化方向**

建立跨格式“语义差异矩阵”：

- 明确哪些是格式必需差异；
- 哪些是产品要求一致；
- 将共同行为抽成纯函数/契约测试；
- 对连续分页、封面+目录、标题跨页建立双格式 smoke fixture。

**建议验证**

- 同一 fixture 分别输出 docx/pdf；
- 对页数、目录条目、标题编号、题注编号、公式编号、脚注、显式分页符做对照；
- 将“允许差异”显式写入断言，而不是依赖人工观察。

**置信度：高（存在差异已由代码注释确认；具体产品影响需主会话结合验收定义确认）。**

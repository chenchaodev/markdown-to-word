# 只读整体架构与工程质量评审结论

## 总结

- **未发现已证实的 Critical 级问题**：当前 Electron 窗口普遍启用 `contextIsolation`、`sandbox`、`nodeIntegration=false`，预览/打印 HTML 有 CSP，外链和 shell 调用已有边界控制。
- 主要风险集中在：
  1. **同一渲染进程缺少 single-flight 操作闸门**；
  2. **可选预处理会静默破坏用户内容**；
  3. **持久化与输出文件不是原子更新**；
  4. **取消、资源预算、预览刷新和设置副作用的状态契约不完整**；
  5. **core/main/renderer 的边界约定没有被代码结构强制执行**。
- 当前 70 段测试、smoke、coverage 全绿，说明正常路径质量较好；但没有覆盖本次发现的主要竞态、恶意输入和失败生命周期路径。
- 标记：
  - **已证实**：源码路径明确，且已有只读探针或直接控制流可证明。
  - **条件性风险**：需要特定输入、时序或环境。
  - **推测**：尚未实测，不应按已确认漏洞处理。

## H1. 同一 renderer 可并发发起转换，context 注册会互相覆盖

**状态：已证实**

### 证据

- `src/renderer/convert/convert-flow.ts:34-53` 的 `withPrecheck()` 没有 `prechecking` 或 in-flight 锁。
- `src/renderer/convert/events/convert-actions.ts:23-41` 可从按钮重复触发。
- `src/main/ipc/register.ts:68-84` 以 `senderId` 为唯一键执行：
  - `ctxByWebContents.set(senderId, ctx)`
  - finally 中无条件 `delete(senderId)`
- `src/main/ipc/logic.ts:52-66` 的 `runConvertTask()` 无条件注销 context。
- `src/main/windows/web-contents-registry.ts:12-16` 是单值 `Map<number, ConvertContext>`，不是操作集合。

### 影响

并发转换时可能出现：

1. 第二次 context 覆盖第一次；
2. 第一次 finally 把第二次 context 删除；
3. `convert:cancel` 找不到真正运行中的 context；
4. 主窗口关闭确认误判，可能直接销毁正在写的窗口；
5. 两个 renderer 流程同时修改同一个 `state.mode`；
6. 预检弹窗的单一 `precheckResolve` 被第二次调用覆盖，第一次 Promise 永远不结束。

### 优化方向

在 **main 进程建立权威 single-flight 约束**，不要只依赖 renderer 按钮禁用：

- 每个 `webContents.id` 只允许一个活动操作；
- 第二次请求明确返回 busy，或进入受控队列；
- context 注销使用 compare-and-delete：只有当前注册的 context 才能删除；
- renderer 增加 `prechecking` 状态，预检期间禁止新的转换命令；
- 预检弹窗使用单实例 Promise 管理。

### 验证

- 在 DevTools 中不等待第一次 `window.api.convert()`，立即发起第二次；
- 快速双击转换按钮、连续按 `Ctrl+Enter`；
- 预检弹窗打开时再次触发转换；
- 观察：
  - 最大活动转换数是否为 1；
  - cancel 是否只取消当前操作；
  - 关闭主窗口是否始终正确弹确认；
  - 第一个预检 Promise 是否必然结算。

## H2. AI/Obsidian 预处理会静默破坏 Markdown 内容

**状态：已证实；影响由用户是否启用对应设置决定**

### 证据

#### AI 清理

- `src/core/markdown/ai-cleanup.ts:19` 的 frontmatter 正则只识别 `\n`。
- `src/core/pipeline/frontmatter.ts:23-25` 的正式解析器支持 CRLF。
- `cleanupBody()` 在 `ai-cleanup.ts:38-83` 会先统一换行，再对 `---` 执行列表标记修复。
- 只读探针已确认：CRLF frontmatter 会被破坏为类似 `- --` 的内容，导致 frontmatter 不再被识别。

#### Obsidian 兼容

- `src/core/markdown/obsidian.ts:23-29` 使用全局正则直接替换 `[[...]]`；
- 没有跳过 fenced code，也没有跳过 inline code；
- 只读探针已确认：代码块中的 `[[...]]` 会被改写。

### 影响

用户启用 `aiCleanup` 或 `obsidianCompat` 后，可能出现：

- frontmatter 丢失；
- 代码示例、JSON、模板字符串被改写；
- 代码中的 Obsidian 链接变成普通 Markdown 链接；
- 预览与最终导出结果不一致；
- 用户没有收到错误，只得到静默的内容变化。

### 优化方向

- 不要再用全局正则扫描所有 Markdown；
- 至少建立统一的代码区保护层：fenced code、inline code、HTML code；
- frontmatter 应复用正式解析器的边界规则，而不是维护另一套 LF-only 正则；
- 更稳妥的方案是采用 tokenizer/AST 位置感知的转换；
- 明确哪些字符序列是语法，哪些只是代码内容。

### 验证

新增并锁定以下 fixture：

- LF、CRLF、单独 `\r` 的 frontmatter；
- 普通文档以 `---` thematic break 开头；
- fenced code、inline code、未闭合 fence；
- `[[link]]` 出现在代码、HTML、escaped 文本中；
- docx、PDF、预览三条链路使用相同输入；
- 开关关闭时必须字节级保持原文。

## H5. settings/ui-state 的写队列只串行写字节，不串行读改写

**状态：已证实**

### 证据

- `src/main/persist/settings.ts:212-215`：
  - 先 `loadSettings()`；
  - 在队列外计算完整 `next`；
  - 再 `saveSettings(next)`。
- `src/main/persist/ui-state.ts:197-245` 同样先读缓存、构造完整 next，再入写队列。
- `src/main/persist/atomic-json.ts:23-31` 只保证 write+rename 不交错。
- `src/renderer/convert/file-list.ts:28-43,89-99` 一次选择变化会重复触发 session 持久化。

现有并发测试 `test/main/settings.test.js:307-326` 只断言最终状态等于最后一个返回值，没有断言所有 patch 的字段都被合并，因此可能在丢字段时仍然通过。

### 影响

典型丢失场景：

1. 批量转换写入 `recentFiles`；
2. 同时主窗口关闭写入 `windowBounds`；
3. 同时预览窗口关闭写入 `previewWindowBounds`；
4. 三者都从同一份旧缓存生成完整 next；
5. 后写入者把前写入者的字段覆盖掉。

同类问题会导致：

- 最近文件丢失；
- 窗口位置/最大化状态丢失；
- 会话文件列表丢失；
- 设置修改丢失；
- renderer 显示“即时自动保存”，但重启后回退。

`src/renderer/settings/settings-panel.ts:287-298` 还把写盘失败完全静默吞掉。

### 优化方向

- 将“读取当前状态 → 合并 patch → 序列化 → 提交缓存”整体放进同一个 mutation queue；
- 或为 settings/ui-state 各自增加单 mutex；
- 只有当前 mutation 成功提交后才更新缓存；
- 写失败要反馈保存失败，而不是保持成功的乐观 UI；
- 去掉重复的 session 持久化调用；
- 对 renderer 增加保存中/已保存/失败状态。

### 验证

使用延迟 writer 或 mock 写盘：

- 并发提交不同顶层字段；
- 转换完成与窗口关闭同时发生；
- 快速连续修改多个设置；
- 模拟写盘失败后再写；
- 重启后检查所有字段是否都存在。

## H6. 路径递归和批量输入没有可靠资源上限

**状态：已证实的结构性风险；具体 DoS 影响需构造输入**

### 证据

- `src/main/converter/paths.ts:80-114` 使用 `path.resolve()` 作为 `seen` key；
- `fs.stat()` 会跟随 symlink/junction；
- 因此 lexical path 去重不能阻止指向祖先目录的循环；
- 没有深度、条目数或总字节数上限。
- `src/main/converter/merge.ts:62-67` 对所有输入文件 `Promise.all()`，一次性读入内存。
- `src/main/ipc/register.ts:226-237,271-301` 只校验数组元素类型，不校验文件数量和大小。
- `src/core/pdf/postprocess.ts:83-110` 的本地图片检查也是无界 `Promise.all()`。

### 影响

- junction/symlink 目录可导致无限递归；
- 选择大目录可能长时间占用主进程；
- 恶意或误选的大批量文件可能导致内存暴涨；
- 大量本地图片可产生大量并发 IO；
- 合并转换没有总资源预算。

### 优化方向

- 明确 symlink 策略：
  - 默认跳过 symlink/junction；或
  - `realpath` 后做 visited，并加深度/条目上限；
- handler 层限制文件数量；
- 转换前限制单文件字节数；
- 合并采用有界 worker；
- 图片检查使用有界并发；
- 对整份文档增加总图片数/总字节预算。

### 验证

- 创建指向祖先目录的 junction；
- 选择包含大量文件的目录；
- 传入数千路径；
- 使用超大 Markdown；
- 观察 CPU、内存、IO 和 UI 是否仍可响应。

## H-SEC. SSRF 防护仍有 DNS TOCTOU 风险

## M1. 预览和预检没有复用真实转换预处理链

**证据**

- `src/main/windows/preview.ts:41-57` 直接将原文交给 `convert()`；
- 实际单文件转换在 `src/main/converter/single.ts:103-107` 执行 `preprocessMarkdown()`；
- `src/main/ipc/register.ts:231-236` 预检直接 `fs.readFile(..., "utf8")`，不经过 `decodeMarkdown()`、Obsidian 或 AI 清理。

**影响：**

- 预览与最终输出不一致；
- GBK/UTF-16 文件的预检结果可能与真实转换不同；
- 启用 Obsidian/AI 后，预检检查的语法不是最终解析的语法；
- 未来新增转换入口容易绕过预检。

## 最终判断

当前架构的主方向是合理的：

- `core` 负责转换语义；
- `main` 负责 Electron、文件、窗口和持久化；
- `renderer` 负责交互；
- docx/pdf 双管线保持独立也是合理决策；
- 安全基线、测试体系和单实例控制已经比一般小型 Electron 项目扎实。

但目前最需要补的不是更多功能，而是**把“同一时刻只能有一个操作”“状态写入不可丢”“输出提交不可覆盖”“可选转换不能改写用户内容”这四个不变量真正落到 main/core 的契约和测试中**。

本代理未修改任何源码、文档或配置。评审期间工作树显示存在未跟踪的 `.opencode/` 及若干 `docs/archive/` 文件；这些文件未被本代理触碰。

说明：以下每条标注 **[证据]**（已读到的代码行）或 **[假设]**（需主会话实测确认）。未修改任何文件，未执行改变仓库的命令。行号为读取时快照。

## Critical

### C1. 同一渲染进程并发转换时 ctx 注册互相覆盖 → 取消失效 + 关窗确认状态错乱
- 证据：`src/main/ipc/register.ts:78-79` 用 `senderId` 单键 `ctxByWebContents.set/delete`；`src/main/ipc/logic.ts:57-66` 每次调用新建 ctx 并在 finally 无条件 `unregisterCtx()`。
- 触发：同一窗口在第一次转换未结束时再次触发 `convert:single|batch|merge`（renderer 侧靠 `state.mode` 守卫，**主进程侧无任何互斥/在途检查**，是唯一的防线）。
- 影响：第二次 set 覆盖第一次 ctx；第一次的 finally 又把第二次的 ctx 删除。此后 `convert:cancel`（register.ts:221-223）取不到 ctx，取消按钮完全无效；`main-window.ts:123` 的 `ctxByWebContents.has(id)` 判定失真，关窗时要么不弹确认（直接销毁，正在写的输出文件可能半成品），要么已取消仍等待 30s（`main-window.ts:168-174`）。
- 方向：主进程侧加「每个 webContents 同时只允许一个在途转换」的闸门（拒绝或先取消），或注册表改为 `Map<number, Set<ConvertContext>>` 并让 `unregisterCtx` 只删自己那一个。
- 验证：DevTools 里对主窗 `window.api.convert(a,'docx')` 不 await，立刻再 `window.api.convert(b,'docx')`，随后 `window.api.convertCancel()`，观察第二次转换是否仍跑完；再测转换中点关闭标题栏是否弹确认。

## High

### H1. markdown 图片 `src` 可指向任意本地路径/UNC → 任意文件被读入产物（潜在信息泄露）
- 证据：`src/main/services/image-downloader.ts:116` `readLocal(path.resolve(baseDir, src))`、`:121` `exists` 同样 `path.resolve`；无扩展名白名单、无「必须位于 baseDir 子树内」约束。`path.resolve` 对绝对路径（`C:\...`）与 `..` 直接生效。
- 触发：待转换的 `.md` 内含 `![](C:/Users/x/Documents/keys.txt)` 或 `![](../../../../secrets/.env)`；用户从网络/仓库拉取的 md 即可携带。
- 影响：文件内容被 base64 内嵌进 docx/pdf 产物 → 若产物随后被分享/上传即泄露；`data:`/`file:` 之外的任意协议已被拒（此面已收口）。
- 方向：resolver 入口做「扩展名 ∈ 图片白名单 + 解析后路径必须 `isInside(baseDir)`（或显式配置的可信根目录）」；PNG/JPG/GIF/WebP/SVG 魔数校验后再读。
- 验证：造一个含 `![](../../../etc/hosts)` 与 `![](C:/Windows/win.ini)` 的 md 走 convert，检查产物内是否含内容。

### H2. 持久化「读缓存 → 计算 → 入队」造成并发丢更新
- 证据：`src/main/persist/ui-state.ts:198`（`loadUiState()` 取缓存）→ `:243` 入队；`atomic-json.ts:23-32` 提交回调才在 `:28` 更新缓存。`settings.ts:212-215` 同样形态。
- 触发（可复现）：A=批量转换完成时 `recordRecentFiles`（register.ts:95）写 `{recentFiles}`；B=同时关闭主窗口（main-window.ts:132）写 `{windowBounds,isMaximized}`；C=同时关闭预览窗（preview.ts:166）写 `{previewWindowBounds}`。三者均在第一次提交前从同一份旧缓存出发，后入队者用「旧快照 + 自己那一项」整体覆盖前者。
- 影响：最近文件、窗口位置、面板展开态随机丢失——正是 index.ts:25 注释里想根治的那类「无法归因的丢失」，只是从双实例缩小成了同实例并发。settings 的 `updateSettings` 同样存在（`settings:set` 与 presets 导入并发）。
- 方向：把「合并」放进写队列内（队列任务体内重新读缓存再 merge），或改为「读-改-写整体串行」的单一 mutex；`recentFiles` 合并逻辑移入队列。
- 验证：脚本化并发调 `uiStateSet({recentFiles})` + `uiStateSet({windowBounds})`，重开应用检查两项是否都在（现有直测只覆盖单次）。

### H3. 发行包无代码签名 / 无发布者身份 → 供应链不可验证
- 证据：`package.json:47-83` electron-builder 配置只有 `appId/target/nsis`，无 `publisherName`、`certificateSubjectName`、`signtoolOptions`；仓库内 grep `certificateSubjectName|publisherName` 无命中（仅 appId/oneClick 命中）。
- 触发：每次 `npm run dist` 产出未签名 exe。
- 影响：SmartScreen 告警、杀毒误报；用户无法校验安装包来源；一旦被投毒无法归因。
- 方向：接入代码签名（OV/EV 证书），并在 CI 中加签名产物哈希公布。
- 验证：`signtool verify /pa MarkdownToWord-Setup-*.exe`（当前预期失败）。

### H4. 关于窗未做 `hardenWebContents`（四类窗口中唯一漏网）
- 证据：`src/main/menu.ts:53-72` 创建 about 窗后直接 `loadFile`，全文件无 `hardenWebContents` 调用；对照 `preview.ts:159`、`single.ts:164`、`mermaid-service.ts:120` 均已加固。
- 触发：about 页内任何可导航路径（`about.js` 里的链接若某次改动去掉 preventDefault，或未来加入 `window.open`）。
- 影响：`window.open` 未 deny、页内跨文档导航未拦截，about 窗可被导航到远程页面并保持 contextIsolation+sandbox（爆炸半径小于主窗，但仍是不一致缺口）。主进程侧也无 `app.on("web-contents-created")` 兜底（`index.ts` 未注册）。
- 方向：about 窗同样调 `hardenWebContents`；或在 index.ts 统一 `web-contents-created` 兜底加固 + `setWindowOpenHandler` deny。
- 验证：DevTools 在 about 窗执行 `location.href='https://example.com'`，观察是否被拦截。

## Medium

### M1. `about:check-update` 网络请求无超时/无取消
- 证据：`src/main/ipc/register.ts:369-372` `fetch(...)` 无 `signal`；返回体 `res.json()` 亦无大小限制；未设 `Accept: application/vnd.github+json`（无头 GitHub API 仍可返回，但易被限流/代理改写）。
- 触发：网络被墙/黑洞/中间设备挂起。
- 影响：关于窗「检查更新」永久转圈，用户只能强杀；且 `about.js` 无超时兜底（假设，需确认 renderer 侧）。
- 方向：`AbortSignal.timeout(8000)` + `res.json()` 前后限制体积 + 失败统一 `{status:"error"}`（已有 catch，可直接接超时）。
- 验证：断网/hosts 劫持 `api.github.com` 到 10.240.0.1 后点击检查更新。

### M2. `shell.openExternal` 白名单只做协议前缀匹配，且放行 `http://`
- 证据：`web-hardening.ts:13-15` `/^https?:\/\//i`；`menu.ts:13-15` `aboutOpenExternal` 对 `url` **无类型/来源校验**（非字符串靠 regex 强制转换兜住，但无 origin 白名单）。
- 触发：about 页传入 `http://`（明文，可被中间人替换为任意站点）或其他任意 https 目标。
- 影响：外链外开到攻击者指定站点；http 明文可被劫持。
- 方向：改为 origin 白名单（仅 `github.com/chenchaodev/markdown-to-word` 与已声明的文档站点），协议限 `https:`。
- 验证：about 页 `aboutApi.openExternal('http://example.com')` 观察是否被系统浏览器打开。

### M3. 输出文件名 TOCTOU + 产物非原子写
- 证据：`converter/paths.ts:67-71` `while (await pathExists(candidate))` 之后，`single.ts:73` / `:209` 用普通 `fs.writeFile(outputPath, ...)`（无 `flag:"wx"`、无 tmp+rename）。
- 触发：批量并发 2（`batch.ts:65`）下同目录同名产物（合并 `{basename}-合并` 与同名源文件的单转、`(2)` 后缀被别的进程/另一实例占用）；或写盘中途崩溃/断电。
- 影响：后者覆盖前者（刚生成的文件被静默清掉）；断电留下截断的 docx/pdf 而用户以为成功。
- 方向：`writeFile(..., {flag:"wx"})` 失败则重取序号（把「取名+占位」做成一次原子操作），或产物也走 tmp+rename 原子替换。
- 验证：同目录放 `a.md` 并用合并模式生成 `a-合并.docx` 两次并发；或对大 PDF 转换中强杀进程看文件大小。

### M4. `collectMarkdownPaths` 递归对符号链接循环防护无效 + 无深度上限
- 证据：`converter/paths.ts:86-87` `path.resolve(p)` **不做 symlink 解析**（canonicalize），注释「seen 集合防符号链接循环」（`:78`）与实际行为不符；`visit` 无深度/条目数上限。
- 触发：Windows 上目录内含指向自身祖先的 junction/symlink（`mklink /D a a\..`），或把 `C:\` 整盘拖入。
- 影响：无限递归 → 栈增长/路径长度爆掉（至 ENAMETOOLONG 才停），UI 卡死且主进程被占；整盘拖入则几十万次 readdir。
- 方向：用 `fs.realpath` 归一后再查 seen，或 `readdir(withFileTypes)` 时对 `entry.isSymbolicLink()` 跳过/单独标记；加深度上限与总数上限。
- 验证：建 junction 环目录后拖入，观察主进程 CPU 与界面。

### M5. 无入参规模上限 → 内存/时长 DoS
- 证据：`register.ts:271-272 / 301-302` 只校验 `isStringArray`（`logic.ts:78-80` 仅逐元素查类型，**无长度上限**）；`convertPrecheck`（`:226-237`）与 `readFrontmatter`（`:324-332`）对任意路径 `fs.readFile` 无大小上限；`convertImpl` 整文件读入内存。
- 触发：被攻破/恶意的 renderer（或误选超大文件）传 10000 个路径或一个 2GB 的 md。
- 影响：主进程内存暴涨、批量 PDF 各起一个隐藏窗（`single.ts:159`）+ printToPDF，机器被打死。
- 方向：handler 侧加数量上限（如 2000）与单文件字节上限（`fs.stat` 预检 + 流式读取）；超限返回可读错误。
- 验证：给一个 500MB 的 .md 走 convert，观察内存曲线。

### M6. `uncaughtException` 兜底不退出，掩盖写入中途的破坏性状态
- 证据：`index.ts:20-23` 注释明说「记录留痕不主动退出」。
- 触发：写盘/rename 期间发生未捕获异常（如 EBUSY、EPERM）。
- 影响：进程带着半初始化状态继续服务，后续行为不可预期；用户侧表现为「什么都没发生」或数据半写。
- 方向：区分「可恢复」与「状态不可续」：涉及持久化/写文件的未捕获异常走 `dialog.showErrorBox` 后 `app.exit(1)`，其余保留只记日志。
- 验证：占用 settings.json 制造 EBUSY 后触发保存，观察应用是否仍可用。

### M7. 窗口 close 拦截与 `app.quit()` 竞态
- 证据：`main-window.ts:122-137` 在 `close` 里 `preventDefault()` + 异步保存后 `destroy()`；`menu.ts:96` 退出走 `role:"quit"`；`index.ts:73-75` `window-all-closed` 才 quit。
- 触发：转换中点菜单「退出」（非标题栏 ×）。
- 影响：`role:quit` 触发 `before-quit` → close 被 preventDefault → 流程依赖后续 `destroy()` 引发 `window-all-closed` 才真正退出；与转换中的确认弹窗叠加时，用户连点「退出」可能出现「不退出也不弹确认」的观感。**[假设：需实测点击序列确认]**
- 方向：统一在 `before-quit` 走同一条「转换中确认 + 优雅收尾」路径。
- 验证：批量转换中通过 Alt 菜单退出，观察是否卡住。

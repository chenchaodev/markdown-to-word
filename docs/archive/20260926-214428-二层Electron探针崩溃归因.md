# 二层 Electron 探针在覆盖轮崩溃的归因(2026-09-26)

> 结论摘要见 `docs/RESEARCH.md`「测试与门禁」节同名条目;本文件保留原始分析依据。

## 现象

GitHub Actions 主 job 的 `verify:ci` 里,`npm run test`(118 段)**全绿**,紧接着的 `test:coverage`(同一 118 段,外面套 `c8 --all --include="dist/**" --check-coverage --statements=90 --branches=85 --functions=90 --lines=90`)**段失败**:

| 轮次 | commit | 失败段 | 期望退出码 | 实际 |
|---|---|---|---|---|
| run 36243022908 | 48594f0 | `segments/entry-exit-guard.test.js` | 4 | 3221225477 |
| run 36243022908 | 48594f0 | `segments/runner-report.test.js` | 7 | 3221225477 |
| run 36245103532 | 2f074ee | `segments/runner-report.test.js` | 7 | 3221225477 |

`3221225477` = `0xC0000005`(Windows `STATUS_ACCESS_VIOLATION`)。覆盖率四项均在门槛之上(如 stmts 93.06 / branch 89.08 / funcs 93.59 / lines 93.06),**失败与覆盖率阈值无关**。

关键细节:`entry-exit-guard` 那个子进程的 stdout/stderr **已完整打印** `[entry:probe-ready] 入口失败 | 阶段:入口执行期(ready) | 退出码 4` 与 `原始错误:Error: PROBE_READY_BOOM`,即判定层与诊断层都对,**只有进程最终退出码被顶掉**。

## 证据链(逐条可复核)

1. **轮次差是唯一分辨维度**:同一 commit、同一台 runner,`test` 轮绿而 `test:coverage` 轮红。c8 12 只注入 `NODE_V8_COVERAGE` 一个变量(`node_modules/c8/bin/c8.js`,无 spawn-wrap、无 `NODE_OPTIONS`);两轮之间所有 Electron 后代的环境差只有它。
2. **Electron 43 主进程认这个变量,且两条退出路径都回写覆盖 JSON**:`app.exit` 与 `process.exit` 各写一份(本地计数 15+20 与实测份数对得上)。即「立即退出」不等于「跳过覆盖回写」。
3. **只有二层子进程会中**:顶层段的 `app.exit` 发生在 app 稳态之后(建过窗口、跑过真实工作),同轮 116/118 全绿;崩的都是**段内嵌套编排派生的夹具进程**与**入口探针进程**。
4. **全仓唯一的 Electron 内无条件 `process.exit()`** 在 `test/segments/runner-report.test.js` 的崩溃夹具(「模拟段崩溃、不回传结果」)。其余 `process.execPath` 子进程都显式走 Node(`ELECTRON_RUN_AS_NODE=1` 或显式 `resolveNode()`)。→ 解释了 `runner-report` 2/2 中、`entry-exit-guard`(`app.exit(4)` 变体)1/2 中这两个不同概率。
5. **与压力/资源无关**:同轮其余段全绿,两轮的段耗时量级一致(109s / 122s),不是超时也不是耗尽。
6. **本机复现不了**:本机全量 `test:coverage` 通过(修复前后各一次),定向复跑同两段亦通过。故本地不是有效的判据环境。
7. **与「覆盖率会静默少算」那条已记录事实同族但不冲突**:`scripts/gate-probes/gates/coverage.mjs:150` 的子 c8 **显式指定自己的 `NODE_V8_COVERAGE` 目录**,不依赖外层环境,故本次剥离不影响该门禁。

## 根因陈述

c8 的覆盖写手注册在被测进程的退出路径上。一个**活着的 Electron 主进程**(Chromium 主循环 / GPU / utility 线程仍在)在退出期回写 V8 精确覆盖时,撞上 Electron 的拆卸,Windows 上以 `0xC0000005` 终止 —— 于是「入口失败应退 4」「崩溃段应上报 7」这类**用退出码当唯一证据**的断言以与被测行为无关的方式判红。`process.exit` 变体把「原语最敌对」与「时机最差」两个不利因子叠满,`app.exit`-at-ready 变体只占一个,故概率不同。崩点具体位置未取到 crashpad/WER 证据,属推测;但「退出路径上不再注册覆盖写手」是可确定性证明的那一半。

## 修法与其代价

- **公共层剥离**:`test/common/runner.js` 的 `runSegmentIsolated` 在「父进程自身是段宿主」(`M2W_SEGMENT_FILE` 存在)时从子进程 env 删 `NODE_V8_COVERAGE`;`test/segments/entry-exit-guard.test.js` 的入口探针 spawn 同样删。顶层段的采集不受影响(顶层 acceptance 进程没有 `M2W_SEGMENT_FILE`)。二层夹具不执行 `dist/**`,对覆盖汇总零贡献。
- **收敛判据用现成事实**（「父进程是段宿主」= 段内嵌套编排的定义本身),与既有先例同形态(`M2W_ONLY` 已因同理由被剥)。段内 4 处 `runAll` 调用点一行未改;`entry-exit-guard` 已有显式 env 对象,加 1 行。
- **必须同批写清的边界**:这条规则今天安全的**唯一**理由是「现有嵌套编排的孙进程只跑测试框架夹具」。若将来新增的嵌套编排会执行 `dist/**`,必须在该分支显式保留采集 —— 否则是**静默少算覆盖率**,比崩溃更难发现。
- **退出码断言一字未动**:`runner-report` 的「父进程原样上报子进程退出码」是唯一端到端验证该契约的地方,不能靠放宽断言来「修」。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 把崩溃夹具的 `process.exit(7)` 改成 `app.exit(7)` | 削弱夹具本意(它模拟「硬崩、不回传」,`app.exit(7)` 是带码的优雅退出);且不解释轮次差 —— `app.exit` 变体在 `entry-exit-guard` 上照样 1/2 挂过 |
| 放宽真实进程层的退出码断言为「非零」 | `runner-report` 那处**不能**:父进程可见文案由 `runner.js` 直接用 OS 退出码拼出,没有诊断文本通道,放宽等于把这句断言的意义删掉。`entry-exit-guard` 可作备选(诊断首行确定性含「退出码 4」),但它会把「剥离是否有效」这个变量糊掉,应留作二道防线 |
| opt-in 标志位(如 `runAll({ childCoverage: false })`) | 要改 4 个调用点,且把「哪些 env 只属顶层」的决定权散回测试点 |
| 新抽象 `test/common/child-env.js` | 只有 2 个站点且要的语义不同(一处无条件剥 `M2W_ONLY`、只对嵌套剥覆盖;一处没有 `M2W_ONLY` 概念),抽象出的参数是冗余的 |
| 改 `defaultElectronExit` 的退出实现 | 覆盖 5 个入口;本地已证 `process.exit` 路径同样回写覆盖,改原语无效 |
| 覆盖轮 `--exclude` 这两段 | 丢掉「接线锚点」与「退出码原样上报」两条唯一验证;且 2/2 的集中性恰恰说明 `runner-report` 是**最值得保**的一段 |

## 「修好了」的判据(这类 runner-only 失败不能靠「CI 绿」自证)

1. **确定性本地证明**:剥离生效后跑 `M2W_ONLY=entry-exit-guard,runner-report npx c8 <同参数>`,断言 (i) 两段的孙进程 `process.env.NODE_V8_COVERAGE === undefined`,(ii) `coverage/tmp` 的 JSON 份数不再随二层子进程数增长。证明**触发条件已消失**,而不是症状碰巧没出现。
2. **覆盖中性**:同一次运行四项无方向性下降(注:四项本身存在运行间抖动,「逐位不变」不是可达标准;数值以 `npm run test:coverage` 输出为准,不入文档)。
3. **CI 侧**:同一 SHA `Re-run all jobs` 连跑 ≥5 次覆盖轮全绿。诚实标注:5 次对单机制复发的排除力有限(粗估 0.84),属弱证据,必须与第 1、2 步并列陈述 —— 写「已消除唯一轮次差分条件」,不写「已修复」。
4. **不堆本地压测**:70/70 同路径复现失败已证明本地压测期望收益低。

## 遗留(另立工作项)

- `output/artifacts/failures/<段名>/failure.log` **没有**进 CI 的诊断 artifact 上传清单(`ci.yml` 只传 `env-fingerprint.txt` 与 `ui-geometry/`),crashpad dump 也没捞。**这是把 H1 从推测升到证实/证伪的唯一途径** —— 本次两轮拿到的仍只有一个数字。
- `runner.js` 在 win32 上把 `code > 0x7fffffff` 直接印十进制;判一下并标成「子进程被 Windows 异常码 0xC0000005 终止」,下次复发日志自带线索。

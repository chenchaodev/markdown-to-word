### 不值得做(及理由)

- **MarkdownIt 实例缓存 / extractHeadings 双扫复用**(render.ts:375、postprocess.ts:32、converter.ts:251):重建开销无感知,缓存引入插件状态风险;正则双扫是小文档量级。YAGNI。
- **renderer window.api 契约代码生成 / IPC 通道名集中**(preload.cts vs renderer.ts:126-173 声明 vs index.ts handler):三处手写契约是漂移风险,但项目小、smoke diag 已守卫,代码生成收益 < 成本。YAGNI。
- **convert-flow.ts runConvert/runMerge 骨架抽象**:三函数差异(取消/成功/失败三态 + 弹窗)使抽象收益一般,平铺可读性反而更好。YAGNI。
- **collectMarkdownPaths 串行递归并行化**:GUI 场景目录规模有限,无实测卡顿。YAGNI。
- **统一测试 zip 解包(tar vs JSZip)**:两套并存各有理由(tar 零依赖 / JSZip 可靠),一致性收益低。
- **统一 docx/pdf 双 parse(remark vs markdown-it)**:推翻性重构,违反项目「双管线」既定选型,风险极大。
- **settings.ts 枚举值列表下沉 core**:轻微契约漂移点,现状注释已互指,可选不做。

## 总体判断

**架构健康度:高。** 三层边界(core 纯逻辑 / main 编排 / renderer GUI)清晰且被测试分层印证(纯逻辑段 → 主进程段 → smoke 端到端)。R1-R8 拆分质量好:函数级职责清楚、重复收敛到位(escape/白名单/警告文案/设置契约均已单一来源),最难得的是注释不仅说明「做什么」还记录「实证结论与勿回退原因」——这是项目最大的可维护性资产。

**最大风险:双渲染管线的语义平行契约。** docx(remark mdast)与 pdf(markdown-it token)各有一套题注/公式编号/白名单/分页实现,已抽共享判定但渲染侧仍需双端同步——任何新语法特性 ≈ 2 倍实现 + 2 倍测试,且两侧行为差异(如 CSS counter 与静态编号的边界差异)已在验收清单留痕。这是架构性成本而非缺陷,但做新特性时应有意识地先评估「双端同步成本」。

**下一阶段最值得投入的一件事:方向 1 第 1 条(convert context 构造收敛)。** 理由:三处重复是当前唯一真实的扩展摩擦点;改动小、风险低、被既有测试全覆盖;且顺带把 `katexDir` 的 `app.getAppPath()` 依赖参数化后,`convertImpl` 可脱离 Electron app 直测(converter.test.js 已在 electron 环境跑,但纯逻辑段化能进一步扩测试面)。做完后建议立即补方向 2 第 1 条(GBK 端到端)——它是用户可见、零 Electron 依赖、成本最低的测试空白。

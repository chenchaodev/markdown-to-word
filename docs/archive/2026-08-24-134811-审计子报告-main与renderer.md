**converter/ 与 ipc/ 边界干净；logic.ts 不过胖（107 行），真正偏胖的是 register.ts（343 行）。**
- `src\main\ipc\logic.ts` 只有纯函数（错误归一、类型守卫、预设解析合并、runConvertTask 样板），零 electron 依赖，可直测——设计良好。
- 但 `src\main\ipc\register.ts` 中三个预设/CSS handler（register.ts:234-261、265-281、286-308）每个都是「对话框 + 文件 IO + 持久化编排」约 30 行的内联流程，三段结构高度相似（showOpenDialog → 取消判断 → readFile → 校验 → saveUiState 记目录 → catch 归一）。可再抽一个「导入文件对话框模板」helper，是 register.ts 里最明显的可收缩处。

**renderer 的 state 三件套设计合理，但存在一个遗留瑕疵。**
- `state\state.ts`（91 行）= 可变单例 + IPC 契约类型；`state\pure.ts`（199 行）= 零 import 纯函数；`state\utils.ts`= 触 DOM 的工具。

## 维度 3：安全性

整体安全 posture 相当好，四类窗口统一加固：

- **web-hardening.ts**（web-hardening.ts:29-39）：setWindowOpenHandler 一律 deny + http(s) 转系统浏览器；will-navigate 无条件 preventDefault；非 http(s) 协议静默拒绝。主窗口、预览、打印、mermaid 四处全部调用。
- **webPreferences**：主窗口全显式（contextIsolation/nodeIntegration/sandbox）。预览窗和打印窗只写了 contextIsolation+sandbox 两项，未显式写 nodeIntegration（默认即 false，无实际风险，但风格不一致）。
- **temp-html.ts**（temp-html.ts:14-28）：写入 os.tmpdir，文件名含 pid+时间戳+6 位随机。两个小瑕疵：(a) Math.random() 非 CSPRNG、writeFile 未用 'wx' 独占标志；(b) 写入成功但调用方崩溃时临时文件残留，无启动期清扫。单用户 %TEMP% 场景风险极低。
- **image-downloader SSRF**（image-downloader.ts:58-66）：对 markdown 中任意 http(s) URL 直接 fetch，**无私网/回环地址过滤**、**无响应体大小上限**（arrayBuffer 会把任意大响应读进内存）、跟随重定向。攻击模型下主要风险是借主进程网络位置做内网探测与内存耗尽，建议至少加 Content-Length 上限与可选私网拦截。超时与「仅 2xx、失败返回 null 不缓存」做得好。
- **html-whitelist 渲染侧防护链完整**：core 白名单 + pdf 模板 CSP `default-src 'none'` + CSS 注入防护剥离 `</style` + 窗口导航收口。纵深防御成立。

## 维度 6：lang-bootstrap.js 为什么是 js

**结论：合理，且是有文档记录的决策。**
- 功能要求它同步执行于 head（index.html:13 无 defer/module），首帧前设置 html lang 防 FOUC；TS 编译产物走 ESM module 语义会被 defer，破坏时序前提。
- copy-renderer.mjs 对它做显式单文件拷贝，注释明说混合目录陷阱。
- 替代方案（内联脚本被 CSP 拦截、visibility:hidden 白屏风险）的排除记录双侧留存。脚本 20 行、try/catch 包裹 localStorage、降级安全。

## 维度 7：main-window 与 preview 对称性

**对称的部分**：都调 hardenWebContents；预览复用 buildConvertContext/renderPreviewHtml 与 PDF 同排版管线；closed 事件清理对称。

**不对称/欠复用**：
1. webPreferences 显式度不一（见维度 3）；
2. **状态记忆不对称**：主窗有 bounds + 最大化恢复，预览窗每次固定 900×1100（preview.ts:131-133），用户调整过的预览窗大小不记忆——pickWindowBounds 本可直接复用；
3. 刷新机制单向：设置变更经 previewRefresh 全量刷，源文件变更只在 focus 时 mtime 对比——预览没有 watcher，属设计取舍而非缺陷；
4. imageResolver 复用有意偏离，理由写在 preview.ts:48-49，合理；
5. 打印与预览共享 writeTempHtml → loadFile → finally 清理骨架但未抽象——生命周期差异大，强行抽象反而别扭，现状可接受。

## 维度 8：persist 层原子写质量（atomic-json.ts）

35 行实现，质量高：
- **原子性**：tmp + rename，Windows 下 rename 可覆盖，失败时原文件不动——隐式回滚策略正确；
- **并发**：promise 链队列串行，「单次写失败不截断队列」正确；每实例独立队列避免互相阻塞；跨进程并发由单实例锁兜底；
- **缓存一致性**：onCommitted 在 rename 成功后同步更新内存缓存——这个回调设计比「写前更新缓存」正确;
- **编码**：显式 utf8 + 2 空格缩进 + 尾换行。
- 两个缺口：(a) **无 fsync**——掉电极端场景风险低但非零；(b) **失败残留 tmp**——磁盘满后 .tmp 不清理。两者对桌面工具均可接受，记录即可。

## 三、内部拆分明细

### 3.1 core/i18n.ts → i18n/{dict,index}.ts ⭐

实际 702 行，区块结构：

| 区块 | 行范围 | 内容 |
|---|---|---|
| 类型+警告构造 | 14-61 | Language/KeyedWarning/ConvertWarning、formatWarning 族 |
| ZH 字典 | 65-355 | `as const` 对象 ~230 键 |
| EN 字典 | 357-651 | `Record<keyof typeof ZH, string>`，编译期锁定键集与 ZH 相等 |
| 运行时逻辑 | 653-702 | t()/setLanguage/applyStaticTexts |

- dict.ts：ZH+EN 原样搬入——两字典必须同文件才能维持键集编译期相等约束
- index.ts：类型 + formatWarning 族 + 运行时逻辑 + re-export DICT
- 引用面全项目最大（~20 个 src 文件 + test/segments/i18n.test.js 31 处），批量替换路径或先留桥接文件渐进迁移

### 3.2 renderer/events.ts → convert/events/ 四文件

607 行单函数闭包 `bindEvents()` 混 6 个事件域：预览打开(73-85)、文件对话框选择(87-111)、拖放+跳过列表(113-~200)、多列表交互、转换按钮+快捷键、弹窗交互+进度订阅+菜单转发。

拆为：drop（拖放+跳过列表）、selection（对话框选择+多列表交互）、convert-actions（转换按钮+快捷键+进度订阅）、dialogs-events（弹窗+菜单转发+预览打开）。bindEvents() 组合入口保留，外部调用方零感知。

### 3.3 main/index.ts → windows/ipc/menu

六块职责：状态样板(1-101)、主窗口创建(103-191)、预览窗口子系统(193-332，~140 行最大独立块)、杂项钩子(334-359)、IPC 注册 ~20 个 handle(361-585)、菜单+生命周期(587-695)。

- 主窗口创建 → windows/main-window.ts；预览子系统 → windows/preview.ts
- IPC 注册 → ipc/register.ts + convert-handlers.ts + file-handlers.ts
- 菜单三函数 → menu.ts；index.ts 只留单实例锁 + whenReady + window-all-closed（~80 行）
- **前置**：ctxByWebContents 被 main-window 与 ipc 共享，先收敛到 ipc/register.ts 导出，避免循环 import

### 3.4 main/converter.ts → converter/ 五文件

- context.ts（ConvertContext/createConvertContext/getImageResolver/ConvertCanceledError）、single.ts、batch.ts、merge.ts、paths.ts
- 原 converter.ts 改桶导出平滑过渡
- 附带发现：BatchResult/BatchItem 在 renderer/state.ts 重复定义——收敛到 core 契约属行为面变更，**另开迭代，本方案不含**

### 3.5 明确不拆的内聚大文件

- core/docx/render.ts（467）：已是 B8 拆分后编排器，「一个 switch 看全分发」可读性优先
- renderer/dom.ts（254）：纯 getElementById 映射 ~120 常量无逻辑，只随目录移动
- core/docx/math.ts（265）：TeX→MathML→docx 三段是同一管线顺序阶段
- core/pdf/bookmarks.ts（223）/ render.ts（214）/ postprocess.ts（142）：单一主题或已拆编排本体
- main/ui-state.ts（252）：sanitize 族是必要防御性冗余
- main/mermaid-service.ts（205）：窗口管理本就是服务一部分
- renderer/file-list.ts（223）/ dialogs.ts（220）/ index.html（630）：同属一个 UI 域
- test/ 各大段（basic-render 521 等）：测试长因覆盖面大，非结构问题

## 六、划分原则（后续扩展按此执行）

1. core 按领域概念分层（pipeline/settings/i18n/markdown/image/util），不再按技术名词平铺；docx/pdf 各留管线私有子树
2. 大字典与逻辑永远分离，字典按语言一文件
3. theme.ts 集中性 > 对称性：即使理想结构中也只允许 docx/ 直属顶层
4. main 按 Electron 职责分层（windows/ipc/services/store/menu），converter 是 core 与 IPC 间适配层
5. renderer 按功能域分组（dom/state/settings/convert/ui/style），组内维持单职责文件
6. 不对称的合理解释：pdf/rules/ 存在是因为 markdown-it 有规则可覆盖；docx 走 mdast 无规则层，对应物是 handlers/（节点处理器），横切关注点（theme/ctx/prescan/chrome）留顶层——这才是正确的对称

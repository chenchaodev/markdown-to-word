**双管线入口与职责**(convert.ts 头注释即双管线差异说明文档):

| | docx 路线 | pdf 路线 |
|---|---|---|
| 入口 | `convert()` → `parseMarkdown()` → `renderDocx(ast, opts)` | `convert()` → `renderPdfHtml(body, opts)` |
| 解析 | remark → mdast AST | markdown-it → HTML 字符串 |
| 产物 | `DocxArtifact { buffer }` 直接落盘 | `PdfArtifact { html, header/footerTemplate }` → 主进程 printToPDF |
| 公式 | Office MathML | KaTeX HTML(katexDir 注入) |
| Mermaid | 内嵌 PNG(2x) | 内联 SVG |
| 目录/脚注 | 静态目录/footnotes.xml | HTML 目录/HTML 脚注 |

## 2. 主要数据流

```
[用户/GUI]
   │  precheck(可选,IPC convert:precheck → core/markdown/precheck.ts,提示后决定是否继续)
   ▼
main/converter/single.ts
   ① readMarkdownDecoded        (IO:读文件 + GBK 解码,core/util/encoding)
   ② preprocessMarkdown         (main/converter/preprocess.ts 编排,core 纯函数):
        obsidianCompat → normalizeObsidian(双链归一)
        aiCleanup     → cleanupMarkdown(引号/列表/空行规整)
   ③ convert(md, format, ctx)   (core/convert.ts):
        parseFrontmatter → metadata + body
        headerFooter/watermark 配置归一化(补 DEFAULT_*)
        ├─ docx:parseMarkdown(body) → renderDocx(ast, …)
        │     prescan 五轮 → 封面 → 目录 → renderBlock 循环 → Document/Packer → Buffer
        └─ pdf :renderPdfHtml(body, …)
              markdown-it(rules 覆写) → 替换 checkbox → 图片检查 → Mermaid 占位替换
              → 封面+目录拼接 → 外链内嵌 → buildTemplate(CSS/KaTeX/水印) → HTML
   ④ persistArtifact(回 main 层):
        docx:直接写盘
        pdf :临时 HTML → 隐藏窗口 loadFile → printToPDF
              → (field 模式两遍打印注入页码) → 书签注入 → setPdfMetadata → 写盘
   ⑤ warnings(ConvertWarning[],keyed)经 IPC → renderer formatWarning 本地化显示
```

**IO 边界设计**:core 主体零 IO(图片经 `ImageResolver` 回调注入、Mermaid 经 `MermaidResolver` 注入、logo 数据由 main 读好注入)。例外见风险点 R3。

- 零 TODO/FIXME/HACK 残留;危险边界(landscape 双重交换、相邻分页符空白页、CSS counter 零级口径)均有「勿回退」式注释

- ✅ **core 零 electron 依赖**:全目录无 `from "electron"` / 无指向 `src/main`、`src/renderer` 的导入(grep 确认)
- ✅ main → core 单向(55 处导入),renderer → core 仅导入 i18n / settings-defaults / frontmatter 类型
- ✅ renderer 运行环境安全:settings-defaults.ts 头注释显式约束「运行时只允许依赖零外部导入的纯模块」,renderer 导入 `DEFAULT_SETTINGS` 不会经 convert 链拉入 node 依赖(i18n 的 `applyStaticTexts` 对 document 做 `typeof` 守卫)

## 6. 风险点(按严重度排序)

### 🟠 中

**R1. 双管线语义对齐依赖人肉 + 测试护栏,无共享渲染抽象**
题注/公式/交叉引用/编号在 docx(mdast 预扫 + 组件)与 pdf(markdown-it rules + CSS counter)各有独立实现,仅共享正则与计数纯函数。CSS counter 分支(template.ts:244-281 的四象限条件组合)与 JS 计数口径需同步修改(heading-numbering.ts 注释已承认「修改计数语义须同步 pdf 显示层两分支」)。缓解:双格式断言测试段覆盖;但新增编号语义时同步成本高,属结构性风险。

**R2. 警告去重机制双源**
docx 侧 `ctx.warnedKeys`(key+JSON(params))与 pdf 侧各 rule 自建 `Set`(引用键)两套并行、互不感知(ctx.ts:62-64 显式声明)。同类悬空引用在两管线的去重粒度可能不一致;若未来统一警告语义需改两处。

**R3. 「core 零 IO」表述与实现有出入**
- `pdf/template.ts` 的 `loadKatexCss` 用 `readFileSync` 直读文件(失败降级空串,有 warnings 通道)
- `markdown/precheck.ts` 默认注入 `fs.existsSync`
- 图片/mermaid/logo 已正确走注入

不影响正确性(均可测、失败可降级),但破坏「core 无 IO」不变量的纯粹性;CLI/浏览器复用 core 时 `template.ts` 的同步 IO 是最先踩到的点。建议要么收口为注入,要么修正注释口径。

### 🟡 低

**R4. pdf/template.ts(409 行)职责偏多**
同一文件含:页眉模板构造 + 120+ 行内联 CSS 字符串 + KaTeX 加载 + CSP + 水印 CSS + 封面 HTML。CSS 字符串内还内嵌了复杂的条件编号分支。接近 CODE-GUIDE ~500 行拆分线,CSS 模板与 KaTeX IO 可考虑拆出。

**R5. hljs 配色板双源**
docx 侧 `handlers/code-highlight.ts`(约 30 个 token 色)与 pdf 侧 `template.ts`(`.hljs-*` 规则)各自硬编码同一套 GitHub Light 色板,调色需改两处,无共享常量、无测试锁定一致性。

**R6. 零散色值未完全入 theme**
`chrome.ts:250` 水印色 `"999999"/"1F2328"` 硬编码(theme 中已有同值 `RULE_GRAY`,且 pdf `template.ts` 水印 CSS 也写死 `#999999/#1f2328`,实为三处);`table.ts:49` 边框 `"000000"`。theme 硬约束主要覆盖字体,颜色常量的集中度略弱。

**R7. convert.ts re-export 兼容层**
`ConvertFormat`/`DEFAULT_PAGE_SETUP` 等从 convert.ts re-export 仅为兼容下游既有导入路径,属于双入口表象(单源仍在 settings-defaults,注释已说明)。长期可随调用点迁移清理,否则新代码可能继续从旧路径导入。

### 🟢 无问题确认

- 无超大文件、无 TODO 残留、无核心→GUI 反向依赖
- pdf 分支已避免白做一次 remark 解析(convert.ts:144-146 注释留痕)
- 空脚注/空批注不生成 XML part、CSP 收紧、`sanitizeStyleCss` 防 `</style>` 注入等边界处理完备

## 7. 总评

`src/core/` 是一个**契约意识极强、文档密度极高**的转换核心:单源收敛(settings/cross-ref/typography/image-resolver)已基本完成并有契约测试锁定,双管线差异被明确标注为「有意设计」而非混乱。主要结构性代价是 docx/pdf 两侧渲染语义的平行实现(R1/R2/R5),这由双格式测试段兜底;中低危问题集中在 pdf/template.ts 的职责聚集与少量色值/IO 口径未完全收口,无阻塞性缺陷。

## 摘要

整体评级是**基本合理，但有明确问题**。

既不是结构性缺陷 —— 层向已从注释约定升级为机器断言，契约单源是真的；也不能算「合理」—— 被写进需求范围与 ADR 的格式扩展能力没有实现载体，且双管线的状态传播模型相反，任何横切特性必然写两遍。

三条判据各一句：

- 判据一，依赖方向已经是机器不变量：四条层向规则加逐文件内建白名单挂在 `verify:ci` 第三道，实测跨层边为 0。
- 判据二，共性语义确有单源（8 个模块消费 `cross-ref.ts`），差异被 21 行可执行矩阵锁死。
- 判据三，被声称的扩展性没有实现层：文档写「格式注册表」，实现是 6 处跨 3 层的 `format` 分支，且 docx 预扫 / pdf 即时两套状态传播模型方向相反。

本轮新发现 3 条：

1. 文档声称的「格式注册表」与实现不符。
2. `core/markdown/` ↔ `core/pipeline/` 是目录级双向依赖，使分类不成立。
3. renderer 内部零依赖方向门禁，是当前结构最大的盲区。

已登记但未解决：REF-007（`settings-panel.ts` god module + 向导外溢）、REF-006（覆盖率下限与 renderer 整层排除）、renderer→main 残余 type-only 边、`windows/preview` 反向依赖 `ipc/logic`、core 内建白名单的文件级粒度。

**本轮零代码改动** —— 只出结论与证据，不含任何实现。

## 二、三条判据

**判据一：依赖方向已是机器不变量。**

- `scripts/check-import-boundary.mjs:102-127` 定义四条层向规则（`core-no-host` / `core-no-upward` / `renderer-no-main` / `preload-no-main`），`scripts/check-import-boundary.mjs:301-306` 定义 core 的 `node:` 内建逐文件白名单，挂在 `package.json` `verify:ci` 第三道。
- 实测佐证：`src/core/` 对 `electron` 匹配 0 处（唯一命中是 `src/core/pdf/bookmarks.ts:4` 的注释），对 `../main` 与 `../renderer` 各 0 处；`src/main/` → `renderer` 0 处。
- 历史唯一的环已被显式规避 —— `src/core/docx/handlers/bookmark.ts:3-5` 注释写明「放独立模块避免 captions→render 运行时依赖环」。

**判据二：共性语义确有单源，差异被可执行矩阵锁死。**

- `src/core/markdown/cross-ref.ts` 零导入，其 `:1-5` 自述「消除原两份平行定义的人肉同步」。
- 消费者 docx 侧 4 处：`src/core/docx/handlers/captions.ts:16`、`src/core/docx/handlers/link-xref.ts:16`、`src/core/docx/handlers/equations.ts:24`、`src/core/docx/render.ts:61`。
- 消费者 pdf 侧 4 处：`src/core/pdf/rules/caption.ts:5`、`src/core/pdf/rules/xref.ts:16`、`src/core/pdf/rules/equation.ts:5`、`src/core/pdf/render.ts:51`。
- `image-size.ts` / `table-width.ts` / `slug.ts` / `heading-numbering.ts` / `html-whitelist.ts` 同构。
- 差异侧由 `test/segments/dual-pipeline-matrix.test.js` 兜底：21 行 mustMatch / allowedDiff，`:6-7` 明确「禁止只列元数据不验证」，真跑双侧产物断言。

**判据三：被声称的扩展性没有实现层，且两条管线的状态模型相反。**

- 文档声称：`docs/ROADMAP.md:121` 写「架构预留其他格式扩展」；`docs/adr/ADR-001-非对称转换管线与格式注册表.md:6-7` 写「`src/core/convert.ts` 以格式注册表分发 / 注册表预留格式扩展」；`docs/ADR.md:12` 索引标「docx 部分仍有效」；`src/core/convert.ts:1-2` 文件头自称「格式注册表」。
- 实现：`src/core/convert.ts:183` 的 `if (format === "pdf") { ... return }`，其后落到底部才是 docx。全库 `format` 分支 6 处跨 3 层（`src/core/convert.ts:183`、`src/main/converter/single.ts:95`、`:116`、`src/main/converter/merge.ts:157`、`:174`、`src/main/converter/paths.ts:53`），类型是 2 元联合（`src/core/settings/settings-defaults.ts:17`）。
- 状态模型：`src/core/docx/prescan.ts:4-10` 自述「本侧在渲染前从 AST 预扫，pdf 侧在渲染期即时完成，`postprocess.ts` 为对应阶段但方向相反」。

## 四、问题清单

### 重要

#### 一、文档声称的「格式注册表」与实现不符

- 症状：文档与 ADR 描述的是注册表（新增格式 = 加一条目 + 一个 render 函数），代码里是分支。
- 证据：见第二节判据三。全库 `format` 分支 6 处跨 3 层，类型是 2 元联合（`src/core/settings/settings-defaults.ts:17`），`src/core/convert.ts:183` 是 `if` 而非查表。
- 为何是结构问题：二者不是同一件事。文档与实现的差距会让后续开发者按 ADR 去「补注册表」，而那会与已有 6 处分支产生第二份分发 —— 越补越乱。
- 方向性建议：二选一并落到 ADR。
  - (a) 承认注册表未实现，ADR-001 加「已被部分取代」并把 `docs/ROADMAP.md:121` 的「预留」降级为「未承诺」。
  - (b) 真做，收敛为 `src/core/convert.ts` 内一张 `{ [format]: (body, ctx) => Artifact }` 表，把 `src/main/converter/single.ts:95`、`:116`、`src/main/converter/merge.ts:157`、`:174`、`src/main/converter/paths.ts:53` 的 `format` 分支改为查表。
  - 时机上，**在 REQ-007（HTML 导出第三格式，`docs/ROADMAP.md:25` 现为「暂缓」）被重提案之前裁决成本最低。**

#### 二、core 两个目录分类不成立，目录级双向依赖

- 症状：`markdown/` 与 `pipeline/` 之间「依赖方向单向」的注释是假的。
- 证据：预设切分是「`markdown/` = 格式无关语义单源（正则族 / 计数器 / 尺寸解析），`pipeline/` = 转换阶段（parse / frontmatter / merge）」，但 `precheckMarkdown`（`src/core/markdown/precheck.ts:194-246`）与 `cleanupMarkdown`（`src/core/markdown/ai-cleanup.ts`）**是阶段不是共享语义** —— 只被 `src/main/converter/preprocess.ts:13-14` 与 `src/main/ipc/register.ts:11` 各调一次，无任何第二条管线消费。
  - 正向边：`src/core/pipeline/parse.ts:4,6,9,11` → `markdown/comment`、`markdown/slug`、`markdown/cross-ref`、`markdown/table-width`。
  - 反向边：`src/core/markdown/precheck.ts:15` → `pipeline/parse.js`；`src/core/markdown/ai-cleanup.ts:12-13` → `pipeline/frontmatter` 与 `pipeline/parse`。
- 为何是结构问题：文件级无环（运行时安全），但**目录级有环**，所以 `src/core/docx/handlers/content.ts:4`、`src/core/pdf/rules/shared.ts:4`、`src/core/docx/ctx.ts:6` 这类「单向」注释在这两个目录之间不成立；按注释做依赖判断会得到错误结论。
- 方向性建议：把这两个文件移到 `pipeline/`，或拆成 `markdown/`（纯策略）+ `pipeline/`（阶段编排）。改动是纯移动 + import 路径，无行为变更。

#### 三、renderer 内部零依赖方向门禁 —— 当前结构最大的盲区

- 症状：跨进程三层有门禁，renderer 内部谁可以依赖谁完全没有约束。
- 证据：`scripts/check-import-boundary.mjs` 只管 core / main / renderer 三层。向导已同时依赖 `settings-bindings-preset.ts`（`src/renderer/wizard/wizard-steps.ts:21`）、`settings-panel.persistSettings`（`src/renderer/wizard/wizard-steps.ts:22`、`src/renderer/wizard/wizard-steps-delivery.ts:16`、`src/renderer/wizard/wizard-fields.ts:24` 三处）、`settings-logic.outputDirDisplayText`（`src/renderer/wizard/wizard-steps-delivery.ts:17`）、`convert/file-list.renderSelection`（同文件 `:18`）、`settings-drawer`（`src/renderer/wizard/book-wizard.ts:44`）。
  - 扇入侧：`src/renderer/ui/first-run-guide.ts:15`、`src/renderer/convert/events/selection.ts:35`、`src/renderer/convert/events/dialogs-events.ts:47` 都依赖 `book-wizard.js` —— 它是 renderer 里扇入最高的模块之一。
- 为何是结构问题：再加「封面元数据编辑 + 模板选择 + 输出目录」三块会逼出 `wizard → settings-panel` 与 `settings-panel → wizard` 的对向依赖（目前只有前者），**无门禁能拦**。等到形成环再发现，处置成本远高于现在加一条规则。
- 方向性建议：复用 `scripts/check-import-boundary.mjs` 已有的规则表机制，加一条 renderer 内部 scope 规则。

#### 四、settings-panel 是 god module，且成了向导的持久化依赖

- 症状：设置抽屉模块同时承担主题、语言、加载回填、文案同步、持久化、预设重建、导入流、弹窗态、Tab 初始化。
- 证据：`src/renderer/settings/settings-panel.ts` 560 行、22 个导出跨 5 类职责 —— 主题（`:97`）、语言（`:113`、`:130`）、加载与回填（`:170`、`:196`）、动态文案同步（`:290-341`）、持久化 5 个入口（`:358`、`:417`、`:422`、`:427`、`:432`）、预设 option 重建（`:443`）、导入流（`:467`、`:487`、`:498`）、弹窗态同步（`:527`、`:535`）、Tab 初始化（`:547`）。
  - 外溢证据：一个模态向导的写路径从设置抽屉借 `persistSettings`（上列三处 import）。
- 为何是结构问题：`persistSettings` 是写路径原语，与 `applySettingsToControls`（`:196`，回填 22 个控件）之间无内聚；模块边界被跨功能复用穿透，导致设置抽屉与向导事实上绑死。
- 已登记：REF-007（`docs/ROADMAP.md:47`，状态「暂缓」/ 低 / L），**不是新发现**。但它是当前结构里最挡「成书向导继续长」的一处。
- 方向性建议：抽出它不需要拆 22 个函数，只需把 5 个 `persist*`（`:358-441`）移到无 DOM 依赖的模块。

#### 五、state 目录名与职责不符，真正的依赖 hub 是 state/utils

- 症状：`src/renderer/state/` 三个文件是三种东西，目录名只对其中一个成立。
- 证据：
  - `src/renderer/state/state.ts:23` 是可变 store，唯一名副其实。
  - `src/renderer/state/pure.ts` 12 个导出（`isMarkdown` / `baseName` / `stageText` / `partitionDuplicates` / `selectionStatus` 等）零导入零 DOM，是真纯函数核。
  - `src/renderer/state/utils.ts` 是 **DOM 工具箱**：`:18` 从 `dom/refs.js` 取元素、`:116` `document.getElementById`、`:167-196` `trapFocus` 挂 document 级 capture 监听、`:227-258` 焦点栈；18 个导出，被 `convert/`（4 处）、`settings/`（5 处）、`ui/`（3 处）、`wizard/`（2 处）全量导入。
- 为何是结构问题：它才是 renderer 实际的中心节点，而 `src/renderer/state/state.ts` 几乎只被 store 消费者引。目录名让新人误判依赖方向（以为可单向依赖 `state/`，实际每个功能目录都深度依赖 `state/utils.ts` 的副作用）。
- 方向性建议：`utils.ts` → `ui/dom-ops.ts`（或与既有 `dom/refs.ts` 同域），`state/` 只留 `state.ts` + `pure.ts`；纯移动。属 REF-007 覆盖边缘。

#### 六、core 内建白名单是文件级不是符号级

- 症状：给一个纯 HTML 生成规则新增 `readFileSync` 不会判红。
- 证据：`scripts/check-import-boundary.mjs:301-306` 只判「该文件是否在 `CORE_NODE_BUILTIN_FILES` 表内」。`src/core/pdf/rules/image.ts` 因 `:12` 的 `node:url` 与 `:15` 传递引入的 `precheck` 而在表内（`scripts/check-import-boundary.mjs:77`）。
  - 根因：`src/core/markdown/precheck.ts` 把两件事放进一个文件 —— 纯策略 `createLocalImagePathPolicy`（`:165-179`，realpath 全靠依赖注入，零 IO）与 IO 驱动 `precheckMarkdown`（`:194-246`，`:11-13` 顶层 `import { existsSync, realpathSync }`）。
  - 后果：`src/core/pdf/render.ts` 传递依赖 `node:fs` —— 一条纯渲染路径。
- 为何是结构问题：白名单注释（`scripts/check-import-boundary.mjs:68-70`）承诺的是「core 触碰宿主能力须先评估能否下沉为入参」，但**文件粒度让这个承诺无法在符号级执行**。
- 方向性建议：`precheck.ts` 拆为 `markdown/image-path-policy.ts`（零 `node:` 导入）+ `precheck.ts`，`src/core/pdf/rules/image.ts` 随即可从白名单移除（它只需要 `node:url`）；改动小，白名单条目净减少。
- 边界说明：`docs/archive/20260926-211455-全库优化计划与执行台账.md` OPT-5.1 的原始问题（明确 core 是严格无 IO 还是 Node-compatible 尽量无 IO）**已用白名单裁决**，本条不是重开那个决策，而是指出现有裁决的粒度缺口。

#### 七、双管线状态传播模型相反，横切特性必然写两遍

- 症状：docx 侧有预扫阶段，pdf 侧没有；同一横切特性两侧落点不同。
- 证据：
  - docx 侧：`src/core/docx/prescan.ts:1-11` 自述五轮预扫（题注 → 章节 label → 公式 → 目录），结果装进 `DocumentPrescan`（`:27-34`，3 个字段）并**就地写入 `ctx`**（`:3`），渲染期由 `renderBlock`（`src/core/docx/render.ts:349-395` 的 8 个 `case`）查表消费。
  - pdf 侧：**无预扫**，题注 / 公式 / xref 由 `rules/*` 在渲染期即时完成（`src/core/pdf/render.ts:187-195`），`src/core/pdf/postprocess.ts` 在渲染后从成品抽取。
  - docx 加一个横切特性 = `prescanDocument` 加一轮 + `DocumentPrescan` 加字段 + `renderBlock` 加 case，漏一处是「引用显示 `图 (?)`」而非报错。
  - pdf 加同一个 = `rules/` 加一条 `override*Rule` + `render.ts` 注册，**且依赖注册顺序** —— `src/core/pdf/render.ts:187-295` 这 11 次 override 的先后已是隐式耦合，源码里没有任何一处声明顺序约束。
- 为何是结构问题：两种模型的扩展点位置不同、失效模式不同。差异矩阵能锁住「结果一致」，但不能替两套模型省掉一次实现，也不能在顺序耦合被破坏时给出定位。
- 已登记：ADR-014（保持独立）。本条是新观察。
- 方向性建议：不合并管线（ADR-014 已定且正确），但把「新增语义维度」在两侧的**落点**写进差异矩阵的行结构（加 `docxLandmark` / `pdfLandmark` 列指向扩展点而非产物），并在 `src/core/pdf/render.ts:179-295` 的 override 注册块加顺序不变量注释。

#### 八、两套 handler / rule 契约不对称，同步只靠注释

- 症状：同主题双实现的同步由显式注释维护，非代码约束。
- 证据：
  - docx 侧 `src/core/docx/handlers/*`（14 文件，2694 行中的 handler 部分，最小 25 行 `bookmark.ts`、最大 340 行 `math.ts`）导出**纯渲染函数**，签名 `render*(node: MdastX, ctx: Ctx)`，由 `src/core/docx/render.ts:38-42` 逐个具名 import 后在 `renderBlock`（`src/core/docx/render.ts:222-232`）里**手写 if/else 分发**（注册 = 中央 switch，无注册表）。
  - pdf 侧 `src/core/pdf/rules/*`（7 文件 832 行，最小 52 行 `caption.ts`、最大 221 行 `xref.ts`）导出 `override*Rule(md: MarkdownIt): void`，内部 `md.core.ruler.push(name, fn)`，由 `src/core/pdf/render.ts:54-60` 连续 7 行 import 后集中调用（注册 = ruler 命名 push，有隐式注册表）。
  - 入参不同构（`ctx` vs `md` + `state.tokens`）；docx 有 prescan 预扫阶段，pdf 无对应物。
  - 结构对称性只有一处：`src/core/docx/handlers/bookmark.ts` 是无状态 helper（导出 `wrapBookmark`，25 行）而 `src/core/pdf/rules/shared.ts`（128 行 `createDepthTracker`）是共享工具 —— 命名与抽象层级不对齐。
  - 同步靠注释：`src/core/docx/handlers/heading.ts:5-7` 与 `:9-14` 各写「双管线对应：`src/core/pdf/rules/heading-id.ts`」「修改须同步核对」；`src/core/pdf/rules/caption.ts:9-18` 同样写明与 `buildCaptionContext` 契约一致。
  - 注释里已自陈一处行为漂移：无 h1 文档的图题注 docx 出「图 N」/ pdf 出「图 0.N」（`src/core/pdf/rules/caption.ts:17-18`）。
- 为何是结构问题：注册机制不同（一侧中央 switch、一侧隐式注册表）使「新增一个语义维度」的成本与失败方式不可比；注释同步在人员轮替下必然衰减，且已经漂了一处。
- 方向性建议：至少把两侧扩展点位置做成可机械核对的落点清单（同第七条）。

- 已登记：REF-006（`docs/ROADMAP.md:46`，暂缓）；33/94 与 44.9% 已登记在 `scripts/gate-probes/coverage-baseline.json:13`。**新的是「renderer 整层排除」这一后果从未被作为条目讨论。**

#### 十一、smoke 让 main 层失去「生产主进程代码」含义，但纪律无门禁

## 七、两条 lane 的一处分歧与裁定

explorer lane 在「模块职责」视角下判定 `core/markdown/` 与 `core/pipeline/` **无职责重叠** —— 依据是前者 11 个文件各 2-11 个导出、后者 3 个文件编排三步，职责清单对不上。

oracle lane 在**目录依赖边**视角下判定两者是目录级双向依赖 —— 依据是第四节第二条列出的正反向边（`pipeline/parse.ts` 指向 4 个 `markdown/*` 单源，而 `markdown/precheck.ts:15` 与 `markdown/ai-cleanup.ts:12-13` 指向 `pipeline/*`）。

**裁定采 oracle。** explorer 看的是模块职责，oracle 看的是目录边，后者才是「依赖方向单向」注释为假的真正原因。职责清单不重叠并不能推出目录依赖单向 —— 恰恰相反，反向边上的两个文件正是「阶段被放进了语义目录」造成的。

记录此分歧是为了让后续读者知道该结论的来源视角，避免按 explorer 的口径重新得出「无重叠」。

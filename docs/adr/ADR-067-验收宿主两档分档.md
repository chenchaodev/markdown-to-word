## 决定

**段契约一个字不改** —— 导出 `run()`、结果文件回传、具名 case、失败产物落盘、`M2W_ONLY` 三态筛选、0 段判红、进程树硬杀全部保留。只把**宿主**分成两档：**纯 node 子进程** 与 **Electron 子进程**，并加一条门禁守住分档不腐烂。

分档判据是机械可判的：**段的传递依赖闭包是否触及 electron。**

## 背景

一次全仓架构评审实测出的缺口：**现行执行模型每段都付 Electron 的成本，而多数段根本不需要它。**

**一、现行模型本身是本仓最扎实的一块，不动的理由是它对。** 每段一个独立 Electron 子进程 ＋ 独立 userData 目录，失败归因度、硬杀超时、退出码判读、0 段判红全都建立在它上面（ADR-015 立这条时的原始失效形态是「同进程段互相污染」＋「无隔离则失败定位失效」）。分档要动的只是**谁来当子进程可执行文件**，不是隔离模型。

**二、大多数段的传递依赖闭包到不了 electron。** 实测 143 段里约 95 段的闭包根本不触及 electron —— 它们在为一个自己不 import 的能力付三样成本：Electron 启动、userData 重定向、超时预算。

> **本条所列三样成本的量级需要分开看**（2026-10-07 订正，与撤步裁决同批）：**userData 重定向是三步同步 fs 操作**（造临时目录 · 写结果文件 · 删目录），实测在**亚毫秒到毫秒量级/段**；Electron 启动与超时预算是**秒量级/段**。⇒ 计划表 #07 的退出条件只写了「纯 node 档段不需要 userData 重定向」，**量的恰是三样里最小的那一样**。逐项取数命令见 [`20261007-092537-REQ-219宿主分档撤步裁决`](../evidence/20261007-092537-REQ-219宿主分档撤步裁决.md) §二。

**三、纯 node 档的超时预算可以收紧。** 现在所有段共用一个预算，是因为档位只有一个：Electron 启动本身就慢。纯 node 档没有窗口可挂、启动开销小得多，同样的预算在它身上是白等的 —— 而白等的代价是**真超时的定位被稀释**：预算一大，一个真挂死的段和一个只是启动慢的段看起来一样。

**四、分档判据本身不需要人为裁定。** 「传递依赖闭包是否触及 electron」可由现有 import 图扫描器算出，不靠人记「这段要不要 Electron」—— 人记的东西会与实际 import 漂移，而漂移的形态是**静默降级**（段标了 Electron 档却实际不需要，代价是多付一次启动，看起来只是慢一点）。

> ⚠ **本节末句「可由现有 import 图扫描器算出」是事实错误，已订正**（2026-10-07，与撤步裁决同批）：**本仓没有闭包解析器**。`gates/repo/check-import-boundary.mjs` 有可复用的**单文件**抽取 `collectImports()`，但它的两个编排入口 `analyze()` 与 `analyzeTreeBoundaries()` **都是逐文件跑规则**，全仓没有任何一处做传递闭包。仓库里唯一带「闭包」字样的实现提供的是**词法层**两个函数，它自己的文件头已写明整套闭包判定**已整删**、只退役消费方。逐行依据见 [`20261007-092537-REQ-219宿主分档撤步裁决`](../evidence/20261007-092537-REQ-219宿主分档撤步裁决.md) §三.1。

**五、隔离的前提是「子进程」，不是「Electron」。** 现行模型真正买到的是：每段一个独立进程 ＋ 独立 userData ＋ 硬超时杀进程树 ＋ 退出码判读 ＋ 0 段判红。**这五项没有一项依赖 electron** —— 它们依赖的是「段跑在另一个进程里」。换可执行文件不动其中任何一项，这正是分档可以只动宿主而不动契约的原因。

## 备选方案

**否决 · 全部留在 Electron 宿主。** 三分之二以上的段为一个自己不 import 的能力付启动与超时预算，而段数还在涨 —— 成本随段数**线性增长**，且每次新增段都要重新付一次。唯一的好处是「只有一种宿主」这个认知负担，而那个负担值不到这个价。

**否决 · 全部退回纯 node，需要 Electron 的段另起一条链。** 需要真实窗口的段（真起窗口、真跑安装冒烟、真打 PDF）拿不到 Electron 运行时 —— 那等于把**最难测的东西挪出默认路径**，默认路径不再覆盖真实宿主，而真实宿主恰恰是出问题最多的地方。这比多付启动代价坏得多。

**否决 · 不分档，只把超时预算调小。** 那是在**惩罚需要 Electron 的段**（它们启动本来就慢）却不让不需要的段受益，两头不讨好 —— 而且判据型缺失仍在：没有任何机制能说清一个段到底需不需要窗口。

**否决 · 按「测试了 renderer 就归 Electron 档」这类语义切分。** 段可以测 renderer 的纯函数而不需要 Electron 运行时（`test/harness/` 下已有纯 Node 段的先例）。按语义分档等于引入第二份需要维护的知识，且它与真实依赖不同步时**不报错**。

**否决 · 一次建三档以上（node / Electron / 「无窗口的 Electron」）。** 第三档的判据是「要不要 `app.whenReady`」而不是「要不要 electron」，它要靠另一种图分析（哪些文件引用了 `app` 的生命周期 API），且两档之间的差异不足以抵掉「段要声明的档位从一个变成两个」的复杂度。真出现大量「要 electron 但不要窗口」的段时再拆，那时它是一个有证据的拆分而不是预想。

**否决 · 用 `electron-mock` 让所有段都跑纯 node。** `test/harness/electron-mock-loader.mjs` 这类拦截已有先例且对纯函数段有效。但 mock 掉 `app` / `BrowserWindow` 之后，那些段的断言对象就不是真运行时 —— **最需要真宿主的段（起窗口、打 PDF）恰好是 mock 覆盖不了的**。用 mock 统一档位，等于让最难的段永远留在最难的状态。

## 后果

**门禁多一条**：标为 node 档的段，其传递依赖闭包内不得出现 electron —— 反向锚点是标为 Electron 档的段闭包内**确实**出现 electron，否则「两档」会退化成「一档 ＋ 一个没有牙的声明」。

> ⚠ **本条门禁的判据在本仓不可达，且反向锚点在正当段上必然假红**（2026-10-07 订正，与撤步裁决同批）。除背景四那处「无闭包解析器」外，还有一处更硬的机制障碍：`test/harness/runner-report.test.js` 是**正当的 Electron 档段**（它自测逐段子进程隔离模型），而它的**静态 import 里零 electron** —— 它的 electron 依赖是**运行期制造**的（把含 electron 导入的段源码写到磁盘沙盒，再经嵌套编排执行）。**任何静态 import 图都看不见这一步** ⇒ 正向判据在它身上恒绿、反向锚点在它身上恒红。**结论：在这一段上「档位」是「子进程之宿主的属性」，不是「段自身 import 的属性」，判据的主体选错了。** 依据见 [`20261007-092537-REQ-219宿主分档撤步裁决`](../evidence/20261007-092537-REQ-219宿主分档撤步裁决.md) §三.2。

**最大的收益**：既有目标「`core`/`convert`/`cli`/`mcp` 零 electron」从**门禁描述的目标**变成**测试系统的实测属性** —— 那几层的段跑在纯 node 子进程里这件事本身就是证据，而不再只是源码面的一条断言。

> **本条收益已由别的路径兑现，本条不新增它**（2026-10-07 订正，与撤步裁决同批）：该目标今天已成立且不依赖分档机制，三条互相独立的机制各占一角 —— ① **源码面**：层向规则表对 core / convert / cli+mcp 三层各有一条 `bare:electron` 硬禁（`faces-no-host` 的理由还写明「需要宿主能力时由该面用子进程重入」）；② **mock 完整性面**：`test/behavior/electron-mock-coverage.test.js` 把「mock ⊇ src 用到的全部 electron 具名导入」做成静态断言，其第 4 条就是「core 侧零 electron import」的旁证；③ **运行期面**：夹具生成器的段级 import 豁免白名单**当前为空**（意为全部段在纯 Node + electron-mock 下均可 import），而该门禁在 `verify:ci` 链内每轮逐段真 import。⇒ #07 新增的是第四份同类覆盖，增量收益为零。

**代价。** 段要声明自己属哪档。**漏声明要有确定的兜底：默认 Electron 档** —— 判错方向的代价不对称，漏声明多付一次启动（只是慢），错声明为 node 档则段在 import 期死掉（红，且现象离根因很远）。

**为什么不改 ADR-015。** ADR-015 立的是**隔离模型**，本条收窄的是**宿主选型**；隔离、归因、硬杀、产物落盘一律不动。ADR-015 的正文按规矩不改，关系在此登记。

**以后会受它约束的。** 新增段必须声明档位；档位由闭包算出来而非由人判断，故段改 import 之后**可能跨档** —— 门禁要能在跨档时报出来，而不是让人回头改声明。

**两档都不许退化。** node 档不因「段跑得快」就放宽断言（它仍然是隔离进程，退出码与结果文件照旧）；Electron 档不因「多数段用不到」就削减 userData 隔离或硬杀超时 —— 那五项是 ADR-015 立这条时对付的原始失效形态，与段数多少无关。

**门禁要双向有牙。** 「node 档闭包内不得出现 electron」是正向；「Electron 档闭包内**确实**出现 electron」是反向锚点 —— 没有反向锚点时，一个把所有段都标成 node 档的门禁会**假绿**，而那正是本条要防的那类漂移。

> ⚠ **本节的判据不可达**（2026-10-07 订正，与撤步裁决同批）：反向锚点要求「Electron 档段的闭包内确实出现 electron」，但**正当 Electron 档段的 electron 依赖可以是运行期制造的**（见上节订正），静态 import 图对它零可见 ⇒ 这条反向锚点会在正当段上恒红。**「双向有牙」这条要求本身是对的**（单向判据确实会假绿），不可达的是实现它的判据形态。

**实施时的连带项。** 段宿主的入口当前从 `electron` 取 `app` 并在 `whenReady` 之后执行段；node 档需要一个同契约的入口（同样回传结果文件、同样走统一入口守卫与退出码表）。**段契约不变、只是多一个入口实现** —— 这是「不动契约」这句话的具体含义，也是本条风险最低的原因。

**不做的事。** 本条不追求「尽可能多」的 node 档。一个段即使能跑 node 档，若它随后要断言真实 Electron 行为，留着更省事。**分档的判据是「需不需要」，不是「能不能」。**

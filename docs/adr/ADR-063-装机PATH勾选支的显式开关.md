# ADR-063 · 装机 PATH 勾选支的显式开关与其真跑验证

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-10-04 |
| 关联 | [ADR-061](ADR-061-多层交付面的已安装入口.md)（多层交付面的已安装入口）· REQ-172 |

## 决定

给安装器加**一个命令行开关** `/M2W_ADD_PATH=1`，在 `.onInit` 的 `preInit` 钩子里把**勾选框那同一个** opt-in 状态 `Var M2W_AddToPath` 置成 `"1"`；写入时机、判定条件、写入逻辑全部沿用勾选框那条既有路径，一行未改。

同时把 `check-install-smoke --execute` 从**一轮**扩成**两轮**：默认支（不带开关，期望装完 PATH 一条不变）+ 勾选支（带开关，期望装完恰好多出安装目录这一项、卸完逐条同序回到基线）。两轮各自跑完整生命周期。

### 开关名为什么是 `/M2W_ADD_PATH=1`

- **带 `=VALUE` 而不是裸标志**：NSIS 的 `GetOptions` 对裸标志也能工作，但带值顺带把「用户以为传了、其实拼错了」显出来（`DetailPrint` 会打出实际匹配到的串），且给日后加第二个值留了位置。
- **不带反向开关**（如 `/M2W_NO_PATH`）：反向开关会让「忘了传」与「显式不要」同形。本仓要的恰恰是后者不存在 —— 唯一状态就是「有没有这个开关」。
- **`=1` 而不是布尔词**：与「勾选框的 `M2W_AddToPath` 只认 `"1"`」对齐，同一个值在两条路径上含义一致。

### 为什么复用 `M2W_AddToPath` 而不是新 Var

`customInstall` 里那条 `${If} $M2W_AddToPath == "1"}` 因此**一字未改** —— 勾选框与开关走同一条判定、同一段写入逻辑（`m2w.ApplyPath`）、同一套约束（七条：追加不覆盖、已在则不重复、账本、超长不截断、广播、只摘自己那条）。

另建一个并行 Var 就等于两套写入逻辑：约束一漂移就得改两处，而这两处都在同一个文件里、只隔几十行，漂移几乎必然发生，且漂移的方向通常是「开关那条忘了加长度守卫」—— 那正是最坏的一种。

### 为什么置 flag 的时机是 `preInit`

`preInit` 在 `installer.nsi:55` 被 insert，位于 `Function .onInit` 内、`initMultiUser`（:77）之前，而 `customInstall` 在 `installSection.nsh:81`（安装段内）—— **时序上必然早于 `customInstall` 调 `ApplyPath`**，这是唯一硬要求。

`preInit` 里只置 flag，**不碰目录、不重复判定**：`ApplyPath` 用的是 `$INSTDIR` 本身，`initMultiUser` 也还没改写它，所以此处无需解析任何路径。

`preInit` **整段**按 `BUILD_UNINSTALLER` 守卫：`installer.nsi:55` 那个 insert **不在任何 `BUILD_UNINSTALLER` 分支内**，即卸载器那趟也会展开本宏；而 `$M2W_AddToPath` 与 `${StrStr}` 都是 installer-only，不守卫就是「引用不存在的 Var」（warning 6001）加「`${StrStr}` 宏压根不存在」（编译期直接失败）。

### 为什么用 `${StrStr}` 而不是 `${GetOptions}`

`${GetOptions}` 属于 **FileFunc**（LogicLib 里没有），且它靠 `Exch $1` / 一串 `Push` 做寄存器上下文的保存与恢复 —— 那套动作对「插入点的栈深」有前提要求，而本宏的插入点是 electron-builder 的 `.onInit`，它自己已经压过栈。实测内联 `${GetOptions}` 直接报 `Usage: StrCpy $(user_var: output) str [maxlen] [startoffset]`。

改用 `${StrStr}` 扫 `$CMDLINE`，两端补空格做整段匹配（与 `ApplyPath` 里判「已在 PATH 里」用的是同一条理由）：不补的话传 `/M2W_ADD_PATH=1` 会连带匹配到 `/M2W_ADD_PATH=10`。`${StrStr}` 是本文件**已在用**的机制（`ApplyPath` 里同一行写法），在 `.onInit` 里插入已知可用。

## 背景

`/S` 静默安装时 `PageEx custom` 那一页整个不跑 ⇒ `m2w.PathPageLeave` 永不执行 ⇒ `M2W_AddToPath` 恒为空 ⇒ `customInstall` 的 `${If}` 恒为假。**结论：写入与还原这两段逻辑在任何自动化安装里都从未被执行过。**

上一轮把整个 `.nsh` 修到能在 electron-builder 真实构建里编过（`-WX` 两趟零 warning），但那是**编译期**证据。`install-smoke` 此前实测「安装前 9 → 装完 9 → 卸完 9」—— 三段全平，因为勾选支根本没被走到；`diffPathEntries` 里那个 `consented` 分支早已写好，却从未被触发。

于是本仓存在一处**只在注释与推理层面成立**的能力：勾选框能加 PATH、卸载能摘掉，两句话都写在文件里，但真机上没有任何一次执行过它们。

## 备选方案

本节是本 ADR 的主要价值 —— **写清各自的失效条件，以便后来人不重复评估。**

**否决 · 让烟测去驱动 UI 真点勾选框。** 四条，任一独立成立：
- NSIS 无跨进程点击 API。要驱动 UI，得靠 `SendMessage`/UI Automation 找控件句柄，而句柄只在页面显示期间存在、随语言/缩放/主题变化 —— 门禁会变成一个脆弱的 UI 自动化脚本。
- 静默安装（`/S`）下**页面根本不显示**，没有控件可点。要点就必须放弃 `/S`，改用交互式安装 —— 而非交互环境（CI）里交互式安装会被 UAC 与无人值守的桌面会话卡住，这条路在 CI 上不可用。
- 门禁的沙盒纪律是「除授权的 `--execute` 外零系统副作用」。UI 驱动会把门禁的失败面从「判定逻辑」扩大到「自动化时序」，且**失败时可能停在半开的对话框上**，把执行环境搞挂。
- 即便做成了，被验的也是「UI 自动化能不能点中一个复选框」，而不是「写入/还原逻辑对不对」—— 后者才是 REQ-172 的目标。**验的目标与手段错位。**

**否决 · 让用户手测。** 用户手测能覆盖「勾选框真的能点、PATH 真的有效果」这条**端到端**链路（本 ADR 的开关**不能**覆盖这一条，见下「未验」），但不能进门禁：不可重复、结果无法作为判据、且事后无从核对。四条：
- 手工验证的结论无法被门禁复现 ⇒ 回归时无人拦截。
- 用户报障时无法区分「勾选框没生效」「写入逻辑错」「卸载没还原」—— 三者现象都是「PATH 里没有/多了那一项」。
- 本仓已有过「守卫静默退 0 骗过门禁」的前科（见 `check-install-smoke` 里 `pathEntriesAfterInstall` 那处注释）：靠人盯着的检查历史上就是会漏的。
- 与「能力缺口必须可判定」的门禁取向冲突：缺口要么被门禁钉住，要么被写进文档承认为未验，不能停在「用户大概试过了」。

**否决 · 把写入逻辑抽成公共段，勾选框与开关各自调用一次。** 表面上比「复用同一个 Var」更显式，实则更差：
- 「调用两次」正是要避免的形态：同一次安装里若两条路都触发（用户勾了框**又**传了开关），写入会执行两次。现有 `ApplyPath` 靠账本（`M2WPathWritten`）挡住第二次追加，所以不会真写坏 —— 但这依赖「幂等由账本兜底」而非「结构上不可能发生」，正是约束四那条账本的职责被挪作他用。
- 抽出公共段后，**长度守卫、`WriteRegExpandStr` 不做类型探测、广播 `WM_SETTINGCHANGE`** 这些约束所在的函数会同时被两条路引用 —— 一旦某条路绕过它（比如日后有人给开关那条加个 early return），七条约束的成立性就依赖人工记得同步。
- 复用同一个 flag 则这些风险**结构上不存在**：`customInstall` 只有一处、只判一次、只调一次 `ApplyPath`。

**否决 · 把开关做成 `nsis.include` 的第二个文件 / 在 `package.json` 里加键。** `nsis` 的 schema 是 `additionalProperties: false`（实测 `shortcuts` 被拒），加不了自定义键；而拆成第二个 `.nsh` 需要在第一个里 `!include`，那样它会**晚于** `MUI2.nsh` 被解析（`multiUser.nsh` 那类符号那时才可用），反而丢掉上轮刚修好的惰性解析性质。

## 落地时踩到并已修掉的坑（真跑才暴露）

**开关必须排在 `/D=` 之前 —— NSIS 的 `/D=` 把「从 `/D=` 到行尾」整段当安装目录。**

第一次真跑 `check:install-smoke --execute` 时勾选支直接判红，报的是「静默安装后安装目录不存在」。那个报错**完全指不到真正的原因**；查安装器留下的 `InstallLocation` 才发现真值是：

```
C:\Users\chenc\AppData\Local\Programs\MarkdownToWord M2W_ADD_PATH=1
```

`/M2W_ADD_PATH=1` 被 `/D=` 吞进了目录名，安装器于是一个不存在的路径当安装目录装了一遍：注册表写了、开始菜单快捷方式写了、文件没落到预期位置。门禁的残留自愈把卸载注册表项与快捷方式清掉了，但 `HKCU\Software\{APP_GUID}` 那个安装键（含被污染的 `InstallLocation`）**不在既有残留检查面上**（既有面只认 Uninstall 注册表根 + 开始菜单），需人工清理 —— 这本身是另一处已知的检查面缺口，记在下面「未验」。

修法是把次序固定成 `['/S', optInSwitch, '/D=' + dir]`，并在门禁里写明原因、在测试里**把次序本身钉成断言**（不只断言「带了开关」）。这个坑值得单独记：它是那种「编译期完全看不出来、只在真机上炸、且报错信息指向错误方向」的典型。

## 影响

- **默认行为逐字节不变**：不带开关时 `preInit` 什么都不做，flag 保持空串，`${If}` 为假 ⇒ 一条 PATH 都不动。`install-smoke` 默认支就是这条断言。
- **对外契约变了**：安装器命令行多认一个 `/M2W_ADD_PATH=1`。这是本 ADR 需要立档的原因（改对外接口）。
- **开关名有三处同名常量**：`installer.nsh` 的 `!define M2W_OPT_IN_SWITCH`、`check-install-smoke.mjs` 的 `PATH_OPT_IN_SWITCH`、测试里的 `OPT_IN_SWITCH`。**故意不解析 `.nsh` 去取**：解析 NSIS 源码会把门禁绑死在脚本语法上（改个引号风格就读不到），而开关名写错时三处一起错反而判定恒绿 —— 那比「改一处漏一处」更危险。代价是「改开关名要同时改三处」，已在此登记。
- 顺带修掉 `check-install-smoke.mjs` 的一处**既存**错误：`装完` 的条目数原先在断言阶段又读了一次实时 PATH，而那时卸载早已跑完，于是两个数字**恒等**、毫无信息量。现在取步骤 1 当时存下的快照（勾选支要报的正是「装完比装前多一条」）。
- 顺带把卸载后的口径从「集合无增删」收紧为「**逐条同序**」：集合相等放过「条目都在但被重排」，而重排恰是「用拼接/拆分重建 PATH 而非精确还原」这类实现错误的典型症状（那种错误在集合口径下完全隐形），且重排会改掉用户各条目的优先级。

## 未验

以下是本 ADR 落地后**仍然没有被证明**的，不因为门禁变绿而消失：

- **勾选框（UI 那条路）本身仍未真跑**。本开关只覆盖 `/S` 静默路径。`m2w.PathPageCreate` / `m2w.PathPageLeave`、复选框默认不勾、`/S` 下该页不执行 —— 这些仍然只有编译期证据与非交互环境下的推断。理由见上文「否决 · 让烟测去驱动 UI」。
- **`M2W_PATH_MAX` 超长分支（8191）未被执行过**。触发它需要构造一条超长 PATH；本轮两轮都在正常长度内，该守卫仍是编译期 + 代码审阅级别的保证。`${M2W_PATH_MAX}` 在 LangString 里编译期展开成字面量 `8191` 这件事已修，但「超长时不写不截断」这个行为没被跑过。
- **「用户装完之后自己改过 PATH」那条卸载分支（`Goto dropRecords`）未被执行过**。触发它需要在装完与卸完之间手动改 PATH，而门禁的两轮是背靠背的，中间没有插手机会。
- **`DetailPrint` 在 `/S` 下的可见性**只到「字符串会打印」这一层；`check-install-smoke` 收集安装器输出的那条通路在勾选支被真实走过后才第一次带上这条 `DetailPrint`，其内容是否完整落进失败日志，本轮未构造失败去验。
- **`SendMessage(HWND_BROADCAST, WM_SETTINGCHANGE)` 的实际生效**（新开的终端能否看到新 PATH）需要在真实交互式 shell 里确认；门禁只能验注册表值，不验 Explorer/终端的环境继承。

## 顺带发现的检查面缺口（未修，已登记）

上面那个 `/D=` 吞参数的事故暴露出：`check-install-smoke` 的残留检查只认**卸载注册表根 + 开始菜单 + 安装目录**三处，而 electron-builder 写的安装键 `HKCU\Software\{APP_GUID}`（含 `InstallLocation` / `KeepShortcuts` / `ShortcutName`）**不在这三处之内** —— 它与本仓的 PATH 账本同巢（见 `installer.nsh` 的 `M2W_LEDGER_KEY`），所以「卸载后这个键是否被清干净」目前**无人断言**。

本轮已人工清掉该次事故留下的键，且两轮跑完后复查确认不存在。但**门禁对它仍然失明**：下一次若安装器因别的原因半途中止，这个键会静默留下。本轮不在授权范围内，故只登记不修（`gates/artifacts/check-install-smoke.mjs` 的残留检查面扩展属另一件事）。

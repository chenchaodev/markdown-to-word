# ADR-013 · 发布供应链与「现阶段明确不签名」

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-09-26 |

## 背景

本条的前提是代码证书的采购与吊销是发布流程之外的长期负担，若让缺签名 fail closed，发布会被卡在流程之外（原文「理由」与「备选」行）。故现阶段明确不签名，把未签名作为**已知风险**对外说明，并用可追溯手段缓解：发布链补 SHA-256 报告、离线 SBOM、许可证 / NOTICE、action 固定到 40 位 SHA、环境指纹。自动更新继续排除，只保留手动检查 / 下载。已知代价：Dependabot 对 SHA 固定 action 的漏洞告警失效，且用户须自行判断未签名产物。来源：campaign 归档升格（REF-001）。

## 决定

### 2026-09-26 19:40:00 发布供应链与「现阶段明确不签名」(ADR-013)
- 决策:现阶段不采购/不接入代码证书,不因缺签名让 Release fail closed,未签名作为**明确风险**对外说明;发布链补 SHA-256 报告、离线 SBOM、许可证/NOTICE、action 固定到 40 位 SHA、环境指纹;自动更新继续排除,只保留手动检查/下载
- 理由:证书采购与 fail closed 会把发布卡在流程之外;供应链风险可用「可追溯 + 明确告知」缓解
- 备选:接入证书并 fail closed(否决:采购与吊销是发布外的长期负担)
- 代价:Dependabot 对 SHA 固定 action 的漏洞告警失效;用户须自行判断未签名产物
- 验证:`npm run check:supply` + `check:signature`
- 来源:campaign 归档升格(REF-001)
- 关联:本 ADR 的「实施约束」节(原独立状态文件已于 2026-09-30 撤销,耦合规则并入本节;该机器硬依赖曾由 [adr-020](ADR-020-文档体系迁移.md) 列为代价 2,同批退役)

## 实施约束:签名声明的三处同改(2026-09-30 补)

本条裁决是「暂不签名,未签名作为明确风险保留」。**风险被如实告知**的前提是三处一致,
故签名状态一旦**有意变更**(例如正式接入证书),必须**同批**修改以下三处,缺一即门禁判红:

1. `scripts/check-signature-status.mjs` 的 `EXPECTED_SIGNATURE_STATUS`(事实侧基准)
2. **本 ADR**「当前状态」表
3. `docs/USER-GUIDE.md` 的已知限制与 SmartScreen FAQ(用户侧唯一提示面)

### 为什么撤销那份独立状态文件

原那份独立状态文件的独特内容**只有上面这条耦合规则**与「下面的三态词汇」,
其余要么复述本 ADR 已有的理由,要么复述 USER-GUIDE 已有的用户须知。独立成文件带来两个负担:

- **生命周期相反**。ADR 是「会被取代的决定」,规则是旧条不改动只标取代;而状态声明必须随代码
  **反复就地改**(它自己的「更新规则」就是这么要求的)。把高频改动的东西放进 `docs/adr/`
  会违反 ADR 自身的约定。
- **把文档漂移治理写成了安全护栏的样子**。原守护测试里有一段只断言「文档中含某几个 token」,
  防的是**文档被编辑**,不是产品出问题;而同测试中断言打包配置无证书、断言 USER-GUIDE
  保留披露的那两段**与文档无关且已经足够**。该段已于 2026-09-30 删除,保留的每一段都断言真实属性。

**产物完全不变** —— 删掉那份文件与那一段断言之后,没有任何用户可观察的行为发生变化。
这正是判断它冗余的依据:它此前只在防自己被改。

### 三态词汇:为什么不能二值

`Get-AuthenticodeSignature` 的 `Status` 取值中,`NotSigned`(真的没签名)与
`NotTrusted`(有签名但证书链不受信)**语义相反**。把后者归入「未签名」即是谎报,
故一律映射为 `indeterminate` 并判红。`UnknownError` / `HashMismatch` / 空状态 /
大小写不匹配同理 —— **取不到事实不得当作「未签名」放行**。探测手段本身不可用
(如 CI 上 PowerShell 模块加载失败)单列为 `probe-unavailable`,与「状态无法判定」**分开**,
同样判红。

### 仍然保留的护栏(删掉的只是那段文档断言)

- 打包配置不得出现证书键;`forceCodeSigning` 不得为 `true` —— 它与本条裁决冲突,
  且会让发布链在无证书时直接失败
- `docs/USER-GUIDE.md` 必须保留 SmartScreen 说明与未签名披露
- 三态映射与探测失败的判定逻辑各有正/负锚点,并先用**合成输入**证明判定函数会抓错,
  再用于真实配置

### 随包分发的可执行入口:不进那道签名判定面(2026-10-03 补)

上面那三道护栏与那道判定面都**以 `.exe` 为判定面**:签名探测递归扫 `release/` 下所有
`.exe`,期望恒为未签名(判据见 `gates/artifacts/check-signature-status.mjs` 的
`EXPECTED_SIGNATURE_STATUS` 与文件收集逻辑),「明确不签名」的范围因此是**全部 exe 产物**。

[ADR-061](ADR-061-多层交付面的已安装入口.md)新增了一个**随安装包分发的可执行入口**
`m2w.cmd`(命令行转发器)。它**是 `.cmd`,后缀不匹配 `.exe`,因此不进入那道判定面**。

**这一层关系要如实说清,三个词都不能混**:

- 它**不是「已签名」** —— 它根本没有签名,与本条「明确不签名」的立场一致,无矛盾。
- 它**不是「漏检」** —— 漏检指「该判而没判」。它不在判定面内是**判定面的定义**
  (只扫 `.exe`)决定的,不是探测失败、不是「取不到事实」。
- 它**确实没有被扫到** —— 这是事实本身。签名状态对它是 `indeterminate`(未探测),
  而按上面「三态词汇」那节的纪律,**取不到事实不得当作「未签名」放行**;这里恰恰相反:
  不在判定面内的文件**根本不产生状态**,连 `indeterminate` 都不是。

**对本条裁决的影响:无。** 本条立的是「暂不签名,未签名作为已知风险保留」,不是
「每个可执行文件都必须被签名探测覆盖」。新增一个未签名的纯文本转发器不改变立场,
因此**不触发**上面「签名声明的三处同改」—— 那条规则的触发条件是「签名状态**有意变更**」,
而这里签名状态没有任何变更。

**要不要补别的护栏:当前不需要,但边界要说清。**

- 现有那道判定面(打包配置不得出现证书键 · `forceCodeSigning` 不得为 `true`)对
  `.cmd` **同样成立** —— 它约束的是打包配置,不是文件后缀。新增 `extraFiles` 不触碰那两个键。
  依据读自 `package.json` 的 `build` 段(证书键与 `forceCodeSigning` 均不在其中,
  `extraFiles` 与那两个键互不相关),**非实测**。
- **不建议**为了覆盖这个 `.cmd` 把判定面从「扫 `.exe`」扩成「扫 release/ 下全部文件」。
  签名探测走 Authenticode,批处理文件不在其判定对象内,硬扩只会造出一条恒红或恒真的假判据。
  判定面应保持「只扫它真正能取到事实的那类文件」—— 这与「取不到事实不得当作未签名放行」
  是同一条纪律的两面。
- 真出现「用户把 `.cmd` 当可疑执行体上报」这类情形时,处置方式是**如实告知它是未签名的
  纯文本转发器**,而不是给它补签名或悄悄改判定面。

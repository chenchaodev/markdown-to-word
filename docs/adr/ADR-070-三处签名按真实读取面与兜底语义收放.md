# ADR-070 · 三处签名按真实读取面与兜底语义收放

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-10-06 |
| 关联 | [ADR-069](ADR-069-dist产出声明文件.md) 打开产物类型面后本条才成立 ｜ 与 [ADR-066](ADR-066-转换契约类型化.md) 同属「签名必须等于运行期契约」这一条线 |

---

## 决定

把三处「类型与语义相反」的签名改成与运行期契约一致，各按其**真实读取面**与**真实兜底语义**收放：

1. **`matchesPreset` / `resolvePresetSelection` 的 `settings` 入参收窄**成 `PresetMatchSettings` —— 排版与页面设置**必填**，交付链四块（`headerFooter` / `watermark` / `equationNumbering` / `breakBeforeH1`）**可选**（实现里本就有「缺任一侧即该项不参与比较」的分支）。
2. **`mergeSettingsWithDefaults` 的入参放宽**成 `SettingsMergePatch` —— 顶层浅可选 + 逐字段兜底的那五块（`typography` / `headerFooter` / `watermark` / `aiCleanup` / `obsidian`）**块内也浅可选**；不在该清单内的字段保持浅可选不变。
3. **harness 的转换上下文构造器**（`convertWithFs` / `convertTyped`）把入参类型从 `Record<string, unknown>` 改成 `Record<string, unknown> & Pick<ConvertContext, "baseDir">` —— **纯类型**约束，运行期一字不改。

## 背景

**一、为什么现在动这些签名。** ADR-069 打开了 `declaration`，构建产物开始带 `.d.ts`。此前产物无声明文件，测试树里每一处 `import … from "../../dist/…"` 的类型都等同于 `any` —— **整个测试树对产物的引用从来没被类型检查过**。真实类型一到位，积压错误浮出，其中一批不是夹具写错，是**按声明写不出该函数的正当调用**：声明面比运行期契约窄（该宽的宽了、该严的严了）。

**二、实测否决了「改夹具」这条路，故修法是签名而非夹具。** 曾试过对 `resolvePresetSelection` 的夹具「按默认补齐」以满足类型 —— **该段从绿变红**：`settings-logic 断言失败:选中项与设置不一致 → 回退全局匹配(paper)`。读源码才看清原因：该函数只经 `matchesPreset` 读排版与页面设置，而**补齐其余字段会改变匹配结果**（交付链四块本就参与比较）。⇒ 夹具是对的、签名过宽。**为了让类型通过而改掉被测语义，方向是反的。**

**三、harness 那两条的成因不同。** `ConvertContext` 必填 `baseDir`，而 60+ 个调用点只传 `{baseDir, warnings, …}` —— 之所以此前不炸，是因为 `Record<string, unknown>` 这个入参声明**把必填性一并抹平**了。故此处只需把既有事实写进类型，不需补默认值。

**四、①②的真实读取面都比「字面看起来」的大。** `matchesPreset` 读六块而非两块（题面直觉里的「只读排版与页面设置」不成立）；两个 merge 函数逐字段兜底的块也不是全部字段。**收放必须按实现逐块核对**，按直觉取「排版 + 页面」两字段会让 `matchesPreset` 的实现体自己判红。

## 备选方案

**否决 · 补齐夹具以满足类型。** 实测使 `settings-logic` 段判红（见「背景」二），证据是那条具体断言与 `paper` 预设 ID。这正是「为了让类型通过而改掉被测语义」—— 用一条看起来正确的夹具换掉被测对象的行为，方向错了。

**否决 · 用 `any`（或整对象 cast）放宽入参。** 与 ADR-069 相悖：本条的起因正是产物类型面到位，测试第一次被真正类型检查；`any` 会把那道刚建起来的检查再拆一次，且掩盖真实缺口。

**否决 · 套一个全局 `DeepPartial<T>`。** 会把 `customPresets` 这类「整块替换、从不逐字段兜底」的字段也一并放宽 —— 声明面比运行期契约宽，与本条要修的是同一类毛病，只是方向相反。改为**只逐块列举**那五块（清单在实现处单点持有，两个签名从它派生）。

**否决 · 给 harness 的 `baseDir` 补一个运行期默认值（如 `""`）。** 改行为：core 只在 pdf 分支把 `baseDir` 交给图片边界判定（经 `path.resolve`），`undefined` 与 `""` 在那里并不等价；且凭空补默认值等于替调用点做它该自己做的决定。实测 60+ 调用点**无一省略** `baseDir`（唯一三处「省略」是注释里的散文提及），故只需把既有事实写进类型。

**否决 · 只改 `resolvePresetSelection` 不动 `matchesPreset`。** 二者成对：单独收窄前者，其函数体把该值交给后者时立刻判红（实测 TS2740）。且只收窄前者会让「该可选的交付链四块」变成必填，与实现里现成的 `undefined` 容忍分支矛盾。

**不做 · 把 `pendingSavePatch` 台账与 IPC `settingsSet` 的 patch 类型一并放宽。** 那是本条的**后续项**而非本条内容：它要动 `src/core/preload-api.ts` 与 `src/main/**` 的跨进程契约（对外接口 + 跨进程数据格式），范围与风险都超出「renderer 设置逻辑层」这一层。留作单独一条，见「后果」。

## 后果

**收益。** 三处签名与运行期契约一致：产物类型面第一次真正约束到这些函数上，而不是靠 `any` 蒙过去。①② 落地后 `settings-logic` 段的类型红由 17 条降到 9 条（余下 9 条属别处，见下），harness 两条 `baseDir` 归零。

**收窄会让哪些调用点变红 —— 已实测核对，无一被误伤。** 收窄 `matchesPreset` 的入参只影响**类型面**：仓内既有调用点（`settings-logic` 的两处、测试段若干处）传的都是完整 `AppSettings`，它是 `PresetMatchSettings` 的子类型，故一条未红。反向风险已排除：若收得更窄（例如只留两字段），实现体自身会因读不到可选块而判红。

**放宽会让哪些调用点变红 —— `mergePendingSavePatch` 是唯一受阻的一处（见下）。** `mergeSettingsWithDefaults` 侧既有调用点（`settings-panel` 两处、测试段若干处）全都通过，因为放宽只增不减可接受面。

**`mergePendingSavePatch` 未在本条落地，代价是它那 3 条类型红仍在**（`settings-logic` 段 560、585 两行）。原因是它的返回值会流向 `pendingSavePatch` 草稿台账与 IPC `settingsSet`，而后两者的 patch 类型是**跨进程契约**（`src/core/preload-api.ts`、`src/main/**`），不在本条的改动面内。**这不是「没想到」，是刻意划界**：改它要动对外接口与跨进程数据格式，须单独决策。

**后续约束（三条）。** ① 若将来把 `mergePendingSavePatch` 的 patch 类型一并放宽，须同批放宽跨进程侧的 `settingsSet` 契约，否则那条链上会出现同一处类型在进程内是深、在进程外是浅的错配。② **未来若某个 merge 函数不再逐字段兜底某块，签名须相应收回** —— `SettingsMergePatch` 的块清单是实现的投影，不是「看起来该有的宽松」；实现改成整块替换的那一刻，那一块就要从清单里去掉。③ `PresetMatchSettings` 里交付链四块的可选性**直接对应实现里现成的 `undefined` 容忍分支**：删掉那个分支（即改成「缺 settings 侧即不匹配」）就必须同步把该块改成必填，否则类型会比实现宽松。

**已知但不在本条范围的两条。** `matchesPreset` 的实现体原先直接读 `settings.headerFooter` / `settings.watermark`（守卫只判了 preset 侧），本条把它们先绑到局部变量再比较 —— **纯局部变量提取，运行期语义逐字不变**，只为让收窄后的可选性在实现体里自洽。`mergeSettingsWithDefaults` 的返回类型仍是完整的 `AppSettings`，本条只放宽其入参，不动出参。

**判据形态。** 「merge 的入参形状 = 实现里逐字段展开的块集合」是一条**内容**型判据，需要读实现而非扫位置，故不适合做成机械门禁 —— 现阶段靠本 ADR 与实现处的单点注释共同看守。

## 决定

**本仓的主目标是「练 AI 开发流程」，「做成有人用的产品」是次要目标、不是判据。** 据此定四条具体做法：

1. **排期判据换轨**：后续排期的首要判据是「**哪项技能还缺外部输入**」，不是「哪个功能 ROI 高」。判据载体是技能矩阵快照（16 项技能 × 验证通道 × 可复算证据）与台账 REQ-264~REQ-270。
2. **功能增量默认不排期**：新功能提议在出现需求信号（REQ-265 跑出的、被外部用户指名过的需求）之前不占台账排期；已在台账的 10 行待拍板保持不排期，直到重看条件触发（每行都写了条件）。
3. **商业路径只作条件性备选**：A 分发与信任 / C MCP-CLI 本体化 / D 收窄滩头 三条登记在台账 REQ-272~REQ-274，各自的启动条件写在「什么条件下重看」列——**它们不因"看起来该做"而启动**。反面选项 E（维持现状：继续加功能 + 保持发版节奏）明确不作登记。
4. **三条不做**：① 不买代码签名证书（沿用 REQ-050 的终审，除非出现企业 / 内网强制签名准入）；② 不做 macOS / 跨平台（**组织成本不是工程成本**：未公证 app 打不开须推翻 ADR-013；且 PDF 默认字体落到 mac/Linux 会静默换字体 ⇒ 分页变、目录页码漂）；③ 不做库模式 npm 包装（除非 MCP 通道达标）。

另外一条**讲法**上的修正（不是新的功能决定）：**"本地离线"继续讲，但不再当作差异点**——外部调研显示它正在被复制为基线要求（网页版本地处理、断网可用；WPS 智能文档主打离线编辑）。它是合格线，不是卖点。

## 背景

2026-10-22 用户澄清：**做这个项目的主目标是学 AI 开发流程**（全局 agent 规则梳理、测试驱动开发、GitHub 流程），不是做产品。澄清之后，本轮把此前散在对话里的三条调研（仓库盘点 / 外部竞品与需求侧 / 战略评审）落盘核对，两条线互相印证：

1. **技能侧**：16 项技能中 8 项已练，但**验证通道全是自证闭环**（自己出题、自己判分）；另 6 项**零外部输入**（需求获取、优先级取舍、缺陷分诊、协作评审、可用性实测、真实被使用与升级运维）。仓里那份 2026-08-08 就写好的真人测量规程（第 84-93 行）**从未执行过**，全仓不存在任何一份真人测试结果载体。
2. **市场侧**：2.5 个月、约 60 个 release 之后，外部触达是 **1 star · 0 fork · 0 issue · 全部 release 资产累计下载约 30 次**；待拍板 10 行里 5 行是作者自己 2026-08 否决、2026-09-29 又恢复的（决策债务，不是需求信号）。
3. **两条线合起来的结论**：这个项目把全部不确定性都内部化成了 86 份 ADR、142 份事实快照与 58 步门禁，而对外的信号通道只有一条。若继续按"加功能"这个默认路径走，练到的仍是已练透的那半边技能，而另一半永远不会被触及。

所以本条不是"要不要做产品"的裁决，而是**排期判据换轨**：把注意力从自证闭环移到真实输入。

## 备选方案

- **否决 · 维持「做产品」定位** —— 它是仓内流程的默认路径、不需要任何新决策，因而默认引力最大；但它自己的领先指标是平的（约 30 次下载 / 1 star / 0 issue），且它继续练的正是已经练透的那半边技能，还会放大"42 个抽屉控件"这个采纳障碍。
- **否决 · 纯作品集定位（明确不追求需求验证）** —— 那会连 B 组六项也不练，把"用 AI 做软件"退化成"用 AI 写代码"。作品集仍然需要真实反馈才能说明它是作品而不是草稿。
- **否决 · 两条线并行且不排序** —— 在没有外部约束的环境里，所有决定都会变成"更正确"；并行只会把默认引力放大，而不是把判断力练出来。**排序本身就是要练的东西**：B 必须在 C / D / A 之前，因为没有一手需求，其余三条都在猜。
- **否决 · 把这条定位写进全局配置仓当通用规则** —— 定位是**本项目的事实**，不是对所有项目成立的方法论；写进全局会变成对无关项目的约束。方法论（规则怎么写、判据怎么落）才是可迁移的那部分，见 REQ-270。

## 后果

**好处**

- 排期有了单一判据（"缺不缺外部输入"），不再靠"哪个功能看起来重要"，也不需要靠 star 数这种既无外部输入又无判据的指标。
- 已有投入不浪费：86 份 ADR、99 道门禁、10 个验收段构成的**自洽基线**是 B 组六项的前置——外部输入进来以后得靠它接住（改不动、说不清、回归不了）。所以本条不是否定 A 组，而是**A 组已够用，该换 B 组练**。
- 六项空白各自在台账占一行（REQ-265~REQ-270），"没练"这件事不再靠记忆。

**代价**

- 功能与发版节奏会明显放慢；对外的 star / 下载数不再是成功指标，这会带来"我在做无用功"的错觉风险——**对策是那张矩阵本身**：每季度复看一次，看的是 B 组的命中数有没有变。
- 台账上会长期存在若干"待拍板"行，看起来像待办堆积——它们是**登记完备**而非积压，每行都写了重看条件。
- 商业路径三条（A / C / D）默认不启动，意味着放弃一部分本来可能带来用户增量的机会；这个代价是显式接受的，换来的是不再把工程投入摊到更窄的受众上。

**以后受本条约束的地方**

- 新功能提议进来 ⇒ 先问"有没有被外部用户指名过"；没有 ⇒ 不占台账排期。
- 商业路径的启动 ⇒ 以对应台账行「什么条件下重看」列为唯一依据，不由"看起来该做"触发。
- 复看节奏 ⇒ 每季度一次，或本仓出现第二维护者 / 第一个外部用户时。

**与既有 ADR 的关系**

- **不取代 ADR-086** —— 其第 9 条「产品定位不变：docx 回读是工具箱里的一件工具，不进主转换路径，不改首页与 README 话术」**限定在 docx 回读这一项决定内**，不是全局定位锁（复核原文见战略评审快照第七节）。本条与它不冲突。
- 沿用 [ADR-013](ADR-013-发布供应链与明确不签名.md) 与 REQ-050 的不签名终审；沿用 ADR-014 的双管线独立与 ADR-060 的四层交付面。**本条不改动任何技术决定**，只改排期判据与对外讲法。

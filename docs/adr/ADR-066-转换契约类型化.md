## 决定

三件事一并决定，因为它们共用同一个病根（跨层契约没有类型）：

1. **转换进度**从跨层裸 `string` 改为 core 导出的**穷尽判别联合 `ConvertStage`**；
2. **装配层返回值**在 `warnings` 之外增加结构化降级清单 `degradations`；
3. 每个交付面**声明**自己的能力集，「支持哪些格式」由声明派生，不再各写一份硬编码分支。
   > **本条已撤步、不做**（正文按规矩未改动）：撤回理由见 [`20261007-083000-ADR-066决定3能力声明撤步裁决`](../evidence/20261007-083000-ADR-066决定3能力声明撤步裁决.md)。一句话：**能力差异是真的，但差异的轴不是「支持哪些格式」** —— 现状已由 `src/core/convert.ts:3-13` 那份手工维护的清单处置，而本条唯一值钱的判据「机械比对声明 vs 分支」经实测不可达（两侧没有共同的可枚举词表）。

## 背景

一次全仓架构评审实测出的缺口：**唯一一条从 core 穿到 renderer 的用户可见流全程是 `string`，而「装配层不知道发生了什么降级」逼出了重复解析。**

**一、进度全程裸字符串，词表有三份、payload 有三种形状。** core 的 `onStage?: (stage: string) => void` → 装配层 `onProgress?: (stage: string) => void` → 渲染层两张 `Record<string, …>` 阶段表。渲染层的表是**开放**的：文案表按 8 个字面量键声明（`read`/`render`/`done`/`parse`/`inline`/`mermaid`/`katex`/`print`），但取值函数签名是 `string` 并靠「未知键原样兜底」维持；百分比表整体是 `Record<string, number>`，消费处用 `?? 0` 与 `!== undefined` 兜底。⇒ **拼错阶段名不编译报错，只静默显示原始 key。** 批量契约另有第三个形状（`BatchProgressInfo`）。

用户可见后果：docx 转换 3 段进度、pdf 7 段 —— 而这不是能力限制，docx 渲染本身就有 prescan → 内容渲染 → 组装三个天然边界。

**二、pdf 特有知识泄漏到 UI 层。** 「`printToPDF` 阶段不可中断」这条只对 pdf 成立的知识，以按 stage 字面量判断的特判形式出现在 convert 事件层。core 若只声明「发哪些阶段」，这个特判就退化为「宿主能力是否可中断」的显式声明。

**三、降级清单缺失逼出一次重复解析 markdown。** 装配层只返回 `warnings`、不返回「发生了什么降级」，于是每个无 mermaid 宿主的面都得自己复制一份「core 会降级什么」的知识，并**抢在渲染前**算一遍 —— `src/mcp/tools.ts` 为此第二次 `parseMarkdown`，注释写明「渲染完再回头查就晚了（产物里已经没有任何线索能区分『本来就没有图』与『图没渲出来』）」。这是把判断抢到渲染前的唯一理由，而这个理由本身源于信息缺口。

**四、交付面能力差异靠函数体字面量。** `src/mcp/tools.ts` 把格式写死在函数体里（`format: "docx"`），cli 支持 docx/pdf/both，三处并列的格式判断。**能力差异的原因是真实的**（mcp 无 `printToPDF` 宿主），**机制是错的**：原因在函数体里既不可枚举也不可测，改一处能力要记得改三处分支。

**五、契约里已有一个正确的样板。** `core/ipc-contract.ts` 已经是跨进程契约的单一来源，`state/state.ts` 从它取批量契约类型（`BatchItem` / `BatchProgressInfo` / `BatchResult`）并保留 re-export 以维持既有导入路径。**类型单源这件事在本仓已经做通了一次**，本条是把它扩到进度与降级 —— 不是引入新做法。

**六、同类边界类型问题的另一半已由别处裁决。** `ConvertContext` 在 core 与装配层各有一份、同名不同形（纯数据 25+ 字段 vs 5 字段 ＋ cancel ＋ getter），类型系统区分不了。改名与拆分归 ADR-064 第 2 条，本条不重复裁决，只承接那一条的结论。

## 备选方案

**否决 · 只给进度加类型，降级仍走 warnings。** 降级是当前**唯一**逼出「重复解析 markdown」的原因。不解决它，就等于把装配层的信息缺口原样留着，只把好解决的那一半解决了；而缺口留下的那半会以「第二次解析」这种看不出成因的形态长期存在。

**否决 · 让每个交付面继续自己预测降级，但抽一个共享的预测函数。** 那是把「core 会降级什么」这份知识**复制第二份并固化**：core 改降级策略时它必须跟着改，而没有任何判据会提醒你。共享函数消掉的是代码重复，不是知识副本 —— 单一来源的收益在它那里拿不到。

**否决 · 进度继续用字符串，靠一张穷尽的常量表在运行时校验。** 漏一个阶段仍是**运行期**才发现，且要等那条路径真的跑过（新增管线阶段时不跑那一档的段就静默绿）；判别联合是**编译期**漏。运行时校验还要多一处抛错路径，收益只是把同一个错误换个时机报。

**否决 · 用 `enum`。** 跨层共享的契约类型不该是运行期实体：它擦除不掉地进入产物、在 JS 侧变成一个真值（与「阶段只是一个字符串」的事实不符），也会给 core 引入本不该有的运行期形状。core 的零依赖取向在这里也受影响 —— 判别联合是纯类型，不产生任何运行期依赖。

**否决 · 能力声明只写在文档里，不落成结构化声明。** 「MCP 为什么不支持 pdf」是真实且已定的产品决策，但它现在只活在 `tools.ts` 的函数体与文件头注释里。写进文档仍然是两份知识（文档一份、代码一份），而代码那份不会被文档提醒同步。**结构化声明的价值在于它可被机械比对**，不在于它好看。

> **本条否决的对象是「文档版声明」，与决定 3 撤步后的现状形态不同，须分开读。** 撤步后的现状是**清单在代码注释里**（`src/core/convert.ts:3-13`），载体是代码而非文档，两者不互相顶替。更要紧的是：这条否决**预设了「可被机械比对」可达**，而该预设已被实测证否（两侧没有共同的可枚举词表，见撤步裁决 §二理由三）⇒ **把一个不可达的目标从文档挪到代码，得到的正是它自己否决的那一项、只换了载体**。这条否决与决定 3 撤步不冲突：它否决的是文档形态，撤步否决的是结构化声明形态。

## 后果

**代价。** core 与 renderer 的进度／降级接口签名变更（跨层契约），两端必须同批改；renderer 那两张阶段表漏键会从「静默绿」变成「编译红」——**这是有意的**，它是本条的主要收益被看见的地方。

**文档连带。** `CHANGELOG` 无需记（内部契约变更，非用户可感知的行为变化）。⚠ **原文写「docx 进度段数从 3 段变多属用户可观察，实施时须核对用户手册」——该预判未兑现**（引述不复现原路径字面量：本 ADR 位于 `docs/adr/`，原写法在本目录下解析不到目标文件）（2026-10-07 订正）：实施后实测 docx 仍发 read/render/done 三段、pdf 七段，与本条「不做的事」里「不统一 docx 与 pdf 的阶段数量、是否补齐属另一条决定」自洽。`docs/USER-GUIDE.md` 已按**实际**补一段（两格式阶段粒度不同 + PDF 写入段不可取消），不是按「段数变多」补的。

**收益。** 两条管线各自声明发哪些阶段之后，「docx 粒度粗」从**省略**变成**声明** —— 省略是不可见的缺陷，声明是可被评审的取舍。降级清单一旦由装配层给出，MCP 那次重复解析连同它的注释一起消失。

**以后会受它约束的。** ① 新增转换阶段必须同时改 core 的联合类型与 renderer 的表，编译期强制；② ~~交付面新增能力只改它自己的声明，判据可机械比对「声明 vs 分支」~~ —— **本条随决定 3 一同撤步**：该判据经实测不可达（声明侧说「支持哪些格式」、分支侧判「哪些条件走 pdf 路」，无共同的可枚举词表），留着即「规则与实际不符」。**交付面能力差异的现状处置**是 `src/core/convert.ts:3-13` 那份手工维护的清单，它不由本条约束；③ 「core 会降级什么」的知识此后**只允许存在一份**，任何面内再写一份即为漂移。

**不做的事。** 本条不统一 docx 与 pdf 的阶段数量。docx 补齐三个天然边界是**能力对齐**（两条管线的进度语义变得可比），不是本条的目标 —— 本条只保证「声明什么就发什么」这件事可判定。是否补齐、粒度取多少，属另一条决定。

**实施时的连带项。** core 的 `onStage` 与装配层的 `onProgress`、跨进程契约 `ConvertProgressPayload`、批量契约 `BatchProgressInfo` 是**同一个字段名的四次声明**，改动必须四路同批 —— 漏一路的表现是「编译红」或「某个面静默不显示进度」，后者更难查。`state/pure.ts` 那两张表的开放索引签名也要一并收紧，否则联合类型在渲染层立刻被重新摊平。

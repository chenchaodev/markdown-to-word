## 决定

`tsconfig.json` 开 `declaration`，让构建产物带 `.d.ts`；测试里的类型引用改指构建产物而不是源码。

**与「是否对外发 npm 包」解耦 —— 本条独立做，不等那个决策。**

## 背景

一次全仓架构评审实测出的缺口：**测试全部跑要发布的那个产物，类型面却查的是源码 —— 两者不是同一个东西。**

**一、测试 import 构建产物而非源码，这个取舍是对的，不要改。** 全部验收段跑的是 `dist/**`。理由有三条：必须跑要发布的那个产物；产物是 ESM 与 CJS 混编、类型擦除已完成，而**这些形态只在产物上可测**（沙箱 preload 的 CJS 形态、`export type` 与 `import type` 的擦除）；改成 import 源码等于测另一个东西。

**二、由此产生一个隐性错配。** 因为产物不带 `.d.ts`，测试里那些 `@typedef {import("../../src/…")}` 引用**只能指源码** —— 于是形成一处错配：**检查的是源码的类型，跑的却是产物**。类型面与被测物不是同一个东西，而这件事不会红。

**三、两个纯类型模块在覆盖率豁免清单里的解释因此是必需的。** `dist` 侧它们只有 `export {};`（无可执行语句），而带 source map 的覆盖率报告把整个 `.ts` 源记成未覆盖。`check-coverage-zero` 的豁免分类里有 `empty-module` 这一档，`coverage-baseline.json` 里两条纯类型模块的 `reason` 都是围绕这件事写的。有了 `.d.ts` 之后，**这个解释不再必要** —— 不是变得不重要，是不再需要。

**四、台账已记载：产物不产 `.d.ts` 是对外暴露类型的唯一障碍。** 本仓 `private: true`，无 `bin` / `exports` / `types` 键；`tsconfig.json` 无 `declaration` 键。做完本条那个障碍直接消失。**但是否对外发包是产品决策，不因此自动开工。**

**五、类型引用指源码的规模不小。** 实测有三十余个段用 `@typedef {import("../../src/…")}` 引用类型 —— 集中在 core 契约（`core/convert.js` 的转换产物、`core/ipc-contract.js` 的跨进程契约、`core/i18n/index.js` 的字典与警告构造器）。它们**只对类型门禁负责、运行期擦除**，所以形态是安全的；错配也正因如此**不会在运行期暴露**。

## 备选方案

**否决 · 测试改成 import 源码。** 等于测另一个东西（见「背景」一），并且会丢掉产物形态的全部覆盖 —— 沙箱 preload 的 CJS 形态与类型擦除恰恰是**只有产物上可测**的那些性质。拿一个能立刻写出来的改法换掉一批不可替代的覆盖，方向错了。

**否决 · 测试里继续 `@typedef` 指源码（保持现状）。** 那正是当前的隐性错配：类型面与被测物不是同一个。它不报错、不变红，所以它会一直待在那儿 —— 而它的失效形态（一个类型改了、被测产物没跟上，或反之）恰好落在「静默」那一侧。

**否决 · 等「是否对外发包」的产品决策一起做。** 绑定的代价是**产物类型面继续缺失**，而收益只是一位产品决策的时点。本条本身就有独立收益（测试获得对真实产物类型的完整检查），不为一个还不存在的消费方押上它。

**否决 · 只在 `dist` 里手写 `.d.ts`（不碰 `tsconfig`）。** 手写的声明文件与源码之间没有任何判据会保持一致 —— 它会静默腐化，且腐化形态恰好是「类型与产物不符」这一最难查的一类。

**否决 · 开 `declaration` 但只对外发，不改测试的类型引用。** 那样只解决了「对外暴露类型」，而当前**没有**对外消费方 —— 本条最大的现实收益恰恰在测试侧（类型面与被测物归一）。只发不改测，等于把一个独立收益换成了一个还不存在的消费方。

**否决 · 用 `declarationMap` 一并解决「点进去看到源码」。** 那会把 `.ts` 源打进产物面，与打包清单只收 `dist/**` 的边界冲突，且源码已随仓库可得 —— 这一项收益不值得开一个新的连带项。

## 后果

**必须同批做的连带项**（漏了会红）：① 打包清单要排除 `.d.ts`，否则声明文件会被打进安装包；② 产物清单门禁的期望清单要更新（产物多出一类文件）。

**收益。** 测试获得对**真实产物类型**的完整检查，类型面与被测物归一；两个纯类型模块在覆盖率豁免清单里的那条解释随之可以退场。

**与库模式决策的关系。** ADR-060 把库模式（摘 `private: true`、写 `exports`）挂在「是否对外发 npm 包」的外部事件上。**本条不推那个决策，也不因那个决策未拍板而挂起** —— 本条的收益不来自对外暴露类型，而来自测试自身。

**以后会受它约束的。** ① 测试树里的类型引用一律指 `dist/`，指 `src/` 视为漂移（当前这批 `@typedef` 要在同批改掉）；② 产物新增文件类型时，打包清单与产物清单门禁两处必须同步。

**③ `check:docs` / 指针类门禁要同批核对。** 本仓已有一批门禁负责抓「注释与代码不一致」，而本条改的正是「类型引用指哪棵树」这类**写在注释与 typedef 里**的事实。改完若指针门禁未同步，它会在下一次运行时判红，而那条红与本条无关（是漏了连带项）。

**④ `noUncheckedIndexedAccess` 等严格选项对 `.d.ts` 生效。** 判别联合收紧后，源码侧原本靠 `?? 0` / `!== undefined` 兜底的访问会变红 —— **这是本条要的效果**，但要预期它会在 `state/pure.ts` 那两张表的消费处集中出现。

**不做的事。** 本条不新增 `exports` / `types` 字段、不摘 `private: true`、不发布任何包。那三件各自属于「是否对外发包」那个产品决策，本条只在**技术上**把它的前置障碍清掉。

**本条也不解决「类型引用指源码」的历史遗留判断。** ADR-064 当时记「它们指 `src/` 而非 `dist/` 是**不得已**（dist 不产 `.d.ts`）」—— 那条判断在今天成立，**在本条落地后失效**。ADR 正文按规矩不改，但它引用「指 `src/`」时须带本条的实测。

**判据形态。** 「测试树里的类型引用不得指向 `src/`」是一条**位置/内容**型判据，可用现有的 test 位置面判据表达（按段扫 typedef 目标），不需要闭包分析 —— 这也是它应当与宿主分档（要算传递闭包）分开建判据的原因：**一个判据只做一件能机械判定的事。**

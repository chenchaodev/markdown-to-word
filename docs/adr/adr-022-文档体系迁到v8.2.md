### 2026-09-27 文档体系迁到全局 v8.2：REQ 兼需求总池，LOG 只留判断依据(ADR-022)

- 决定 1 **`docs/REQ.md` 兼作需求总池**：**提出需求时**（不是开工时）取号登记一行、状态「待拍板」；**开工时先查本表**，已有该需求就**只把状态改成「在办」并沿用原号**，禁止另取新号。本表**只写「是什么、在哪」**，理由与触发条件不写在这里。
- 决定 2 **`docs/LOG.md` 只装「为什么落到这个状态」**：① 判断依据表，**按号索引**，号只许出现在这张表里；② 考虑过但否决的方案。**需求清单不在本文件**。
- 决定 3 **状态取值域改为全局 v8.2 的五个**（`待拍板` / `未开工` / `在办` / `已完成` / `已作废`），并**实际取消两个值的用法**：`未开工`（v8.1 为「号已分配但需求从未开工」而设）由「还没决定 → `待拍板`」「决定不做 → `已作废`」这一拆分取代；`暂缓` 是 v8.1 的值，v8.2 已取消。
- 决定 4 **`暂缓` 的语义不丢，改由两处承载**：REQ 状态仍是 `待拍板`，**LOG 判断依据里写了「触发条件」的就是「已决定推迟」，没写的就是「还没决定」**。这是本次迁移唯一的信息压缩点，代价是两种情形在台账里不再可区分 —— 故要求推迟的条目**必须**在 LOG 写触发条件，否则会被读成「没人决定过」。
- 决定 5 **原三张表（待拍板 / 暂缓 / 不做）整体删除**，其事项进 REQ 登记表、理由进 LOG 判断依据；`已作废` 的需求在 REQ 里 `~~` 划掉保留（号永不复用），在 LOG 留否决理由，**两侧行都永久保留**。
- 理由一：**「有哪些需求」与「为什么是这个状态」是两个不同的问题，混在一份文件里必然有一份是过期的。** 原三张表把事项与理由并排，`docs/REQ.md` 只有号没有状态、状态全在 `docs/LOG.md`，于是「这个号现在什么状态」必须同时读两份文件才能答 —— 而 v8.2 之前开工时只需扫一眼 `docs/LOG.md` 的待拍板表，这是它唯一的优点，代价是台账失去了作为需求总池的能力。
- 理由二：**「未开工」是含糊中间态的真实代价已经付过了。** 33 条从未开工的项挤在一个值里，导致「哪些还活着、哪些已被否决」不可区分，进而在 v8.1 逼出「一律写成已作废」这个被否决的选项（见 [adr-020](adr-020-文档体系迁移.md) 备选表与本文件下方同项）。v8.2 的五值域把「还没决定」与「决定不做」分开，中间态不再需要。
- 理由三：**提出即登记、开工沿用原号**堵住了一个真实事故 —— 本轮开工时我曾按 v8.1 的「未开工项另拿新号」把 `REQ-017` 划掉并新发 `REQ-053`，而 v8.2 要求沿用原号。后果不是数字难看，而是 `git log --grep='(REQ-017)'` 会指向一个从未开工的号，与「号 ↔ 提交」这条唯一的机器可查连接脱钩。
- 备选与后果：
  - **保留 `docs/LOG.md` 三张表、只加 `待拍板` 状态值** —— 否决。那样 REQ 仍是「只有号没有状态」的台账，需求总池能力没拿到，等于把 v8.2 的改动做一半。
  - **给 `暂缓` 重新加回状态值** —— 否决。项目级文件只能对全局规则**加严**，把全局已取消的值加回来是反转而非细化。
  - **两种待拍板在台账里用标题区分**（如标题加「（暂缓）」后缀）—— 否决。标题是「是什么」，把状态判断塞进去会让台账再次同时承载两件事；且标题里出现状态词，扫表时反而更容易漏看真实状态。
  - 后果：3 条原本无号的事项（CI 侧加速比未实测 · lint 缓存收益待生效 · `main/image-downloader` 疑似 flake）按新规则补号登记；7 处指向旧三表的指针（`AGENTS.md` · `README.md` · `WPS-COMPAT.md` · `docs/SIGNATURE-STATUS.md` · `large/01` 两处）改指新结构。

# adr-029 · main 侧输出骨架抽函数，保留刻意的不统一

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-09-29 |
| 关系 | 承接步 01 的两项前置（`fa65b86` 删恒真分支并留证、`1d1bcc6` 补第 4 道闸门的护栏测试）。本条是它们的收口。 |

## 决定

把 `single.ts` 与 `merge.ts` 两份逐行同构的输出骨架抽成**一个新模块的函数**（2 个消费点）。**不抽对象、不抽主管线。** 共享骨架的入参只有「一段 markdown + 来源路径 + 可选基名 + 解析基准目录/可信根」，**不含文件列表**。

## 背景

诊断实测：两处输出段逐语句 36 条里 **31 条逐字相同（86.1%）**，7 处差异**全部是「值不同」或「可选实参的有无」，没有一处逻辑不同**。即这是真重复，且是可安全归拢的那一类。

本步是全方案里唯一**新增模块间依赖方向**的一步（`main/converter/*` 之间多一条边），故必须立 ADR。

**入参为何不含文件列表** —— 这直接回答了「会不会把『多文件 → 一个产物』压扁成『一进一出』」：不会。多对一的塌缩已在骨架**上游**完成（合并函数把 N 个文件压成一段 markdown，发生在落盘之前）；骨架入参是「一段 markdown」，**骨架内部根本看不到几个文件进来**。若把文件列表塞进入参，等于把「N 个」这个概念重新引进骨架内部，反而制造了它本不该关心的形态。

## 决定要点

### 一、第 4 道取消闸门不进骨架，保留在合并侧

`merge.ts` 的「N 文件有界并发读取完成、`mergeMarkdowns` 之前」有一道取消闸门，`single.ts` **没有这个窗口**（单文件没有「长批次读取期间」）。

把它并进骨架只有两种结果：**要么删掉一道真实防护**，**要么在 single 造假闸门**（一个永不触发的检查看起来像防护，实际是噪音，且会骗过后续维护者）。故它是「相似但刻意」，不进骨架。

**它的存在由步 01 的护栏测试证明**：`test/main/merge-cancel.test.js` 的第 5 个用例在取消发生于该窗口时断言「抛 `ConvertCanceledError` + 零产物 + 阶段序列不含 `render`」；临时移除该闸门时该用例变红（已实测）。**这是唯一能证明第 4 道闸门在重构后仍没被误删的证据** —— 抽完后它必须仍绿。

### 二、恒真分支删除不改变任何行为（步 01 已留证）

`merge.ts` 原先的 `if (!ctx.skipAfterConvert)` 恒真，步 01 已删除并在原处留下恒真性证明：`skipAfterConvert` 全仓唯一写入者是 `batch.ts` 的 `batchConvertImpl`，而 batch 只调 `convertImpl`、从不调 `mergeConvertImpl`；合并路径的 ctx 出自无参 `createConvertContext`，其返回值不含该字段 ⇒ 恒 `undefined`。

**本步抽函数时，`single.ts` 里的同名分支是真分支，必须原样保留**（批量是它的唯一写入者，批量确实调 single）。两侧同名不同性质，正是「同名不等于同义」的又一处。

### 三、让位标志由骨架**读**，不由骨架**判断拥有者**

共享骨架读 `ctx.skipAfterConvert` 决定是否触发副作用，但**不得自己推断谁拥有该标志**。批量的让位上下文构造留在批量侧。

### 四、批量的第三份「导出后行为」实现保持独立

批量那份不判让位标志，改为「取第一个成功项」，与骨架的「判让位标志」**语义不同构**。强行统一要么引入一个策略维度（`自己的` / `第一个成功的`），要么牺牲掉一个真实语义。**判定为不并入，并在此登记为刻意相似** —— 下一个人看到三份相似代码时，答案在这里。

### 五、其余刻意不统一项

| 项 | 为什么不统一 |
|---|---|
| 参数/预算校验段 | 单文件查扩展名、合并查空数组与上限 —— **判据完全不同**，合并会造出语义模糊的校验器 |
| 合并专属的封面元数据形参 | 可选实参，骨架不感知 |
| 预览与转换两处映射上下文的差异 | 预览用降级 Mermaid、不共享图片缓存、无取消 —— 都是有意的 |
| `renderPdf` 内部的双闸门 | `printToPDF` 不可中断的补偿机制，合并侧复用已自动继承 |
| 批量侧的进度包装 | 在单文件实现**外面**，把「每文件一次」包成批次进度 |

该统一的：落盘提交器调用及其参数 · 「转换后/落盘前」与「落盘后/导出后行为前」两道取消闸门（**两侧注释都刻意论证过这个位置，该刻意性要保留进共享骨架的注释**）· 读取/渲染两处进度与 pdf 独有的 stage 透传 · 落盘警告汇总。

## 备选方案

- **抽「转换请求」对象** —— 不采纳。收益是让 renderer 的 3 个命令与 main 的 2 个 handler 共用形状，但**它们在不同进程**；跨进程复用要动 4 个契约文件，等于换一层参数封装。
- **抽主管线**（把整个流程编排成一条可配置管线）—— 不采纳。会扭曲进度粒度与让位语义：进度该在「每文件一次」还是「每批次一次」上收，取决于调用方而非流程本身。
- **把第 4 道闸门做成骨架的可选钩子**（由调用方传一个「读取后再查一次」的回调）—— 不采纳。那等于用一层间接把一道单文件侧不存在的窗口抽象成通用概念，掩盖了它存在的唯一理由。
- **连批量的第三份实现一起统一** —— 见要点四。

## 后果

- 两个消费点各自的输出段从 ~50 / ~45 行降到 ~10 行。
- **等价性的机械证明是 diff 本身**：抽完后的 diff 应接近剪切粘贴 + 参数化，**不是靠测试推断**。若 diff 形状不符，说明抽错了边界。
- 批量与预览路径**零改动**（diff 可证）。
- 回滚：新旧并存一个提交周期即可，无需回滚数据格式。
- **受本条约束的**：任何想统一第 4 道闸门、让位标志归属判定、或批量第三份实现的改动，都必须先推翻本条并说明如何保住「长批次读取期间仍可取消」与「批量取第一个成功项」这两个真实语义。

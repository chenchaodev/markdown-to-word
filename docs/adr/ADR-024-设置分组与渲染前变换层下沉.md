# ADR-024 · 设置分组与渲染前变换层下沉 core

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-09-28 |

## 决定

把「渲染前变换」类设置按概念分组成对象（`aiCleanup: { enabled, tidy, rewrite }` · `obsidian: { compat, attachmentFolder }`），并把档位到 per-rule 的映射函数从 `main/converter/preprocess.ts` 下沉到 `core/markdown/ai-cleanup.ts`，让 `core/convert.ts` 对「先变换后渲染」这个阶段有显式概念。

## 背景

诊断（`docs/evidence/20260927-222300-设置改动面放大器诊断.md`）的结论是：加一个输出内容级能力时改动面 12~22 个源文件，根因不是「六种模式各有实现」，而是**「设置已加载」这条链上没有一个声明式中枢**，每一层各自手写枚举。渲染前变换类设置在 `core/convert.ts` 里的引用数为 **0** —— core 的转换入口根本不知道它们存在。

2026-09-28 开工前的实测复核确认了诊断，并补出三处规格未覆盖的事实：

1. **这 5 个平铺键当前参与 `isValidSettings` 的整文件形状校验**（任一非法 → 整文件回退默认），而 `headerFooter` / `watermark` / `typography` 走的是字段级兜底。照抄现成的分组对象 sanitizer 范式会把校验口径从「整文件拒绝」静默改成「字段级兜底」—— 那是行为变化，规格没提。
2. `aiCleanupOptions` 确实是纯函数（只读设置、零 IO），但下沉的障碍是**分层不是 IO**：core 只需 `import type { AppSettings }`，而 `settings-defaults.ts` 头部注释明确支持该形态。
3. 这 5 个键**不参与**自定义预设导入导出（`CustomPreset` 只有 name / typography / pageSetup），搬它们不会连带动预设体系。

## 决定要点

### 一、分组后的校验口径必须与今天等价

分组键**同时**补两处：进 `isValidSettings` 的对象形状校验（保持整文件拒绝语义）+ 进加载兜底（经字段级 sanitizer 兜底）。只补后者会静默放宽校验强度；只补前者会让新写的 settings.json 缺字段时整文件回退。

### 二、双重门控不得压成一层

门控分散在三处且都是 [adr-021](adr-021-AI清理开关分档.md) 写死的不变式：总开关在 `preprocessBody`、档位到 per-rule 的派生在下沉后的映射函数、per-rule 全 false 时零改动短路在 `cleanupMarkdown`。**三者任一被合并成一层，验收判据「关掉结构改写 = 回到本决策前的产物」就不成立。**

### 三、档位是派生量，映射表位置必须显式

2 个档位映射到 6 个 per-rule 布尔。映射表随函数下沉到 core 后仍留在 AI 清理自己的模块内，**不得**上浮成通用注册表。

### 四、迁移必须让存量用户的产物逐字节一致

旧 3 个平铺键 → 新对象的迁移走分组对象 sanitizer 范式（非对象/数组/null → `{}`；`{...DEFAULT}` 打底；逐字段 `if` 覆盖，从不 `delete`）。迁移函数保留旧键读取能力一个版本。

### 五、新落点不得携带宿主能力

下沉后的文件与新建的 `source-ranges.ts` 都**不得** import 任何 `node:*` —— 边界门禁的 node: 内建白名单是**逐文件**的（`scripts/check-import-boundary.mjs` 的 `CORE_NODE_BUILTIN_FILES` 只列了 5 个具体文件），新文件不在名单内即判红。

## 备选方案

- **照 headerFooter / watermark 的做法只走字段级兜底** —— 不选。那会把「任一字段非法 → 整文件回退」放宽成「该字段回退、其余保留」，是未被请求的行为变化，且与用户已有的 settings.json 兼容性策略脱节。
- **映射函数上浮到 `core/settings/` 或做成通用「档位 → 规则」注册表** —— 不选。只有 2 个档位、一条映射，抽象撑不起一层间接；且档位语义是 AI 清理特有的，把它做成通用物会让下一个功能来复用错误的形状。
- **把 `preprocessBody` 整体下沉 core** —— 不选。它要读文件、解码、收集 warning，依赖宿主能力；本次只下沉其中唯一纯的那段。
- **旧键读取能力只保留一个版本即删** —— 不选。已发布版本的迁移必须双向可逆，否则回滚用户就会丢设置。

## 后果

- 持久化结构变更：`settings.json` 的这 5 个键从平铺变嵌套。旧文件仍能读入（迁移函数），新文件不再被旧版本读懂 —— 这是单向的，回滚需靠迁移函数。
- 新增一个渲染前变换类设置，持久化侧只改 `AppSettings` + 迁移 + `core` 的阶段契约，不再需要在 main 侧加 mapper。
- **受本条约束的**：任何后续想把这三处门控合并、或把档位映射改成注册表的改动，都必须先推翻本条并说明如何保住「关掉结构改写 = 回到现状」这条判据。

# adr-032 · 转换入参改为阶段产物：frontmatter 只解析一次

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-09-30 |
| 关联 | [REQ-069](../REQ.md) · 波次 4 · 排期载体 `docs/large/01-非功能需求排期.md`（收尾时入档） |
| 命名 | 本文件用 `adr-0NN-` 前缀，与既有 31 条保持一致（新全局规则的 `ADR-0NN-` 大写形态属 REQ-101 迁移范围，不在本条内改） |

## 决定

`convert` 的第 1 参由裸 markdown 字符串改为**阶段产物** `PreprocessedMarkdown = { body: string; metadata?: DocMetadata }`。frontmatter 的隔离与解析**只在准备阶段做一次**，由调用方交下来；core 不再解析。

## 背景

同一次转换里 frontmatter 被解析两次：`src/main/converter/preprocess.ts:77` 解析一次并把 frontmatter **拼回正文**（`:66`、`:91`），该整串进 `src/core/convert.ts` 又 `parseFrontmatter` 一次。

裸字符串入参使两件事都做不到：**「core 不解析」在类型层不可表达**（core 拿到的仍是带 frontmatter 的全文），且**「只解析一次」无处可断言**（没有可计数的位置）。

该重复当初被推迟，理由是「与持久化 schema 步耦合同一映射文件、成本高于收益」——**该耦合已随 REQ-061 步 04 解除**，本条恢复为待拍板后排期落地。

## 备选方案

1. **保持 `string`，只在 `ConvertContext` 加 `metadata`** —— 否决。无法表达「body 已剥离 frontmatter」：core 拿到的仍是带 frontmatter 的全文，要么渲进正文（回归），要么仍需自己解析（重复照旧）。**否决理由：解决不了问题本身。**
2. **`string | PreprocessedMarkdown` 联合入参** —— 否决。core 仍需对 `string` 分支解析，即「只解析一次」对半数调用点是假的；且违反 [adr-026](adr-026-阶段契约落在core分派点.md) 已记录的「类型谎言」模式（宣告支持的形状实际不生效）。**否决理由：判据会退化成「大部分时候只解析一次」，而这正是本条要消灭的那件事。**
3. **改 `mergeMarkdowns` 返回 `{ markdown, metadata }`，把合并侧一起统一** —— 否决。牵动 `core/pipeline/merge.ts` 纯逻辑与 `merge.test.js` / `merge-toc.test.js`，属一次行为面更大的变更。改为在 main 侧补一次等价解析，达成同样效果。**否决理由：成本与风险远超收益，且与「不统一 3 个非 convert 消费者」的既定边界冲突。**
4. **把 `PreprocessedMarkdown` 品牌化**（如带唯一 symbol 的 type）—— 否决。品牌化会让测试里 `convert(rawString)` 变成编译错误，而那些段本就按裸字符串写样例（测试包装统一走 `prepareForConvert`）。[adr-026](adr-026-阶段契约落在core分派点.md) 已否决品牌化。**否决理由：为了「类型更严」而让测试无法表达真实调用形态。**

## 后果

- core 单文件转换路径 frontmatter 解析次数 **2 → 1**。
- `core/convert.ts` 不再依赖 `pipeline/frontmatter` 的**值**导出（只留 `import type` 的 `DocMetadata`）—— 这也是「core 不解析」的**结构面**判据。
- 跟改面 = **5 个生产 + 12 个测试文件**（实测数；其中 4 个测试包装与 `convertWithFs` 刻意保持裸字符串签名 ⇒ 10+ 个段**零改动**）。新增判据段 1 个。
- **`mergeMarkdowns` 与 `core/pipeline/merge.ts` 契约不变**。

## 不做项

1. `core/pipeline/merge.ts:72` —— 不改 `mergeMarkdowns` 的返回形状，只保行为等价。
2. `core/markdown/ai-cleanup.ts:81` —— 不动。AI 清理独立解析 frontmatter，与 `convert` 无关。
3. `main/converter/merge.ts` 的解析点 —— **刻意停在 main 侧**，不上提到 core（那即备选方案 3）。
4. **preview 的 `context.metadata` 不「修」**。它不是缺失，是通道语义不同：`context.metadata` 是**向导封面的显式覆盖项**，预览不设封面；preview 走第 1 参拿 frontmatter metadata，与改动前**完全等价**。把它「对齐」反而是另一次行为变更。
5. `PreprocessedMarkdown` 品牌化 —— 不做（见备选方案 4）。

## 一条容易漏的连带事实（写进本条以免后人重蹈）

`mergeMarkdowns` 按设计**保留首文件 frontmatter 原样**，该整串经 `OutputSkeletonDoc.markdown` 直进 `convert`。core 一旦不剥离，**合并产物正文会渲染出 `---` / `title: x` / `---` 三行** —— 且**不报错、不失败**，是静默回归。故 `main/converter/merge.ts` 与 `src/main/converter/single.ts` 是**必改**文件，不是顺手扩项。**教训**：改「core 不再自己剥离」这类契约时，**必查所有把整串喂进 core 的调用方**，尤其那些「按设计保留原文」的路径。

# ADR-061 · 多层交付面的已安装入口

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-10-03 |
| 关联 | [ADR-060](ADR-060-多层交付面与headless装配层.md)（多层交付面与 headless 装配层）· [ADR-013](ADR-013-发布供应链与明确不签名.md)（发布供应链与明确不签名） |

## 决定

给安装版加**一个命令行转发入口**（`m2w.cmd`）：**复用应用自带的 Electron 运行时** —— `.cmd` 置 `ELECTRON_RUN_AS_NODE=1` 后调应用自身的 exe，入口脚本指向 `app.asar` 内的 `dist/cli/index.js`。

**不引第二套运行时、不引打包器、不引任何 npm 依赖。**

三条支撑结论，全部来自本仓真实产物的**实测**（采样与逐条数据见 [事实快照](../evidence/20261003-180918-命令行exe分发路径调研.md)）：

1. **`RunAsNode` fuse 在本仓真实产物里已开启** —— 从 `node_modules/electron/dist/electron.exe` 的 fuse wire 实读到 `RunAsNode='1'`；且打包配置未出现 `electronFuses`。⇒ **不需要动打包配置，也不存在「为用它而削弱安全姿态」的代价。**
2. **`app.asar` 在该模式下对 `fs` 完全透明** —— 实测可 `readFileSync` 其中的 `dist/**` 与 `node_modules/**`。⇒ **不需要 `asarUnpack`、不需要 `extraResources` 搬代码、不需要碰被门禁写死的 `build.files` 与 asar 顶层清单。**
3. 内置 Node 24.x，满足 `engines.node >= 22.13`。

**只有转发器本身落在 asar 之外**，经 `build.extraFiles` 落安装根目录、与 exe 并列（2026-10-03 用户裁决落安装根而非 `extraResources` 那一层，理由是可发现性不是技术）。

## 背景

`ADR-060` 把 CLI 落成「本地可执行形态」，但那条路只覆盖**机器上有 node** 的用户。安装版用户手上只有一个 exe —— 装版用户要调用命令行与 MCP，缺的不是入口脚本，是**一个能跑 JS 的运行时**。

**绕不开的前置，且它不是打包路径的选择题**：`require("electron")` 在已安装语境下**必然拿不到用户的宿主 exe**。三条独立来源交叉确认：① `electron` 包的 `index.js` 全逻辑就是读同目录 `path.txt` 再拼 `dist/`；② 发布的包里**根本没有 `path.txt`**（它由 `install.js` 在开发机安装时生成）；③ 打包时 `node_modules/electron` 被剥离。
⇒ 定位逻辑必须改为「`process.versions.electron` 有值 ⇒ 宿主是 `process.execPath`」。**这一条卡住所有路径** —— 每条候选路线产出的 exe 内部都没有 `node_modules/electron`、也没有 `path.txt`，不改它，下面每条路都做不通。

「机器上没有 node」这个前提不是推测出来的：`electron` 是 devDependency、不在 PATH 上，MCP 客户端配置里写死一个 electron 路径只在开发检出里成立。

## 备选方案

本节是本 ADR 的主要价值 —— **写清各自的失效条件，以便后来人不重复评估。**

**否决 · 官方 SEA（自包含 exe）。** 四条，任一独立成立：
- Node 22 / 24 LTS 的 SEA **只吃 CommonJS 入口**（ESM 入口是 25.7+ 才有，而 25 已 EOL、26 是 Current，与稳定优先冲突）⇒ 必须先用打包器把 remark / markdown-it / katex / mermaid / docx 整棵 ESM-only 依赖图转成单文件。**这是硬前置，不是可选。**
- **产物体积量级远大于当前安装包**（裸运行时那一个数值是已确证的，依赖子图的实际体积属推论、随依赖图变化而变，两者的量级区间与「哪部分已确证」的划分见 [事实快照](../evidence/20261003-180918-命令行exe分发路径调研.md)，此处不复述数值；当前安装包的基线可从 `gates/artifacts/pack-size.baseline.json` 重新取到，同样不复制）。
- SEA 稳定度仍标 `1.1 - Active development`，无转正路线图。
- 单一个 exe 就会让 `pack-size` 的 installer 闸需重登记（该闸是「基线 + 相对/绝对双闸取较宽者」，换一个数量级的产物等于重登记基线）。

**否决 · `bun build --compile`。** 运行时被换成 Bun，与 `engines.node >= 22.13` **正面冲突**；且 pdf 路线强依赖 Electron `printToPDF`，与「产物内无 electron」正面冲突。两条各自独立成立。

**不否决 · npm bin**（另一条在办工作项）：对 npm 用户它**仍是更轻的路**，本决策不与之竞争。但它解决不了装版用户 —— 那些机器上没有 node。

## 后果

**1. 两条不可省的约束，都是「漏一行就静默失败」那一类。**

- **`ELECTRON_RUN_AS_NODE` 必须 `delete`，不能置 `=0`。** Electron 只判断该变量**是否存在**、不读取值；实测 `=0` 与 `=1` 同样导致 pdf 宿主崩溃（两者都留下 `ENOENT` 的 result.json）。写成 `ELECTRON_RUN_AS_NODE: "0"` 是**看起来修了其实没修**。该不变量落在宿主启动的环境构造里，两种入口形态都必经。
- **`--pdf-host` 形态的 `setPath("userData")` 必须在 `app.whenReady()` 之前完成，且须由 `main/index.ts` 在动态 import 重模块之前同步调用。** Electron 只保证 `ready` 排在主脚本同步求值之后，那次 import 要拉装配层与 pdf-lib，冷缓存或慢盘上完全可能输给 `ready` —— 而输掉的代价是 Chromium 已在用户真实 `%APPDATA%` 建好 profile，宿主还在往别处重定向：**往用户真实 profile 里写数据，静默且难查**。一次实测「恰好成立」不构成依据，判据是「这条顺序在结构上有没有可能输」。

**2. `ELECTRON_RUN_AS_NODE=1` 成为安装版的隐式环境契约 —— 这是长期最易被踩坏的地方。**
任何第三方工具链、清理脚本或用户环境里出现同名变量，都会打断 pdf。而同源的第二条传播路径（`.cmd` 的 `setlocal` 会**隔离**环境变量，使变量对后续进程不可见）恰好是**不该**防的：转发器刻意不做任何环境隔离，隔离只会掩盖这条。

**3. Electron 大版本升级面。** `ELECTRON_RUN_AS_NODE` 是官方 Production Variable（**未标弃用**，官方来源），但 fuse 的默认值与 wire 长度会随版本变；electron-builder 若哪天改默认，本路线要重评。
⇒ **一条可执行判据**：对解包产物跑一次转发器的 `--help` 并断言 **exit 0**。它能在升级当天抓住回归，而不是等到用户报「pdf 转不出来」。

**4. `ELECTRON_NO_ASAR` 置 1 会让 asar 不再透明、打断已安装形态（实测）。但它是否也该被剔除、以及「置空」是否有效都还没实测，故当前实现刻意不剔除** —— 凭推测加进剔除列表比留着更危险。**记为待验**，不要当已解决。

**5. 入口的可发现性是已知缺口。** 落安装根目录已比埋进 `resources\` 好找得多（与 exe 并列），但入口**不在 PATH、无开始菜单快捷方式**，用户仍需知道它的落点，得靠文档写明。

**6. 上述验证是在解包产物上做的，不是走完安装器。** `extraFiles` 落安装根目录这一落点由「文档化行为 + 解包产物实测」三方印证，但仍未经真安装验证。

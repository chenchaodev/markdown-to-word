## 决定

`test/fixtures/` 的子目录一律按**内容是什么**命名，不按「谁生成」或「被谁读」命名。落地形态：

```
test/fixtures/
├── docs/     ← 原 acceptance/（生成器落盘的渲染输入样例文档）
├── input/    ← 原 main/ + 原散落在根的两个 png（最小输入桩）
└── manual/   ← 不变（人工目检长文档）
```

根目录只留这三个子目录，**不留散落文件**。三处改名与一次归位各自的理由不同：

1. **`acceptance/` → `docs/`。** `acceptance` 是**流程词**（验收阶段）不是内容词；这批文件的内容是「一份渲染输入样例文档」，与 `manual/` 同类 —— 现在两者是同一类东西被拆成两个名字。同时消解「生成物 vs 手工」被当成目录分类轴的误用：**来源差异不由目录名表达**，由生成器落盘的 README 首行「勿手改」+ `check:fixtures` 的漂移门禁表达（两者都已是既有机制，不需新增）。
2. **`main/` → `input/`。** `main` 只表达「被谁读」（`test/main/`），不表达「是什么」，且与段目录 `test/main/` 撞名；ADR-051 落地后 `test/` 下已有 `main/` 与 `gates/` 两个段目录，撞名更刺眼。`input/` 是内容词。
3. **两个散落 png（`g1-tiny.png` `img-800x400.png`）→ `input/`。** 它们是**图像输入桩**，与 `test/fixtures/input/converter-sample.md`（最小 md 输入桩）同类，与「样例文档」不同类。

**图片字节基线必须经 `--print-image-baseline` 重新登记，不得手改 `IMAGE_DIGEST_BASELINE`。** `listImageFixtures()` 的覆盖面判据是「磁盘派生」，移动会改 `rel`（相对 `test/fixtures` 的 POSIX 路径），`check:fixtures` 因此判红是**预期行为**而非回归。手改 JSON 过门禁等于把「派生结果」手写成「手写意图」，正是 ADR-037 一贯治的那类形态。

**树边界规则零改动。** `gates-stay-in-gates` 的 allow 面是字面 `test/fixtures`（`gates/repo/check-import-boundary.mjs`），按**路径段**比（`fixtures-old/` 判红即证明不是 `startsWith`），改子目录名不触碰它。`gates/repo/check-import-boundary.mjs` 本次**不改**。

## 背景

**一、三子目录各按不同命名轴。** 实测：`acceptance/` 按**生成器流程名**、37 个文件、由 `gates/fixtures/gen-fixtures.mjs` 机器生成、漂移受 `check:fixtures` 逐字节守恒；`manual/` 按**使用方式**（人工目检长文档）、15 个文件、产出的 docx/pdf 被 `.gitignore` 排除；`main/` 按**消费者目录名**（`test/main/`）、2 个文件、只被 `test/main/` 与 `test/common/` 读。三套轴混用，读者必须逐个查源码才知道哪个是生成物 —— DEV-GUIDE 当时只有一句「静态样例入 `test/fixtures/`（acceptance/ 生成 + manual/ 手工）」，用的正是**来源**维度。

**二、根目录散落两个 png。** `g1-tiny.png`（70 B，1px 桩图）与 `img-800x400.png`（1886 B，尺寸边界图）直接躺在 `test/fixtures/` 根，而另外三个子目录都规整分了目录。两者是图像输入桩，与「样例文档」不同类；归位到 `input/` 后与 `test/fixtures/input/converter-sample.md` 同属一类。

**三、「生成物 vs 手工」不适合当目录分类轴。** 这个区分已经在别处被机械表达了两次：生成器落盘的 README 首行写明「由 `gen-fixtures.mjs` 自动生成（勿手改）」，`check:fixtures` 对全部生成产物逐字节比对。用目录名再表达一次，等于给同一条信息开第二个来源 —— 且开在一个不会随判据演进而更新的地方。

## 备选方案

1. **否决一：把 `acceptance/` 提到顶层新目录（如 `samples/`）。** **不选**，理由：56 个文件不值得换一棵顶层树。留在 `test/fixtures/docs/` 时 `gates-stay-in-gates` 的 allow 面已放行整个 `test/fixtures`，树边界规则**零改动**；提到顶层则要么新开顶层目录（连带顶层清单、`repo-manifest`、各 selftest 的 `BASE_SHAPE` 配额一起动），要么把 `samples` 加进 allow 面（为一个目录名放宽规则边界）。代价与收益不成比例。
2. **否决二：改叫 `samples/` 或 `corpus/`。** **不选**，理由：这两个词都是「语料/样本」轴，与 `manual/` 的「使用方式」轴继续混用 —— 即只换掉三套轴里的一套。`docs/` 是唯一与 `manual/` 落在**同一根轴**（内容是什么）上的选项。
3. **否决三：保留 `acceptance/` 与 `main/`，只把两个 png 归位。** **不选**，理由：那样只治了根目录散落，没治三套命名轴混用这一根因；`test/fixtures/main/` 与段目录 `test/main/` 的撞名仍在（ADR-051 落地后更刺眼），而撞名的代价是每次看测试树都要重新判断一次「这两个 main 是什么关系」。

## 后果

- **收益：三目录同轴，根目录零散落文件。** `docs/` 与 `manual/` 都是「给人读 / 给渲染器读的文档」，`input/` 是「最小输入桩」。找样例文档看两个目录，找输入桩看一个目录。
- **收益二：树边界规则不动。** 本条不触碰 `check-import-boundary.mjs`，也不需要为新子目录名开任何 allow 面例外（allow 面是路径段粒度）。
- **代价一：`test/fixtures/` 下的图片引用路径全部要加 `input/` 前缀。** 散落时它们以 `./g1-tiny.png` 形式被 8 个测试文件按 `FIXTURES_DIR` 基准解析；归位后必须改成 `./input/g1-tiny.png`（或 `path.join(FIXTURES_DIR, "input", …)`）。基准目录仍统一是 `FIXTURES_DIR`，故**不新增**可变基准。
- **代价二：生成产物 `docs/` 下多一层 `input/`。** 生成器复制被引用图片时保持引用路径不改写（`dest = ACCEPTANCE_DIR / ref`），故样例文档落在 `docs/input/g1-tiny.png`。这正是「引用路径不改写 + 样例自包含」这条既有设计的直接结果，不是新分歧；`docs/` 整棵被 `listImageFixtures()` 排除，字节基线不覆盖它，覆盖面由 `imageCopies` 那条判据管。
- **代价三：受影响的段超出本条点名的范围。** 两个 png 的消费面不止方案原文列出的两处 —— 逐处核出 8 个文件（`dual-samples` · `dual-sandbox` · `basic-render` · `cross-ref` · `image-size` · `toc-caption` · `image-downloader` · `image-request-budget`）与 `converter`，它们经 `FIXTURES_DIR` 解析图片，不含 `fixtures/main` 字面量，只能靠改路径常量与引用串发现。**判据教训：消费面靠字面量 grep 找不全，须按「路径常量 + 解析基准」两条轴各扫一遍。**
- **代价四：`test/fixtures/docs/README.md` 与四个含图样例文档的内容随引用路径重生成**（`check:fixtures` 逐字节比对，不重生成即判红），且旧位置的图片副本（`docs/g1-tiny.png`、`docs/img-800x400.png`）成为无源孤儿，须一并删除 —— 生成器不清目录，不删就是静默残留。

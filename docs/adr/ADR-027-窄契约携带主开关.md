# ADR-027 · 窄契约携带主开关,分派点才算真的移出 main

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-09-28 |
| 关系 | **部分取代 [adr-026](adr-026-阶段契约落在core分派点.md) 的「决定要点一」**。要点二/三/四与决定、后果沿用。 |

## 决定

`core/markdown/preprocess-body.ts` 的窄契约**携带主开关**：形如 `{ aiCleanup: Pick<AiCleanupSettings, "enabled" | "tidy" | "rewrite">; obsidian: ObsidianSettings }`。「主开关不进 core」这条只约束**档位映射函数**（`aiCleanupOptions` 的入参仍是不含 `enabled` 的窄 `Pick`），**不约束分派函数的契约**。

## 背景

adr-026 的形状评审给出一条明确的成功判据：「新增一个渲染前变换类设置的**枚举点落在 core，main 侧改动恒为 0**」。同时它把窄契约写成了 `{ obsidian: ObsidianSettings; aiCleanup: Pick<AiCleanupSettings, "tidy" | "rewrite"> }`，并注明「沿用 F5 的『总开关不进 core』惯例」。

**这两句放在一起无法同时成立。** 主开关判定读的就是 `settings.aiCleanup.enabled`；该字段既不在 core 契约里，就只能由 main 侧读，于是：

| 枚举点 | 位置 | 是否需要枚举变换键 |
|---|---|---|
| 分派函数 | core | 是 |
| 档位映射 `aiCleanupOptions` | core | 是 |
| **主开关判定** | **main**（因契约里没有 `enabled`） | **是** |

三处 —— 正是 adr-026 决定要点三要守的上限、也是它否决形状 1 的第一条理由（「它自己就是第三个 mapper」）。**照字面实现会造出它本来要消灭的东西。**

根因是评审时把两件同名不同物混成了一件：`aiCleanupOptions` 的入参**不该**看到 `enabled`（那是既有惯例，源自 adr-021 的双重门控），与分派函数的契约**可以**看到 `enabled`（那是它必须做判断的输入），是两回事。

## 决定要点

### 一、两层各守各的

- **`aiCleanupOptions`（档位映射，core/markdown/ai-cleanup.ts）**：入参保持 `Pick<AppSettings["aiCleanup"], "tidy" | "rewrite">`，**不含 `enabled`**。理由不变 —— 类型上即表达「本函数不判总开关」，这是 adr-024 决定要点二（双重门控不得压成一层）的延续。
- **`preprocessBody`（分派，core/markdown/preprocess-body.ts）**：契约携带 `enabled`，主开关判定在它体内。

三重门控**仍是三处**，没有被压成一层：主开关在 `preprocess-body.ts` · 档位派生在 `ai-cleanup.ts` · per-rule 全 false 短路在 `cleanupMarkdown`。

### 二、契约仍是窄的

「窄」指**只含与变换相关的键组**，不指「缺主开关」。`obsidian` 侧本来就是完整块（`compat` 正是它的主开关），aiCleanup 侧带上 `enabled` 之后也是完整块 —— 两侧形态终于对称了。契约不含 typography / headerFooter / watermark 等任何非变换键。

### 三、main 侧薄壳的形态

`main/converter/preprocess.ts` 只剩两件事：frontmatter 隔离与拼回、IO（读文件 / 解码 / warning 收集）。它**不再出现任何变换键名**，`preprocessBody` 的调用形态是「把 settings 投影成契约再传入」—— 投影本身是机械的块提取，不是枚举：新增一个变换键组时它自动带上。

## 备选方案

- **照 adr-026 字面实现（契约不含 `enabled`，主开关留在 main）** —— 否决。造出第三个 mapper，直接违反 adr-026 决定要点三，且会被本步的门禁（枚举点计数恰为 2）当场判红 —— 门禁按设计工作，暴露的是规格自身的矛盾。
- **把主开关判定也上浮成通用机制** —— 否决。三重门控本就该分处三处，合并即破 adr-024 决定要点二。
- **契约直接收整个 `AppSettings`** —— 否决。那不是窄契约，core 会重新依赖全部设置类型，新加一个非变换键也会出现在 core 签名里，与本条「只含变换键组」相悖。

## 后果

- 「main 侧改动恒为 0」这条判据才真正可达成，adr-026 后果行那句「新增一个变换类设置的枚举点落在 core」从愿望变成事实。
- 主开关判定的位置从 main 移到了 core。**这是行为位置的变化、不是行为变化**：判定逻辑本身（`if (aiCleanup.enabled) …`）逐字迁移，产品行为不变，由 `main/preprocess.test.js` 的产物断言与预检回归守住。

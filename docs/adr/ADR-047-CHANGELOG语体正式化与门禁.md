# ADR-047 · CHANGELOG 的内容标准与语体：判据本身要经得起「有没有意义」这一问

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-10-01 |
| 关联 | [ADR-009](ADR-009-文档与流程契约口径.md)（其中「豁免 CHANGELOG 容量上限」一条相关） |

## 决定

`docs/CHANGELOG.md` 与 GitHub Release 的写法由**两条**判据约束，分开定、分开治：

### 一、内容标准：**有意义，且别处查不到**（两条并列，须同时满足）

1. **有意义** —— 对终端用户**或维护者**有实际影响：用户能看见的界面 / 行为 / 产物变化；**或**维护者需要知道的长期约束与决策（安全加固、性能特性、兼容性破坏、迁移步骤）。**非用户感知层的内容可以进**，判据是「有没有长期后果」，不是「用户能不能看见」。
2. **别处查不到** —— git 历史、`docs/adr/`、代码、`docs/DEV-GUIDE.md` 已能重新取到的，不写。判据是能不能重新取到，不是「重不重要」。

不写三类：**载体维护**（重新截图、修正图片格式、替换示例路径、更新索引）· **工程状态**（CI 与依赖升级、测试补齐、覆盖率、目录重组、文件拆分、门禁细节）· **流程自述**（「本版发布说明改为面向用户视角」）。

### 二、语体：**平实的专业书面语**

正式的技术写作是**平实、直白、具体**。**把口语换成文言不是变正式，是换一种毛病** —— 禁用文言虚词（亦 / 兹 / 遂 / 盖 / 矣 / 焉 / 尔）与装饰性副词（仅 / 均 / 一概 / 悉）；一条里最多一次时间对比且只用来界定问题边界；不写「现在都恢复正常」这类收尾；规格值（11pt / 315° / 0.9 倍）该留就留。

### 三、门禁 `check-changelog` 进 `verify:ci`

守护上述两条，禁可枚举的那几类：内部工程词 · 第二人称 · 内部编号（`REQ-0NN` 与 commit hash）· 文言虚词 · 载体维护指纹词 · 装饰性副词（带实义限定放行）。**比喻、调侃、术语一名仍无封闭词表**，靠人写 —— 门禁只保证最易退化的那几类不退化，这是已知不覆盖项。

### 四、条目只增不删，但单条措辞可改

「只追加」的原意是**版本条目不删整条**；单条措辞可按上述判据改写。已同步改写全局 `AGENTS.md` 六 的 CHANGELOG 生命周期行与全局配置目录 `templates/docs-init/CHANGELOG.md`。**已发布的 GitHub Release 是发版时的一次快照，改本地文件不追溯**，故须逐个 `gh release edit`。

## 背景

用户 2026-10-01 提出「CHANGELOG 非常口语化，想改得更正式且只关心用户感知层」。

**这个需求在两轮之间改了口径，第二轮才是对的。** 第一轮我按字面把规则定成「只写用户可感知的变化」，并认定内部条目泄漏属「执行缺口、规则早就有」。改写结果被用户判为质量不合格，三条理由：

1. **语体失败** —— 我把「机械删口语标记」当成了改写方法，产出满篇「亦 / 现已 / 均 / 同」的**文言腔**。半文半白比口语更难读。
2. **内容判据错了** —— 「只写用户可感知」这把**唯一**筛子架在用户视角上，于是「关于窗口启用系统沙箱」「补齐两处权限校验」这类**有长期后果的安全约束被删掉**；而「截图重新拍摄」「路径已替换为示例路径」这类**对谁都没意义的载体维护却留在原地**。**同一次改写里同时犯了这两个方向的错。**
3. 用户明确裁决：**非用户感知层的内容，只要对用户和维护者有意义，就可以进。**

由此得本条的核心：**内容标准不能只问「谁看得见」，还要问「有没有长期后果」和「别处能不能查到」**。前者决定「能不能写」，后者决定「要不要写」——两个问题缺一不可，而第一轮的规则只答了前者的一半（且答错成「只能写用户看得见的」）。

### 顺带查实的两件事（与写法无关，但影响「历史条目可不可信」）

- `0a740fe`（发 3.12.0）把 `## [3.11.8]` 标题**改名**成 `## [3.12.0]`，而非在其上方新增一节 —— 违反「条目只增不删」。v3.11.8 的正文被遗弃在 3.12.0 底下形成第二个 `### 改进` 节，而 GitHub 上 v3.11.8 的 Release 照常生成，两侧永久错位。
- `## [3.11.4]` 有 CHANGELOG 条目但**无 GitHub Release**（tag 在、Release 未生成）。

两处实测数据见 [evidence](../evidence/20261001-203000-CHANGELOG与Release版本对账.md)。

### 为什么此前无门禁

`grep CHANGELOG gates/ test/ tools/` 零命中 —— 全仓**无任何门禁覆盖 CHANGELOG**。这是 8 条内部条目能长期存在的机制性原因，也是 3.11.8 错位能长期存在的机制性原因。**规则没被执行与规则不存在，在结果上无法区分**，所以补门禁与补规则要同时做。

## 备选方案

1. **只改内容不改规则** —— 不选。语体无判据则必然退化，下一个项目也会重犯。
2. **语体判据写进项目 AGENTS.md，全局不动** —— 不选。口语腔是所有下游项目的共性问题，不属本仓事实；且项目 AGENTS.md 有容量上限。
3. **新增一条「CHANGELOG 要正式」的综合性规则** —— 不选。等于把内容标准重写一遍，两处定义必然漂移。
4. **保留文言腔，只删口语标记** —— 不选（第二轮否决）。见背景第 1 条。
5. **维持「只写用户可感知」，只是删得更保守些** —— 不选（第二轮否决）。这是第一轮失败的根因，不是程度问题。
6. **门禁只禁第二人称** —— 不选。8 条泄漏里一条「你」都没有，只禁一面会让内容泄漏继续漏。
7. **门禁判据放全局 `check-pointers.mjs`** —— 不选。该文件是「指针存在性 + 容量契约」两族判据，内容族混进去会让它的单一职责失效。

## 后果

**收益**：内容与语体各有判据且可执行；工程约束不再被误删；有长期后果的内容有唯一的用户可读载体；门禁让成果不退化；下一个项目继承规则不必重犯。

**代价与已知边界**：

- 改写 37 个版本条目约 180 行是一次大 diff。改写**只改表述与按判据增删，不改事实** —— 事实都在 git 历史里。
- `gh release edit` 是 37 次**对外可见写操作**，GitHub 上不可回滚，只能用本地备份写回。执行前必须先确认备份齐全。
- **门禁管不了比喻、调侃与术语一名** —— 中文无封闭词表可枚举「这句是不是在开玩笑」。这一面靠人写，是已知不覆盖项，不是遗漏。
- **枚举词不可凭直觉增补，必须先在真实语料上量误报面。** 实测推翻了「`盖` / `概` 误报面≈0」的判断：`盖` 的全部命中都落在「覆盖 / 遮盖 / 涵盖 / 覆盖层」里（覆盖是本仓描述「预设覆盖哪些设置」的高频正当用词），`概` 的唯一命中是「概览」—— 裸字判红即 100% 误报，而**噪声源的下场是被关掉**。两者最终保留但各带**字级成词护栏**（逐字，不是逐行：逐行放行会把同行的真裸用一起放过）。判据七「破折号密度」同样被实测否决：改写前语料 11 行里单条超过 1 个破折号的只有 1 行，且那行是中文标准的成对夹注、完全正当。
- **`仅` 这条判据当前行为等价于「不判红」** —— 真实语料 21 处命中全是实义限定用法。它提供的是对未来的保护，不是已发生的保护；该事实写在门禁文件头，避免后人把它当成「已验证有效」。
- 「别处查不到」这条需要判断「别处」指哪些载体。本仓定为 git 历史 · `docs/adr/` · 代码 · `docs/DEV-GUIDE.md` 四处；换一个项目要重新确认这四处是否成立。
- 第一轮的产出留在 git 历史里（尚未提交），本 ADR 记录的是**它为什么被否**，不是把它抹掉。

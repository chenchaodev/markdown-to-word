# adr-028 · 持久化 schema 表与转换上下文契约收口

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-09-28 |
| 关系 | 承接 [adr-024](adr-024-设置分组与渲染前变换层下沉.md)（分组键的校验口径不得放宽）。本条是它的反面 —— 把「哪些键用哪种口径」从散落的手写枚举收成一张可读的表。 |

## 决定

把持久化侧的手写枚举收成一张声明式 schema，每键一条；形状校验、加载兜底、更新 switch 三个消费点读同一张表。`version` 从「被校验的键」变成 schema 声明的格式版本参数。`buildConvertContext` 改为按类别批量映射，且把 3 个仅测试注入的字段移出生产 `ConvertContext` 类型。

## 背景

诊断（`docs/archive/20260927-222300-设置改动面放大器诊断.md`）的结论：加一个设置项要在持久化侧改 **4 个编辑点 + 单独做一次向后兼容决策**。根因是「设置已加载」这条链上没有声明式中枢，每一层各自手写枚举。

2026-09-28 开工前的实测复核发现规格（`docs/large/01` 步 04）**两处数字过期、一处结构判断不足**：

1. **键数 21 → 18**。步 02 把 5 个平铺键收成 2 个对象（`aiCleanup` / `obsidian`），`SETTING_KEYS` 随之缩短。
2. **「每键一条（用哪套校验模式）」的单选结构不够用。** 实测 `isValidSettings` 的真实形态是**三条正交轴**：

| 轴 | 取值 | 落在哪些键 |
|---|---|---|
| **缺失是否合法** | 必填 / 缺失合法 | 必填：`version` `format` `afterConvert` `breakBeforeH1`；其余缺失合法（旧文件兼容） |
| **非法时的处置** | 整文件拒绝 / 整块修正 / 仅字段级兜底 | 整文件拒绝：多数键；**整块修正**：`pageSetup`（交 core 的 `correctPageSetup`，注释写明「非法值只修正该块，不能让旧配置连带丢失其它用户设置」）；**仅字段级兜底**：`language`（注释写明语言裁撤迁移场景下整文件拒绝会把用户全部偏好覆盖成默认） |
| **是否完全不做形状校验** | 是 / 否 | 是：`typography` `headerFooter` `watermark` `customPresets` —— 它们连 `isValidSettings` 都不出现，只有 sanitizer 兜底 |

3. **旧形状的 4 个键不在 `SETTING_KEYS` 里**（`aiCleanupTidy` / `aiCleanupRewrite` / `obsidianCompat` / `obsidianAttachmentFolder`）—— 它们只在校验与迁移路径出现。schema 若只按 `SETTING_KEYS` 建表，这 4 个键的校验会无处安放。

**若 schema 只有一条「校验模式」单选字段，上述三档会被压成一档，4-2 的「三处合并为一处」就会静默改变行为** —— 尤其 `language` 与 `pageSetup` 两键，它们「不参与整文件拒绝」是**有意为之**（各自有注释说明理由），压成整文件拒绝是真实回归。

## 决定要点

### 一、每键条目是三轴，不是单选

条目形状：`{ 默认值 · 缺失是否合法 · 非法时处置 · 取值域（枚举/钳制/路径规则）· 键路径 }`。非法处置三档：`reject-whole-file` / `repair-block` / `fallback-field`。**「完全不做形状校验」由「缺失合法 + fallback-field」组合表达**，不需要第四个枚举值。

### 二、`version` 不升位，但移出被校验键集合

步 02 改了设置形状（5 个平铺键 → 2 个对象）而 `version` 仍是 1。**决定不升位**，理由：加载器靠**形状**判别（`readLegacyTransformFlags` 读旧键 + `isValidSettings` 对 `aiCleanup` 双形状放行），`version` 从未参与判别；升位只会多加一条按 version 分支的路径，而那条路径什么都不决定，反倒制造「version 说 1 却可能是两种形状」的新含糊。

但规格 4-3 的要点成立：`version` **必须移出被校验键集合**，改为 schema 声明的 `CURRENT_SETTINGS_VERSION`。否则 schema 表自己要被 schema 校验，形成循环依赖 —— 那才是真问题。

### 三、schema 放 core，校验策略作为条目上的一个字段

表放 `src/core/settings/`（它描述 `AppSettings` 的形状与默认值，属该类型的定义层），**renderer 也能复用同一份「键 → 类型/枚举/默认」**，逐步消掉 `settings-logic.ts` 那份手写平行副本（步 03 的 3-2 正在做这件事）。

**校验策略（哪键参与整文件拒绝）作为条目上的一个字段**，由 main 的三个消费点读取。策略是持久化层的关注点，但判定它所需的信息在类型层，两者不必分居两地 —— 分居两地正是「键组与校验分处两文件」的老毛病。

### 四、4-4 不得退化成「遍历 schema 塞进上下文」

`buildConvertContext` 有 3 个字段**故意没有生产写入者**（`headingNumbering` / `captionNumbering` / `imageBudget`，步 01 的 1-4 已逐条标注「生产零注入 / 仅测试注入」）。按类别批量映射时若把它们一并接上，等于造出「设了也不生效」的假开关 —— **而这正是步 01 刚清掉的那类静默失效**。映射必须按类别显式列出「生产有的」与「测试注入的」。

### 五、采纳 4-5

把 3 个仅测试注入的字段移出生产 `ConvertContext`，测试用独立的覆盖类型。这是 REQ-068 剩下那一半（其判断依据写明「应与持久化 schema 步合并，否则同一个上下文类型动两次」）。

## 备选方案

- **每键一条「校验模式」单选字段（规格原文）** —— 否决。会把三档压成一档，`language` / `pageSetup` 两键的「不参与整文件拒绝」被抹掉，而那两处各有一条注释说明它是有意的。
- **schema 只覆盖 `SETTING_KEYS`，旧形状 4 键另找地方放** —— 否决。那 4 个键的校验与 `SETTING_KEYS` 里的键是同一种代码路径，分开放等于把「同一个 switch」拆成两处，正是本步要消灭的形态。schema 需要一个「仅迁移期校验、不参与落盘」的角色字段。
- **`version` 升到 2** —— 否决，理由见要点二。步 02 已经改过形状而没升位，此刻升位等于追认一个从未生效的版本号体系。
- **schema 放 `src/main/persist/`** —— 否决。renderer 侧就复用不了，`settings-logic.ts` 的手写副本消不掉，步 03 的 3-2 也就失去「从 `AppSettings` 派生」的单一来源。
- **不做 4-5，把测试专用字段留在生产类型里** —— 否决。那是 `CODE-GUIDE.md`「不造类型谎言」的反面：一个生产类型宣告它支持某字段，而生产侧没有任何写入者。步 01 的 1-4 只补了注释，没解决类型归属。

## 后果

- 新增一个双管线渲染语义类设置 = **1 条 schema + 1 个映射项 + 两侧渲染实现**（目标值见 `docs/large/01` 步 04 退出条件），且不再需要单独做一次向后兼容决策 —— 因为「缺失是否合法」已经写在条目里。
- **`test/main/settings.test.js` 里那段 21 键全量硬编码副本可删**，改为遍历 schema 断言。
- **schema 与 `AppSettings` 之间会出现一个「同源不同处」的风险**：类型是手写的，表也是手写的。防线是既有门禁（`identity-guards.test.js` 的双侧恒等）+ 一条新增的「schema 键集 ≡ `SETTING_KEYS` 键集」断言，**不靠类型派生**（`AppSettings` 是手写 interface，派生自它会引入循环依赖）。
- **受本条约束的**：任何想把 `language` 或 `pageSetup` 改成整文件拒绝的改动，都必须先推翻本条并说明如何保住「语言裁撤迁移不丢用户偏好」与「单块非法不连带清空其它设置」这两条既有理由。

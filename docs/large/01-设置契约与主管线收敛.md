## 为什么做

加一个输出内容级能力时改动面极大。实测两个真实选项：

| 选项类别 | 需改 src 文件 | 需改 test 文件 |
|---|---|---|
| 渲染前变换（插在格式分叉**之前**，双格式自动共享） | **12 ~ 13** | 4 |
| 双管线渲染语义（插在格式分叉**之后**，两侧各实现） | **22** | 7 |

**根因不是「6 种模式各有实现」** —— 六条路径实际只有 2 套实现（批量是 `convertImpl` 的并发池），格式分叉全库只有 `core/convert.ts:192` 一处。**根因是「设置已加载」这条链上没有一个声明式中枢，全靠每一层各自手写枚举。**

具体是三处同源缺陷：

1. **一个键组的固定落点 15 个站点**，其中最贵的四处（`persist/settings.ts` 的白名单、形状校验、加载兜底、更新 switch）**每一处都要独立回答一次「旧 settings.json 缺这个键怎么办」** —— 即每加一个键都要重做一次向后兼容决策。
2. **没有「设置类别」概念** → 每出现一个新类别的能力就发明一个新 mapper。实测 `core/convert.ts` 对渲染前变换类设置的引用数为 **0** —— core 的转换入口根本不知道它们存在。
3. **类型层是单源的，但校验/回填/映射全是手写平行副本** —— `SettingsControlValues` 是 `AppSettings` 41 字段的副本且无类型派生；`SETTING_KEYS` 白名单与类型无编译期关联，漏加则 patch 被静默丢弃。

同时双管线实现侧存在**机制性盲区**：差异矩阵对 8 个双管线键只覆盖 4 个，而**两处已确认的「设置项在一侧静默失效」恰好都在零覆盖的 4 个键上**；矩阵本身不在任何门禁里，66 条源码锚点有 25.8% 指向空行或注释、1 条行号越界。

## 步 02 · 渲染前变换层归位与判据统一

**目标**：给「渲染前变换」这个类别一个家。三件事：分组、归位、判据统一。

| 子步 | 内容 | 形状 | 行为等价 |
|---|---|---|---|
| 2-1 | **分组**：`aiCleanup` 三个平铺顶层 boolean → `aiCleanup: { enabled, tidy, rewrite }`；`obsidianCompat` + `obsidianAttachmentFolder` → `obsidian: { compat, attachmentFolder }` | ~8 文件，机械改写为主 | 可做到是，**持久化格式变** |
| 2-2 | **归位**：`aiCleanupOptions` 从 `main/converter/preprocess.ts` 移进 `core/markdown/`（它是纯函数、零 IO，只读设置） | 1 文件搬迁 + 导入路径 | 是 |
| 2-3 | **判据统一**：新建 `core/markdown/source-ranges.ts`，把两份 `SourceRange`、两套 masking、两套切行口径合一，2 个消费点（渲染前变换 + 预检）共用 | 新文件 + 2 消费点 | 可做到是，**节点集合须参数化** |
| 2-4 | **阶段契约最薄版**：引入一个渲染前变换上下文类型，让 `core/convert.ts` 对「先变换后渲染」这个阶段有显式概念（当前它对渲染前变换类设置的引用数为 0） | 1~2 文件 | 是 |

**2-1 的两个必须守住的不变量：**

1. **双重门控不得压成一层。** 现在是 `preprocess.ts` 的总开关 + `ai-cleanup.ts` 的「6 个 per-rule 全 false 则直接返回原文，零改动契约」+ 函数注释明说「本函数不含总开关判定，档位不构成旁路」。这是既有 ADR 写死的不变式，搬的时候最容易破坏。
2. **分档是派生量。** 2 个档位映射到 6 个 per-rule 布尔；**本方案不加第 7 条规则**，但迁移后映射表的位置必须显式。

**2-1 的额外收益**：`obsidianAttachmentFolder` 现在**和 `obsidianCompat` 之间没有耦合表达** —— 单独设了 folder 而 compat 关着，folder 就是死值。分组成对象后这个耦合才说得清。

**2-3 的关键约束**：两份 `SourceRange` 的**节点类型集合已经分叉** —— 渲染前变换侧是「代码 / 行内代码 / HTML」，预检侧多认了「公式 / 行内公式 / 表格」（它需要）。**合并集合会改变改写行为**，所以集合必须**参数化传入**，不能硬合并成一份全局常量。

**迁移要求**：旧 3 个平铺键 → 新对象的迁移必须让**存量用户的转换产物逐字节一致**，这条要断言，不能靠推理。迁移模板用现有的分组对象 sanitizer（`persist/settings.ts` 里的页眉页脚与水印两处）。

**退出条件**

- 迁移前后同一份 markdown 的 docx 与 pdf 产物**逐字节一致**（有断言）
- 「6 个 per-rule 全 false → 零改动」有测试守护，且总开关与档位双重门控各自独立可验
- **该类设置在全仓只被枚举 2 处**（变换分派 + 核心侧选项组装），不再有第三个 mapper
- 渲染前变换类设置的**节点类型集合在源码内只有一份定义**，两处调用点各自传入自己需要的集合
- `core/convert.ts` 对这批设置的引用数**从 0 变为「有，且只经一个入口」**
- 升级路径：新旧两种形状的 `settings.json` 都能正确读入

**回滚**：迁移函数保留旧键读取能力一个版本；未发布前可整体 revert，已发布则靠迁移函数把新形状写回旧形状。

**ADR**：需要（改持久化结构 + mapper 从 main 移进 core = 改分层）。ADR 须写明双重门控不变式与「档位是派生量」这条。

## 步 03 · renderer 设置管道表驱动 ★最高杠杆

**目标**：把「新增一个设置控件」的 renderer 侧成本从 **6 个文件**降到 **1 个表条目**。

**现状（加一个开关必碰）**：`index.html` 控件与文案 → `dom/refs.ts` 加 ref → `settings-bindings-<域>.ts` 写 change 监听 → `settings-logic.ts` 的回显类型与取值映射 → `settings-panel.ts` 回填 DOM → `settings-bindings-app.ts` 恢复默认与复位。`refs.ts` 目前是 **141 个 ref 的平铺映射**，无「id 存在」编译期校验，id 拼错只运行期为 null。

**目标形态**：一次声明（键 → 控件 id → 读控件 → 写控件 → 依赖）驱动 **bind / hydrate / reset** 三件事。

| 子步 | 内容 |
|---|---|
| 3-1 | 建立声明表，承接控件定位、回显读写、复位 |
| 3-2 | 回显类型与取值映射改为**从 `AppSettings` 派生**（当前是 41 字段的手写平行副本，无类型派生关系） |
| 3-3 | 域内 change 监听样板收敛（当前同域内多个开关的监听结构逐字相同） |
| 3-4 | 依赖门控以**显式登记的例外**方式表达（见下） |
| 3-5 | 逐控件断言 hydrate / bind / reset 三条行为不变 |

**两个高风险点，必须提前定调：**

1. **依赖门控怎么表达。** 现在只有 2 个手写同步函数（页眉自定义可见性、渲染前变换分档可用性），步 01 还要加第 3 个（目录模式）。表驱动后要么让依赖可声明式表达，要么**保留这 3 个为显式登记的手写例外**。**建议后者** —— 依赖关系是少数情况，强行声明式化会让表里出现第二套 mini 语言。
2. **`settings-bindings-*` 6 个文件按 Tab 分组切**（与 `index.html` 的 `data-group` 一一对应），不是按设置域。**保留文件切分** —— 它对齐 UI 导航结构，不是抽象维度；表只管每个域内部。

**退出条件**

- 新增一个 checkbox 的 renderer 侧改动 = **1 个表条目 + 1 个 HTML 控件**
- **逐控件**断言：初值回填正确、change 写回正确、恢复默认正确（不是抽样，是全量）
- 截图回归全绿（控件位置与可见性不得变化）
- 3 个依赖门控的既有行为逐个断言守护
- 控件 id 拼错能在类型检查或测试期暴露（当前只在运行期为 null）

**回滚**：表驱动与旧样板并存一个提交周期，逐控件对比通过后再删旧路径。

**ADR**：不需要（纯内部结构，行为等价）。工作日志留一行即可。

## 步 04 · 持久化 schema 表与转换上下文契约收口

**目标**：把「加一个设置项」的持久化侧成本从 **4 个编辑点 + 一次向后兼容决策**降到 **1 条 schema 条目**。

**本步有且只有一个真正需要设计判断的地方：`persist/settings.ts` 有两套并存且不等价的校验语义。**

| 语义 | 位置 | 行为 |
|---|---|---|
| **整文件拒绝** | 形状校验段 | 任一字段非法 → 整个 settings 回退默认 |
| **字段级兜底** | 加载兜底段 | 单字段非法 → 该字段回落默认，其余保留；`typography` / 页眉页脚 / 水印**明确注释「不参与整文件形状校验」** |

**schema 表必须逐键标注用哪一套。** 这张表本身就是规格书。

| 子步 | 内容 | 前置 |
|---|---|---|
| 4-0 | **先写「逐键兜底语义」表驱动测试** —— 把 21 个键在两套语义下各自的行为固化成表 | — |
| 4-1 | 声明式 schema：每键一条（类型 / 枚举 / 默认 / 缺失是否合法 / 用哪套校验模式） | 4-0 |
| 4-2 | 形状校验、加载兜底、更新 switch 三处合并为一处 | 4-1 |
| 4-3 | `version` 从「被校验的键」变成 schema 的格式版本参数 | 4-1 |
| 4-4 | `buildConvertContext` 从逐字段枚举改为**按类别批量映射** | 4-2 |
| 4-5 | （可选）把 3 个仅测试注入的上下文字段移到测试专用的覆盖类型，生产类型不再背负 | 4-4 |

**4-3 为什么必须在 4-1 一起做**：`version` 今天是「被校验的键」（形状校验里 `version !== 1` 则整文件回退），真实语义是「settings.json 的格式版本」。若它继续留在被校验集合里，**schema 表自己也要被版本号管，形成循环依赖**。

**4-4 的设计要点**：`buildConvertContext` **不该变成「遍历 schema 塞进上下文」** —— 那个上下文有 3 个字段**故意没有生产写入者**（步 01 的 1-4 只纠正了表述，类型归属留到此处）。应按类别显式映射，把「生产有的」与「测试注入的」分开。

**最难搬的键：`typography`。** 四层叠加：

1. 11 个字段，其中标题缩放与标题间距是**档位枚举 + 系数表**，不是标量
2. 它的 sanitizer 在**另一个文件**，而该文件同时服务自定义预设的导入导出 —— 改它会连带碰到预设文件
3. 被 5 个内置预设各带值消费 —— **搬它等于搬预设体系的一半**
4. 档位系数已有单源（带 pt 与 twips 两个换算出口），**这部分不要动**

**次难：页眉页脚。** 构建映射上下文时需要读 logo 文件，这让它变成异步函数。若想把它变回纯映射，得先决定 logo 读取归谁。**注意 pdf 侧用 data URI、docx 侧用另一字段名，消费的是同一个解析结果 —— 这部分已经是对的，不要拆。**

**退出条件**

- 新增一个双管线渲染语义类键 = **1 条 schema + 1 个映射项 + 两侧渲染实现**
- 4-0 的表驱动测试全绿，且它在 4-2 之后**仍然全绿**（证明合并未改行为）
- 21 个键在两套语义下的行为逐一有断言
- 旧格式 `settings.json` 读入行为不变；格式版本变更时有一次明确的迁移路径
- 测试内的「21 字符串键名全量硬编码副本」可删（改为遍历断言）
- 4-5 若采纳：`ConvertContext` 的生产类型不再包含仅测试注入的字段，且测试全绿

**回滚**：schema 与旧三处并存一个提交周期，逐键比对通过后再删旧路径。

**ADR**：需要（改持久化结构 + 改对外接口类型）。ADR 须写明两套校验语义如何共存于一张表、以及 `version` 的角色变更。

## 步 05 · main 侧主管线收敛

**目标**：把 `single` 与 `merge` 两份逐行同构的输出骨架合成一份。实测逐语句 36 条里 **31 条逐字相同（86.1%）**，7 处差异**全部是「值不同」或「可选实参的有无」，没有一处逻辑不同**。

**抽函数，不抽对象，不抽主管线。**

| 方案 | 判定 | 理由 |
|---|---|---|
| **抽函数**（新模块 + 2 消费点） | **采纳** | 批量与预览零改动 |
| 抽「转换请求」对象 | 不采纳 | 收益是让 renderer 3 个命令与 main 2 个 handler 共用形状，但**它们在不同进程** —— 跨进程复用要动 4 个契约文件，换一层参数封装 |
| 抽主管线 | 不采纳 | 会扭曲进度粒度与让位语义 |

**共享骨架的入参必须只有「一段 markdown + 来源路径 + 可选基名 + 解析基准目录/可信根」，不含文件列表。**

> **这直接回答了「会不会把『多文件→一个产物』压扁成『一进一出』」：不会。** 多对一 的塌缩已经在骨架**上游**完成 —— 合并函数把 N 个文件压成一段 markdown，发生在落盘之前。共享骨架的入参是「一段 markdown」，**骨架内部根本看不到几个文件进来**。

**逐条裁决 —— 该统一 vs 不该统一：**

| 该统一 | 不该统一（相似但刻意） |
|---|---|
| 落盘提交器调用及其参数 | **`merge.ts:147` 的第 4 道取消闸门**（并发读取窗口，single 无此窗；合并它 = 要么删掉真实防护，要么在 single 造假闸门） |
| 「转换后 / 落盘前」取消闸门 | **让位标志的归属判定**（唯一写入者是批量，而批量只调单文件实现） |
| 「落盘后 / 导出后行为前」取消闸门（两侧注释都刻意论证过这个位置，**该刻意性要保留进共享骨架的注释**） | 批量侧的进度包装（在单文件实现**外面**，把「每文件一次」包成批次进度） |
| 读取/渲染两处进度、pdf 独有的 stage 透传 | 批量的让位上下文构造（共享骨架必须**读**该标志，不得自己判断拥有者） |
| 落盘警告汇总 | `renderPdf` 内部的双闸门（`printToPDF` 不可中断的补偿机制，合并侧复用已自动继承） |
| | 参数/预算校验段（单文件查扩展名，合并查空数组与上限 —— **判据完全不同，合并会造出语义模糊的校验器**） |
| | 合并专属的封面元数据形参 |
| | 预览与转换两处映射上下文的差异（预览用降级 Mermaid、不共享图片缓存、无取消 —— 都是有意的） |
| | **批量的第三份「导出后行为」实现**（见下） |

**批量的第三份实现如何处置 —— 判定：保持独立，并登记为刻意相似。** 批量那份不判让位标志，改为「取第一个成功项」，与共享骨架的「判让位标志」语义不同构。强行统一要么引入一个策略维度（`自己的 / 第一个成功的`），要么牺牲掉一个真实语义。**判定为不并入，在 ADR 中写明理由。**

**退出条件**

- 两个消费点各自的输出段从 ~50 / ~45 行降到 ~10 行
- 抽完后与抽前的 diff **接近剪切粘贴 + 参数化**（这是等价性的机械证明，不是靠测试推断）
- **步 01 的 1-1 护栏测试在抽取后仍绿**（这是唯一能证明第 4 道闸门没被误删的证据）
- 合并转换的产物路径命名、导出后行为、取消语义与抽前一致
- 批量与预览路径零改动（diff 可证）

**回滚**：新旧并存一个提交周期。

**ADR**：需要（新增共享模块 = 改模块间依赖方向）。ADR 须写明两件事：**第 4 道取消闸门保留的理由**、**恒真分支删除不改变任何行为的证明**。

## 步 06 · 双管线决策项台账与水印缺陷裁决

**目标**：不是重构，是**建台账 + 补机制 + 修缺陷**。代码本身没有「该重构」的地方 —— 重复都是局部的、成对的、有注释标注的。缺的是一张表，和一个保证新键会进表的机制。

### 6-A 建决策项台账

把 45 项决策层条目（默认值字面量 15 项、推导逻辑 20 项、排序编号规则 10 项）逐条归类为四档：

| 档 | 含义 | 处置 |
|---|---|---|
| 载体所迫 | 同一规则在两种数据结构上的表达（AST 遍历 vs token 遍历、CSS counter vs OOXML 域） | 登记，不动 |
| 实质漂移 | **同一输入 → 不同输出** | 修或登记为已知差异并进矩阵 |
| 设置项失效 | 设置项在一侧无消费或行为不同 | 必修（6-B / 6-C） |
| 已被矩阵锁住 | 有 `mustMatch` 行守护 | 不动 |

**台账的价值不是「发现」，是「让下一次有人加键时有地方登记」** —— 这是当前完全缺失的机制。

### 6-B 必修的三个缺陷

| # | 缺陷 | 证据 | 判定 |
|---|---|---|---|
| **6-B1** | **水印角度的符号约定两侧相反** —— docx 侧注释写「正值 = 逆时针」，用 DML 单位系数；pdf 侧用 CSS `rotate()`，**CSS 正值 = 顺时针**。**未找到任何补偿性取负** | `core/docx/chrome.ts:265` · `core/pdf/template.ts:110` | **先人工看一次双格式产物**。若确认反转 → 两侧共用一个「角度→旋转量」换算并统一符号（改产物，需 ADR）。若不反转（存在别处补偿）→ 补注释说明补偿在哪 |
| **6-B2** | **水印不透明度在 docx 侧零消费** —— 全目录 grep 只命中一行注释「由浅灰配色近似」；pdf 侧真实输出 | `core/docx/chrome.ts:254` · `core/pdf/template.ts:104,115` | **取向需产品裁决**：实现 / 或在界面上按格式条件禁用并说明。**不能继续静默** |
| **6-B3** | **页眉页脚「默认」模式两侧产物不同** —— docx 侧渲染「文档标题居中页眉」，pdf 侧渲染**空页眉**（标题只进页面 title） | `core/docx/headers.ts:31` · `core/pdf/template.ts:47` | **统一 or 登记为已知差异并进矩阵**。需产品裁决 |

**6-B1 的优先级应高于本步其他所有项** —— 它是用户可见的**方向反转**，而其他项要么是内部表述，要么是外观差异。

### 6-C 补机制

| # | 内容 | 成本 | 说明 |
|---|---|---|---|
| 6-C1 | **把差异矩阵接进门禁** —— 新增一个双管线键而矩阵无对应行时门禁判红 | 1 个探针 | 现状：矩阵只守「已有行的形状」，不守「键的覆盖」，且**不在任何门禁里**，只挂在验收测试的一个段上 |
| 6-C2 | **补 4 行矩阵覆盖**：正文字体/字号/行距/缩进/对齐 · 一级标题前分页 · 页眉页脚 · 水印 | 约 120 行 | 这 4 个键当前**零覆盖**，而两处失效缺陷恰好都在其中 |
| 6-C3 | **处理 66 条源码锚点** —— 它们只校验格式不校验存在性，实测 25.8% 指向空行或纯注释、1 条行号越界（指向一个只有 364 行的文件的第 399 行） | 1 探针 或 删字段 | 二选一：**改成打开文件校验行号存在**（成本低、价值中），或**直接删掉该字段**并让可执行的 `verify` 承担全部导航职责。**现状是「有字段但零约束」，比没有字段更误导** |
| 6-C4 | 修正一处**归因错误的注释** —— 题注章节号门控的差异被归因为「CSS counter 无法条件输出的平台限制」，但那是 JS 生成的静态文本，可以条件输出；**根因是决策重复** | 1 行注释 | 留着会让下一次有人按错误归因去做无效优化 |

### 6-D 纯收益项（与 6-B/6-C 独立）

| # | 内容 | 形状 | 行为等价 |
|---|---|---|---|
| 6-D1 | **默认解析收进共享函数** —— 12 个默认值字面量收成 1 个来源，并把 docx 侧已有的「构造时统一解析默认、故全字段必填」形态**推广到 pdf 侧**（pdf 侧目前散在 3 个位置，其中 1 个在 convert 层） | 1 个新纯函数 + 2 消费点各改 3~5 行 | 可做到是，**需逐键断言** |
| 6-D2 | **两侧渲染选项交叉继承** —— 把 15 个共有字段抽成基类型，两侧各自加自己的独有条目。**不强迫 docx 声明 pdf-only 字段** | 2 文件纯类型，运行时零影响 | **严格是** |
| 6-D3 | 公式引用默认文本集与悬空警告文案并入交叉引用种类的单源表（当前该表只有图/表/章节三类，公式游离在外，两侧各写一份） | 1 常量表 + 2 消费点 | 可做到是 |

**6-D2 单独做无效，必须配 6-D1** —— 类型系统对可选字段没有默认值检查，交叉继承只让 JSDoc 单源，**不解决漏传**。而「漏传不报错、只静默用默认值」正是 `convert.ts` 两个并列表的真债（两侧字面量交集 15、独有 8 个全部有意，但两边的选项类型都不强制对方同步）。

**退出条件**

- 45 项决策条目全部归类完毕，台账落盘且**有唯一写者**
- 6-B1 有明确结论（是 bug 则已修并有断言；不是 bug 则补了注释说明补偿在哪）
- 6-B2 / 6-B3 有产品裁决并落地，**两者都不得继续静默**
- 6-C1 生效：故意新增一个无矩阵行的双管线键，门禁判红
- 6-C2 的 4 行矩阵通过
- 6-C3 已裁决（校验存在性 or 删字段），且 66 条锚点中不再有越界项
- 6-C4 注释已改
- 6-D1 与 6-D2 配套落地，逐键默认值断言全绿

**回滚**：台账与门禁探针可独立回滚；6-B 的三处若改产物则需对应 revert。

**ADR**：6-D2 需要（改对外接口类型）。6-B1 若改产物需要（改产物 + 记录「两处『同口径』注释此前与代码不符」这类既有失真）。6-B2/6-B3 视裁决结果。

## 已评估但**不做**的项（记录在案，防下个会话重新提）

| 项 | 不做的理由 | 重新评估的触发条件 |
|---|---|---|
| **引入「能力（capability）」抽象层** | 与 [adr-014](../adr/adr-014-双管线保持独立.md) 冲突而非补充。既有手段是**函数级共享**（章节号模块抽了 3 个纯函数，两侧各消费一次，零载体）；能力抽象要求**声明级共享**，而**载体恰恰是 ADR 明说「差异是设计意图」的那部分** —— 把「差异是设计意图」的东西抽象成统一接口，是在撤销该 ADR 的核心判断。且 8 个能力撑不起一层抽象（载体专属抽象已有两套，再加总层数 3，净收益只是少写一遍注释）。反证：pdf 的文件系统能力接口**刻意只声明两个函数**并注明「新增用途必须显式改这个接口，而不是顺手拿到整个 fs」—— 用能力接口的名义去统一它恰好会破坏它 | 出现第 3 种载体（HTML 导出等），或双管线键超过 15 个 |
| **渲染前变换注册表**（每条变换自描述：名/开关组/纯函数签名/是否需要选项组装/是否需要保护区感知） | 当前只有 2 条变换，YAGNI 撑不起一层间接。**其真实收益不是减文件数**（预处理只占 1 个文件），而是给第 3 条变换留位置、免得再发明一个 mapper。步 02 的 2-3（判据统一）已经把「加一条新规则要改几处」压到最小 | 出现第 3 条渲染前变换，或单条变换的规则数需要注册化 |
| **合并双管线公式编号的两套算法** | docx 走 AST 预扫（能提前算出跳过集合），pdf 走 token 流（只能在渲染期边走边记）—— **两者可用的输入信息不同**，强行共享要引入一个中间表示，净增复杂度。已发生的两次漂移（粗斜体 label 解析、缺 counter-increment）都已被矩阵锁住，这是「决策重复被测试契约覆盖」的正确形态 | pdf 路线改为也走 AST（则两侧可共用同一预扫） |
| **把预检拆成多个文件** | 601 行装 4 个互不相关的检查族，拆分收益纯审美；既有 ADR 明确要预检作为一条统一通路，拆了会让 1 个 import 变 4 个 | 该 ADR 被推翻 |
| **把预检并入转换管线** | 既有 ADR 明确预检是独立通路；且预检消费的是变换后正文而转换消费的是拼回 frontmatter 的全文，**两条数据流本就不同**。另有一处未查清的注释与数据流张力（注释称预检不受档位管辖，但它消费的正文已经过变换） | 那处张力查清且证明是失误 |
| **frontmatter 单次转换只解析一次** | 真实重复（预处理层为拼回原文解析一次、convert 层为取元数据再解析一次），但**不是痛感来源**，且改法要动 `convert` 的元数据来源，与步 04 都触及 `context.ts` —— 合并做更省。价值低于它与步 04 的耦合成本 | 步 04 完成后仍觉得解析开销可观测（如大文件转换耗时） |
| **内容区宽推导单源化**（docx 走 twips 路径、pdf 走 mm 路径，导致 0.03px 差） | 真漂移，且**两处注释都宣称「同口径」而代码不符** —— 但量级 0.03px，收益仅止于「让注释不再说谎」。**行为等价性为否**（会改产物） | 用户报告过图片/表格宽度与预期不符 |
| **删掉 `convert.ts` 里两个选项字面量的重复** | 8 个独有条目逐个核实**全部为有意**（docx 零 IO 不需要基准目录与文件系统能力；pdf 走 CSS 载体才有自定义样式；封面元数据只有合并有入口）。交叉继承的收益只是 Javadoc 单源，见 6-D2 | — |
| **把 `format` 从 `AppSettings` 迁到界面状态文件** | 归属确实可疑（它只是「重启后恢复上次选的格式」，且 main 侧从不读它决定格式），但**有一处未查清**：命令函数里存在「格式未持久化」的合法态，迁移可能引入「重启后格式丢失」的行为变化 | 那处合法态查清后 |
| **三语言 i18n 精简** | 卖 3 种语言的固有成本，且已被编译期门禁锁住（键集单源 + 三份 `satisfies` 记录），**不可压缩** | 决定放弃某种语言 |
| **core/main/renderer 三进程分离的合并** | Electron 固有架构，边界门禁让它近乎免费（能独立测试 core 的原因就是这道门禁） | — |
| **自定义预设/内置预设体系的重构** | 只被步 04 的「最难搬的键」间接触及（搬正文字体设置会连带动预设的一半）。不在本方案范围内 | 步 04 实施时若发现预设侧成本超过预期 |

## 怎么回滚

| 步 | 回滚方式 | 风险 |
|---|---|---|
| 01 | 5 项独立提交，逐项 revert | 无 |
| 02 | 未发布：整体 revert。已发布：迁移函数把新形状写回旧形状（保留一个版本） | **中** —— 持久化格式已变 |
| 03 | 新旧并存一个提交周期后再删旧路径 | 低 |
| 04 | schema 与旧三处并存一个提交周期，逐键比对后删旧路径 | **中高** —— 加载路径是全应用热路径，且与迁移写队列交织；**必须先有 4-0 的表驱动测试兜底** |
| 05 | 新旧并存一个提交周期 | 低 |
| 06 | 台账与门禁探针可独立 revert；6-B 三处若改产物需对应 revert | 中 —— 改产物 |

**整体回滚**：6 步各自独立可回退，无跨步耦合，因此不需要「整体回滚」这个动作。最坏情况是逐个 revert 到步 01 之后的状态 —— 即**保留全部护栏与缺陷修复，回退所有结构改动**。

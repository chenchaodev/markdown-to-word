### 2026-08-05 批次 4 脚注实现结论(@librarian 调研 + 待实测)
- PDF 侧:@mdit/plugin-footnote@^1.0.2(peer 显式 markdown-it ^14.2.0,与已装 tasklist 同源同仓库);`md.use(footnote)` 命名导出;输出锚点 footnote-N/footnote-ref-N;重复引用编号 [2]/[2:1];合并多文件时可用 env.docId 锚点前缀防冲突(md 拼接单实例渲染天然唯一,无需)
- **Chromium 不支持 CSS float: footnote,PDF 脚注集中在内容末尾渲染(非页脚)——HTML→PDF 通用行为差异,验收预期**
- PDF 侧需补 CSS(.footnotes 9pt、hr.footnotes-sep、ol.footnotes-list、li.footnote-item break-inside: avoid、sup.footnote-ref a 去下划线、a.footnote-backref);插件输出走 renderer 规则,不受 overrideHtmlRules 白名单影响
- docx 侧零新依赖:9.7.1 Document 级 `footnotes: Record<id字符串, { children: Paragraph[] }>` + 正文 `new FootnoteReferenceRun(id)`;id 从 1 起唯一,分隔线/编号自动(Word 按引用出现顺序编号,自动上标);**footnotes 只挂 Document 级,不在 section 级**
- **docx 侧实现要点:全局递增计数器统一编号(md 拼接合并天然连续,勿按文件重置);footnoteDefinition 内容嵌套引用需递归渲染且共用计数器;重复引用按引用次数逐个编号(与 markdown-it 对齐),而非按定义去重**
- remark 侧零新依赖:remark-gfm 4.0.1 已解析 footnoteDefinition/footnoteReference
- **语法不对称:内联脚注 ^[...] 只有 PDF 侧支持(markdown-it),remark 侧 mdast 无对应节点 → docx 侧按字面量/不支持处理,需在需求层面确认**
- 风险:脚注引用放标题行会被 TOC 域带进目录条目文本(建议不放);Word/WPS 原生支持 OOXML 脚注,保持双实测红线

### 2026-08-05 批次 4 docx 页眉页脚 + 页码实现结论(@librarian 调研 + 待实测)
- Header/Footer 构造:`new Header({ children: (Paragraph|Table)[] })`,children 只收段落/表格,不能放裸 TextRun;页码字段必须包在 Paragraph 里
- **挂载点只有 `sections[].headers/footers`**(Document 级无此选项);9.x 单节文档直接加到现有唯一 section;首页不同用 `properties.titlePage: true` + headers.first/footers.first
- **坑:9.x 无 `PageNumberFormat`(旧版 API 已移除,改名 `NumberFormat`);页码格式写 section `properties.page.pageNumbers.formatType`;中文模板「第 X 页 / 共 X 页」用 `PageNumber.CURRENT`/`TOTAL_PAGES` 放 `TextRun({ children })` 混排;建议默认 decimal(与 PDF 阿拉伯数字对齐)**
- 合并场景:文本拼接后单次渲染单 section → 页眉页脚自动覆盖全页、页码连续;TOTAL_PAGES 统计全文档(含封面/目录),与 PDF footerTemplate 的 totalPages 语义一致
- 封面页码:titlePage + 空 first footer 会让 pdf/docx 分叉(printToPDF 无法按页排除),保持所有页显示与 PDF 对齐
- 页眉标题优先级:`metadata.title ?? options.title`(与 pdf 相同);docx 侧 renderDocx 需新增 title 选项,convert.ts docx 分支补传

### 2026-08-05 批次 4 书签「点击不跳转」修复结论(已验证)
- 用户实测:书签目录显示正常,但点击不跳转对应页面。根因:所有书签 Dest[0] 全部回退到首页(2 0 R=封面)——`destKeyText` 对 PDFName key 用了 `decodeURIComponent(key.asString())` 永远匹配不上

- 教训:smoke 原断言只查标题文本,不查 Dest 指向,漏过「全部回退首页」类 bug;已补断言 `Dest[0] instanceof PDFRef`(单文件+合并两处),并手动校验验收样例每条书签页面 index 与章节位置吻合(简介→2/安装→3/配置说明→9…)

### 2026-08-05 批次 4 书签实现结论(pdf-lib 注入,已验证)
- 方案落地:printToPDF 产物 **无 /Names 名称树,而是旧式直接 `/Dests` 字典**(catalog /Dests → {key: dest});前置实测记录的「Names Dests 引用 1 处」为误读(那是 catalog 的 Dests 引用)。需兼容两种结构(名称树 + 直接字典),勿只按名称树实现
- **坑:pdf-lib 的 `dict.lookup(key, type)` 在 key 缺失时抛 `UnexpectedObjectTypeError` 而非返回 undefined**(实测崩溃根因);必须用 `dict.get(key)` + 手动 `context.lookup(ref)` 解引用
- **坑:旧式直接字典的 key 是 PDFName 百分号编码 UTF-8**(如 `%E7%9B%AE%E6%A0%87`=「目标」),必须 `decodeURIComponent(name.asString())`;PDFName 的 decodeText 走 PDFDocEncoding 会把 UTF-8 中文解成乱码(勿用)
- 注入实现(src/core/pdf/bookmarks.ts,自研):`lookupNamedDest`(名称树/直接字典双兼容 + PDFDict 间接目标取 /D)+ `setOutline`(marp-cli setOutline 样板:pageRefs 经 `catalog.Pages().traverse` 收集、嵌套 First/Last/Count、F 标志 italic|bold、顶层 Count=flatten.length)+ `buildBookmarkTree`(扁平标题 → 按 level 嵌套)+ `injectBookmarks`(主入口);标题 id 即命名目标名(slug 与 /Dests key 一一对应,免文本定位)
- 实测验证:对 14 页合并 PDF 注入成功(236492→219361 bytes);读回断言 Outlines Type/Count=3、中文标题 UTF-16BE hex 解码正确(简介/项目背景/使用说明)、Dest[0]=页面 PDFRef(2 0 R)、First/Next 兄弟链与嵌套正确;smoke 断言单文件 + 合并 PDF 均含正确中文书签
- pdf-lib 1.17.1 为最新稳定版(package.json 原依赖 ^1.17.1);ESM 用包名导入,勿碰 `pdf-lib/es/index.js`(无扩展名相对导入,Node ESM 抛 ERR_MODULE_NOT_FOUND);中文标题必须 PDFHexString.fromText(UTF-16BE),PDFString 乱码(issue #516);子项 Count 负值=折叠;save() 不破坏原 Link 注释/字体/图片(实测)
- 来源: @librarian(lib-1)调研样板 + 自查实测(迭代验证)
